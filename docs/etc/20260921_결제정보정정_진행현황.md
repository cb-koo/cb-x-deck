# 결제 정보(수취 정보) 정정 회신 — 진행 현황 (2026-09-21)

> 정산 프로덕트(미러) 팀의 2026-09-21 요청 「결제 정보 정정 회신 API」에 대한 cb-x-deck(소스) 쪽 대응 현황.
> 이 문서는 개발자가 아닌 분도 읽을 수 있게 썼습니다. 기술 상세는 `docs/superpowers/specs/2026-09-21-settlement-payment-info-correction-design.md`, 상대팀 계약은 `docs/api/settlement-external-api.md` §6-1.

## 이게 무슨 일인가 (배경 한 줄)

정산 담당자가 송금 직전에 인플루언서의 **계좌번호·PayPal 아이디 오타**를 발견하면, 지금까지는 우리에게 알려서 **요청을 취소하고 새로 만드는** 방법밖에 없었습니다(정산 건 번호가 두 개로 갈라지고 이력이 끊김). 이제 정산 쪽에서 고친 수취 정보를 **같은 요청에 그대로 반영**받는 창구를 만들었습니다. 요청 번호·금액·처리 상태는 전부 그대로이고, **받을 곳(계좌·아이디)만** 바뀝니다.

## ✅ 적용된 것 (코드·문서 — 이 컴퓨터에 작성 완료, 아직 배포 전)

### 1. 정산 쪽이 고친 수취 정보를 받는 창구 (API)
- 정산 프로덕트가 "이 요청의 계좌번호를 이렇게 고쳤다"고 보내면 우리 쪽 요청에 반영됩니다.
- 안전장치:
  - **취소된 요청·이미 지급 완료된 요청**은 받지 않고 "안 된다"고 돌려보냅니다.
  - 정산 쪽이 **옛 내용을 보고** 고쳤으면(그 사이 우리가 요청을 수정했으면) 반영하지 않고 최신 내용을 돌려줍니다.
  - **같은 정정이 두 번 오면 한 번만** 반영됩니다(네트워크 재전송에 안전).
  - 고칠 수 있는 항목은 **수취인·이메일·PayPal.me 아이디·수취 식별 정보·은행·지점·계좌번호** 7가지뿐. 수단 종류(PayPal↔계좌)·통화·금액은 종전처럼 우리 쪽에서 고칩니다.
  - PayPal 수단인데 "은행"을 고치겠다고 오는 식의 **맞지 않는 값은 거절**합니다. 고친 결과는 우리가 새 요청을 만들 때와 같은 검사(이메일 형식 등)를 통과해야 합니다.
- 정산 쪽에 나가는 요청 정보에 **"정산 쪽이 고쳤다"는 표식**과 **인플루언서 표시명**(정산 화면용)을 함께 싣습니다. 표식은 정산 쪽이 "이건 내가 보낸 정정이 돌아온 것"임을 알아보는 데 쓰입니다(그쪽 요청 항목 5번, 가장 중요하다고 표시한 항목).

### 2. 우리 화면에 보이는 것
| 화면 | 무엇이 보이나 |
|---|---|
| 정산 요청 내역 → 요청 펼치기 → **결제수단** 줄 | "정산 쪽이 수취 정보를 고쳤어요 · 담당자 · 시각 — 사유" + "이 요청에만 반영됐어요 — **인플루언서 명부의 결제 수단도 같은지 확인해 주세요**" |
| 정산 요청 내역 → **[고친 값으로 다시 반영]** 대화상자 | 정산 쪽이 고친 요청이면 "다시 반영하면 결제 수단이 **명부의 값으로 되돌아가요** — 명부를 먼저 확인" 경고 |
| 인플루언서 프로필 → **활동 기록** | "정산 쪽이 수취 정보 정정 · 담당자: 계좌번호 1234567 → 7654321 — 사유 (명부는 그대로예요)" |

> 왜 "명부도 확인"인가: 정정은 **이번 지급 건**에만 반영됩니다. 인플루언서 명부(프로필)의 결제 수단은 그대로라, 명부를 고치지 않으면 **다음 요청에 같은 오타가 다시 나갑니다.** 명부는 우리 원본 데이터이므로 사람이 확인해서 고치도록 화면이 안내합니다(자동으로 덮어쓰지 않음).

### 3. 데이터 저장 구조 (마이그레이션 파일 — 작성됨, DB에는 아직 미적용)
- `056`(신규): 요청마다 붙는 "정정됨" 표식 칸 1개 + 정정 이력 장부(누가·언제·무엇을·왜 고쳤나, 중복 방지) + 활동 기록에 새 이벤트 종류 1개 허용.
- 번호는 다른 개발자의 `055`(캠페인 작업 취소)가 먼저 들어와 `056`으로 붙였습니다. 이전 파일(048·055)의 재실행 안전장치(`not valid`)는 이미 적용돼 있어 따로 고칠 것이 없습니다.

## 상대팀에 맞춰 달라고 한 것 (회신 문안 26번에 포함)
1. `base_source_updated_at`(기준 시각)은 **비교하지 않음** — 정산 쪽 자신의 상태 전송으로도 우리 시각이 바뀌어, 정확히 맞추라고 하면 정상 흐름에서도 거절이 나기 때문. 기준 판(`revision`)만 비교.
2. 성공 응답에 `version` 항목을 **넣지 않음** — 그쪽 프로그램이 세 항목만 엄격히 받기 때문.
3. `payment_method` 안에 모르는 항목이 오면 **거절(400)** — "고쳤다고 믿은 값이 조용히 버려지는 것"을 막기 위해.
4. 판정 순서: 취소 → 지급 완료 → 기준 판 불일치(그쪽 테스트 서버와 같은 순서).

  - **교훈:** 이 문서 4번의 "반드시 5번보다 먼저"는 자동 배포가 켜진 뒤로는 **사람이 지킬 수 없는 순서**가 됐다. 마이그레이션이 필요한 작업은 앞으로 머지 전에 운영 DB를 먼저 맞추거나, 새 칸을 읽는 코드를 한 배포 뒤로 미루는(칸 추가 → 배포 → 읽기 시작) 방식이 필요하다.
  - **테스트 결함 2건 수정:** `settlementStore.test.ts`가 정정 식별자(`correction_id`)를 테스트마다 같은 값으로 써서, 먼저 성공한 테스트가 그 값을 소진하면 뒤 테스트가 `invalid(correction_id)`로 막혔다(따로 돌리면 통과, 같이 돌리면 실패). 제품 동작은 정상 — 오히려 "다른 요청에 이미 쓴 식별자는 500이 아니라 400으로 거절"이라는 설계대로였다. 성공하는 테스트마다 자기 번호를 주도록 고쳤다(제품 코드 변경 없음).
