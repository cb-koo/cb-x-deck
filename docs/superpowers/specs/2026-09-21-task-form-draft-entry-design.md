# 새 작업 폼에서 원고까지 — 설계 결정 (2026-09-21)

> **한 줄**: `+ 작업 추가` 폼에 원고 칸을 두고, `[만들기]` 한 번이 "작업 생성 + 원고 부착"을 한 트랜잭션으로 끝낸다.
> **서버·스키마 변경 없음** — 08-31에 만든 계약(`TaskCreateRequest.draftId`)을 반대 방향으로 쓴다.

## 0. 문제

koo 09-21: 새 작업을 만들 때 패널에서 원고까지 이어질 줄 알았는데 원고 칸이 없다.

- **현행**: `TaskPanel.tsx:410` — new 모드는 `PANEL_FIELD_ORDER`에서 `'draft'`를 뺀다. `[만들기]` 뒤 같은 자리에 편집 패널이 다시 열리고(`FlowDetail.tsx:480`), 원고 세 버튼은 **거기서만** 보인다.
- **뿌리**: 작업 저장과 원고 저장이 분리돼 있다. 원고는 작업에 붙으므로(`campaign_task.draft_id`) 붙일 작업이 먼저 저장돼 있어야 한다.
- 원고를 **만드는 것** 자체는 작업이 없어도 된다 — AI 생성은 원래 미부착으로 만들고(v2 §5-1 "생성은 미부착, 선택 시 부착"), 직접 쓰기 API도 `taskId`가 선택 인자다(`src/app/api/drafts/manual/route.ts:21,71`). 제약은 **붙이는 순간에만** 걸린다.

## 1. 결정 (koo 09-21)

| 항목 | 결정 |
|---|---|
| 방향 | **B안 + 단일 트랜잭션** — 폼에 원고 칸을 두고, `[만들기]` 한 번이 작업 생성과 원고 부착을 함께 한다 |
| 인플루언서·유형 | 원고가 폼에 들어오면 **잠근다**. 원고를 떼면 풀린다 |
| `[만들고 하나 더]` | 폼을 비울 때 **원고 칸까지 비운다** |
| 고아(미부착) 원고 누적 | 이번 범위 밖 — 후보 200건 상한(v2 §8)과 같은 문제, 같이 처리한다 |

**기각한 선택지**

- **A안(만들면 바로 원고 모드)**: 저장 로직을 안 건드리고 변경도 가장 작지만, RT 작업이나 주간 일괄 적재("자리부터 잡고 원고는 나중에")에서 방해가 된다.
- **C안(안내 문구 한 줄)**: 기대와 화면의 어긋남을 문장으로 덮을 뿐이다.

## 2. 서버는 바뀌지 않는다 — 이미 있다

| 있는 것 | 위치 |
|---|---|
| `TaskCreateRequest.draftId` | `src/lib/campaignApi.ts:64-70` |
| 작업 생성과 원고 부착을 **한 트랜잭션**에서 | `src/lib/campaignTaskStore.ts:163` (`createTasks` → `attachDraft`) |
| 이미 다른 작업에 붙은 원고면 **409** | `src/app/api/campaigns/[id]/tasks/route.ts:34-37` |

**선례**: `/generate`(`src/app/generate/page.tsx:671`)와 기존 캠페인 상세(`src/app/campaigns/CampaignDetail.tsx:394`)의 "원고 카드 → 작업 만들기"(08-31 스펙). 그 주석이 이유를 말한다 — *"따로 하면 작업만 만들고 붙임에 실패했을 때 원고 없는 고아 작업이 남는다(리뷰 발견)."* 이번 작업은 **같은 규칙을 반대 방향(작업 폼 → 원고)에 놓는 것**이다.

**지켜야 할 서버 제약 두 개** (`campaignTaskStore.ts:144` 주석)

- `draftId`는 `influencers` 항목이 **1개 이하**일 때만 보낸다
- `count`(뼈대 N개)와 `draftId`는 함께 쓸 수 없다

`[만들기]`는 항상 한 행을 만들므로 둘 다 자연히 지켜진다. 그래도 폼이 보내는 본문에서 명시적으로 지킨다.

**설계에 반영해야 하는 서버 부작용**: `attachDraft`는 작업의 인플루언서가 비어 있으면 원고의 값으로 채우고(`coalesce`), 반대로 작업에 인플루언서가 있으면 **원고의 주인을 작업 값으로 덮어쓴다**(`campaignTaskStore.ts:222,230`). @A로 쓴 원고가 조용히 @B 것이 될 수 있다 — §4-3 잠금 결정의 근거다.

## 3. 왜 이 모양인가 (근거)

`docs/research/parent-child-save-patterns-20260921.md` — 8개 제품의 공식 문서를 1차 출처로 조사.

- 제품들이 실제로 쓰는 전략은 둘뿐이었다: **(a) 부모 없는 자식을 아예 못 만들게 막거나**(Shopify Draft Order, Notion `pages.create`), **(b) 부모 없는 자식을 정식 재고로 인정하고 목록으로 노출**(Stripe pending invoice item).
- 우리는 이미 (b)다 — 미부착 원고가 '있는 원고 고르기'에서 재사용되는 것이 정식 기능이다. (a)로 되돌리는 것은 기존 기능을 없애는 일이다.
- **TTL 자동 삭제로 고아를 청소하는 선례는 없었다.** 유일하게 만료가 있는 X API 미디어(24시간)는 "한 번 쓰고 버리는 업로드 세션"이라 성격이 다르다. → 미부착 원고 누적은 **삭제가 아니라 목록 UI 문제**이고, 후보 200건 상한과 한 묶음이다(§6).

## 4. 화면

### 4-1. 폼의 원고 칸

- `PANEL_FIELD_ORDER`를 그대로 쓴다 — new 모드의 `.filter((f) => f !== 'draft')`(`TaskPanel.tsx:411`)를 없앤다. 칸 순서가 편집 패널과 같아진다(투고: 인플루언서 → 비용 → **원고** → 게시 예정일 → 메모).
- **RT 유형은 그대로 원고 칸이 없다** — `PANEL_FIELD_ORDER.rt`에 `'draft'`가 원래 없어서 따로 막을 필요가 없다.
- 원고 없음: `[AI로 만들기] [직접 쓰기] [있는 원고 고르기 n]` — 편집 패널과 같은 세 버튼, 같은 라벨.
- 원고 고름: `제목 · 상태` + `[열기] [떼기]`, 그 아래 한 줄 — **"만들기를 누르면 이 원고가 함께 붙어요"**(UX 원칙 2: 행동 전 기대).
- 후보 수 `n`은 캠페인 단위 조회라 작업이 없어도 읽힌다(`GET /api/campaigns/[id]/draft-candidates`).
- `[열기]`는 edit 모드와 같은 `DraftCard`를 보여준다(다시 쓰기·번역·이미지·버전·상태 — 원고가 이미 저장돼 있으므로 그대로 동작한다). `DraftCard`는 `task.onDetach`로 원고 떼기 컨트롤(`DraftTaskField`)을 받을 수 있지만(`/generate` 선례, `generate/page.tsx:666`), 패널(폼·편집 패널 모두)은 이 `task` prop 자체를 넘기지 않는다 — 작업 칸을 그리지 않는다(`FlowDetail.tsx`의 `renderDraftCard` 주석). 원고를 떼는 `[떼기]`는 카드가 아니라 **원고 칸 자리**(원고 고름 상태의 두 번째 버튼)에 있고, 폼에서는 서버 detach가 아니라 **폼에서 내려놓기**로 연결한다 — 아직 붙은 적이 없어 서버가 할 일이 없다.

### 4-2. 원고 모드가 폼에서 열릴 때 — 끝이 '붙이기'가 아니라 '고르기'

- 같은 패널이 원고 모드로 바뀐다(`← 작업으로`). **폼 입력값은 그대로 유지**된다 — new 모드는 지금도 모든 값을 로컬 상태로 들고 있다(`TaskPanel.tsx:27` 주석).
- 원고 모드 위쪽의 **읽기 전용 칩**(클라이언트·인플루언서·유형·대상)은 edit 모드에서는 `task`에서 왔다. new 모드에서는 **폼 상태로 만든 맥락 객체 하나**에서 온다 — 세 탭이 보는 모양은 같게 유지한다. (이 칩은 '원고 모드 안에서는 못 고친다'는 뜻이고, 폼 자체의 잠금은 §4-3이다 — 두 가지는 다른 규칙이다.)
- 세 탭의 마지막 동작이 **부착 → 선택**으로 바뀐다. `DraftMode`에 출구 하나(`onSelect(draftId)`)를 더해 세 갈래가 같은 길로 나온다. 갈래마다 분기를 흩뿌리지 않는다.

| 탭 | edit 모드 (현행, 그대로) | new 모드 (이번) |
|---|---|---|
| AI로 만들기 | `[이 시안 붙이기]` → `PATCH /api/drafts/[id] {taskId}` | **`[이 시안 쓰기]`** → 부착 없이 폼으로 |
| 직접 쓰기 | `[저장하고 붙이기]` → `manual {taskId}` | **`[저장하고 쓰기]`** → `manual`(taskId 없이) → 폼으로 |
| 있는 원고 고르기 | 고르면 붙는다 | 고르면 폼으로 |

문구가 다른 이유: 이 시점에는 **붙일 작업이 없다**. '붙이기'라고 쓰면 거짓 어포던스다(UX 원칙 1·2).

- 인플루언서가 미정이어도 원고 모드는 열린다(편집 패널과 같은 규칙).
- 생성은 비용 유발 opt-in 그대로 — 버튼 옆 비용 문구도 그대로(UX 원칙 6).

### 4-3. 잠금 (koo 09-21)

- 원고가 폼에 들어오는 순간 **인플루언서·유형 칸이 칩으로** 바뀌고 옆에 **"원고를 떼면 바꿀 수 있어요"**.
- `[떼기]`는 **폼에서 원고를 내려놓는 것**일 뿐 원고를 지우지 않는다 — 미부착으로 남아 '있는 원고 고르기'에 다시 나온다. 문구가 그렇게 말해야 한다.
- **잠기는 것은 인플루언서·유형 둘뿐이다.** 비용·게시 예정일(방문일)·대상·메모는 원고와 무관하므로 계속 고칠 수 있다.
- 근거 둘: ① §2의 주인 덮어쓰기(@A로 쓴 글이 @B 것이 되는 일)를 원천 차단 ② 유형을 RT로 바꿨을 때 "이미 쓴 원고를 어떻게 하나"라는 문제가 생기지 않는다.

**고르는 순간의 주인 불일치** — 잠금은 '고른 뒤'를 막을 뿐, '고를 때'는 여전히 어긋날 수 있다(있는 원고 고르기에만 해당 — AI 생성·직접 쓰기는 폼의 인플루언서로 만들어지므로 어긋나지 않는다).

| 폼의 인플루언서 | 고른 원고의 주인 | 동작 |
|---|---|---|
| 비어 있음(미정) | @A | 폼을 **@A로 채우고** 잠근다 — 서버가 `coalesce`로 하는 일과 같으므로 화면이 먼저 사실대로 보여준다 |
| @B | 없음 | 그대로 진행(붙을 때 원고가 @B 것이 된다) |
| @B | @A (다름) | 그대로 진행하되 **고르기 전에 한 줄로 알린다** — "이 원고는 @A로 쓴 글이에요. @B 작업에 붙이면 @B 것이 돼요." 막지는 않는다(편집 패널의 현행 동작과 같다) |

### 4-4. 이탈과 실패

- **닫기**: 원고가 들어와 있으면 묻되 **사실대로** 말한다 — *"고른 원고는 '있는 원고 고르기'에 남아요. 닫을까요?"* 기존 `DRAFT_WRITE_LOST_CONFIRM`("사라져요")은 **저장 전 작성 중**일 때만 참이므로 그 문장을 재사용하지 않는다.
- **409 (고르고 `[만들기]` 사이에 다른 작업이 그 원고를 가져감)**: 폼을 닫지 않고 원고 칸이 말한다 — *"다른 작업에 붙었어요 — 다시 고르기"*. 서버는 이미 이 응답을 준다.
- **`[만들기]` 실패**: 트랜잭션이라 작업도 부착도 없다. 만들어 둔 원고는 재고로 남는다 — 유실 0.

### 4-5. `[만들고 하나 더]`

- 폼을 비울 때 **원고 칸까지 비운다**. `createTask(body, more)`의 기존 초기화에 한 줄이 는다.
- 이유: 방금 만든 작업이 그 원고를 가져갔다. 같은 원고를 두 작업에 붙일 수 없다(서버 409).

### 4-6. 배선 — 누가 무엇을 들고 있나

원고 모드 세 갈래의 알맹이는 지금도 `FlowDetail`이 만들어 `TaskPanel`에 넣는다(클라이언트·시술·레퍼런스·후보 같은 자료를 거기서 들고 있어서다). 그런데 폼의 인플루언서·유형·대상은 **`TaskPanel`의 로컬 상태**다. 둘을 잇는 방법을 하나로 정한다:

- `TaskPanel`이 폼 맥락(`{ type, handle, target }`)이 바뀔 때마다 위로 알린다(콜백 하나).
- `FlowDetail`은 그 맥락으로 세 갈래를 만든다 — **선택된 작업으로 만들 때와 같은 함수**를 쓰고, 입력만 `task`에서 맥락 객체로 바뀐다.
- 고른 결과(`draftId`)는 `TaskPanel`의 로컬 상태로 돌아와 `[만들기]` 본문에 실린다.

새 상태 보관소를 만들지 않는다. 폼 값은 지금처럼 `TaskPanel`에, 자료는 지금처럼 `FlowDetail`에 둔다.

## 5. 검증

- **순수 함수 + 테스트**: 폼 상태 → `TaskCreateRequest` 매핑(`draftId`·`influencers` 길이 제약 포함), 잠금 판정, 원고 칸 문구. `src/lib/campaignFlowView.ts` 또는 `draftPickView.ts` 옆에 둔다.
- 새 마이그레이션 없음, 서버 테스트 변경 없음.
- **손으로 볼 것 5가지**: ① 폼에서 AI 생성 → 고르기 → `[만들기]` → 만들어진 작업에 원고가 붙어 있다 ② 직접 쓰기도 같다 ③ 있는 원고 고르기도 같다 ④ `[떼기]` 뒤 인플루언서·유형 칸이 다시 열린다 ⑤ `[만들고 하나 더]` 뒤 원고 칸이 비어 있다 ⑥ 인플루언서를 비워 둔 채 @A 원고를 고르면 폼이 @A로 채워진다.

## 6. 범위 밖 (의도적으로 안 하는 것)

- **후보 200건 상한**(v2 §8) — 별건. 이번에 원고를 만드는 입구가 늘어 더 빨리 닿을 수 있다는 점만 기록한다.
- 편집 패널(edit 모드)의 동작 변경 — 없다.
- `DraftEditModal` → X 컴포저 통일(v2 §8), v2 1.5 두 건(레퍼런스 고르기 재설계·예산 기간 모델).
- 원고를 **다른 캠페인**의 작업으로 옮기기(v2 §8) — 여전히 기존 캠페인 화면에만 있다.
- 캠페인을 바꿀 때는 폼의 입력·고른 원고를 묻지 않는다(이 브랜치 이전부터의 사각지대 — 원고는 남으므로 유실은 아니다).

구현 중 드러난 미결(짧게 기록, 별건으로 다룬다):

- 고른 원고가 그 사이 삭제되면 400 안내만 뜨고 폼에는 없는 원고가 남는다(스펙은 409만 규정했다).
- '있는 원고 고르기'의 행 문구 중 '고르는 중…'은 실제로는 뜨지 않는다(고르기가 즉시 끝나서).
- 폼에서 원고 카드로 인플루언서를 바꾸는 경로는 이번에 처음 생겨 화면 확인이 필요하다.
