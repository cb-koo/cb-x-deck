# 새 DB 칸을 읽는 코드가 마이그레이션보다 먼저 배포되지 않게 한다

2026-09-21에 정산 기능이 약 2시간(14:17~16시경) 깨져 있었다. 원인은 사람의 실수가 아니라 **순서를 지킬 수 없게 된 구조**다. 이 ADR은 문제와 선택지를 기록한다 — **아직 결정하지 않았다.**

## 무슨 일이 있었나

`c00065a`(정산 수취 정보 정정)는 새 칸 `payment_request.payment_method_correction`을 읽는 코드와 그 칸을 만드는 `056`을 함께 담고 있었다. 작업자는 진행 현황 문서에 **"운영 DB 적용은 반드시 배포보다 먼저"** 라고 굵게 적어 뒀다. 그런데 같은 날 GitHub↔Vercel 연동을 켠 뒤라, main에 머지되는 **순간** Vercel이 자동 배포했다. 사람이 4번(DB 적용)을 끼워 넣을 자리가 없었다.

그 사이 `payment_request`에서 행을 반환하는 조회(`R_SELECT`)는 전부 `42703 column "payment_method_correction" does not exist`로 실패하는 상태였다.

**외부 영향이 없었던 것은 운이었다.** `external_api_log` 기준 그날 `/api/external/settlement/*`는 200이 136건, 5xx가 0건이었다. `listForExport`가 커서 페이지가 비면 `exportRows`(→`R_SELECT`)를 건너뛰는데, 마지막 `payment_request` 변경이 **14:07 — 배포 10분 전**이라 그쪽 커서가 이미 따라잡은 상태였기 때문이다. **요청이 한 건이라도 바뀌었으면 곧바로 500이 났다.** 정산 요청 목록 화면(`listRequests`)은 그런 우회로가 없어 열었다면 실패했다(그 시간대 열람 기록은 없다).

## 왜 재발하는가

- 자동 배포를 켜기 전에는 `vercel --prod`를 사람이 눌렀으므로 "DB 먼저, 배포 나중"이 지켜질 수 있었다.
- 켠 뒤로는 **머지 = 배포**다. 그 사이에 사람이 할 수 있는 일이 없다.
- 자동 배포를 끄는 것은 답이 아니다 — 태정님처럼 Vercel 접근 권한이 없는 사람도 자기 작업을 배포할 수 있게 된 것이 연동의 이유였다.
- 즉 **다음에 마이그레이션이 필요한 작업이 머지되면 같은 일이 난다.** 그때 데이터가 조용하지 않으면 오늘처럼 넘어가지 못한다.

## Considered Options

### A. 확장–이행–수축 (칸 추가 배포 → 읽기 시작 배포)

한 작업을 두 번 머지한다. ①칸을 만드는 마이그레이션만(아무도 읽지 않음) → 배포 → ②그 칸을 읽는 코드 → 배포.

- 장점: 사람의 기억에 의존하지 않는다. 롤백해도 안전하다(옛 코드는 새 칸을 모를 뿐).
- 단점: 작업이 두 머지로 쪼개진다. 작은 변경에도 왕복 두 번이라 마찰이 크다.

### B. 빌드 단계에서 마이그레이션 실행 (운영 빌드일 때만)

배포 빌드가 트래픽을 받기 **전에** 마이그레이션을 돌린다. `VERCEL_ENV === 'production'`일 때만 실행해 프리뷰 빌드가 운영 DB를 건드리지 않게 한다.

- 장점: 순서가 구조적으로 보장된다. 작업자가 아무것도 기억하지 않아도 된다. 지금처럼 한 번의 머지로 끝난다.
- 단점·열린 질문:
  - 현재 `apply-migrations.sh`는 `psql`을 쓴다. **Vercel 빌드 이미지에 psql이 있는지 확인되지 않았다** — 없으면 node 스크립트로 바꿔야 한다.
  - `PG*` 환경변수가 **빌드 시점에도 읽히는지** 확인 필요(지금은 Production 스코프로만 확인됨).
  - 빌드가 마이그레이션을 적용한 뒤 배포가 실패하면 DB만 앞서간다 — 마이그레이션이 **추가만 하는(backward-compatible)** 한 무해하다. 이 전제를 규칙으로 못박아야 한다.
  - 동시 빌드가 같은 마이그레이션을 겹쳐 돌릴 수 있다 — 전 문장이 멱등(`if not exists`)이라 현재는 안전하지만, 이 역시 전제다.

### C. 머지 전 운영 DB 적용을 체크리스트로 (사람 규율)

PR 본문·머지 절차에 "마이그레이션 있으면 머지 전에 운영 DB 적용" 항목을 둔다.

- 장점: 오늘 당장 할 수 있고 비용이 0이다.
- 단점: **이번에 실패한 방식이 바로 이것이다.** 작업자는 문서에 굵게 적어 뒀는데도 막지 못했다. 게다가 운영 DB 접근 권한이 없는 사람은 지킬 수 없다.

### D. 자동 배포를 끄고 수동 배포로 되돌린다

- 연동을 켠 이유(권한 없는 사람도 배포, PR 프리뷰)를 잃는다. 퇴행이다.

## 추천

**B를 본선, A를 예외 규칙으로.** B가 사람의 기억을 구조로 대체하는 유일한 안이다. 다만 B는 "마이그레이션은 추가만 한다"를 전제하므로, **칸 이름 변경·삭제·타입 변경처럼 기존 코드를 깨는 변경은 A(두 번 머지)로 처리한다**고 함께 정해야 한다.

C는 B가 준비될 때까지의 임시 방편으로만 쓴다 — 단독으로는 이미 실패한 방식이다.

## 다음에 할 일

1. B의 열린 질문 셋을 실측으로 닫는다 — 빌드 이미지의 `psql` 유무, 빌드 시점 `PG*` 접근, 동시 빌드 겹침.
2. `psql`이 없으면 `apply-migrations.sh`를 node 스크립트로 옮긴다(`postgres` 패키지는 이미 의존성에 있다).
3. `package.json`의 `build`를 `마이그레이션(운영일 때만) → next build` 순으로 바꾼다.
4. "마이그레이션은 추가만 한다 / 깨는 변경은 두 번 머지"를 AGENTS.md에 규칙으로 적는다.
5. 스테이징에서 먼저 돌려 프리뷰 빌드가 운영 DB를 건드리지 않는지 확인한다.

## Consequences

- 결정 전까지는 **마이그레이션이 포함된 작업을 머지하기 전에 운영 DB를 먼저 맞춰야 한다**(C). 이 ADR이 `accepted`가 되기 전에 마이그레이션 작업이 또 생기면, 그 작업은 이 임시 규칙을 따른다.
- `056`처럼 이미 적용된 마이그레이션은 재실행해도 안전하다(전 문장 멱등) — B로 옮겨도 기존 파일을 손볼 필요는 없다.
