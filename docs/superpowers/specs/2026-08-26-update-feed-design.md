# 업데이트 소식 (업데이트 피드) — 설계 스펙

- 날짜: 2026-08-26
- 브랜치: `cb-koo/update-feed`
- 배경: 8월 한 달에 배포가 20건 가까이 나갔지만 사용자(비개발 콘텐츠 기획 담당자 2~5명)가 "뭐가 바뀌었는지" 알 길이 없다. 기능이 추가·수정될 때마다 소식을 올려 두는 페이지를 만든다.
- 시안: `~/claude-outputs/cb-x-deck-업데이트피드-타임라인-시안-20260826.html` (koo 확인 완료 — 타임라인·가운데 정렬·본문 16px)

## 0. 목적·범위

- 목적: 배포된 변화를 **사용자 말로** 시간순으로 보여주는 한 페이지. 사용자가 새 기능을 발견하고, 바뀐 동작에 당황하지 않게 한다.
- 결정 사항(브레인스토밍 확정):
  - 글은 **코드 저장소 안의 파일**로 관리한다 — 기능 커밋과 같은 브랜치에 실려 머지·배포와 함께 자동으로 게시된다. DB·API·관리 UI 없음.
  - **배포되는 변화는 종류를 가리지 않고 전부** 올린다 — 보이는 변화(새 기능·개선·수정)뿐 아니라 보이지 않는 변화(성능·안정성·보안·기반)도. 다만 쓰는 법이 다르다(§5).
  - 알림 방식은 **사이드바 메뉴 하나**. 안 읽음 표식·팝업 없음.
  - 텍스트만. 이미지 없음. 관련 화면 **바로가기 링크는 선택**.
  - 첫 배포 때 **7월 19일 이후 배포분을 소급**해서 채운다(§6 — 25건).
- 범위 밖(§9 백로그): 안 읽음 표식, 내부 변화 숨기기 토글, 이미지, 검색·필터, 항목 앵커 공유, 연도별 파일 분리.

## 1. 데이터 — `src/content/updates.ts`

```ts
export type UpdateType = '새 기능' | '개선' | '수정' | '내부';

export type UpdateEntry = {
  date: string;                 // 'YYYY-MM-DD' — 배포일(KST). 작성 시점의 배포 예정일
  type: UpdateType;
  title: string;                // 사용자 말 한 줄 — "~할 수 있어요", "~를 고쳤어요"
  summary: string;              // 1~3문장
  bullets?: string[];           // 세부 항목
  link?: { label: string; href: string };  // 관련 화면. href에 `{ws}` 토큰 허용(§3)
};

export const UPDATES: UpdateEntry[] = [ /* 최신이 위 */ ];
```

- 파일 하나, 배열 하나. **최신 항목을 맨 위에** 추가한다(정렬은 로직이 다시 하므로 순서가 어긋나도 화면은 맞다 — 파일을 읽는 사람을 위한 관례).
- 검증은 TypeScript가 한다: 유형 오타·필드 누락 → `next build` 실패 → 잘못된 글이 배포되지 않는다. 날짜 형식(`YYYY-MM-DD`)과 빈 문자열은 타입으로 못 잡으므로 §7의 테스트가 `UPDATES` 전체를 훑어 검사한다.
- 왜 마크다운이 아닌가: 프로젝트에 마크다운 렌더러가 없다. 자체 파서를 두면 형식이 살짝 어긋날 때 화면이 조용히 깨지고, 의존성을 추가하면 이 한 페이지 때문에 번들이 커진다. 작성자는 사실상 Claude(머지 시)라 코드 파일이어도 마찰이 없다.

## 2. 순수 로직 — `src/lib/updates.ts`

- `sortUpdates(entries)` — `date` 내림차순, 같은 날은 배열 순서 유지(안정 정렬).
- `groupByMonth(entries)` → `{ ym: '2026-08', label: '2026년 8월', entries: UpdateEntry[] }[]` — 최신 월이 앞.
- `isMonthOpen(index)` — **항목이 있는 최신 3개 월은 펼침, 그 이전은 접힘**. 달력 기준("최근 90일")이 아니라 "글이 있는 월 3개"로 정한다 — 페이지가 정적 렌더라 `now`가 빌드 시각이 되는데, 배포가 뜸해지면 빌드 시각 기준 3개월 안에 글이 없어 전부 접히는 일이 생긴다. 월 개수 기준이면 시계와 무관하게 결정적이다.
- `formatDay(date)` → `8월 25일` (`datetime.ts`의 `kstMonthDayKo`가 ISO 인스턴트를 받으므로 그대로 쓰지 않고, `YYYY-MM-DD` 문자열을 파싱해 표기하는 작은 함수를 이 모듈에 둔다. 날짜 문자열은 이미 KST 달력일이라 시간대 변환이 필요 없다).
- 전부 순수 함수, 단위 테스트(§7).

## 3. 화면 — `/updates`

- 파일: `src/app/updates/layout.tsx`(`GlobalShell`로 감싼다 — `/usage`와 동일 패턴), `src/app/updates/page.tsx`(서버 컴포넌트). 데이터가 빌드 시점 상수라 `force-dynamic` 없이 **정적 렌더**. DB 조회 0.
- 레이아웃(시안 확정): 메인 영역 안에서 **가운데 정렬**, 본문 폭 최대 760px, 상단 여백 48px. Reading 스케일 — 이 저장소의 덱 토큰(15/13/11)이 아니라 읽기용 크기를 쓴다: 페이지 제목 24px·항목 제목 18px·본문/불릿 16px(행간 1.7)·날짜/월 헤더 14px·배지 12px·바로가기 15px. 근거: 도구 화면이 빽빽하다는 반복 피드백, 프로젝트 방향(덱=X 스케일 / 도구·읽기=Reading 스케일).
- 헤더: `업데이트 소식` + 한 줄 설명 `기능이 추가되거나 바뀌면 여기에 올립니다. 눈에 보이지 않는 변화도 모두 적어요.`
- **타임라인**:
  - 왼쪽에 세로 축선(2px, `#e1e8ed`), 항목마다 점(10px). 점 색은 유형과 같다 — 새 기능 `x-blue` / 개선 `x-green` / 수정 주황(`#f59e0b`) / **내부는 빈 원**(흰 바탕 + `x-border-strong` 테두리). 축선만 훑어도 "큰 소식/잔잔한 소식" 리듬이 보이게.
  - 항목 = 날짜 `·` 유형 배지 / 제목(굵게) / 요약 / 불릿(있을 때) / `→ 바로가기`(있을 때). 카드 테두리·구분선 없음 — 여백(항목 간 40px)과 축선이 구분한다.
  - 같은 날 여러 건은 각각 점을 가진다(날짜 반복 표기).
  - 배지 색: 새 기능 `bg #e8f4fd / text x-blue-text`, 개선 `#e6f7f0 / #0a7a52`, 수정 `#fff4e0 / #9a5b00`, 내부 `#f1f3f4 / x-secondary`. 색은 배지 글자와 함께 쓰므로 색만으로 전하지 않는다.
- **월 접기(누적 대응, v1 포함)**: 월 단위 `<details>/<summary>`. `isMonthOpen`이 참인 월은 `open`, 나머지는 접힌 상태로 렌더하고 `summary`에 `2026년 5월 · 12건`처럼 건수를 붙인다. JS 0, 정적 렌더 유지. 접힌 `<details>` 안의 글도 크롬이 Ctrl+F로 찾으면 자동으로 펼치므로 검색 기능을 따로 만들지 않는다. 접힌 월도 축선은 이어지게(헤더 왼쪽에 짧은 축선 조각). 지금은 8·7월만 있어 전부 펼쳐 보인다.
- **바로가기 링크**: `next/link`. 이 페이지엔 편집 상태가 없어 `interceptNav` 가드는 태우지 않는다. 워크스페이스 안 화면(덱·보관함·브리핑·리서치)은 정적 페이지가 `wsId`를 모르므로 `href`에 `{ws}` 토큰을 허용한다 — 작은 클라이언트 컴포넌트 `UpdateLink`가 `GlobalShell`의 `LAST_WS_KEY`(localStorage `cbx-last-ws`)로 치환하고, 값이 없으면 링크를 렌더하지 않는다(거짓 어포던스 방지). 토큰이 없는 `href`는 그대로 `<Link>`.
- 빈 상태: `아직 올라온 소식이 없어요` 한 줄(방어용 — 소급 덕에 실제로는 보이지 않는다).

## 5. 작성 규칙 — `AGENTS.md`에 절 추가

`AGENTS.md`에 "업데이트 소식 작성 규칙" 절을 추가한다. 내용:

- **언제**: 사용자에게 배포되는 변화를 main에 머지할 때(QA 완료 후, 머지 직전). `src/content/updates.ts` 맨 위에 항목을 추가해 같은 브랜치에 커밋한다.
- **무엇을**: **변화 종류를 가리지 않는다.** 새 기능·개선·버그 수정은 물론 성능·안정성·보안·데이터 구조 변경(내부)도 올린다. 사용자 화면에 변화가 없어도 "무엇을 왜 했고, 사용자에게 달라지는 점이 무엇인지(없으면 없다고)"를 적는다.
- **단위**: 하나의 작업(스펙/브랜치) = 한 건. 커밋 수와 무관. QA 후속 수정은 새 항목이 아니라 기존 항목의 불릿을 고친다. 내부 변화가 기능 작업의 일부면 그 건의 불릿으로 흡수, 단독 작업이면 별도 건.
- **유형**: `새 기능`(없던 화면·동작) / `개선`(있던 동작이 더 좋아짐·바뀜) / `수정`(잘못 동작하던 것을 고침) / `내부`(화면 변화 없는 성능·안정성·보안·기반).
- **문체**(UX 원칙 1·3·5의 적용):
  - 제목은 사용자 말 한 줄 — `~할 수 있어요` / `~가 생겼어요` / `~를 고쳤어요`. 메커니즘 대신 이득.
  - 내부 용어 금지: 마이그레이션 번호·컬럼명·라이브러리명·포트·리전·커밋 해시. ✗ "PGPORT 6543 트랜잭션 모드 전환" → ✓ "덱에 '트윗 없음'이 뜨던 문제를 고쳤어요 — 서버가 동시에 여러 요청을 받을 때 연결이 부족해지는 원인이었어요".
  - 쓰던 방식이 바뀐 것은 반드시 적는다(안 알리면 "왜 바뀌었지?"가 된다).
  - 바로가기는 갈 화면이 있을 때만. 워크스페이스 안 화면은 `{ws}` 토큰.
- 강제 장치(커밋 훅 등)는 두지 않는다 — 내부 작업도 `feat`일 수 있어 오탐이 많고, 우회가 습관이 되면 규칙이 형식이 된다. 머지 절차(`finishing-a-development-branch`)에서 확인한다.

  - `isMonthOpen` — 월 3개 이하면 전부 펼침, 4개 이상이면 앞 3개만.
  - `formatDay` — `2026-08-05` → `8월 5일`(0 제거).
  - **데이터 검사**: `UPDATES` 전체가 `^\d{4}-\d{2}-\d{2}$`이고 실제 날짜로 파싱되며, `title`·`summary`가 빈 문자열이 아니고, `link.href`는 `/`로 시작한다.
- `npm run build` 성공(타입 = 데이터 검증), `npm run lint` 기준선 유지.
- 화면 확인: `next build && next start -p 3001` 후 `127.0.0.1:3001/updates`(로컬 dev는 하이드레이션 문제로 신뢰 불가 — 프로젝트 관례). 사이드바 활성 표시, 월 접기·펼치기, `{ws}` 링크가 워크스페이스 방문 후엔 나타나고 localStorage를 지우면 사라지는지.

## 8. 엣지

- `UPDATES`가 비어 있으면 빈 상태 문구. 월이 1~3개면 접힘 없음.
- `{ws}` 토큰 링크는 서버 렌더 시 아무것도 그리지 않고 클라이언트에서만 나타난다 — 하이드레이션 불일치가 없도록 `useEffect` 이후에 렌더한다.
- 같은 날 항목의 순서는 파일 순서(위가 먼저). 하루에 두 건이면 더 큰 소식을 위에 쓴다.
- 날짜가 미래(배포 예정일)여도 렌더한다 — 배포된 시점엔 이미 지났고, 미리 렌더돼도 해가 없다.
