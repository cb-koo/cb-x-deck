# 캠페인 작업에서 원고 쓰러 가기 — 설계 스펙

작성: 2026-08-31 · 브랜치 `cb-koo/data-flow-audit` · 상태: 설계 확정, 구현 대기
선행 스펙: `docs/superpowers/specs/2026-08-28-campaign-task-design.md`(캠페인 작업 — 이 문서는 그 §4-2 원고 칸을 **보완**한다. 데이터 모델·API·정산 계약은 전혀 건드리지 않는다)
근거: 2026-08-31 데이터 흐름 감사 — koo 확인 "실제 업무는 캠페인을 먼저 만들고 거기 필요한 콘텐츠를 생성하는 순서가 맞다"

## 0. 한 줄 정의

**이미 만들어 둔 작업 줄에서 원고를 새로 쓰러 갈 수 있게 한다.** 지금은 그 입구가 작업을 *만드는 순간*에만 열린다.

## 1. 왜 바꾸나

08-28 전환으로 데이터 모델은 이미 캠페인 우선이 됐다 — 039가 `draft`에서 `campaign_id`·`scheduled_on`·`cost`를 떼어내 `campaign_task`로 옮겼고, §0이 "원고는 작업에 *붙을 수도 있는 것*"이라 정의했다. §5는 이미 반대 방향(원고 카드 → 새 작업 만들기)을 제공한다.

그런데 캠페인 쪽 입구는 절반만 구현됐다. `/generate?task=&campaign=` 딥링크를 발급하는 코드가 저장소 전체에 한 줄뿐이고(`CampaignDetail.tsx:449`), 그것이 `TaskAddModal`의 제출 콜백 안에 있다. 즉 **"작업을 만들면서 그 자리에서 원고까지 쓴다"** 는 한 경우만 상정돼 있다.

캠페인 골격(작업 전량)을 먼저 짜두고 며칠에 걸쳐 원고를 채우는 실제 업무 방식에서는, 원고를 쓰러 갈 때 언제나 *이미 만들어진 작업*에서 출발한다. 그 자리에 입구가 없어 사용자는 캠페인 화면을 떠나 `/generate`로 가서 클라이언트를 다시 고르고, 다 쓴 뒤 원고 카드에서 캠페인·작업을 손으로 찾아 붙인다 — 화면 2회 왕복.

부수 문제: `AttachDraftModal`의 빈 상태 문구가 *"붙일 수 있는 원고가 없어요 — '새로 만들기'로 바로 써도 돼요"* 인데, 그 창에는 그 버튼이 없다. 문구가 가리키는 것은 `TaskAddModal`의 라디오이고 작업은 이미 만든 뒤라 갈 수 없다 — **거짓 어포던스**.

## 2. 범위

**한다 (3건, 한 브랜치 = 업데이트 소식 1건)**

1. 작업 줄에 "새로 만들기" 입구
2. 원고 화면 왕복을 매끄럽게 — 라우터 이동 + 돌아가기 링크
3. 새 캠페인 창의 옛 안내 문구 수정

**안 한다 (다음으로)**

- 원고 → 작업 인플루언서 역전파
- 시안 B·C를 작업에 붙일 때 떼고-다시-붙이는 2단계 줄이기
- `/generate` 표 보기·칸반에서 작업에 붙이기
- `attachDraft`에 작업 유형 검사 추가(rt 작업에 원고가 붙는 서버 구멍)

**전제**: 스키마 변경 0 · 마이그레이션 0 · API 라우트 변경 0 · 서버 로직 변경 0. 전부 화면 코드다.

## 3. 작업 줄 입구 (`TaskTable` 원고 칸)

### 3-1. 표시

원고가 없고 유형이 `post`·`quoteRt`·`visit`인 행:

| 지금 | 바뀐 뒤 |
|---|---|
| `원고 없음 · 붙이기` | `원고 없음 · 새로 만들기 · 고르기` |

- **새로 만들기** — `<Link href="/generate?task={t.id}&campaign={campaign.id}">`. `TaskTable`은 이미 `next/link`를 import하고 `campaign: CampaignRow`를 prop으로 받으므로 배선이 없다.
  - 링크로 두는 이유: 가운데 클릭·⌘클릭으로 새 탭에서 열 수 있다. 캠페인 화면을 띄워둔 채 원고만 따로 쓰는 방식이 공짜로 생긴다.
- **고르기** — 지금의 `onAttachDraft(t)` 그대로. 시각적으로 보조(muted)로 두어 표가 빽빽해지지 않게 한다.
- `rt` 행은 지금처럼 `—`. 원고가 이미 붙은 행도 지금처럼 제목 링크.

### 3-2. 라벨 결정

**"새로 만들기"** — `TaskAddModal:205`의 라디오와 같은 말. 같은 동작에 두 이름을 두지 않는다(AGENTS.md 원칙 4). "새로 쓰기"는 쓰지 않는다. `직접 쓰기`는 다른 뜻(LLM 없이 쓰기)이므로 혼용 금지.

### 3-3. 주소 조립은 순수 함수로

`campaignJudgment.ts`에 `draftWriteHref(taskId, campaignId): string`을 둔다(리포 관례 — 판정·조립은 순수, DB·네트워크 없음). 두 파라미터가 모두 있어야 `/generate`가 배너를 켜므로(`page.tsx:299`), 조립 규칙이 한 곳에만 있어야 한다. 호출자는 `TaskTable`(새 입구)과 `CampaignDetail`(작업 생성 직후 이동) 둘이다.

"이 줄에 새로 만들기를 보일 것인가"는 별도 함수로 뽑지 **않는다**. 원고 칸은 이미 `rt → —` / `원고 있음 → 제목` / `그 외` 세 갈래로 갈리고, 세 번째 갈래가 곧 그 조건이다. 이름을 붙이면 소비자 없는 추상이 하나 늘 뿐이다(YAGNI). 대신 `rt`를 먼저 거르는 기존 분기 순서를 **그대로 유지한다** — 순서를 바꾸면 "rt 작업에 붙은 원고가 표에 안 보인다"는 별건(§2 안 한다 목록)의 동작이 딸려 바뀐다.

## 4. 원고 고르기 창의 빈 상태 문구 (`AttachDraftModal`)

이 창은 **두 곳**에서 쓰인다:

| 호출자 | 상황 | 맞는 문구 |
|---|---|---|
| `TaskAddModal:328` | 작업을 만드는 중 — 같은 창에 라디오가 있다 | `…'새로 만들기'를 고르면 바로 써도 돼요` |
| `CampaignDetail:455` | 작업 줄에서 — 창을 닫아야 한다 | `…창을 닫고 '새로 만들기'를 누르면 바로 쓸 수 있어요` |

문구를 한 줄로 고정하면 둘 중 한쪽이 다시 거짓 안내가 된다. **`emptyHint` prop을 받아 호출자가 넘긴다**(기존 `title` prop과 같은 관례). 기본값은 두지 않는다 — 두면 새 호출자가 조용히 틀린 문구를 쓴다.

## 5. 화면 왕복 (`CampaignDetail` · `/generate` 배너)

### 5-1. 이동 방식

`CampaignDetail:449`의 `window.location.assign(...)` → `next/navigation`의 `useRouter().push(...)`.

리포 표준은 `useRouter`다(`page.tsx`·`clients`·`workspaces`·`settlement`·`tracking` 전부). `window.location.assign`은 이 한 곳뿐인 예외였다. 앱이 통째로 다시 켜지지 않아 눈에 띄게 빨라진다.

### 5-2. 딥링크 소비 판정 단단히 하기

`/generate`의 `taskLinkDone = useRef(false)`(`page.tsx:108`)는 **"매번 페이지가 새로 열린다"는 전제** 위에 있다. 5-1로 전체 리로드를 없애면 그 전제가 약해진다.

→ 참·거짓 대신 **소비한 작업 id**를 기억한다: `taskLinkDone = useRef<string | null>(null)`, 가드는 `taskLinkDone.current === targetTask`. 같은 작업으로 다시 들어오면 무시하고, 다른 작업으로 들어오면 새로 처리한다. 조용히 무시되는 경우가 사라진다.

### 5-3. 돌아가기 링크

배너(`page.tsx:802-820`)에 `← {캠페인 이름}으로 돌아가기`를 붙인다. 목적지는 `/campaigns?id={campaignId}` — `campaigns/page.tsx:43`이 `?id=`를 읽어 그 캠페인을 선택한다.

- **붙기 전에도, 붙은 뒤에도 항상 보인다.** 다 쓰고 돌아가는 것과 "역시 나중에 쓰자" 하고 돌아가는 것이 같은 자리다.
- 기존 `[해제]` 버튼은 그대로 둔다 — 맥락만 풀고 이 화면에 남는 것과, 캠페인으로 가는 것은 다른 행동이다.
- 이동은 `<Link>`. 새 탭으로도 열 수 있다.

## 6. 새 캠페인 창 안내 문구 (`CampaignCreateModal:100`)

옛 UI를 가리키는 잔재다. `[+ 원고 추가]`는 08-28에 `[+ 작업 추가]`로 바뀌며 사라졌다.

- 지금: `클라이언트 한 곳 × 기간 하나예요. 원고는 만든 뒤 [+ 원고 추가]로 넣거나 콘텐츠 생성에서 바로 만들어요.`
- 바꿈: `클라이언트 한 곳 × 기간 하나예요. 만든 뒤 [+ 작업 추가]로 이번 주에 나갈 일을 올리고, 원고는 각 작업에 붙여요.`

## 7. 동작 계약 — 바뀌지 않는 것

원고를 만들고 붙이는 서버 동작은 **전혀 손대지 않는다.** 확인한 현행 동작이 그대로 유지된다:

- 생성과 붙이기는 한 트랜잭션(`generate.ts:148-152`, `drafts/manual/route.ts:54-79`)
- 작업 1개 = 원고 1개는 4겹으로 강제(입력 파서 → 라우트 사전 검사 → 스토어 `for update` → DB unique index)
- 다른 사람이 먼저 붙였으면 409 → 배너가 "붙었어요"로 전환(`page.tsx:448-450`). 이때 내가 쓴 원고는 작업 없이 남는다 — **기존 동작이며 이번에 바꾸지 않는다**. 입구가 늘어 이 상황이 조금 더 자주 생길 수 있으나, 원고가 사라지지 않고 나중에 아무 작업에나 붙일 수 있으므로 손실이 없다.
- 시안을 여러 개 만들면 첫 시안만 붙는다(`generate.ts:130`). 배너가 미리 알린다.
- 붙는 순간 작업의 인플루언서가 원고에 밀려 들어간다(작업이 이긴다, `campaignTaskStore.ts:188-190`)

## 8. 검증

- **단위 테스트**: `campaignJudgment.test.ts`에 `draftWriteHref` 추가(테스트 `5)`). 기존 파일의 결정적 테스트 관례를 따른다(DB·네트워크 없음).
- **회귀**: `npm test` 전량 통과(실 DB, 약 4분). 린트 기준선 24개 유지.
- **화면 확인**: OAuth 도메인 게이팅이라 koo만 가능. 확인 항목 —
  1. 작업 줄에서 "새로 만들기" → 원고 화면이 그 작업 맥락으로 열림(클라이언트 자동 선택, 배너 문구)
  2. 원고 생성 → 저절로 붙고 배너가 "붙었어요"로 바뀜
  3. 돌아가기 → 그 캠페인이 선택된 채 열림
  4. 연달아 다른 작업으로 "새로 만들기" → 배너가 새 작업으로 갱신됨 (5-2 검증)
  5. 원고 고르기 창을 두 경로에서 열어 빈 상태 문구가 각각 맞는지
  6. RT 행에는 "새로 만들기"가 안 보임
- **업데이트 소식**: 머지 직전 `src/content/updates.ts` 맨 위에 1건(유형 `개선`).
