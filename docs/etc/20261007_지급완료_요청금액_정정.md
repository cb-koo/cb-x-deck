# 지급 완료 정산 요청의 엔화 금액 정정 절차

2026년 10월 7일 기준. `@17dsy_` 인용RT 요청 `5288a9d3-c36d-4c80-8505-6841825d1ee9`의 **요청 금액 ¥4,000을 ¥6,000으로 바로잡는** 운영 절차다. 실제 송금액 ¥6,000과 지급 완료 기록은 이미 맞으므로 유지한다. 정산코드는 `CBX-261006-009`다.

이 건은 지급 완료 상태여서 `cb-x-deck`의 **고친 값으로 다시 반영** 버튼과 수정 API가 막는다. 운영 DB의 원본 요청 한 건을 정정하고, 정산 시스템이 변경된 요청을 다시 가져왔는지 확인한다. 아래 SQL은 운영 DB 접근 권한이 있는 담당자가 실행한다.

## 바꿀 값과 유지할 값

| 구분 | 현재 | 정정 후 |
| --- | ---: | ---: |
| 요청 순액 `amount_net` | ¥4,000 | ¥6,000 |
| 요청 송금액 `amount_gross` | ¥4,000 | ¥6,000 |
| 요청 원화 `amount_krw` | ₩40,000 | ₩60,000 |
| 요청 송금액의 원화 환산 `gross_krw` | ₩40,000 | ₩60,000, DB 자동 계산 |
| 실제 송금액 `paid_amount_jpy` | ¥6,000 | 그대로 |
| 실제 지급 원화 `paid_amount_krw` | ₩50,963 | 그대로 |

요청 원화는 이 요청에 저장된 **1엔=10원** 기준이다. 실제 지급 원화 ₩50,963은 송금일 환율로 계산된 별도 기록이므로 ₩60,000으로 바꾸지 않는다. `revision`, `revised_at`, `status`, `external_status`, `paid_at`, `external_id`도 유지한다. 특히 `revision`을 올리면 정산 시스템이 지급 후 수정본으로 판단해 오류를 기록할 수 있다.

## 실행 전 원본 확인

반드시 **`cb-x-deck` 운영 Supabase 프로젝트의 SQL Editor 또는 운영 DB에 연결된 SQL 도구**에서 조회한다. 연습용 DB와 혼동하지 않는다. 결과 한 건에서 요청 ID·정산코드·통화·환율·수수료·지급 상태가 아래 정정 SQL의 조건과 일치하는지 확인한다. 조회 결과와 실행자·시각·정정 사유는 내부 운영 기록에 남긴다.

```sql
select
  p.id, p.task_id, p.influencer_handle, p.task_type,
  p.amount_krw, p.cost_currency, p.payout_currency,
  p.rate_krw_per_jpy, p.amount_net, p.fee, p.fee_amount,
  p.amount_gross, p.gross_krw,
  p.status, p.external_status, p.external_id,
  p.paid_amount_jpy, p.paid_amount_krw, p.paid_at,
  p.revision, p.updated_at,
  t.cost as task_cost
from payment_request p
left join campaign_task t on t.id = p.task_id
where p.id = '5288a9d3-c36d-4c80-8505-6841825d1ee9';
```

`task_cost`는 캠페인 작업에 기록된 원래 비용이다. 이것도 ¥4,000이고 실제 약속한 작업 비용이 ¥6,000이었다면 **작업 비용도 별도로 정정**해야 캠페인 비용·예산 화면이 맞는다. 작업 비용을 고쳐도 이미 생성된 정산 요청 값은 자동으로 바뀌지 않는다. 이 문서의 기본 SQL은 정산 요청만 바꾼다. 작업 비용이나 인플루언서 프로필의 기본 단가를 임의로 함께 바꾸지 않는다.

## 원본 요청 정정

아래 SQL을 **전체 선택해 한 번에** 실행한다. 현재 값이 지정한 조건과 다르거나 수정된 행이 한 건이 아니면 오류가 나고 변경은 취소된다. 오류가 나면 `ROLLBACK;`으로 해당 세션의 거래를 닫고, 조건을 느슨하게 바꿔 재실행하지 말고 원본을 다시 확인한다. 실행 도구에서 자동 커밋을 사용하더라도 이 블록을 나눠 실행하지 않는다.

```sql
begin;

do $$
declare
  changed_rows integer;
begin
  update payment_request
  set amount_krw = 60000,
      amount_net = 6000,
      amount_gross = 6000,
      updated_at = clock_timestamp()
  where id = '5288a9d3-c36d-4c80-8505-6841825d1ee9'
    and status = 'requested'
    and external_status = 'paid'
    and external_id = 'CBX-261006-009'
    and revision = 0
    and cost_currency = 'JPY'
    and payout_currency = 'JPY'
    and rate_krw_per_jpy = 10
    and fee is null
    and fee_amount = 0
    and amount_krw = 40000
    and amount_net = 4000
    and amount_gross = 4000
    and gross_krw = 40000
    and paid_amount_jpy = 6000
    and paid_amount_krw = 50963;

  get diagnostics changed_rows = row_count;
  if changed_rows <> 1 then
    raise exception '요청의 현재 값이 예상과 달라 정정을 중단했습니다';
  end if;
end $$;

commit;
```

`gross_krw`는 생성 컬럼이므로 직접 `UPDATE`하지 않는다. `updated_at`을 갱신해야 정산 시스템의 다음 폴링에 이 요청이 다시 실린다. 지급 상태나 실제 지급액을 다시 보내는 작업은 하지 않는다. 실행 직후에는 위의 **실행 전 원본 확인** 조회를 다시 실행해 변경값과 유지값을 확인한다.

## 반영 확인

1. `cb-x-deck` 정산 요청 내역에서 이 건의 요청 송금액이 **¥6,000**, 실제 송금 엔화가 **¥6,000**, 지급 상태가 **완료**인지 확인한다. 엔화 기준 차액은 0이 되어야 한다.
2. 정산 시스템의 다음 폴링이 끝난 뒤 요청 상세에서 요청 금액 **¥6,000**, 요청 원화 **₩60,000**, 실송금액 **¥6,000**, 실제 지급 원화 **₩50,963**, 정산코드 `CBX-261006-009`가 표시되는지 확인한다. 폴링 목록에는 갱신 후 약 30초가 지나야 나타나며, 권장 폴링 주기는 5분이다.
3. 정산 시스템 DB를 조회할 수 있다면 아래 결과도 확인한다. `consistency_error`는 `false`여야 한다.

```sql
select
  m.request_id, m.revision, m.amount_krw,
  m.payout ->> 'gross' as requested_jpy,
  m.payout ->> 'gross_krw' as requested_krw,
  s.status, s.paid_amount_foreign as paid_jpy,
  s.paid_amount_krw, s.consistency_error, s.error_code
from public.mirror_requests m
join public.settlement_states s using (request_id)
where m.request_id = '5288a9d3-c36d-4c80-8505-6841825d1ee9';
```

정산 시스템에는 원본 요청을 고칠 필요가 없다. 같은 `revision`의 요청 금액 변경은 다음 폴링에서 미러에 반영되도록 구현되어 있다. 반영되지 않았다면 정산 시스템 DB만 손으로 고치지 말고, 원본 요청의 `updated_at`과 폴링 상태를 먼저 확인한다.
