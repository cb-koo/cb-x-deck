# 콘텐츠 생성 — 신뢰 회복 + 상태 축 설계

날짜: 2026-08-06
상태: 설계 확정 (사용자 승인 대기)
선행 스펙: `2026-08-03-content-generator-design.md` (콘텐츠 생성 v1)

## 0. 배경과 목적

콘텐츠 생성 기능은 배포·QA를 마쳤고, 실사용 관점에서 두 가지 구조적 문제가 확인됐다.

1. **도구를 믿을 수 없는 순간이 있다.** 편집 모달·레퍼런스 시트가 실수 한 번(배경 클릭·Esc)으로 작업물을 버리고, 생성 취소 후엔 사용자가 직접 새로고침해야 하며, 비용·글자수 표기가 실제와 어긋난다. 신뢰가 깨지면 팀은 도구 밖(메모장·슬랙)으로 도망간다.
2. **생성 이후가 보이지 않는다.** 실제 프로세스는 `초안 생성 → 담당자(일본인 팀원) 검수 → 사용 여부 결정 → 그대로/수정 사용 → 인플루언서 전달`인데, 이 퍼널이 시스템에 없다. 초안은 최신순 피드에 쌓이기만 한다.

단, 프로세스 자체가 아직 유동적이다(검수 생략 가능, 담당자가 직접 생성해 사용하는 경로도 가능). 따라서 관리 인프라를 완성형으로 짓지 않고, **상태라는 축을 최소 형태로 심어 실사용으로 검증한 뒤 확장**한다.

### 리서치 근거 (요약)

- X 컴포저 도구(Typefully·Buffer·Hypefury 등)와 에이전시 협업 도구(Planable·Kontentino 등) 조사 결과: 네이티브 실측 피드는 **검토 표면**으로는 업계 표준(Planable의 기본 뷰가 피드)이나, **관리**는 예외 없이 상태 칩 + 필터/탭/칸반으로 푼다. 생산과 관리를 한 화면이 겸하는 도구는 없다.
- 우리 서비스는 예약 발행이 없어(인플루언서 전달이 종착) 캘린더/큐 축은 해당 없음. X 실측 카드는 제품 가치이므로 유지.

## 1. 범위

### 1단 — 신뢰 회복 (스키마 변경 없음)

| # | 항목 | 내용 |
|---|---|---|
| 1-1 | 편집 모달 유실 방지 | 수정된 상태에서 Esc·배경 클릭·✕ 시 확인 후 닫기 |
| 1-2 | 레퍼런스 시트 유실 방지 | 선택 변경 상태에서 Esc·배경 클릭 시 확인 후 닫기 |
| 1-3 | 취소 후 자동 반영 | 생성 취소 후 폴링으로 완성본 자동 표시 — "새로고침" 문구 제거 |
| 1-4 | 비용 표기 정정 | 버튼의 "약 $0.1 이하"(옵퍼스 시절) 정리 |
| 1-5 | 모델명 노출 제거 | 카드 풋터의 `claude-sonnet-5` 문자열 제거 (DB엔 유지) |
| 1-6 | 글자수 단위 통일 | "단문 (~140자)" ↔ 카운터 "N / 280" 단위 불일치 해소 |
| 1-7 | 클라이언트 미선택 안내 | 클라이언트 없이 생성할 때 막지 않고 알려주기 |
| 1-8 | 레퍼런스 모두 빼기 | 연결된 레퍼런스를 한 번에 비우는 링크 |

### 2단 — 상태 축 (이번 작업의 몸통, 최소 형태)

| # | 항목 | 내용 |
|---|---|---|
| 2-1 | `draft.status` 컬럼 | 마이그레이션 016 |
| 2-2 | 상태 칩 + 변경 UI | DraftCard 도구층(회색 밴드)에 표시·즉시 변경 |
| 2-3 | 상태 탭 + 클라이언트 필터 | `/generate` 피드 위에 — 별도 페이지를 만들지 않는다 |

### 범위 밖 (백로그 — 트리거 조건과 함께 기록)

- **3단: 전용 관리 표면 `/drafts`** (표 뷰 + 검색) — 트리거: ① 필터로도 스캔이 힘든 규모(수백 건) 도달 또는 ② 상태 모델이 실사용에서 안정. 2단의 부품(상태 모델·필터·탭)이 그대로 이사 간다.
- 버전별 피드백 라벨 — 트리거: 버전을 3개 이상 오가는 사용 패턴 관찰
- 같은 조건 다중 시안 생성 — 트리거: 같은 조건 재생성 반복 패턴 관찰
- 레퍼런스 시트 검색·정렬 — 트리거: 보관함 수백 건 도달
- 일본인 담당자용 UI 언어 — 트리거: 담당자가 직접 도구 사용 시작
- 편집 되돌리기 — 기존 백로그 (updateDraft coalesce 제약, 별도 작업)

## 2. 상태 모델 (2단의 핵심 결정)

### 상태 집합

| 키 (DB) | 라벨 (UI) | 의미 |
|---|---|---|
| `draft` | 초안 | 만들어졌고 아직 아무 결정 없음 (생성 시 기본값) |
| `review` | 검수 대기 | 담당자 확인 차례 |
| `approved` | 사용 확정 | 쓰기로 결정 (그대로든 수정해서든) |
| `delivered` | 전달됨 | 인플루언서에게 전달 완료 |
| `unused` | 미사용 | 안 쓰기로 결정 — 삭제와 달리 기록이 남음 |

### 설계 원칙

- **전이 제약 없음.** 어느 상태에서 어느 상태로든 바로 변경한다. 검수 생략(`draft→approved`), 담당자 직접 사용(`draft→delivered`) 등 실재하는 모든 경로를 수용. 워크플로 엔진이 아니라 자유 라벨.
- **상태는 "결정 진행도" 축이다.** '수정해서 사용'을 별도 상태로 두지 않는다 — 수정 여부는 기존 '편집됨' 표시가 담당(축 분리, 라벨-값 일치 원칙).
- **상태 변경 이력은 v1에서 기록하지 않는다.** `status` 단일 컬럼. 감사 로그가 필요해지면 그때 추가.

### DB / API

- 마이그레이션 `016_draft_status.sql`:
  `ALTER TABLE draft ADD COLUMN status text NOT NULL DEFAULT 'draft' CHECK (status IN ('draft','review','approved','delivered','unused'));`
  기존 행은 DEFAULT로 전부 `draft`.
- `draftStore`: `DraftRow.status` 추가, `updateDraft`가 `status` 패치 수용.
- `PATCH /api/drafts/[id]`: `status` 허용 — enum 검증, 불일치 시 400.
- `GET /api/drafts`: `?status=` 파라미터 추가(`?clientId=`는 기존). 단, 이번 UI는 클라이언트 사이드 필터를 쓰므로 서버 파라미터는 3단 대비 정합성용.

## 3. UI 설계

### 3-1. `/generate` — 상태 탭 + 클라이언트 필터 (2-3)

- 컴포저와 초안 목록 사이에 필터 행 추가:
  - **상태 탭**: `전체 N · 초안 N · 검수 대기 N · 사용 확정 N · 전달됨 N · 미사용 N` — 건수 표시, 클라이언트 사이드 필터링(현재 목록 로드 기준, limit 50). 기본 `전체`.
  - **클라이언트 필터**: 셀렉트(전체 클라이언트 / 각 클라이언트 / 클라이언트 없음). 상태 탭과 AND 조합.
- 필터 행은 초안이 1건 이상일 때만 노출(빈 상태에서 도구부터 보이지 않게).
- 필터 상태는 저장하지 않는다(새로고침 시 전체) — 작업 세션용 렌즈이지 영구 설정이 아님.
- 검수 담당자의 일감함 = "검수 대기" 탭.

### 3-2. DraftCard — 상태 칩 (2-2)

- 위치: **도구층(회색 밴드)** 최상단 행. X 콘텐츠층(흰색)은 건드리지 않는다(미러링 원칙).
- 형태: 현재 상태를 칩으로 표시 + 클릭 시 5개 상태 드롭다운, 선택 즉시 `PATCH` 저장(낙관적 갱신, 실패 시 롤백+토스트).
- 색: 초안=중립 회색 · 검수 대기=앰버 · 사용 확정=파랑 · 전달됨=초록 · 미사용=회색 취소선 없이 저채도. 도구층 톤에 맞춰 은은하게.
- 새 초안 생성 직후 카드에도 `초안` 칩이 바로 보인다 — "상태를 바꿔가며 관리한다"는 어포던스.

### 3-3. 편집 모달 유실 방지 (1-1)

- dirty 판정: `texts`가 열 때의 `base.posts` 텍스트와 하나라도 다르면 dirty.
- dirty 상태에서 Esc·배경 클릭·✕ → `window.confirm('저장하지 않은 수정이 있어요. 닫을까요?')`. 확인 시 닫기, 취소 시 유지.
- dirty 아니면 기존대로 즉시 닫힘. IME 조합 중 Esc 무시(기존 동작 유지).
- 편집 모달은 ✕도 확인 대상이다 — 이 모달엔 별도 '취소' 버튼이 없어 ✕가 유일한 출구라, "버리겠다"는 명시적 의사와 구분되지 않기 때문(레퍼런스 시트와 기준이 다른 이유는 3-4 참고).

### 3-4. 레퍼런스 시트 유실 방지 (1-2)

- dirty 판정: `sel`이 열 때의 `selectedIds`와 집합으로 다르면 dirty.
- dirty 상태에서 Esc·배경 클릭 → `window.confirm('선택을 적용하지 않았어요. 닫을까요?')`.
- **'취소' 버튼과 ✕는 명시적 의사이므로 확인 없이 닫는다** (버리기가 의도인 동선). 기준은 "우발(배경·Esc) vs 명시(버튼)" — 시트엔 '적용'과 '취소'가 나란히 있어 ✕/취소가 명시적 버리기로 읽힌다.

### 3-5. 취소 후 자동 반영 (1-3)

- 취소 시점의 최신 초안 id를 기억하고, 5초 간격 폴링(`GET /api/drafts`, 최대 2분)으로 새 초안이 나타나면 목록에 끼워 넣고 토스트 "아까 취소한 원고가 완성됐어요".
- 폴링 중단 조건: 발견 성공 · 2분 경과 · 새 생성 시작 · 페이지 이탈.
- 취소 토스트 문구 변경: "기다리기를 취소했어요 — 완성되면 목록에 자동으로 나타나요".
- 생성 자체를 중단하는 게 아니라는 점은 스켈레톤 안내문 유지.

### 3-6. 표기 정리 (1-4·1-5·1-6)

- 생성 버튼: `원고 만들기 (약 $0.1 이하)` → **`원고 만들기`**. 비용은 버튼 밖 캡션으로 이동: "생성 1회 ≈ $0.02" (CONTENT_MODEL=sonnet 기준 실측 ≈$0.015의 보수적 반올림). 비용 유발 액션 고지(원칙 6)는 유지하되 버튼 라벨은 행동만.
- 카드 풋터의 모델명(`· claude-sonnet-5`) 제거. DB `draft.model`은 유지(원가 추적용).
- 형식 라벨: `단문 (~140자)` → **`단문 (트윗 1개, X 기준 280 이내)`**, `스레드 (3~5개)` → `스레드 (트윗 3~5개)`. 카운터 "X 기준 N / 280"과 같은 단위 체계.

### 3-7. 클라이언트 미선택 안내 (1-7)

- 조건: 등록된 클라이언트가 1개 이상 있는데 `clientId`가 비어 있고, 생성은 가능한 상태(`canGenerate`).
- 생성 버튼 근처 캡션: "클라이언트 정보 없이 만들어요 — 요약줄 '바꾸기'에서 선택할 수 있어요". 막지 않는다(의도적 미선택도 정상 경로).

### 3-8. 레퍼런스 모두 빼기 (1-8)

- 컴포저 레퍼런스 밴드에서 연결 2건 이상일 때 "모두 빼기" 링크. 클릭 시 `refRows` 비움(확인 없음 — 시트에서 다시 고르면 되는 가역 동작).

## 4. 에러 처리

- 상태 변경 PATCH 실패: 낙관적 갱신 롤백 + 토스트(기존 `patchDraft` 패턴 재사용).
- 폴링 요청 실패: 조용히 다음 주기 재시도(취소 후 폴링은 부가 기능 — 실패가 사용자 흐름을 막지 않게).
- 마이그레이션 전 코드/후 코드 호환: `status` 없는 행은 존재하지 않음(NOT NULL DEFAULT). 구버전 클라이언트가 보낸 PATCH에 status가 없으면 기존 값 유지(coalesce).

## 5. 테스트

- `draftStore`: status 저장·패치·기본값 라운드트립, 잘못된 enum 거부(DB CHECK).
- API: `PATCH` status enum 검증(불일치 400), `GET ?status=` 필터.
- 순수 헬퍼: 편집 모달 dirty 판정, 시트 선택 dirty 판정(집합 비교), 상태 필터·건수 계산 — 컴포넌트 하네스가 없으므로 판정 로직을 순수 함수로 추출해 tsx 단일 파일 테스트.
- 수동 확인(OAuth 게이팅으로 사용자만 가능): 상태 칩 변경·탭 필터·취소 후 자동 반영·모달 확인 동작.

## 6. 배포 순서

1단(신뢰 회복)은 스키마 무관이므로 먼저 배포 가능. 2단은 마이그레이션 016 적용 후 배포. 한 브랜치에서 커밋을 나눠 진행하되, 필요시 1단만 먼저 내보낼 수 있는 순서로 커밋한다.
