# 마이그레이션을 빌드 단계에서 돌리려 합니다 — 배경과 제안 (2026-09-22)

9/21 정산 장애의 후속입니다. 결정 문서는 `docs/adr/0007-migration-before-deploy-ordering.md`(status: proposed), 구현은 브랜치 `cb-koo/migrate-on-build`에 있습니다(main 미머지). 규칙은 `AGENTS.md` "마이그레이션과 배포 순서" 절에 적었습니다.

---

## 1. 무슨 일이 있었나

9/21 14:17에 `c00065a`(정산 수취 정보 정정)가 main에 들어가면서 곧바로 배포됐는데, 그 기능이 쓰는 마이그레이션 `056`이 운영 DB에 없는 상태였습니다. 그래서 `payment_request`에서 행을 반환하는 조회(`R_SELECT`)가 전부 실패했습니다 — `42703 column "payment_method_correction" does not exist`. 16시경 056을 적용해 복구했습니다.

**외부 영향은 없었지만 운이 좋았습니다.** 그날 정산 폴링은 200이 136건, 5xx가 0건입니다. `listForExport`가 커서 페이지가 비면 `exportRows`(→`R_SELECT`)를 건너뛰는데, 마지막 `payment_request` 변경이 14:07 — 배포 10분 전이라 그쪽 커서가 이미 따라잡은 상태였습니다. 요청이 한 건이라도 바뀌었으면 즉시 500이었습니다. 정산 요청 목록 화면(`listRequests`)은 그런 우회로가 없어 열었다면 실패했겠지만, 그 시간대 열람 기록은 없습니다.

## 2. 왜 막을 수 없었나

문서에는 순서가 정확히 적혀 있었습니다. 진행 현황 문서 4번 항목이 "운영 DB 적용은 **반드시** 배포보다 먼저"이고, 후속 단계도 8개로 정리돼 있었습니다. 그런데 두 가지가 겹쳤습니다.

**하나, 9/21에 GitHub↔Vercel 연동을 켰습니다.** 그때부터 main 머지가 곧 운영 배포입니다. 머지와 배포 사이에 사람이 끼어들 시간이 0초입니다. 그 전까지는 `vercel --prod`를 사람이 눌렀으므로 그 자리가 관문 역할을 했습니다.

**둘, 머지할 수 있는 사람이 DB 작업을 할 수 없습니다.** GitHub는 write 권한이 있어 머지(=배포)가 되는데, DB 접속 정보는 연습용조차 없습니다. `c00065a` 커밋 메시지에 "로컬에 `.env.staging`이 없어 미실행"이라고 적혀 있는 게 그 얘기입니다.

즉 **먼저 해야 하는 일의 권한은 없고 나중 일의 권한만 있는 구조**입니다. "문서에 적어두면 지켜진다"는 이미 실패가 증명됐습니다. 그리고 자동 배포를 끄는 것은 답이 아닙니다 — Vercel 권한이 없는 사람도 자기 작업을 배포할 수 있게 하려고 켠 것이기 때문입니다.

## 3. 제안 — 빌드 첫 단계에서 마이그레이션

Vercel은 빌드를 끝낸 뒤에야 트래픽을 새 배포로 옮깁니다. 빌드 중에는 이전 배포가 계속 서비스합니다. 그래서 **빌드에서 칸을 만들면 그 칸을 읽는 코드가 살아나기 전에 칸이 항상 존재**합니다. 순서가 사람의 기억이 아니라 구조로 보장됩니다. 마이그레이션이 실패하면 빌드가 실패해 **배포 자체가 일어나지 않습니다**(fail closed).

구현은 `scripts/migrate-on-build.mjs`이고 `build` 명령의 첫 단계로 넣었습니다. 설계에서 신경 쓴 지점은 다음과 같습니다.

- **`VERCEL_ENV=production`일 때만 실행.** 프리뷰·로컬 빌드가 운영 DB를 건드리는 것이 이 방식의 최대 위험이라 첫 관문에 뒀습니다.
- **접속 정보가 없으면 종료코드 1로 빌드 중단.** 조용히 넘기면 9/21과 같은 상태가 됩니다. Vercel 환경변수를 `sensitive`로 등록하면 빌드에서 읽히지 않는데, 그 실수도 여기서 드러납니다.
- **`psql`을 쓰지 않음.** 빌드 이미지에 있는지 확인되지 않아, 이미 의존성인 `postgres` 패키지로 짰습니다. 확인해야 할 불확실성 하나가 사라집니다.
- **전 파일을 한 트랜잭션에.** 하나라도 실패하면 아무것도 적용되지 않습니다.
- **잠금은 `pg_advisory_xact_lock`.** `PGPORT` 6543은 트랜잭션 모드 풀러라서 세션 단위 잠금이 커넥션 멀티플렉싱 때문에 신뢰할 수 없습니다.
- **멱등 문장의 NOTICE는 건수만 집계.** 57개 파일이면 수백 줄이 되어 정작 중요한 실패 메시지가 묻힙니다.

## 4. 검증 결과

스테이징 Vercel 프로젝트(`cb-x-deck-staging`)에 실제로 배포해 클라우드 빌드 로그로 확인했습니다.

```
> node scripts/migrate-on-build.mjs && next build
[migrate] 대상 postgres (…:6543) · 파일 57개
[migrate] 완료 — 57개 파일, 15.9초, 이미 적용돼 건너뛴 문장 146건
✓ Compiled successfully in 21.1s
Build Completed
```

이 방식의 유일한 미확인 지점이 "빌드 컨테이너에서 DB에 붙을 수 있는가"였는데 해결됐습니다. `PG*` 5개가 운영·스테이징 양쪽 모두 `encrypted`로 등록돼 있습니다 — Vercel의 `sensitive`는 런타임 전용이라 그것이면 불가능했습니다.

함께 확인한 것: 로컬 빌드는 건너뜀 · 접속 정보를 비우면 종료코드 1로 중단 · 실행 후 스테이징 스키마 무결(테이블 39, 정산 요청 43, 작업 55).

## 5. 같이 정해야 할 규칙 — 마이그레이션은 추가만

이 방식은 전제가 하나 있습니다. 빌드 중에는 **새 DB + 옛 코드**가 공존하고(이전 배포가 계속 트래픽을 받습니다), 롤백하면 다시 그 조합이 됩니다. 그래서 마이그레이션은 옛 코드와 공존해도 안전해야 합니다.

여기서 방향이 갈립니다. **칸 추가는 DB가 먼저**여야 하고(옛 코드는 새 칸을 모르니 무해), **칸 삭제는 코드가 먼저**여야 합니다(옛 코드가 없는 칸을 읽으면 500). 빌드는 항상 DB를 먼저 적용하므로 **추가는 자동으로 맞고 삭제는 자동으로 틀립니다.**

그래서 깨는 변경은 머지를 나눕니다.

| 하는 일 | 머지 | 방법 |
|---|---|---|
| 칸 추가 | 1번 | 그대로 |
| 칸 삭제 | 2번 | ① 코드에서 그 칸을 읽지도 쓰지도 않게(마이그레이션 없음) → ② `drop column` |
| 칸 이름 변경 | 3번 | ① 새 칸 추가 + 양쪽에 쓰고 옛 칸을 읽음 + 백필 → ② 새 칸만 읽고 씀 → ③ 옛 칸 `drop` |
| 타입 변경 | 3번 | 이름 변경과 동일(새 타입의 새 칸을 만들어 옮김). `alter column type` 직접 금지 |
| 제약 추가 | 1번 | `not valid`를 붙임. 단 옛 코드가 넣던 값을 거부하는 제약이면 삭제와 같은 취급(2번) |

`rename column`을 한 번에 돌리면 옛 이름이 사라지는 순간 아직 트래픽을 받고 있는 옛 코드가 전부 500이 납니다. 9/21 장애와 같은 모양이고 방향만 반대입니다.

**이 규칙은 새로 만드는 것이 아닙니다.** `039_campaign_task_cutover.sql` 주석에 이미 적혀 있습니다 — *"새 코드는 이 컬럼들을 읽지 않으므로 늦게 적용해도 무해하고, 일찍 적용하면 옛 코드가 500이 난다."* 그걸 `AGENTS.md`에 명문화한 것입니다.

## 6. 권한

연습용(스테이징) DB 접속 정보와 Vercel 읽기 권한이 필요합니다. 전자가 없어 작성한 DB 테스트를 한 번도 실행하지 못했고, 그 안에 있던 결함 2건이 9/21에 늦게 발견됐습니다. 후자는 이 변경 뒤에 더 필요해집니다 — 마이그레이션 실패가 빌드 실패로 나타나는데 지금은 빌드 로그를 볼 수 없습니다.

**운영 DB 쓰기 권한은 이 방식에서는 불필요합니다.** 빌드가 대신하기 때문입니다. 이 프로젝트는 운영 DB 사고가 두 번 있었으므로(9/1 지급완료 유실, 9/9 테스트 픽스처 유출) 접근 가능한 사람을 늘리지 않는 편이 낫습니다.

**PR 필수화(브랜치 보호)는 이 건과 분리했습니다.** `main`에 보호가 없어 직접 푸시가 되는 것은 사실이지만(9/21 `c00065a`가 그렇게 들어왔습니다), 이 방식을 넣으면 순서 문제 해결에는 필요 없습니다. 코드 리뷰 관점의 논의로 따로 다루는 게 좋겠습니다.
