# 정산 요청 사전 차단 — 그쪽이 받지 않는 요청은 만들지 않는다

브랜치: `cb-koo/payment-api`. 선행: `2026-08-28-settlement-page-design.md`(§3-7 신호등), `2026-09-01-proof-to-partner-design.md`(증빙 전달).
결정: koo 2026-09-02.

## 1. 문제

정산 프로덕트는 지급 전 확인 자료가 없는 요청을 받지 않는다(보류로 돌려보냄, 명세 §5 `proof`). 우리 검토 대기는 그 두 항목을 🟡 경고로만 두고 요청을 만들어 보냈다 → 나갔다가 되돌아오는 왕복이 생긴다.

## 2. 결정

| 항목 | 전 | 후 | 근거 |
|---|---|---|---|
| RT 증빙 스크린샷 없음 | 🟡 | 🔴 | 그쪽 확인 자료. 명세에 "on_hold로 돌려보내 달라"고 우리가 적음 |
| 참고 링크 없음 — 투고·인용RT·방문 | 🟡 | 🔴 | 그쪽 확인 자료(인플루언서 본인 게시물) |
| 참고 링크 없음 — RT | 🟡 | 🟡 유지 | RT의 링크는 클리닉 원본 트윗이라 확인 자료가 아님. 슬랙 RT 405건 중 350건이 링크 없이 갔음(스펙 3-6) |
| PayPay 수취 정보 미입력 | 🟡 | 🟡 유지 | 그쪽이 거절한 사례 없음. 정책 정해지면 재검토(koo) |
| 게시 내려짐 | 🟡 | 🟡 유지 | 우리 내부 주의 |
| 결제 수단 없음 | 🔴 | 🔴 | 이미 그대로 — 계좌·PayPal·PayPay 중 하나면 통과 |

이미 만들어진 요청은 소급하지 않는다. 그쪽 API 계약은 바뀌지 않는다(명세 `proof` 행에 "09-02부터 새 요청에는 rt+proof null이 없다"만 덧붙임).

## 3. 판정은 한 곳

`settlementCalc.assessReadiness`가 수준을 정하고, `effectiveIssues(candidate, edit)`가 사람이 채운 분류·참고 링크를 얹는다. 화면(`CandidateRow`)과 서버(`settlementStore.createRequests`)가 이 함수 하나를 부른다 — 한쪽만 바뀌어 어긋나는 결함(09-02 차액 판정에서 겪음)을 구조로 막는다.

- `effectiveIssues`의 `edit`에 `referenceUrl` 키가 있으면 서버의 no-reference를 버리고 그 값으로 다시 판정한다. 키가 없으면(옛 호출) 서버 판정 유지.
- 서버는 `effectiveIssues(cand, { category: item.category, referenceUrl: item.referenceUrl })`의 🔴를 전부 모아 그 문구를 실패 사유로 돌려준다(전체 거절 규칙 §5-2 유지).

## 4. 화면

- 검토 대기 행: 🔴면 체크 불가·맨 아래 정렬(기존). 참고 칸 안내문이 유형에 따라 "인플루언서 게시물 링크(필수)" / "게시물 링크(선택)". 필수인데 비면 빨간 테두리(분류 칸과 같은 표현).
- 링크를 넣으면 즉시 풀려 체크 가능, 지우면 다시 🔴 + 체크 자동 해제(분류 칸의 기존 동작과 동일).
- 증빙 없음 문구: "증빙 스크린샷을 넣어야 요청할 수 있어요 — 정산 쪽이 지급 전에 확인해요 · 캠페인에서 채우기 →".
- 만들기 성공 시 요청 내역 탭으로 이동(원 스펙 QA 항목 "만들기 → 내역 이동"이 구현에서 빠져 있었음, koo 확정).

## 5. 검증

- 순수(`settlementCalc.test.ts`): 유형별 🔴/🟡, `referenceRequiredFor`, 링크 입력→해제/삭제→차단, RT 링크 없음은 🟡.
- 실 DB(`settlementStore.test.ts`): 증빙 없는 RT 거절→증빙 채우면 통과 / 투고 링크 없음 거절→아이템에 링크 넣으면 통과. 요청 생성이 목적인 RT 픽스처에는 `postedRtWithProof`로 증빙을 채움(`campaignStore.test.ts`·`seed-staging.ts`도 동일).
- 화면: koo 스테이징 확인 — 증빙 없는 RT 🔴, 링크 없는 투고 🔴→링크 입력→체크→만들기→요청 내역 이동.
