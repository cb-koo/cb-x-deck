# 전체 캠페인 모니터링 페이지 — 시작 인계 (2026-11-12)

koo와 의도 확인까지 마쳤다. 구현은 시작하지 않았고, 기획 논의(브레인스토밍)부터 이어간다.

## 1. 문제

X 캠페인과 작업은 **개별 캠페인 단위**로는 진행 상황과 성과를 볼 수 있다. 그러나 **전체 캠페인이 잘 진행되고 있는지** 볼 방법이 없다. 캠페인을 하나씩 열어 머릿속으로 합쳐야 한다. 캠페인 목록 패널의 진행바는 작업이 몇 건 끝났는지만 알려줘서 부족하다(koo: "진행바를 확인하는 것만으로는 부족해").

## 2. 목적 (koo 확인: "맞음")

**한 주 동안 전체 캠페인이 잘 진행되고 있는지, 진행된 캠페인의 성과가 어떻게 나오고 있는지를 전체 팀원이 이해할 수 있는 모니터링 페이지.**

- 한 화면에서 전체 캠페인을 주 단위로 본다.
- 답해야 하는 질문 둘: ① 계획대로 진행되고 있나, 어디가 막혀 있나 ② 게시된 것들의 성과가 어떻게 나오고 있나.
- 보는 사람은 koo만이 아니라 **팀원 전체**. 캠페인을 직접 담당하지 않는 사람도 "잘 되고 있다 / 여기가 문제다"를 바로 읽을 수 있어야 한다. 숫자 나열 금지, 판단까지 서술(AGENTS.md UX 원칙 3).
- 일을 처리하는 화면이 아니라 **상황을 파악하는 화면**. 문제를 발견하면 해당 캠페인으로 넘어가 처리한다.

## 3. koo가 답한 기준

1. **"잘 진행되고 있다"의 기준**
   - 1차: **계획된 작업이 완료됐는지**
   - 2차: **성과가 잘 나오고 있는지**
2. **성과 기준**
   - 기본은 **조회수**.
   - CPV도 중요하지만, 작업 1건당 지출 비용이 어느 정도 범위로 정해져 있어서 **조회수 중심으로 보고 CPV를 함께 확인**하는 정도.
   - 다른 지표들도 함께 확인할 수 있으면 좋다.
   - **성과 흐름을 시각적으로 확인할 차트**가 있으면 좋겠다.
3. **이전 '클라이언트 현황(/status)'과의 관계:** 그것과 **별개로 진행**한다. (/status는 클라이언트별 주간·월간 판정 페이지로 스테이징까지만 갔고 11-10에 `archive/chart-kit` 태그로 보관됨. 되살리거나 이어 붙이지 않는다. 참고만 가능.)
4. **언제 보나:** **주기적으로** 캠페인이 어떻게 진행되고 있는지 확인하기 위한 용도.

## 4. 아직 열려 있는 질문 (브레인스토밍에서 koo에게 확인)

- "계획된 작업 완료"의 정확한 뜻: 게시 확인까지인가, 정산까지인가? 진행 안 됨(취소) 작업은 어떻게 세나?
- "막힌 곳"으로 드러내야 하는 상태: 게시 예정일이 지났는데 미게시, 섭외 미완, '안 보임' 게시물, 성과 미측정 등 중 팀이 실제로 챙기는 것.
- 주의 기준: 캠페인 주차 규칙(월~일 주를 월 경계에서 잘라 그 달 N주차)을 따르나, 달력 주인가? 지난 주들과 비교가 필요한가?
- 장기 캠페인(주차 캠페인이 아닌 것)을 주간 화면에서 어떻게 다루나?
- 성과가 "잘 나온다"를 판정해 줄지(지난 주, 평소 대비), 숫자와 흐름만 보여줄지. 판정한다면 기준선.
- 묶는 단위: 캠페인별, 클라이언트별, 인플루언서별 중 무엇이 기본 보기인가.
- 차트로 보고 싶은 흐름: 주 안에서 날짜별 누적 조회수인지, 주차별 추이인지, 게시물별 성장 곡선인지.
- 사이드바 위치와 이름.

## 5. 참고할 기존 자산 (main bcdbe62 기준)

- **캠페인 v2 화면:** `src/app/campaigns/flow` — 목록(장기/주차/지난, 색 점, 진행 막대), 상세 상단(예산 두 잔액, 2×2 카드, 성과 ↻와 최종 업데이트).
- **데이터:** `campaign`, `campaign_task`(유형 post/quoteRt/rt/visit/other, 게시일, 취소, 비용), `tracked_post` + `post_metric_snapshot`(views, likes, retweets, replies, bookmarks, quotes), `post_metric_estimate`(빈 날 조회수 추정, '추정' 칩으로 실측과 분리).
- **성과 자동 측정:** 게시 시각 기준 15분~14일 체크포인트, pg_cron 5분. '안 보임' 감지(`unseenSince`).
- **기존 성과 화면:** `/performance`(콘텐츠 성과), `/influencers/performance`(인플루언서 성과 비교, 참여율 = 공개 반응 5종 ÷ 조회), `/tracking`.
- **차트 부품:** `src/components/charts/`(LineChart, ColumnChart, DayBarsChart, GrowthCurves, TimeCompareChart, Sparkline, SegmentedBar, BulletList, ChartCard 등)와 샘플 페이지 `/debug/charts`. 새 라이브러리 도입 없이 이것을 쓴다.
- **주차 규칙:** 메모리 `cb-x-deck-campaign-week-rule` — 월~일 주를 월 경계에서 잘라 그 달 N주차(3~7일).
- **koo의 관점:** X 성과(조회, 반응, CPV)는 핵심 지표다. 예측력이 약해도 빼지 않는다.

## 6. 다른 작업과의 관계

- **인스타그램 캠페인**(워크트리 `instagram-campaign`, 기획 중): X와 분리해서 만들되 캠페인은 같은 저장소에 플랫폼 표시를 붙이는 방향. 이 모니터링 페이지는 **지금은 X 캠페인만** 대상으로 하되, 나중에 인스타 캠페인이 같은 화면에 들어올 수 있게 플랫폼별로 집계가 갈릴 수 있는 구조를 염두에 둔다(지금 구현할 필요는 없음).
- **마이그레이션:** main 최고 번호는 090. 인스타 작업이 091부터 쓸 예정이다. 이 작업은 읽기 중심이라 마이그레이션이 없을 가능성이 높다. 필요해지면 번호를 정하기 전에 koo(조율 세션)에게 확인한다.
- **배포:** main push는 운영 자동 배포다. koo 지시 없이 push하지 않는다. 다른 브랜치와 동시에 push하지 않는다.

## 7. 진행 방식

superpowers로 진행한다. 순서: 브레인스토밍 → 설계 문서(`docs/superpowers/specs/`) → **화면 시안을 구현 전에 koo 확인** → 구현 계획(`docs/superpowers/plans/`) → 구현·검증 → 스테이징에서 koo QA → 머지 직전 `src/content/updates.ts` 추가.

- 이 워크트리에는 `.env`가 없다. 구현 단계에서 `vercel link` 후 `vercel env pull .env --environment=production`으로 받는다(`.vercel/project.json`이 맞는 프로젝트인지 확인).
- 테스트는 연습용 DB에서만.
- 화면 관련 koo 선호: 빽빽한 화면 거절(글자 14~15px, 행 44px 이상, 여백 넉넉, 한 행 정보 6개 이하), 표의 행은 한 줄, 라벨은 짧은 명사형, 가운뎃점 구분자 남발 금지, 비개발자 기준의 쉬운 말.
