# 새 DB 칸을 읽는 코드가 마이그레이션보다 먼저 배포되지 않게 한다

2026-09-21에 정산 기능이 약 2시간(14:17~16시경) 깨져 있었다. 원인은 사람의 실수가 아니라 **순서를 지킬 수 없게 된 구조**다. 이 ADR은 문제와 선택지를 기록한다 — **아직 결정하지 않았다.**

## 무슨 일이 있었나

`c00065a`(정산 수취 정보 정정)는 새 칸 `payment_request.payment_method_correction`을 읽는 코드와 그 칸을 만드는 `056`을 함께 담고 있었다. 작업자는 진행 현황 문서에 **"운영 DB 적용은 반드시 배포보다 먼저"** 라고 굵게 적어 뒀다. 그런데 같은 날 GitHub↔Vercel 연동을 켠 뒤라, main에 머지되는 **순간** Vercel이 자동 배포했다. 사람이 4번(DB 적용)을 끼워 넣을 자리가 없었다.

그 사이 `payment_request`에서 행을 반환하는 조회(`R_SELECT`)는 전부 `42703 column "payment_method_correction" does not exist`로 실패하는 상태였다.

**외부 영향이 없었던 것은 운이었다.** `external_api_log` 기준 그날 `/api/external/settlement/*`는 200이 136건, 5xx가 0건이었다. `listForExport`가 커서 페이지가 비면 `exportRows`(→`R_SELECT`)를 건너뛰는데, 마지막 `payment_request` 변경이 **14:07 — 배포 10분 전**이라 그쪽 커서가 이미 따라잡은 상태였기 때문이다. **요청이 한 건이라도 바뀌었으면 곧바로 500이 났다.** 정산 요청 목록 화면(`listRequests`)은 그런 우회로가 없어 열었다면 실패했다(그 시간대 열람 기록은 없다).

## 왜 재발하는가

- 자동 배포를 켜기 전에는 `vercel --prod`를 사람이 눌렀으므로 "DB 먼저, 배포 나중"이 지켜질 수 있었다.
- 켠 뒤로는 **머지 = 배포**다. 그 사이에 사람이 할 수 있는 일이 없다.
- 자동 배포를 끄는 것은 답이 아니다 — 태정님처럼 Vercel 접근 권한이 없는 사람도 자기 작업을 배포할 수 있게 된 것이 연동의 이유였다.
- 즉 **다음에 마이그레이션이 필요한 작업이 머지되면 같은 일이 난다.** 그때 데이터가 조용하지 않으면 오늘처럼 넘어가지 못한다.

## Considered Options

### A. 확장–이행–수축 (칸 추가 배포 → 읽기 시작 배포)

한 작업을 두 번 머지한다. ①칸을 만드는 마이그레이션만(아무도 읽지 않음) → 배포 → ②그 칸을 읽는 코드 → 배포.

- 장점: 사람의 기억에 의존하지 않는다. 롤백해도 안전하다(옛 코드는 새 칸을 모를 뿐).
- 단점: 작업이 두 머지로 쪼개진다. 작은 변경에도 왕복 두 번이라 마찰이 크다.

### B. 빌드 단계에서 마이그레이션 실행 (운영 빌드일 때만)

배포 빌드가 트래픽을 받기 **전에** 마이그레이션을 돌린다. `VERCEL_ENV === 'production'`일 때만 실행해 프리뷰 빌드가 운영 DB를 건드리지 않게 한다.

- 장점: 순서가 구조적으로 보장된다. 작업자가 아무것도 기억하지 않아도 된다. 지금처럼 한 번의 머지로 끝난다.
- 단점·열린 질문:
  - 현재 `apply-migrations.sh`는 `psql`을 쓴다. **Vercel 빌드 이미지에 psql이 있는지 확인되지 않았다** — 없으면 node 스크립트로 바꿔야 한다.
  - `PG*` 환경변수가 **빌드 시점에도 읽히는지** 확인 필요(지금은 Production 스코프로만 확인됨).
  - 빌드가 마이그레이션을 적용한 뒤 배포가 실패하면 DB만 앞서간다 — 마이그레이션이 **추가만 하는(backward-compatible)** 한 무해하다. 이 전제를 규칙으로 못박아야 한다.
  - 동시 빌드가 같은 마이그레이션을 겹쳐 돌릴 수 있다 — 전 문장이 멱등(`if not exists`)이라 현재는 안전하지만, 이 역시 전제다.

### C. 머지 전 운영 DB 적용을 체크리스트로 (사람 규율)

PR 본문·머지 절차에 "마이그레이션 있으면 머지 전에 운영 DB 적용" 항목을 둔다.

- 장점: 오늘 당장 할 수 있고 비용이 0이다.
- 단점: **이번에 실패한 방식이 바로 이것이다.** 작업자는 문서에 굵게 적어 뒀는데도 막지 못했다. 게다가 운영 DB 접근 권한이 없는 사람은 지킬 수 없다.

### D. 자동 배포를 끄고 수동 배포로 되돌린다

- 연동을 켠 이유(권한 없는 사람도 배포, PR 프리뷰)를 잃는다. 퇴행이다.

## 추천

**B를 본선, A를 예외 규칙으로.** B가 사람의 기억을 구조로 대체하는 유일한 안이다. C는 B가 준비될 때까지의 임시 방편으로만 쓴다 — 단독으로는 이미 실패한 방식이다.

### B의 전제 — 왜 "추가만"인가

빌드에서 마이그레이션을 돌리면 **새 DB + 옛 코드가 공존하는 구간**이 생긴다. 빌드가 끝나기 전까지 트래픽은 이전 배포가 받고 있고, 롤백하면 다시 같은 조합이 된다. 그래서 **마이그레이션은 옛 코드와 공존해도 안전해야 한다.**

여기서 방향이 갈린다.

| 하는 일 | 필요한 순서 | 이유 |
|---|---|---|
| 칸 **추가** | **DB 먼저** → 코드 나중 | 옛 코드는 새 칸을 모른다. 있어도 무해 |
| 칸 **삭제** | **코드 먼저** → DB 나중 | 옛 코드가 없는 칸을 읽으면 500 |

빌드 단계 마이그레이션은 **항상 DB를 먼저** 적용한다. 추가는 그래서 자동으로 맞고, **삭제는 자동으로 틀린다.**

### 경우별로 머지 몇 번인가

- **추가만 — 1번.** 실무의 대부분이 여기다(이 저장소 57개 중 칸을 지운 건 `039` 하나뿐).
- **칸 삭제 — 2번.** ① 코드에서 그 칸을 읽지도 쓰지도 않게 고친다(마이그레이션 없음) → 배포 → ② `drop column` 마이그레이션을 넣는다. **`039`가 정확히 이 방식이고 그 파일 주석에 이유가 적혀 있다** — "새 코드는 이 컬럼들을 읽지 않으므로 늦게 적용해도 무해하고, 일찍 적용하면 옛 코드가 500이 난다."
- **칸 이름 변경 — 3번.** 추가와 삭제가 합쳐진 것이다. ① 새 칸 추가 + 코드가 양쪽에 쓰고 옛 칸을 읽음 + 백필 → ② 코드가 새 칸만 읽고 씀 → ③ 옛 칸 `drop`. **`rename column`을 빌드에서 한 번에 돌리면 그 순간 옛 이름이 사라지는데 아직 옛 코드가 트래픽을 받고 있어 모든 요청이 500이 된다** — 2026-09-21 장애와 같은 모양, 방향만 반대다.
- **타입 변경 — 3번.** 이름 변경과 같은 방식(새 타입의 새 칸을 만들어 옮긴다). `alter column type`을 직접 하면 옛 코드가 새 타입을 다루지 못할 수 있다.
- **제약 추가 — 대체로 1번.** `not valid`를 붙이면 새 행부터만 검사하므로 안전하다(이 저장소 관례: 036·040·048·055). 단 **옛 코드가 넣던 값을 새 제약이 거부한다면** 삭제와 같은 취급(코드 먼저, 2번)으로 한다.

## 검증 결과 (2026-09-21, 스테이징)

**열린 질문 셋이 전부 닫혔다.** B를 채택하는 데 남은 기술적 장애물은 없다.

| 질문 | 결과 |
|---|---|
| 빌드 이미지에 `psql`이 있는지 | **무효화** — `psql`을 쓰지 않는다. 이미 의존성인 `postgres` 패키지로 `scripts/migrate-on-build.mjs`를 짰다 |
| 빌드 시점에 `PG*`로 접속되는지 | **된다** — `PG*` 5개가 운영·스테이징 양쪽 모두 `encrypted`(빌드에서 읽힘). Vercel의 `sensitive`는 런타임 전용이라 그것이면 불가능했다 |
| 동시 빌드 겹침 | **설계로 처리** — 전 파일을 한 트랜잭션에 넣고 `pg_advisory_xact_lock`을 잡는다. `PGPORT` 6543(트랜잭션 모드 풀러)에서는 세션 단위 잠금이 커넥션 멀티플렉싱 때문에 신뢰할 수 없다 |

스테이징 Vercel 프로젝트(`cb-x-deck-staging`)에 실제로 배포해 **클라우드 빌드 로그로 확인**했다.

```
> node scripts/migrate-on-build.mjs && next build
[migrate] 대상 postgres (…:6543) · 파일 57개
[migrate] 완료 — 57개 파일, 15.9초, 이미 적용돼 건너뛴 문장 146건
✓ Compiled successfully in 21.1s
Build Completed
```

함께 확인한 것: 로컬 빌드는 건너뜀(`VERCEL_ENV` 없음) · 접속 정보를 비우면 종료코드 1로 빌드 중단 · 실행 후 스테이징 스키마 무결(테이블 39·정산 요청 43·작업 55).

## Consequences

- ~~결정 전까지의 임시 규칙(머지 전에 운영 DB를 먼저 맞춘다)~~ — 채택으로 불필요해졌다. 빌드가 한다.
- `056`처럼 이미 적용된 마이그레이션은 재실행해도 안전하다(전 문장 멱등) — B로 옮겨도 기존 파일을 손볼 필요는 없다. 매 운영 빌드가 전 파일을 다시 돌리며 약 17초를 쓴다(대부분 멱등 무동작).
- **권한:** B를 채택하면 사람이 운영 마이그레이션을 손으로 돌릴 일이 없어져 **태정님에게 운영 DB 쓰기 권한을 줄 필요가 없다**(이 프로젝트는 운영 DB 사고가 두 번 있었다 — 09-01 지급완료 유실, 09-09 테스트 픽스처 유출). 다만 **연습용 DB 접속 정보와 Vercel 읽기 권한은 별개로 필요하다**: 전자가 없어 본인이 쓴 DB 테스트를 한 번도 돌리지 못했고(그 결함 2건이 09-21에 늦게 발견됐다), 후자가 없으면 이 변경 뒤 **마이그레이션 실패가 빌드 실패로 나타나는데 그 로그를 볼 수 없다.**
- **Vercel 읽기 권한은 줄 수 없다(09-22 확인)** — 무료 플랜이라 팀원 초대가 안 된다. 다만 GitHub 커밋에 Vercel 상태 체크가 붙어 **성공/실패는 보이고 이유(로그)만 못 본다**(체크의 링크가 Vercel 대시보드). 그래서 **연습용 DB 접속 정보가 더 중요해졌다** — 머지 전에 `migrate:staging` + `npm test`로 미리 걸러내면 실패가 운영 빌드까지 가지 않는다. 그래도 빌드가 실패하면 koo가 로그를 옮겨 준다. 반복되면 GitHub Actions로 PR마다 연습용 DB에 적용해보는 검사를 붙이는 안을 검토한다(태정님이 GitHub에서 로그를 직접 볼 수 있다).
- **`sensitive` 함정:** 빌드에서 써야 하는 Vercel 환경변수를 `sensitive`로 등록하면 조용히 읽히지 않는다(현재 `MARKETING_EXPORT_API_KEY`가 `sensitive`인데 런타임 전용이라 무관하다). 스크립트가 접속 정보 부재를 종료코드 1로 알리므로 이 실수는 빌드 실패로 드러난다.
- **PR 필수화(브랜치 보호)는 이 결정과 분리한다.** `main`에 보호가 없어 직접 푸시가 가능한 것은 사실이지만(09-21 `c00065a`가 그렇게 들어왔다), B를 넣으면 순서 문제 해결에는 필요 없다. 코드 리뷰 관점의 논의로 따로 다룬다.
