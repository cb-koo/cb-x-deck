# 초안 이미지 첨부 — X와 같은 첨부·같은 표시 (설계)

2026-08-12.

**배경.** 원고 생성 스펙(`2026-08-03-content-generator-design.md`)은 이미지 첨부를 "다루지 않는 것"에 넣고 확장 지점만 남겼다 — `DraftPost.media: DeckMedia[]`는 항상 빈 배열로 저장되고, `MediaGrid`는 0건이면 `null`을 반환한다. 그 자리를 이제 채운다.

원고는 텍스트만으로 완성되지 않는다. 담당자가 인플루언서에게 넘기는 것은 **문구 + 이미지 한 세트**인데, 지금은 이미지가 도구 밖(메신저·드라이브)에 흩어져 있다. 어느 이미지가 어느 원고의 몇 번째 트윗에 붙는지는 사람 머릿속에만 있다. 스레드에서 특히 위험하다 — 순서가 어긋나면 그대로 잘못 게시된다.

**해결.** 초안에 이미지를 붙이고, X와 동일한 그리드로 보여주고, 담당자가 파일로 받거나 복사해 전달한다.

## 원칙

- **X 미러링은 제품 가치다.** 첨부된 모습이 실제 게시물과 같아야 담당자가 "이대로 나간다"를 판단할 수 있다. 사용자 확인: 전달한 이미지가 그대로 올라가는 경우가 95%이고 나머지도 경미한 수정이다 — 이 카드가 보여주는 것은 예시가 아니라 **확정에 가까운 결과물**이므로 미러링이 곧 정확한 표현이다.
- **이미지는 인증된 사람만 본다.** 버킷을 비공개로 두고 표시할 때마다 서명된 URL을 발급한다.
- **X 레이아웃은 한 벌만 존재한다.** 초안용 그리드를 따로 만들지 않는다. 두 벌이 되는 순간 미러링이 드리프트한다.
- **없는 것을 만들지 않는다.** 데이터 모델·렌더 컴포넌트·저장 컬럼이 이미 있다. 새 컬럼도 새 API 라우트도 만들지 않는다.
- **전달 수단을 정직하게 말한다.** DM 전송은 아직 없다. 지금 이미지가 앱 밖으로 나가는 경로는 다운로드와 복사뿐이고, 화면이 그렇게 말해야 한다.

## 확정 판단

**미디어는 포스트 단위다.** `DraftPost`에 이미 그렇게 잡혀 있고, X도 스레드의 트윗마다 이미지가 따로 붙는다. 초안 단위로 모으면 스레드에서 "몇 번째 트윗 것인지"가 사라진다 — 이 기능이 없애려는 문제 그 자체다.

**첨부는 즉시 저장한다.** 카드에서든 모달에서든 파일을 올린 순간 PATCH가 나간다(낙관적 갱신 + 실패 시 롤백, `assignInfluencer`와 같은 패턴). 모달의 `저장` 버튼에만 매달면 이미지를 붙이고 Esc를 누른 사용자가 업로드는 됐는데 첨부는 사라진 상태를 겪는다. 같은 UI가 두 저장 의미를 갖는 것은 인플루언서 스펙이 §E에서 명시적으로 피한 실패다. **모달의 `dirty` 판정(텍스트 기준)은 그대로 두고 미디어를 넣지 않는다** — 이미 저장된 것을 "저장 안 됨"으로 경고하면 거짓말이 된다.

**파일명은 저장 시점이 아니라 다운로드 시점에 조립한다.** 스토리지 키(불변·내부용)와 사용자가 받는 파일명(가변·사람용)을 분리한다. 이미지를 먼저 붙이고 인플루언서를 나중에 배정하는 실제 흐름이 이 분리로 해결된다 — 배정 후에 내려받으면 그때 핸들이 파일명에 들어가고, 배정이 바뀌어도 파일을 옮길 일이 없다. 규칙을 나중에 바꿔도 조립 함수 하나만 고치면 되고 마이그레이션이 없다.

**스토리지 객체는 지우지 않는다.** 초안에서 이미지를 떼어내도 파일은 남긴다. 버전 이력(`history`)이 과거 버전의 `media`를 그대로 들고 있어서, 파일을 지우면 이전 버전이 깨진다. 고아 파일이 쌓이지만 사용자 2~5명 규모에서 무시할 수 있는 비용이고, 이력의 재현성이 더 비싸다. **그래서 버킷 정책에 `delete`를 주지 않는다** — 쓰지 않을 권한이다.

**시안 간 이미지 공유는 만들지 않는다.** A·B·C에 같은 이미지를 붙이느라 업로드를 3배 하는 시나리오가 지적됐으나, 그 전제가 이 제품과 다르다. 인플루언서 스펙 §확정 판단이 "셋 다 배정하면 사실과 어긋난다 — 실제로는 **그중 하나를 골라** 전달한다"고 정해두었다. 이미지는 고른 시안에만 붙는다.

**규제 검사는 넣지 않는다.** 사용자 확인: 이미지는 담당자가 사전 검수하므로 도구가 개입할 지점이 아니다.

## A. `migrations/024_draft_media_bucket.sql`

버킷을 대시보드가 아니라 마이그레이션으로 만든다 — 이 저장소는 001~023을 SQL로 관리하고, 대시보드 설정은 DB를 다시 세울 때 재현되지 않는다.

```sql
-- 024: 초안 이미지 첨부용 비공개 버킷.
-- 비공개(public=false) — 표시·다운로드 모두 서명 URL로만 접근한다.
-- delete 정책을 주지 않는 이유: 버전 이력이 과거 media를 참조하므로 객체를 지우지 않는다(설계 §확정 판단).
insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values ('draft-media', 'draft-media', false, 5242880,
        array['image/jpeg','image/png','image/gif','image/webp'])
on conflict (id) do nothing;

-- create policy에는 if not exists가 없다 — apply-migrations.sh가 매번 전 파일을 재실행하므로 선drop.
drop policy if exists "draft-media read" on storage.objects;
create policy "draft-media read" on storage.objects
  for select to authenticated using (bucket_id = 'draft-media');

drop policy if exists "draft-media write" on storage.objects;
create policy "draft-media write" on storage.objects
  for insert to authenticated with check (bucket_id = 'draft-media');
```

**멱등성이 필수다.** `scripts/apply-migrations.sh`에는 적용 이력 테이블이 없고 `migrations/*.sql`을 매번 전부 재실행한다. 기존 파일이 모두 `if not exists`인 이유가 이것이다.

**권한 — 확인 완료(2026-08-12).** `storage.objects`는 `supabase_storage_admin` 소유이고 정책 DDL은 소유권을 요구해서, 대시보드 폴백이 필요할 수 있다고 봤다. 실제로 이 프로젝트의 `postgres` 역할에는 `supabase_storage_admin` **멤버십이 없다**(`pg_has_role` 조회 결과 0행). 그런데도 정책 생성은 통과한다 — 직접 부여된 권한이 있다. 롤백 트랜잭션으로 먼저 확인한 뒤 프로덕션에 적용했고, 버킷(`public=f`, 5MB, 이미지 4종)과 정책 2개(authenticated SELECT·INSERT)가 정상 생성됐다. **멤버십 조회만 보고 판단했다면 오진했을 것이다 — 권한은 실행으로만 확인된다.**

**권한을 로그인 여부로만 가르는 이유.** 이 앱의 스키마에는 멤버십 모델이 없다 — 워크스페이스 전체가 콘텐츠를 공유하는 것이 의도된 설계이고, `requireMember()`가 하는 일은 접근 제어가 아니라 신원 해석이다. 로그인 자체가 도메인 게이팅(Google OAuth + 허용 이메일)으로 이미 좁혀져 있다.

## B. 저장 형식 — `DeckMedia` 재사용

`src/lib/types.ts:55`의 `DeckMedia { type, url, videoUrl }`를 그대로 쓴다. 타입 변경 없음.

```ts
{ type: 'photo', url: 'draft/<draftId>/<uuid>.jpg', videoUrl: null }
```

**`url`에 절대 URL이 아니라 스토리지 경로가 들어간다.** 비공개 버킷이라 고정 URL이 존재하지 않는다. 기존에 이 필드에 들어있던 값(X 스크래핑 CDN URL, `https://pbs.twimg.com/...`)과 형태가 다르므로 읽는 쪽에서 **`http`로 시작하면 절대 URL, 아니면 스토리지 경로**로 판별한다. 이 판별 하나로 두 출처가 공존하고 기존 트윗 미디어는 아무것도 바뀌지 않는다.

**필드를 새로 만들지 않은 이유.** `DeckMedia`에 `path`를 추가하면 5개 호출부의 타입이 흔들리고, 마이그레이션 없이 저장된 기존 jsonb와도 어긋난다.

**동영상·GIF 확장.** `type`이 문자열이고 `videoUrl` 자리가 있어서 나중에 동영상을 넣어도 구조는 그대로다. 바뀌는 것은 버킷 MIME 화이트리스트와 업로드 UI의 `accept`뿐이다.

## C. 업로드 — `src/lib/draftMedia.ts` (신규)

```ts
uploadDraftImage(draftId: string, file: File): Promise<DeckMedia>
```

브라우저 Supabase 클라이언트로 `draft-media`에 올리고 `DeckMedia`를 돌려준다. 경로는 `draft/<draftId>/<crypto.randomUUID()>.<확장자>`.

클라이언트에서도 형식·용량을 먼저 검사한다. 5MB를 다 올려보낸 뒤 거절당하는 것과 고르는 즉시 아는 것은 다르다. 오류 문구: "형식을 지원하지 않아요(jpg·png·gif·webp만 올릴 수 있어요)", "5MB를 넘어요 — 크기를 줄여서 다시 올려주세요".

**남는 자리보다 많이 넣으면 앞에서부터 채우고 나머지는 사유를 알린다.** 2장 있는 포스트에 6장을 드롭하면 2장만 받고 "2장만 넣었어요 — 트윗당 4장까지예요".

**리사이즈·크롭은 하지 않는다.** 담당자가 검수한 이미지가 그대로 올라가야 하고, 라이브러리를 들일 이유가 없다.

## D. 표시 — 서명 URL은 초안 경로에서만

```ts
useSignedMedia(posts: DraftPost[]): DraftPost[]   // src/components/useSignedMedia.ts (신규)
```

**포스트 배열 전체를 받아 카드에서 한 번만 호출한다.** 포스트 하나씩 훅을 부르면 안 된다 — `MediaGrid`는 `shown.posts.map(...)` 안에서 렌더되고(`DraftCard.tsx:143`), `shown`은 버전 페이저가 고르는 값이라(`:163-171`) 트윗 5개 버전과 3개 버전을 오갈 때 훅 개수가 바뀌어 React가 "Rendered fewer hooks than expected"로 터진다. §G1의 스레드 축소가 정확히 이 경우다.

모든 포스트의 경로를 모아 `createSignedUrls(paths, 86400)` **한 번**으로 서명하고, `url`을 치환한 같은 모양의 배열을 돌려준다. 절대 URL 항목은 통과시킨다.

**`MediaGrid`에는 선택적 오버레이 슬롯 하나만 추가한다.**

```ts
MediaGrid({ media, renderOverlay }: { media: DeckMedia[]; renderOverlay?: (i: number) => ReactNode })
```

이미지별 hover 액션(떼기·받기·복사)은 그리드 셀 안에서만 그릴 수 있어서 컴포넌트를 완전히 안 건드릴 수는 없다. 초안용 그리드를 따로 만들면 X 레이아웃이 두 벌이 되어 미러링이 드리프트한다(§원칙). 선택적 prop 하나면 **기존 4개 호출부(TweetCard·BriefingSection·RefPickerSheet·QuotedCard)는 무변경**이고 순수 렌더 성질도 유지된다.

기존 레이아웃(1장 크게 / 2장 반반 / 3장 1+2 / 4장 2×2, `rounded-2xl`, `gap-0.5`=2px)은 그대로 쓴다.

**만료를 무시하지 않는다.** 유효기간 24시간이지만 탭을 켜둔 채 다음 날 열면 이미지가 깨지고, "이대로 나간다"를 판단하는 카드에서 그것은 이미지가 날아간 것으로 읽힌다. `<img onError>`에서 한 번 재서명한다. 다운로드·복사는 **클릭 시점에 새로 서명한다** — 렌더 때 받은 URL을 재사용하면 조용히 실패한다.

## E. 첨부 UI

**첨부는 카드와 모달 양쪽에 둔다. 단, 카드 액션 행에는 넣지 않는다.**

액션 행(`DraftCard.tsx:182-202`)은 X 액션 바를 미러링하는 자리이고, 인플루언서 스펙 180행이 "관리용 컨트롤을 섞으면 X 화면 재현이 깨진다"고 정해두었다. X의 트윗 카드에는 첨부 버튼이 없다 — 있는 건 컴포저다.

대신 **포스트별 메타 행**(`DraftCard.tsx:144`, 이미 글자수·"이 트윗만 다시"·"복사"가 있는 그 줄)에 넣는다. 미디어가 포스트 단위이므로 층위가 정확히 맞고, 그 줄은 이미 포스트 단위 액션의 자리다.

- **`＋ 이미지 2/4`** — 남은 자리를 상시 표시한다. 4장이 된 뒤에 "4장까지예요"를 띄우는 것은 사후 통보다(AGENTS #2). 4장이면 비활성 + 툴팁.
- 드래그앤드롭: 포스트 블록에 파일을 떨구면 그 포스트에 첨부
- 업로드 중 진행 표시, 실패 사유는 그 자리에
- 첨부된 이미지 hover → **✕(떼기) · 받기 · 복사** (`renderOverlay`로 주입)
- 이전 버전을 보는 중(`!isLatest`)에는 첨부·떼기를 막는다 — 편집 버튼과 같은 규칙

모달도 같은 컨트롤을 각 포스트 입력 아래에 둔다(X 컴포저 미러). 첨부는 §확정 판단대로 즉시 저장되므로 모달의 `저장` 버튼은 텍스트만 책임진다.

## F. 서버 검증 — `src/app/api/drafts/[id]/route.ts`

**"API 변경 없음"은 틀렸다.** PATCH는 지금 `media: Array.isArray(p.media) ? p.media : []`로 배열이기만 하면 통과시킨다 — 항목 형태 검사도, 4장 제한도 없다. 검증 안 된 jsonb가 `<img src>`와 `createSignedUrls`로 흘러간다. 4장 제한이 UI에만 있으면 서버는 무제한으로 받는다.

각 항목이 `{ type: string, url: string, videoUrl: string | null }`인지 확인하고 `.slice(0, 4)`한다. 텍스트 검증이 이미 그 자리에 있으므로 같은 블록에 붙는다.

## G. 다운로드와 복사

지금 이미지가 앱 밖으로 나가는 두 경로다. 이미지 영역 아래에 한 줄 — **"이미지는 받거나 복사해서 인플루언서에게 전달하세요"**.

**파일명 규칙** (`draftMediaFilename()`, 다운로드 시점 조립)

```
<초안 생성일>_<인플루언서 핸들 또는 클라이언트명>[_<시안>]_<트윗번호>-<이미지순번>.<확장자>
```

- `20260812_hadakan_2-1.jpg` — 2번 트윗의 첫 이미지
- **단문도 `1-1`로 통일한다.** 단문에서 `_1`만 쓰면 그 숫자가 트윗번호인지 이미지 순번인지 알 수 없다.
- 미배정이면 그 자리에 **클라이언트명** — `20260812_강남OO의원_1-1.jpg`
- 다중 시안이면 시안 라벨 — `20260812_hadakan_A_1-1.jpg`. 같은 날 같은 인플루언서의 A·B·C가 확실히 충돌한다. 시안이 아니면 넣지 않는다.
- 날짜는 **초안 생성일**. 다운로드한 날로 하면 며칠에 걸쳐 받을 때 같은 초안 파일이 다른 이름으로 흩어진다.
- 핸들의 `@`는 뺀다. 파일명 금지문자(`/ \ : * ? " < > |`)는 `_`로 바꾼다.

**미배정 상태로 받으면 알린다.** "아직 인플루언서가 정해지지 않아 클라이언트명으로 저장했어요." 배정 전후로 같은 이미지가 두 이름으로 남는 것을 사용자가 모르고 겪지 않게 한다.

**다운로드 두 층위**
- 이미지 개별 — hover 버튼
- 이미지가 2장 이상이면 미디어 영역 아래에 **"이미지 7장 모두 받기(파일 7개)"** — 개수를 밝혀서 여러 파일 확인창을 예고한다. 액션 행이 아니라 콘텐츠 열에 둔다.

서명 URL로 받아 `Blob` → object URL → `<a download>`로 떨군다. blob이므로 `download` 파일명이 그대로 적용된다.

**클립보드 복사** — 이미지 개별만. `navigator.clipboard.write([new ClipboardItem(...)])`. 제약을 안고 간다: 한 번에 한 장, 브라우저가 클립보드 이미지로 PNG만 받으므로 jpg는 캔버스를 거쳐 PNG로 변환된다(화질 손실 없음, 용량 증가). 향후 GIF 지원 시 GIF에는 복사 버튼을 그리지 않는다 — 캔버스를 거치면 움직임이 죽는다.

**ZIP은 지금 넣지 않는다.** "매번 여러 파일 받는 게 번거롭다"가 실사용으로 확인되면 그때 원고 텍스트 + 이미지를 한 파일로 묶는다. 이 저장소는 이미지 관련 의존성이 하나도 없다 — 확인되지 않은 마찰에 라이브러리를 먼저 들이지 않는다.

**텍스트 복사는 이번에 건드리지 않는다.** `draftCopyText`(`draftUi.ts:16`)는 계속 텍스트만 복사한다. 다만 이미지가 붙은 초안에서 "복사"가 절반만 넘긴다는 사실을 위 안내 한 줄이 덮는다.

## H. 기존 동작과 부딪히는 두 곳

**1. 다시 쓰기로 스레드가 짧아지면 이미지가 사라진다.**

`generate.ts:180`이 `media: base.posts[n]?.media ?? []`로 위치 기준 이월한다(`regen-post`도 `:241`에서 보존). 대부분 유지되지만 트윗 5개가 3개로 줄면 4·5번 이미지가 **조용히** 버려진다.

미리 막지 않는다 — 확인 창을 세우면 마찰이 크다. 대신 사후에, **왜인지와 손잡이를 함께** 알린다:

> "다시 쓴 원고가 트윗 3개로 줄어 4·5번의 이미지 2장이 빠졌어요 [이전 버전 보기]"

파일은 지우지 않으므로 이전 버전에서 실제로 받을 수 있다 — 문구가 사실과 일치한다.

**2. 이미지만 붙여도 "편집됨"이 뜬다.**

`DraftCard.tsx:117`이 `draft.edited &&`만 본다. 첨부는 `edited`에 쓰이므로 텍스트를 한 글자도 안 고쳐도 "· 편집됨"이 붙는다. 조건을 **텍스트가 실제로 달라졌을 때**로 좁힌다 — 모달이 이미 쓰는 `textsChanged`(`src/lib/draftUi.ts`)를 재사용한다. 이미지 첨부 사실은 이미지 자체가 보여주므로 별도 배지를 만들지 않는다.

## I. 넣지 않는 것

- 동영상·GIF 업로드 (데이터 구조만 열어둔다 — §B)
- 이미지 크롭·리사이즈·대체 텍스트(alt)
- **순서 바꾸기** — 드래그 다중 선택은 파일 순서를 보장하지 않아 자주 어긋난다. "순서를 바꾸려면 떼고 다시 올려주세요"를 도움말에 명시한다. 파일을 지우지 않으므로 재업로드가 싸다.
- 시안 간 이미지 공유 (§확정 판단)
- AI 이미지 생성
- DM 전송 — 별도 기능. 그때 서버가 서명 URL로 파일을 받아 X `upload_media`에 올려 `media_id`를 얻는 2단계가 필요하다. URL을 그대로 넘기는 방식은 X가 지원하지 않는다.
- 고아 파일 정리 배치, 스토리지 용량 모니터링
