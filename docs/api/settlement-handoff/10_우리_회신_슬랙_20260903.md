# 우리 회신 (우리 → 정산 프로덕트, 슬랙용) — 2026-09-03

> 아래 그대로 붙여넣기. 첨부: `settlement-external-api.md` 현재 판(2026-09-03 갱신본, 이전 판 전부 대체).

---

회신 감사합니다. 정정할 것 하나와 문의하신 것들 답 드립니다.

*1. `proof.url`은 서명 URL이 아니라 저희 API입니다 — 화면에 바로 못 넣습니다*
7-1에서 `proof.url`을 "브라우저에서 직접 열리는 서명 URL"로 이해하고 `<img>`에 그대로 쓰신다고 하셨는데, 아닙니다. `proof.url`은 저희 엔드포인트 `GET /api/external/settlement/requests/{id}/proof`이고, 다른 호출과 똑같이 `Authorization: Bearer <API 키>` 헤더가 있어야 열립니다. 헤더 없이 열면 401(본문 없음)입니다. 브라우저 `<img src>`는 이 헤더를 못 보내서, 지금 방식대로면 화면에 깨진 이미지만 보일 겁니다.
필요하신 것: 그쪽 서버가 키를 넣어 이 주소를 GET하면 이미지 바이트가 그대로 옵니다(`Content-Type`은 `image/jpeg`·`image/png`·`image/webp` 중 하나, 404면 증빙 없음). 이걸 (a) 그쪽 인증된 화면 경로로 중계해서 보여주시거나 (b) 그쪽 저장소에 복사해 두고 그걸 보여주시면 됩니다. 주소는 고정이라 만료 없음 — 매번 새로 받으셔도 되고 캐시하셔도 됩니다(그쪽 선택).
7-3의 "증빙 이미지 응답 조건(용량·Content-Length·캐시) → 해소"는 이 전제 위에서 닫으신 것이라 다시 열어 둡니다. 중계하실 때 필요한 헤더가 있으면 말씀해 주세요, 명세에 추가하겠습니다. (7-3의 "증빙 갱신 시 재유입 → 해소"는 그대로 맞습니다.) 혼동의 원인은 저희 9/2 안내의 "열 때마다 저희 쪽에서 새로 서명합니다"라는 문장으로 보입니다 — 그건 저희 서버가 내부 저장소에 접근하는 방식을 말한 것이고, 그쪽에 주는 주소는 명세 §4-1대로 키가 필요한 API 주소입니다. 표현이 헷갈리게 했습니다.

*2. 지금 보시는 명세가 8/28 판입니다 — 첨부한 9/3 판으로 교체 부탁드립니다*
변경분: `payout.gross_krw` 추가(9/1, §5) / `proof` 필드·`GET .../{id}/proof` 엔드포인트 추가, 증빙만 최신값(9/2, §5·§4-1·§3-2) / RT는 `proof`, 투고·인용RT·방문은 `reference_url` 없으면 저희 쪽에서 요청 생성 자체를 막음 → 신규 요청엔 항상 채워짐(9/2) / PayPay `identifier` 필수화, `payment_method` 빈 값은 키 생략(9/3, 아래 3·5번). 이 판 기준으로 검증 맞춰 주시고 8/28 사본은 폐기 부탁드립니다.

*3. 문의 3건 답*
• `payout.gross_krw` — 지금도 나가고 있고 현재 명세 §5에 있습니다(보고 계신 8/28 판엔 없었을 뿐). 뜻: 실제 송금액(`payout.gross`)의 원화 환산값 — `payout.currency`가 KRW면 `gross` 그대로, JPY면 `gross × rate_krw_per_jpy`. 원화 지출 집계용이고 통화별 분기 필요 없습니다.
• 필드 추가·변경 사전 통보 — 수용합니다. 새 필드·값은 배포 최소 하루 전에 슬랙으로 알리고 갱신된 명세 원문을 같이 보내겠습니다. 9/1 `gross_krw`, 9/2 `proof`가 사전 통보 없이 나가 그쪽 수신이 멈췄던 것, 저희 잘못입니다.
• `payment_method` 빈 값 — 값 없는 키는 `null`이 아니라 **키 자체가 없습니다.** `type`·`holder`·`currency`는 항상 있습니다. 9/3 안내의 "비어 있을 수 있다"는 "키가 없을 수 있다"는 뜻이었습니다.

*4. 8/28 회신에 있었지만 다시 적습니다 (§3 1·2·4)*
• 폴링 에코 — 상태 POST를 받으면 그 건 최상위 `updated_at`이 갱신돼 다음 폴링(30초 안전 지연 뒤)에 다시 내려옵니다. 자기 변경 구분: `settlement.updated_at`(보내신 `updated_at` 되비침)이 마지막 전송 시각과 같으면 에코.
• 그쪽 발 취소 사유 — `status: "cancelled"` + `note` → `cancelled.by_name = "정산 프로덕트"`, `cancelled.reason` = `note`(없으면 "정산에서 취소").
• 커서 무효화 — 커서는 그 건의 `updated_at`(µs)+`id`에서 파생돼 재배포·스키마 변경으로 무효해지지 않습니다. 해석 불가(형식 손상)면 항상 400 `{ field: "cursor" }` → 커서 버리고 처음부터 다시 받으시면 됩니다.

*5. PayPay 수취 식별값 필수화 (9/3 배포, 신규)*
7-2에서 물으신 정책이 정해졌습니다. 9/3부터, PayPay가 기본 결제 수단인 인플루언서는 `identifier`(수취 식별 정보)가 있어야 저희 쪽에서 요청 자체를 만듭니다. 신규 요청은 `payment_method.type == "paypay"`면 `identifier`가 항상 있습니다. 그 전 요청엔 빠져 있을 수 있지만 지금 운영엔 해당 건이 없습니다. 그쪽의 "PayPay 수동 보류" 장치는 신규 건엔 필요 없으실 겁니다.

*6. external_id 에코 확인 (§6-4)*
아직 확인해 드릴 게 없습니다 — 9/2 이후 신규로 유입된 요청이 0건이라 저희가 부여한 코드가 없습니다. 다음 신규 요청이 나가면 단건 GET의 `settlement.external_id`를 저희도 함께 확인해서 알려드리겠습니다.
