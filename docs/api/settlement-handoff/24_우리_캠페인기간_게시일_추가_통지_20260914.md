# 우리 통지 (우리 → 정산 프로덕트, 슬랙용) — 2026-09-14 Item에 캠페인 기간·게시일 4개 필드 추가

> 아래 그대로 붙여넣기. 첨부: `settlement-external-api.md` 현재 판(§5 `campaign.starts_on`·`campaign.ends_on`·`posted_on`·`confirmed_on` 행, §8 개정 기록).

---

정산 요청 API(GET 목록·단건, POST 응답의 `request`)에 날짜 필드 4개를 추가했습니다. **키만 늘었고 기존 키·의미는 그대로**라 그쪽 파서에 영향은 없습니다. 화면에 쓰시려면 매핑만 추가하시면 됩니다.

*1. 추가된 필드*
• `campaign.starts_on` / `campaign.ends_on` (`YYYY-MM-DD` | null) — 캠페인 기간.
• `posted_on` (`YYYY-MM-DD` | null) — 게시일. `task_type`이 `post`·`quoteRt`·`visit`일 때만 값이 있습니다. 인플루언서 본인 게시물의 트윗 시각에서 뽑은 서울 날짜입니다.
• `confirmed_on` (`YYYY-MM-DD` | null) — RT 확인일. `task_type`이 `rt`일 때만 값이 있습니다. 단순 RT는 새 게시물이 없어 실제 리트윗 시각을 알 수 없고, 저희 담당자가 피드 스크린샷을 확인하고 적은 날짜입니다.
• `posted_on`과 `confirmed_on`은 한쪽만 값이 있습니다. "날짜 하나"가 필요하면 둘 중 값이 있는 쪽을 쓰시면 됩니다. 뜻이 달라 일부러 필드를 갈랐습니다(같은 칸에 넣으면 RT 날짜를 게시일로 읽게 됩니다).

*2. 값의 성격 — 요청 시점 스냅샷*
• 단가·결제 수단과 같은 규칙입니다. 요청을 만든 시점의 값이 고정되고, 그 뒤 저희가 캠페인 기간을 고쳐도 요청의 값은 바뀌지 않습니다.
• 고친 값을 보내야 할 때는 저희가 제자리 수정(§3-1)으로 다시 반영합니다 — 그때 `revision`·`updated_at`이 함께 바뀌므로 지금 폴링 그대로 다시 집어가시면 됩니다. 조용히 값만 바뀌는 일은 없습니다.

*3. 기존 요청*
• 이미 보낸 요청에는 현재 캠페인·작업 값으로 채워 두었습니다. 다만 `updated_at`은 건드리지 않았으니 폴링에 다시 잡히지는 않습니다. 기존 건에도 값이 필요하시면 말씀해 주세요 — 저희가 `updated_at`만 갱신해 다시 내려가게 하겠습니다.
• `null`이 나오는 경우는 2026-09-14 이전 요청 중 캠페인·작업이 삭제된 건뿐입니다. 새 요청은 항상 채워집니다.
