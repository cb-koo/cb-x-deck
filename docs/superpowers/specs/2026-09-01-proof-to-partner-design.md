# 증빙을 정산 프로덕트가 지급 전에 확인할 수 있게 — 설계 (2026-09-01)

브랜치: 미정(아래 §9 — 현재 `cb-koo/payment-api`의 9태스크 작업이 머지된 뒤 시작). 선행: `2026-08-28-payment-api-design.md`(연동 계약), `2026-08-31-rt-proof-screenshot-design.md`(RT 증빙 스크린샷), `2026-09-01-settlement-partner-result-design.md`(그쪽이 보낸 결과 기록·차액 확인).

## 0. 한 줄 정의

**정산 프로덕트가 지급하기 전에 "그 작업이 실제로 이루어졌는지"를 우리 자료로 확인할 수 있게 한다.**

## 1. 왜 (koo, 2026-09-01)

- 용도는 **지급 전 확인**이다. 그쪽 담당자가 송금하기 전에 실제 이행 여부를 본다. 장기 보관용이 아니다.
- **투고·인용RT·방문은 콘텐츠 링크가 증빙이다**(koo). 그리고 그 링크는 **이미 그쪽에 나가고 있다** — `settlementCalc.referenceUrlFor`가 이 세 유형에 `postUrl`(인플루언서 본인 게시물)을 넣고, 그 값이 아이템의 `reference_url`로 실린다.
- **RT만 빠진다.** 단순 RT는 새 게시물 URL이 없어서 `referenceUrlFor`가 `targetTweetUrl`(클리닉 원본 트윗)을 넣는다. 원본을 보여줄 뿐 그 인플루언서가 RT했다는 증거가 아니다 — 그래서 RT 증빙 스크린샷 기능이 생겼고, 그 스크린샷이 지금 그쪽에 안 나간다.

| 유형 | 그쪽이 지금 받는 확인 자료 | 충분한가 |
|---|---|---|
| 투고·인용RT·방문 | `reference_url` = 인플루언서 본인 게시물 링크 | ✅ 이미 됨 |
| RT | `reference_url` = 클리닉 원본 트윗 | ❌ 이행 증거 아님 |

**그래서 이 작업의 실체는 하나다: RT 증빙 스크린샷을 그쪽이 볼 수 있게 한다.**

## 2. 범위

| 한다 | 하지 않는다 |
|---|---|
| 아이템에 `proof` 블록 추가(§3) | 확인 자료 없는 요청의 **생성을 막기** — 급한 요청을 먼저 걸어두는 실무를 막는다(koo 기각) |
| 증빙 전용 **인증된 고정 엔드포인트**(§4) | `reference_url`을 라이브로 바꾸기 — 그건 담당자가 손으로 넣는 값이라 스냅샷이 자연스럽다 |
| 증빙은 **작업의 현재값**에서 읽고 스냅샷으로 폴백(§5, koo 결정 B) | 소급 강제 — 이번 규칙 이전 RT 요청에 증빙을 요구하지 않는다 |
| 우리 화면의 거짓이 된 문구 수정(§6) | 그쪽 보류 판단을 자동화하기 — 판단은 그쪽 담당자가 한다 |
| 그쪽 계약 변경 제안 문서(§7) | 마이그레이션 — 새 칸이 없다(기존 칸을 읽는다) |

## 3. 계약 변경 — 아이템에 `proof` 추가

그쪽 문서 §5 Item에 필드 하나가 늘어난다. **기존 필드는 하나도 바뀌지 않는다**(추가만 하는 변경이라 그쪽이 무시해도 깨지지 않는다).

```json
"proof": {
  "url": "https://cb-x-deck.vercel.app/api/external/settlement/requests/<request_id>/proof",
  "uploaded_at": "2026-08-31T10:12:00Z",
  "uploaded_by": "박구건"
}
```

`null`인 경우가 둘이다:

1. **RT가 아닌 유형** — 확인은 `reference_url`(인플루언서 본인 게시물)로 한다.
2. **RT인데 아직 증빙이 없음** — 이번 규칙 이전 요청을 포함한다.

그쪽은 이미 아이템에 있는 `task_type`으로 둘을 가릴 수 있다: `task_type == "rt"` 이고 `proof == null` 이면 **확인 자료가 없는 요청**이다.

## 4. 새 엔드포인트

```
GET /api/external/settlement/requests/{request_id}/proof
Authorization: Bearer <그쪽 운영 키>          ← 이미 쓰는 그 키
```

| 응답 | 조건 |
|---|---|
| **200** + 이미지 바이트(`Content-Type: image/*`) | 증빙이 있음 |
| **404** | 요청이 없음 / 증빙이 없음 |
| **401** (본문 없음) | 키 불일치 |

**왜 서명 URL을 아이템에 직접 넣지 않는가:** 서명 URL은 만료된다. 그쪽이 목록을 캐시해 두고 며칠 뒤 열면 죽은 링크가 된다. 고정 주소는 열 때마다 우리가 새로 서명하므로 만료 문제가 없고, 그쪽 코드도 "GET 한 번"으로 끝난다.

**왜 302 리다이렉트가 아니라 바이트를 흘려보내는가:** 302는 그쪽 HTTP 클라이언트가 리다이렉트를 따라가야 하고, 안 따라가면 우리가 볼 수 없는 실패가 된다. 증빙은 스크린샷(버킷 상한 10MB)이라 그냥 흘려보내는 편이 모호함이 없다.

**보너스 — 이게 오히려 이 기능의 값이다:** 이 호출은 **호출 기록에 남는다**(경로에 `/proof`, 결과 `ok`). "지급 전 확인 자료" 목적이라면 **그쪽이 언제 확인했는지가 기록되는 것** 자체가 근거가 된다.

## 5. 증빙은 작업의 현재값에서 읽는다 (koo 결정 B)

**문제:** 계약상 요청은 수정되지 않는다(그쪽 문서 §3-1) — 보류를 푸는 유일한 경로가 **취소 + 새 요청**이다. 게다가 `payment_request.proof`는 요청 생성 시점의 **스냅샷**이라(044), 보류를 받고 담당자가 그 작업에 스크린샷을 올려도 그 요청에는 반영되지 않는다. 스크린샷 한 장 때문에 `요청 → 보류 → 취소 → 재요청`이 된다.

**규칙:**

- 아이템의 `proof`는 `campaign_task.proof`(**현재값**)에서 읽는다.
- `task_id`가 없는 오래된 요청은 `payment_request.proof`(스냅샷)로 **폴백**한다.
- **금액·계좌·기한 같은 돈 관련 값은 스냅샷 그대로 둔다.** 그게 스냅샷의 존재 이유다. 증빙은 돈 값이 아니라 확인 자료이고, 목적이 "지급 전에 실제로 했는지 본다"이므로 최신이 맞다.

**효과:** 그쪽이 보류로 돌려보내면 → 담당자가 그 작업에 스크린샷을 올린다 → **다음 폴링에 반영돼 보류가 풀린다.** 취소·재요청이 필요 없다.

이 비대칭(돈은 스냅샷, 확인 자료는 라이브)은 의도된 것이므로 코드 주석과 그쪽 문서에 이유를 남긴다.

## 6. 우리 화면 — 거짓이 되는 문구 수정

직전 작업에서 요청 펼침의 증빙 줄에 `정산에는 안 보내요 (우리 보관용)`을 넣었다. 이 작업으로 **그 문장이 거짓이 된다.** 유형에 따라 사실대로 바꾼다:

- RT: `정산 프로덕트도 이 증빙을 봐요`
- 그 외: 증빙 줄 대신 참고자료 줄에 `이 링크가 정산 쪽 확인 자료예요`

## 10. 테스트

- `proof`가 **작업의 현재값**을 따른다: 요청 생성 후 작업에 증빙을 올리면 아이템의 `proof`가 채워진다.
- `task_id`가 null이면 **스냅샷 폴백**이 동작한다.
- RT가 아닌 유형은 `proof`가 `null`이다.
- 엔드포인트: 키 없음 → 401 / 없는 요청 → 404 / 증빙 없는 요청 → 404 / 있으면 200 + 이미지 Content-Type.
- 엔드포인트 호출이 **호출 기록에 남는다**(경로·결과).
- 기존 외부 응답 계약 테스트를 갱신한다 — **키 집합이 `proof` 추가 외에는 그대로**임을 단정한다(파트너 영향 0을 못으로 박는다).
