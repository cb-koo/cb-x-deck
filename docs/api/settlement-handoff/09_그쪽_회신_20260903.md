정산 API 협의 회신 (협찬 비용 관리 → cb-x-deck, 2026-08-28 · 최종 갱신 2026-09-03)

보내주신 「협의 체크리스트 회신」과 최종 명세(settlement-external-api_최종.md) 잘 받았습니다. 요청드렸던 사항(집계 키 non-null, task_id 연결, 스테이징 가짜 데이터)이 반영되어 감사합니다. 문의하신 4가지에 답하고, 남은 확인 사항을 정리해 보냅니다.

1. 문의하신 것에 대한 답

1-1. paid 이후 되돌림 — 동의합니다

환불 상태 없이 "paid 이후 변경은 409 + 정정은 사람 협의"로 가는 방식에 동의합니다. 우리 쪽도 환불은 1차 스코프에서 제외했고, 지급 확정 데이터 보호는 우리가 원했던 바입니다. 금액 정정은 paid → paid 재전송으로 처리하겠습니다.

1-2. 개인정보 보호 방침

결제수단 민감정보(계좌·PayPal 식별값 등)는 다음과 같이 다룹니다:

별도 신규 Supabase DB 사용, 기존 운영 DB와 분리 + 접근 권한 분리.

결제수단 민감 필드는 저장 시 암호화.

RLS(Row Level Security) 로 DB 접근 제한.

화면에서는 마스킹 표시(계좌 뒷자리만 표시 등) — 마스킹 수준은 설정에서 관리하며 기본은 마스킹 켜짐.

1-3. 기획서 공유 — 공유합니다

0828Plan.md를 함께 보냅니다. 체크리스트 밖 요구(기간 집계 기준일 토글, 금액 기준선 배지 등)와 API 커버리지 대조 부탁드립니다.

1-4. 시간대 — 문제 없습니다

시각 필드 UTC ISO 8601, deadline 한국 날짜 방식 그대로 진행해 주세요. 우리 쪽에서 표시 시 KST 변환하고, 데드라인 판정은 한국 날짜 기준으로 합니다.

2. "부탁드리는 것" 수용 확인

가져간 직후 received 전송 — 수용. 폴링으로 새 요청(재요청 포함)을 수신하면 즉시 자동 전송하겠습니다.

updated_at은 우리 서버의 실제 변경 시각 — 수용 (요청별 단조 증가 보장).

실패 시 같은 본문 재전송, 409는 단건 재조회 — 수용.

폴링에서 cancelled 확인 시 지급 중단 — 수용. 추가로 우리 쪽에서 송금 실행 직전 단건 GET으로 취소 여부를 재확인하는 절차를 넣습니다.

수정 요청은 on_hold + note — 수용.

요청자 슬랙 멘션은 우리가 발송 — 수용 (slack_id, 없으면 email로 users.lookupByEmail).

payer/cc는 우리 설정으로 — 수용.

3. 남은 확인 요청 (4건)

폴링 에코 여부: 우리가 상태 POST를 보내면 그 건의 최상위 updated_at이 갱신되어 다음 폴링에 다시 내려오나요? (우리 쪽 변경 감지·알림 중복 방지 설계에 필요)

우리 발 취소의 사유 전달: 우리가 status: cancelled + note를 보내면 cancelled.reason에 note가 들어가나요? (§3-1은 그쪽 담당자 취소 케이스만 명시)

payment_method 명세 정리: 회신에는 type이 paypal/paypay/bank로 안내됐는데, 최종 명세 필드표에는 "빈 객체 가능"이 남아 있습니다. 결제수단 없는 요청은 업무상 없을 것으로 보이니 type 필수로 확정 부탁드립니다.

커서 무효화: 서버 재배포·스키마 변경 등으로 저장해 둔 커서가 무효해지는 경우가 생기면 반드시 400을 주시나요? (그러면 우리가 커서를 버리고 전량 재동기화합니다)

(2026-09-03 추기) 3번은 9/3 「결제 요청 필수 항목 안내」로 해소되었습니다 — payment_method의 type·holder·currency는 항상 채워진다고 확인받았습니다(§7-1). 1·2·4번은 계속 회신 대기 중입니다.

4. 운영 합의 제안

긴급 취소 병행 통지: 취소 전파가 폴링(5분)이라, 지급 임박 건을 급히 취소하실 때는 슬랙/구두로도 알려주시면 안전합니다.

담당자·채널: 사내 직접 소통(오프라인)으로 진행하시죠. 스테이징 URL·키·상세 문서 전달 일정 알려주시면 맞춰 시작하겠습니다.

5. 추가 공유 (2026-08-29 — 프론트 확정에 따른 우리 쪽 운영 방식)

프론트 설계를 확정하면서 우리 쪽 처리 방식이 일부 구체화되어 공유합니다. API 계약 변경은 없습니다 — 그쪽 화면에 보이는 상태 흐름이 달라지는 부분만 미리 알려드립니다.

scheduled(지급 예정)도 수신 직후 자동 회신합니다. 우리는 결제를 매주 토요일 일괄 실행하기로 확정했고, 새 요청은 별도 검토 대기 없이 지급 예정 큐로 들어갑니다. 따라서 received 회신 직후 scheduled를 이어서 보냅니다 — 그쪽 화면에는 가져간 직후 "정산 접수"를 거쳐 곧바로 "지급 예정"으로 표시됩니다. 내용에 문제가 있는 건만 on_hold(+note)로 전환합니다.

결제 실행은 매주 토요일 일괄 진행합니다. deadline은 그대로 존중합니다(토요일 결제로 마감 내 처리, 임박 건은 앞당겨 처리). 지급 임박 건을 급히 취소하실 때의 병행 통지(§4)는 이 운영에서 특히 중요하니 다시 한번 부탁드립니다.

잔여 확인 4건(§3)은 계속 회신 대기 중입니다.

6. 추가 공유 (2026-09-02 — 상태 POST에 external_id 포함 시작)

명세 §"상태 POST 본문"의 선택 필드 external_id를 우리 쪽 정산코드로 채워 보내기 시작합니다. 선택 필드이므로 API 계약 변경은 없습니다 — 그쪽 처리·저장·에코(settlement.external_id) 로직에 손댈 것은 없고, 화면에 우리 정산코드를 노출해 주시면 양쪽 담당자가 같은 번호로 건을 부를 수 있습니다.

형식: CBX-YYMMDD-NNN (예: CBX-260902-001). 문자열, 최대 16자 안팎(명세 상한 100자 이내). YYMMDD는 우리 쪽에 처음 유입된 날(KST), NNN은 그날 순번(001부터, 하루 1000건 이상이면 자릿수가 늘어남).

부여 시점·불변: 요청을 폴링으로 처음 가져온 순간 1회 부여하며 이후 바뀌지 않습니다. 같은 건의 모든 상태 POST(received→scheduled→…→paid, 금액 정정 paid→paid 재전송 포함)에 동일한 값이 실립니다.

소급 없음: 지금까지 이미 넘어간 기존 건에는 부여하지 않습니다. 기존 건의 상태 POST에는 external_id 키 자체를 넣지 않으니 settlement.external_id는 null로 유지됩니다. 신규 유입 건부터 적용됩니다.

부탁: 신규 건 1건이 넘어간 뒤 그쪽 단건 GET의 settlement.external_id에 우리가 보낸 값이 그대로 에코되는지 함께 확인해 주시면 감사하겠습니다. 이후 문의·정정 요청 시 이 코드로 건을 지칭해 주세요.

잔여 확인 4건(§3)은 계속 회신 대기 중입니다.

7. 회신 (2026-09-03 — 「지급 전 확인 자료(증빙) 전달」(9/2)·「결제 요청 필수 항목 안내」(9/3)에 대한 답)

두 안내 모두 잘 받았습니다. 유형별 확인 자료 규칙(RT → proof.url, 투고·인용RT·방문 → reference_url)과 9/2 이후 신규 요청의 필수 항목 보장은 그대로 반영해 진행하겠습니다. 수용 사항과 우리 쪽 조치, 그리고 확인이 필요한 몇 가지를 정리합니다.

7-1. 수용 확인

증빙(proof) 필드 수신 — 수용. 아이템의 proof { url, uploaded_at, uploaded_by } | null을 받아 우리 DB(미러)에 함께 저장하고, 결제 담당 상세 화면에 증빙 이미지를 표시합니다. proof.url이 브라우저에서 직접 열리는 서명 URL임을 확인받아, 화면이 그 URL을 그대로 <img>로 표시합니다(별도 서버 중계·Bearer 호출 없이). 화면에 표시할 때는 폴링으로 받은 최신 proof.url을 씁니다.

RT 증빙 규칙 — 수용(단순화). 증빙(url/이미지) 없는 RT 요청은 그쪽이 생성 단계에서 사전 차단한다고 확인받았습니다. 따라서 신규 RT에는 proof가 항상 존재하므로, 우리 쪽은 "증빙 없는 RT 자동 보류·배지·복귀" 로직을 별도로 두지 않습니다(발생하지 않는 상황을 위한 장치는 만들지 않습니다). 만약 9/2 이전 소급 건에 proof가 없으면 담당자가 기존 수동 보류로 처리하며, 소급분을 한꺼번에 보류로 돌려보내지는 않습니다.

필수 항목 보장 — 확인. 9/2 이후 신규 요청에서 influencer·clinic·category·amount_krw·payout.*·deadline·item·purpose·requester.name·payment_method(type·holder·currency)가 항상 채워진다는 점, RT는 proof, 나머지 유형은 reference_url이 필수라는 점을 기준으로 우리 쪽 검증·화면 안내를 맞추겠습니다. 이로써 §3-3(payment_method.type 필수 확정)은 해소된 것으로 정리합니다.

비어 있을 수 있는 항목 — 확인. RT의 reference_url, RT가 아닌 유형의 proof, payment_method.identifier(PayPay), campaign.id·task_id(삭제 시), cancelled(취소 건만)는 null/부재를 정상으로 처리합니다. (우리 수신 검증도 미지 필드·null을 무시하도록 완화해 두었습니다.)

7-2. 우리 쪽 조치 예정 (그쪽 작업 불필요)

아이템 proof 수신·미러 저장, 상세 화면에서 proof.url 직접 표시(업로더·업로드 시각 함께). RT의 원본 트윗(reference_url)은 "증거 아님"으로 안내합니다.

PayPay 건: 우리 결제 플로우는 송금 개시 시점에 수취 식별값을 필수로 확인하므로, identifier 정책이 정해지기 전까지 PayPay 요청은 송금을 시작할 수 없습니다(담당자가 수동 보류로 처리). 정책이 정해지면 안내 부탁드립니다.

7-3. 확인 요청

(2026-09-03 갱신) 당초 5건 중 3·4번은 우리 쪽 확인으로 해소되어 실제 문의는 아래 3건입니다.

payout.gross_krw: 9/3 안내의 필수 항목에 payout.gross_krw가 적혀 있는데, 최종 명세 §5와 현재 응답에는 없는 필드입니다. 실제로 내려오는(또는 내려올) 필드인지, 뜻(gross의 원화 환산값?)과 명세 반영 여부를 확인 부탁드립니다. (화면엔 이미 원화 환산 금액을 표시 중이라 급한 사안은 아닙니다.)

필드 추가·변경의 사전 통보: 우리 수신 검증은 (완화 전) 명세에 없는 필드를 계약 불일치로 판정해 그 페이지 수신을 중단했습니다. 이번 proof 추가처럼 "추가만 하는 변경"도 수신 실패로 이어질 수 있어, 새 필드·값은 운영 배포 전에 미리(최소 하루) 알려 주시고 갱신된 명세 원문(§3-2·§4-1·§5 반영본)을 보내 주시길 부탁드립니다. (우리 쪽은 이미 미지 필드·null을 무시하도록 검증을 완화해 재발을 막았습니다.)

증빙 갱신 시 재유입 조건 → 해소. 증빙(url/이미지) 없는 RT 요청을 생성 단계에서 차단하신다고 확인받아, 신규 RT는 proof가 처음부터 존재합니다. "나중에 채워 재유입" 시나리오가 없으므로 문의를 닫습니다.

증빙 이미지 응답 조건(용량·Content-Length·캐시) → 해소. 우리가 이미지를 중계 저장하지 않고 proof.url을 브라우저에서 직접 표시하기로 해, 프록시 스펙 협의가 필요 없습니다.

payment_method의 빈 값 표현: 명세는 "있는 키만 내려온다"인데 9/3 안내에는 "identifier가 비어 있을 수 있다"고 되어 있습니다. 값이 없을 때 키를 생략하는지 null로 내려오는지 확정 부탁드립니다. (우리 검증은 null도 허용하도록 완화했지만, 표현 방식을 명세에 명시해 주시면 좋겠습니다.)
