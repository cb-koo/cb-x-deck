# 초안 이미지 첨부 — X와 같은 첨부·같은 표시 (설계)

2026-08-12.

**배경.** 원고 생성 스펙(`2026-08-03-content-generator-design.md`)은 이미지 첨부를 "다루지 않는 것"에 넣고 확장 지점만 남겼다 — `DraftPost.media: DeckMedia[]`는 항상 빈 배열로 저장되고, `MediaGrid`는 0건이면 `null`을 반환한다. 그 자리를 이제 채운다.

원고는 텍스트만으로 완성되지 않는다. 담당자가 인플루언서에게 넘기는 것은 **문구 + 이미지 한 세트**인데, 지금은 이미지가 도구 밖(메신저·드라이브)에 흩어져 있다. 어느 이미지가 어느 원고의 몇 번째 트윗에 붙는지는 사람 머릿속에만 있다. 스레드에서 특히 위험하다 — 순서가 어긋나면 그대로 잘못 게시된다.

**해결.** 초안에 이미지를 붙이고, X와 동일한 그리드로 보여주고, 담당자가 파일로 내려받아 전달한다.

## 원칙

- **X 미러링은 제품 가치다.** 첨부된 모습이 실제 게시물과 같아야 담당자가 "이대로 나간다"를 판단할 수 있다. 사용자 확인: 전달한 이미지가 그대로 올라가는 경우가 95%이고 나머지도 경미한 수정이다 — 즉 이 카드가 보여주는 것은 예시가 아니라 **확정에 가까운 결과물**이므로, 미러링이 곧 정확한 표현이다.
- **이미지는 인증된 사람만 본다.** 버킷을 비공개로 두고 표시할 때마다 서명된 URL을 발급한다. 병원 콘텐츠라 URL이 새면 곤란하다.
- **없는 것을 만들지 않는다.** 데이터 모델(`DraftPost.media`)·렌더 컴포넌트(`MediaGrid`)·저장 API(PATCH가 이미 `media`를 화이트리스트로 통과시킨다)가 전부 준비돼 있다. 마이그레이션도 새 API 라우트도 필요 없다.
- **공유 컴포넌트의 계약을 깨지 않는다.** `MediaGrid`는 초안 외에 트윗 카드·브리핑·레퍼런스·인용 4곳이 더 쓴다. 서명 URL 로직을 그 안에 넣지 않는다.
- **전달 수단을 정직하게 말한다.** DM 전송은 아직 없다. 지금 이미지가 앱 밖으로 나가는 경로는 다운로드뿐이고, 화면이 그렇게 말해야 한다.

## 확정 판단

**미디어는 포스트 단위다.** `DraftPost`에 이미 그렇게 잡혀 있고, X도 스레드의 트윗마다 이미지가 따로 붙는다. 초안 단위로 모으면 스레드에서 "몇 번째 트윗 것인지"가 사라진다 — 이 기능이 없애려는 문제 그 자체다.

**파일명은 저장 시점이 아니라 다운로드 시점에 조립한다.** 스토리지 키(불변·내부용)와 사용자가 받는 파일명(가변·사람용)을 분리한다. 이미지를 먼저 붙이고 인플루언서를 나중에 배정하는 실제 흐름이 이 분리로 저절로 해결된다 — 배정 후에 내려받으면 그때 핸들이 파일명에 들어가고, 배정이 바뀌어도 파일을 옮기거나 이름을 고칠 일이 없다. 규칙을 나중에 바꿔도 조립 함수 하나만 고치면 되고 마이그레이션이 없다.

**스토리지 객체는 지우지 않는다.** 초안에서 이미지를 떼어내도 파일은 남긴다. 버전 이력(`history`)이 과거 버전의 `media`를 그대로 들고 있어서, 파일을 지우면 이전 버전을 열었을 때 깨진 이미지가 뜬다. 고아 파일이 쌓이지만 사용자 2~5명 규모에서 무시할 수 있는 비용이고, 이력의 재현성이 더 비싸다.

**규제 검사는 넣지 않는다.** 텍스트에는 금칙어 검사(`collectDraftFlags`)가 있으니 이미지에도 대응이 필요한지 검토했다. 사용자 확인: 이미지는 담당자가 사전 검수하므로 도구가 개입할 지점이 아니다.

## A. Supabase Storage 버킷 (대시보드 설정, 마이그레이션 아님)

버킷 `draft-media`를 만든다.

| 항목 | 값 |
| --- | --- |
| Public | **off** (비공개) |
| Allowed MIME types | `image/jpeg`, `image/png`, `image/gif`, `image/webp` |
| File size limit | 5 MB |

`storage.objects`에 정책 3개 — `authenticated` 역할에 `select` / `insert` / `delete`, 대상 `bucket_id = 'draft-media'`.

**권한을 로그인 여부로만 가르는 이유.** 이 앱의 스키마에는 멤버십 모델이 없다 — 워크스페이스 전체가 콘텐츠를 공유하는 것이 의도된 설계이고, `requireMember()`가 하는 일은 접근 제어가 아니라 신원 해석이다. 로그인 자체가 도메인 게이팅(Google OAuth + 허용 이메일)으로 이미 좁혀져 있다. 이미지에만 더 촘촘한 권한을 두면 본문과 어긋난다.

**service role key를 쓰지 않는다.** 이 저장소는 지금 어디서도 쓰지 않는다. 브라우저가 로그인 세션(anon key + JWT)으로 직접 업로드하면 서버 홉도, 새 시크릿도, multipart 처리 코드도 필요 없다.

## B. 저장 형식 — `DeckMedia` 재사용

`src/lib/types.ts:55`의 `DeckMedia { type, url, videoUrl }`를 그대로 쓴다. 타입 변경 없음.

```ts
{ type: 'photo', url: 'draft/<draftId>/<uuid>.jpg', videoUrl: null }
```

**`url`에 절대 URL이 아니라 스토리지 경로가 들어간다.** 비공개 버킷이라 고정 URL이 존재하지 않는다. 기존에 이 필드에 들어있던 값(X에서 스크래핑한 공개 CDN URL)과 형태가 다르므로, 읽는 쪽에서 **`http`로 시작하면 절대 URL, 아니면 스토리지 경로**로 판별한다. 이 판별 하나로 두 출처가 한 필드에 공존하고, 기존 트윗 미디어는 아무것도 바뀌지 않는다.

**필드를 새로 만들지 않은 이유.** `DeckMedia`에 `path`를 추가하면 5개 호출부의 타입이 전부 흔들리고, 마이그레이션 없이 저장돼 있는 기존 jsonb와도 어긋난다. 판별 함수 하나가 훨씬 싸다.

**동영상·GIF 확장.** `type`이 문자열이고 `videoUrl` 자리가 이미 있어서, 나중에 동영상을 넣어도 이 구조는 그대로다. 바뀌는 것은 버킷의 MIME 화이트리스트와 업로드 UI의 `accept`뿐이다.

## C. 업로드 — `src/lib/draftMedia.ts` (신규)

```ts
uploadDraftImage(draftId: string, file: File): Promise<DeckMedia>
```

브라우저 Supabase 클라이언트(`src/lib/supabase/client.ts`)로 `draft-media` 버킷에 올리고 `DeckMedia`를 돌려준다. 경로는 `draft/<draftId>/<crypto.randomUUID()>.<확장자>`.

클라이언트에서도 형식·용량을 먼저 검사한다. 버킷 설정이 최종 방어선이지만, 5MB를 다 올려보낸 뒤 거절당하는 것과 고르는 즉시 "5MB를 넘어요"를 보는 것은 다르다.

오류 문구는 사용자 언어로 — "형식을 지원하지 않아요(jpg·png·gif·webp만 올릴 수 있어요)", "5MB를 넘어요 — 크기를 줄여서 다시 올려주세요".

**리사이즈·크롭은 하지 않는다.** 담당자가 검수한 이미지가 그대로 올라가야 하고, 라이브러리를 하나 들이는 값을 지금 치를 이유가 없다.

## D. 표시 — 서명 URL은 초안 경로에서만

```ts
useSignedMedia(media: DeckMedia[]): DeckMedia[]   // src/components/useSignedMedia.ts (신규)
```

`url`이 스토리지 경로인 항목만 골라 `createSignedUrls(paths, 86400)`으로 **한 번에** 서명하고, `url`을 치환한 배열을 돌려준다. 절대 URL 항목은 건드리지 않고 통과시킨다.

`DraftCard`는 `<MediaGrid media={signed} />`로 넘긴다. **`MediaGrid`는 한 글자도 바꾸지 않는다** — 트윗 카드·브리핑·레퍼런스·인용 4개 호출부가 같은 컴포넌트를 쓰고 있어서, 그 안에 비동기 서명 로직이 들어가면 서명이 필요 없는 화면까지 영향받는다. 순수 렌더 컴포넌트라는 성질을 지킨다.

`MediaGrid`가 이미 X의 레이아웃(1장 크게 / 2장 반반 / 3장 1+2 / 4장 2×2, radius 16, 0.5px 간격)을 구현하고 있으므로 표시 쪽 작업은 이 훅을 끼우는 것이 전부다.

유효기간 24시간. 만료돼도 새로고침하면 다시 발급되므로 사용자가 겪는 문제가 아니다.

## E. 첨부 UI

**두 곳 모두에 둔다** — 초안 카드(`DraftCard.tsx`)와 편집 모달(`DraftEditModal.tsx`). 카드에서 바로 붙일 수 있어야 "편집 열기 → 붙이기 → 저장"의 3단계가 사라진다.

- 진입: X 컴포저와 같은 이미지 아이콘 버튼 + **드래그앤드롭**(카드/모달의 포스트 영역에 파일을 떨구면 첨부)
- 스레드는 트윗마다 개별 첨부 — 각 포스트 블록이 자기 첨부 영역을 가진다
- 포스트당 **최대 4장**. 4장이면 버튼을 비활성화하고 "이미지는 트윗당 4장까지예요"를 옆에 붙인다(누른 뒤 거절하지 않는다)
- 업로드 중 진행 표시, 실패 시 사유를 그 자리에
- 첨부된 이미지에 마우스를 올리면 **✕(떼기) · 다운로드 · 복사**

저장은 기존 흐름을 그대로 탄다 — `edited`를 PATCH `/api/drafts/[id]`로 보낸다. 이 라우트는 이미 `media`가 배열이면 그대로 저장한다(`Array.isArray(p.media) ? p.media : []`). **API 변경 없음.**

카드에서 첨부할 때는 텍스트를 건드리지 않으므로, 현재 표시본의 `posts`에 `media`만 갈아끼워 보낸다.

이전 버전을 보는 중(`!isLatest`)에는 첨부·삭제를 막는다 — 편집 버튼과 같은 규칙이다.

## F. 다운로드와 복사

지금 이미지가 앱 밖으로 나가는 유일한 경로다. 이미지 영역 아래에 한 줄로 밝힌다 — "이미지는 받아서 인플루언서에게 전달하세요".

**파일명 규칙** (`draftMediaFilename()`, 다운로드 시점 조립)

```
<초안 생성일>_<인플루언서 핸들>_<트윗번호>-<이미지순번>.<확장자>
```

- 스레드: `20260812_hadakan_2-1.jpg` (2번 트윗의 첫 이미지)
- 단문: `20260812_hadakan_1.jpg` (트윗이 하나뿐이라 트윗번호 생략)
- **인플루언서 미배정이면 그 자리에 클라이언트명** — `20260812_강남OO의원_1.jpg`. 항상 있는 값이고 다운로드 폴더에서 바로 식별된다. "미배정" 같은 문자열보다 쓸모 있다.
- **다중 시안이면 시안 라벨을 넣는다** — `20260812_hadakan_A_1.jpg`. 같은 날 같은 인플루언서의 A·B·C가 확실히 충돌하기 때문이다. 시안이 아닌 단일 초안에는 넣지 않는다.
- 날짜는 **초안 생성일**. 다운로드한 날로 하면 며칠에 걸쳐 받을 때 같은 초안의 파일이 다른 이름으로 흩어진다.
- 핸들의 `@`는 뺀다. 파일명에 못 쓰는 문자(`/ \ : * ? " < > |`)는 `_`로 바꾼다.

**다운로드 두 층위**
- 이미지 개별 — hover 버튼
- 카드 액션 행에 **"이미지 전체 받기"** — 초안에 붙은 이미지를 순차 저장. 브라우저가 "여러 파일 다운로드" 확인을 한 번 물을 수 있다.

서명 URL로 받아 `Blob` → object URL → `<a download>`로 떨군다. blob이므로 `download` 파일명이 그대로 적용된다.

**클립보드 복사** — 이미지 개별만. `navigator.clipboard.write([new ClipboardItem(...)])`. 제약을 그대로 안고 간다: 한 번에 한 장, 브라우저가 클립보드 이미지로 PNG만 받으므로 jpg는 캔버스를 거쳐 PNG로 변환된다(화질 손실은 없고 용량이 는다). 향후 GIF를 지원하면 GIF는 복사에서 제외한다 — 캔버스를 거치면 움직임이 죽는다. 복사 버튼을 GIF에는 그리지 않는다.

**ZIP은 지금 넣지 않는다.** "매번 여러 파일 받는 게 번거롭다"가 실사용으로 확인되면 그때 원고 텍스트 + 이미지를 한 파일로 묶는 쪽으로 올린다. 이 저장소는 이미지 관련 의존성이 지금 하나도 없다 — 확인되지 않은 마찰에 라이브러리를 먼저 들이지 않는다.

## G. 기존 동작과 부딪히는 두 곳

**1. 다시 쓰기로 스레드가 짧아지면 이미지가 사라진다.**

`generate.ts:180`이 `media: base.posts[n]?.media ?? []`로 이미지를 위치 기준으로 이월한다(`regen-post`도 `p.media`를 보존한다). 그래서 대부분은 유지되지만, 트윗 5개가 3개로 줄면 4·5번 이미지가 **조용히** 버려진다.

미리 막지 않는다 — 이미지가 붙었다고 다시 쓰기에 확인 창을 세우면 마찰이 크다. 대신 **사후에 알린다**: 이월되지 못한 이미지가 있으면 "이미지 N장이 새 버전으로 옮겨지지 못했어요 — 이전 버전에서 받을 수 있어요". 파일은 지우지 않으므로(확정 판단 참조) 이전 버전에서 실제로 받을 수 있다. 문구가 사실과 일치한다.

**2. 이미지만 붙여도 "편집됨"이 뜬다.**

`DraftCard.tsx:117`이 `draft.edited &&`만 본다. 첨부는 `edited`에 쓰이므로 텍스트를 한 글자도 안 고쳐도 "· 편집됨"이 붙는다. 조건을 **텍스트가 실제로 달라졌을 때**로 좁힌다 — 편집 모달이 이미 쓰는 `textsChanged`(`src/lib/draftUi.ts`)를 재사용한다. 이미지 첨부 사실은 이미지 자체가 보여주므로 별도 배지를 만들지 않는다.

## H. 넣지 않는 것

- 동영상·GIF 업로드 (데이터 구조만 열어둔다 — B 참조)
- 이미지 크롭·리사이즈·순서 바꾸기·대체 텍스트(alt)
- AI 이미지 생성
- DM 전송 (별도 기능. 그때 서버가 서명 URL로 파일을 받아 X `upload_media`에 올려 `media_id`를 얻는 2단계가 필요하다 — URL을 그대로 넘기는 방식은 X가 지원하지 않는다)
- 고아 파일 정리 배치
- 스토리지 용량 모니터링
