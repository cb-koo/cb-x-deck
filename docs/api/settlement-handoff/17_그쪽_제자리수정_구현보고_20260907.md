제자리 수정 수용 회신 반영 및 전환 절차

작성: 2026-09-07 · 대상: 정산 미러(cb-marketing-ex)
근거: 소스팀 수용 회신 초안

현재 상태

정산 미러의 수신·상태 회신 코드를 구현했다. 운영 DB 적용·배포·스위치 활성화 및 소스팀에 메시지 발송은 아직 하지 않았다. 링크는 회신 초안이므로 실제 양측 합의나 소스팀 배포 완료의 증거로 취급하지 않는다.

기존 제안 문서는 당시 제안으로 보존한다. 사건 작업 7cf4dfaa…의 핸들은 @Qni6F다. 기존 취소+재요청을 목록에서 묶는 임시 처리는 전환 전과 과거 기록에 계속 적용한다.

구현한 동작

request_id로 기존 미러를 갱신한다. task_id와 정산코드는 유지하며 소스가 다른 값을 보내면 거부한다. 이 저장소에는 원본 수정 화면을 만들지 않는다. 실제 요청 수정·변경 전 원본 보존·신규 생성과 동일한 검증은 소스팀 담당이다.

revision은 0 이상의 정수로 수신한다(PostgreSQL integer 범위). 수정은 requested인 요청의 revision 증가로 판정한다. 정산 상태의 null만으로는 재접수하지 않는다. 취소는 status로 판정한다.

새 수정본은 DB 잠금 이후 판정하여 received → scheduled 이력, 이전 전송 폐기, 새 수정본 상태 회신, 담당자 수정 알림을 한 트랜잭션으로 만든다. 담당 잠금·보류 사유·지급 초안은 해제한다. 잠금이 있던 요청에는 미송금 확인을 요구하여 중복 지급을 예방한다.

기존 판의 중복 수신, 상태 POST 에코, 더 오래된 수정본에는 재접수 이력을 추가하지 않는다. 정렬과 커서는 기존 updated_at 규약을 유지한다. 같은 시각의 상위 revision은 적용하지 않는다.

모든 새 상태 POST에는 outbox 생성 당시 revision을 고정한다. 전송·재시도 시점의 최신 revision으로 바꾸지 않는다.

409 { code: "revision-mismatch", request: Item }를 받으면 최신 Item을 폴링과 같은 원자적 경로로 처리하고 해당 과거 판만 폐기한다. 새 판의 outbox는 보존한다. 오래된 paid를 새 판으로 바꿔 자동 재전송하지 않는다.

결제 시작 단건 GET에서 수정본이 바뀌었으면 최신본을 반영하고 새로고침을 요구한다. 로컬 전이 중 수정이 끼어들어도 DB에서 기대 revision을 검사한다.

로컬 paid 또는 현재 잠금에서 송금 완료가 기록된 amount/confirm 단계라면 수정본으로 금액을 덮지 않는다. 지급 증적을 보존하고 revision-after-transfer 정합 오류를 기록하며 추가 처리와 전송을 막는다. 운영 런북 R4로 확인한다.

지급 확정 후 즉시 상태 POST를 시도하는 기존 경로는 유지한다. 외부 송금 자체를 실행하는 API는 이 제품에 없다.

기능 스위치

마이그레이션 017_in_place_revision.sql이 settings.in_place_revision_enabled = false를 만든다. DB가 수신·전이·outbox의 공통 스위치다.

OFF에서는 기존 0/1 취소 규약과 revision 없는 상태 POST가 유지된다. 소스가 미리 제자리 수정본을 보내면 저장·커서 진행을 실패시켜 수정 신호를 잃지 않게 한다. 기존 레거시 취소 수신은 계속 처리한다.

ON부터 새 outbox에 revision을 필수로 넣고 수정본을 재접수한다. 양측의 준비 상태를 확인하지 않고 ON으로 바꾸지 않는다.

활성화 전에 남은 합의 — 송금 시점

회신 ①(revision 포함)와 ③(정수 수용)은 구현했다. ② “송금 실행과 paid를 같은 시점에 전송”은 현재 수동 송금 → 실지급액 입력 → 최종 지급 확정 흐름으로 보장할 수 없다. paid에는 실제 지급액과 지급 시각이 필수이고, 전송 지연·실패도 가능하다. 실제 송금 전에 임의의 금액으로 paid를 보내지 않는다.

따라서 이 구현을 근거로 송금과 수정 사이의 틈이 완전히 사라졌다고 답하면 안 된다. 활성화 전에 소스팀과 다음 중 실제 운영할 절차를 확정해야 한다.

송금 전 소스에서 수정 금지 잠금을 획득하고 성공 확인 후 송금한다. 송금 성공은 실제 지급액으로 paid를 회신하고, 미송금이 확인된 실패만 잠금을 해제한다. 송금 결과 불명확 시 잠금을 유지하고 대사한다. 이 방식에는 별도 소스 API 명세와 양측 구현이 필요하다.

별도 잠금 API 도입 전에는 합의된 송금 작업 시간 동안 소스의 수정 기능을 막고, 미완료 송금·미전송 paid가 없다는 대사 후 다시 연다. 실제 차단 장치와 담당자를 양측이 확인해야 한다.

미러의 충돌 감지와 잠금 해제 후 미송금 확인은 추가 방어이며 이 합의를 대신하지 않는다.

배포·전환 순서

스테이징에 017 마이그레이션 적용(OFF) → 미러 앱 배포. 이 상태에서는 현행 계약 유지. 모의 소스 테스트 및 스테이징의 수정·취소·paid 충돌을 확인한다.

양측 명세·위 송금 절차 합의 및 소스팀 배포 완료를 확인한다. 기존 계획의 “초안 합의 후 2~3일”은 소스팀 초안의 예상 일정이며 이 작업에서 확정하지 않는다.

전환 시간에는 신규 결제 조작을 멈추고 진행 중 송금과 상태 POST를 마무리한다. 실행 중인 폴링·전송 작업이 없는지 확인한다. 이전 계약의 pending/failed_permanent outbox를 모두 처리·대사한다. 특히 revision 없는 오래된 본문에 최신 판을 임의로 붙이지 않는다.

합의한 시각에 양측 스위치를 활성화한다. 소스가 먼저 수정본을 발행하지 않게 맞춘다. 미러 스위치는 아래 SQL로 변경하되 사전 점검이 완료된 환경에서만 실행한다.

UPDATE public.settings
SET value = 'true'::jsonb
WHERE key = 'in_place_revision_enabled';

한 건을 두 번 수정하여 같은 request ID·같은 정산코드·revision 0→1→2, 수정 이력 및 새 판 POST를 확인한다. 옛 판 POST의 409, 실제 폐기, paid 정정은 독립적으로 점검한다. 운영 지급 테스트는 실제 송금 없이 paid를 허위 생성하지 않는다.

구계약 전송 또는 정합 오류가 있으면 해당 건을 멈추고 R4로 대사한다. 전환 데이터가 생긴 뒤에는 revision을 0/1로 되돌리지 않는다. 필요한 경우 양측 수정·지급 동작을 일시 중지하고 전진 수정한다.

017 롤백은 아직 전환 데이터를 만들지 않았을 때만 허용한다. revision > 1 또는 revision을 포함한 outbox가 하나라도 있으면 자동 롤백을 거부하여 돈 기록을 보존한다.

outbox에서 과거 판만 폐기하고 새 판 보존, 배치 조회 뒤 폐기된 행의 전송 차단을 검증한다.
