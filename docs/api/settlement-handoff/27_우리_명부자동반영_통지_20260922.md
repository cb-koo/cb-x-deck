# 우리 통지 (우리 → 정산 프로덕트, 슬랙용) — 2026-09-22 수취 정보 정정의 "명부 자동 반영" 전환

> 아래 그대로 붙여넣기. **그쪽이 조치할 것은 없습니다** — `POST …/payment-info`의 요청·응답·판정은 그대로입니다. 저희 쪽 수신 후 처리만 바뀝니다. 첨부: `settlement-external-api.md` 갱신본(§6-1 "명부 자동 반영" 문단, §5 `payment_method_correction` null 설명, §8 개정 기록 2026-09-22).

---

「수취 정보 정정(`…/payment-info`)」 관련 저희 쪽 처리 방식 하나를 바꿔 알려 드립니다. **계약(요청 필드·응답 형태·409 판정)은 전혀 바뀌지 않습니다** — 그쪽 전송 코드는 그대로 두시면 됩니다.

*무엇이 바뀌나 (저희 쪽만)*
• 지금까지: 그쪽 정정은 **해당 지급 건에만** 반영하고, 저희 인플루언서 명부(원본)는 저희 담당자가 화면 안내를 보고 손으로 고쳤습니다(handoff 26 §3).
• 2026-09-22부터: 정정이 오면 정정이 **고친 항목만** 저희 인플루언서 명부의 해당 결제 수단에도 자동 반영합니다(수수료·기본 수단 설정 등 정정과 무관한 값은 그대로 둡니다). 실사용에서 "명부를 한 명씩 열어 고치는" 마찰이 커서 자동화로 올렸습니다.
• 그래서 같은 인플루언서의 **다음 요청부터는 정정 값이 나갑니다** — 전에는 옛 값이 다시 나갈 수 있었습니다.

*그쪽에 영향 있나 → 없습니다*
• 요청 본문(7키·`operator`·`reason`·`correction_id`…), 200 응답(`{ applied, correction_id, request }`), 409 코드 3종, 멱등 규칙 — **전부 그대로**입니다.
• `request`의 `payment_method`·`payment_method_correction`도 그대로 내려갑니다. 폴링 재유입·상관관계(`correction_id`)도 동일합니다.
• 굳이 남기는 차이 한 가지: 저희 화면 표시가 "명부는 그대로예요"에서 "명부에도 반영했어요"로 바뀝니다(저희 내부 표시).

*예외 한 가지*
• 명부에 수단이 없거나, 같은 종류가 여럿이라 어느 것인지 못 가리거나, 정정이 명부 수단과 맞지 않을 때만 명부를 못 고치고, 저희 화면(호출 기록)에 "명부는 확인이 필요해요"로 뜹니다. 그쪽 응답은 이 경우에도 200입니다(요청 건 정정은 정상 반영).

*배포*
• 저희: 마이그레이션 + 처리 변경을 스테이징 → 운영 순으로 배포합니다. 그쪽 조치가 없어 **별도 공동 점검 없이** 저희가 배포 후 알려 드리겠습니다.
