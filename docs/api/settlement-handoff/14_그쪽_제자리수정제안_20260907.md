성격: 계약의 근본 원칙 변경 제안 — 소스팀 합의 필요. 이 문서는 제안이며, 합의 전까지 계약서는 현행 유지.

1. 요청 한 줄 요약

요청 수정을 지금의 "옛 요청 취소 + 새 요청 생성"(계약 §3-1)에서 "같은 요청을 제자리에서 수정"으로 바꿔 주세요. 같은 request_id·external_id(정산코드)를 유지한 채 금액 등을 갱신하고 revision을 올려 다시 유입시키는 방식입니다. 그러면 한 작업의 정산이 하나의 정산코드로 등록 → 수정 → 완료까지 이어집니다.

2. 배경 — 왜 바꾸나

지금 무슨 일이 일어나나 (라이브 사건)

한 RT 정산(task_id 7cf4dfaa-…, @Qni6F)에서 요청자(박구건)가 수수료를 재설정하자, 소스가 계약 §3-1대로 처리해 정산 미러에 두 건이 들어왔습니다:

 | 

 | 
 | request_id
 | status
 | 정산코드
 | 내용

 | 옛 건
 | f6189ec9-…
 | cancelled (사유 "수수료 재설정")
 | CBX-260907-004
 | 수수료 없음(gross 8,000)

 | 새 건
 | 1f264104-…
 | requested
 | CBX-260907-005
 | 수수료 5%(gross 8,421)

이게 만드는 문제

하나의 작업이 두 개의 정산코드로 쪼개진다. 결제담당 화면에서 "같은 건"이 004(취소)·005(신규)로 나뉘어 보이고, 상태·이력·완료가 갈라집니다.

사용자(결제담당)의 멘탈 모델은 "수정요청 → 재요청" 인데, 데이터는 "취소 → 신규" 로 표현되어 "왜 취소지?" 하는 혼선이 생깁니다. 여기서 "취소"는 폐기가 아니라 소스 내부의 "스냅샷 교체" 용어일 뿐이지만, 화면에는 폐기처럼 보입니다.

정산코드가 건마다 새로 발급되어, "CBX-260907-004 하나로 등록→수정→완료" 라는 운영 요구를 구조적으로 만족할 수 없습니다.

정산 미러는 이 사건에 대한 임시 대응으로, 같은 task_id의 "취소 옛 건 + 활성 새 건"을 화면에서 하나의 스레드로 접어 보이도록 구현해 두었습니다(활성 대표 1건 + 개정 이력). 하지만 이는 표현 계층의 봉합일 뿐, 정산코드가 둘로 나뉘는 근본 문제는 남습니다. 본 제안이 채택되면 애초에 쪼개지지 않으므로 이 봉합이 불필요해집니다.

3. 현재 vs 제안 플로우

현재(§3-1):
  요청A(지급예정) ──[취소]──▶ 요청A(cancelled, 코드 004)
                              +  요청B(requested, 코드 005 신규)   ← request_id·정산코드 2개

제안(제자리 수정):
  요청A(지급예정) ──[보류: 수정요청]──▶ 요청A(보류) ──[수정 반영]──▶ 요청A(지급예정, 코드 004 그대로)
                                                                      revision 0 → 1     ← request_id·정산코드 1개

4. 수정의 출발점은 두 가지 — 둘 다 같은 방식으로

 | 

 | 트리거
 | 설명
 | 이번 사건

 | (a) 미러발
 | 정산 미러 결제담당이 보류(수정요청) 를 걸어 수정을 요구
 | —

 | (b) 소스발
 | 소스 요청자가 스스로 금액·수수료 등을 수정
 | ✅ (박구건 수수료 재설정)

두 경우 모두 해결책은 동일합니다: 소스가 "취소+재생성"을 멈추고, 같은 request_id·external_id로 제자리 수정 후 재유입. 계약 변경안은 두 트리거를 모두 포섭합니다.

5. 계약 변경안

5-1. §3-1 대체

현행 §3-1을 다음으로 대체합니다.

(현행, 폐기) "요청은 만든 뒤 바뀌지 않는다(스냅샷). 수정이 필요하면 그 요청을 취소하고 같은 작업으로 새 요청을 만든다."

(신규) "미지급(paid 이전) 요청은 제자리에서 수정할 수 있다. 수정 시 같은 request_id·external_id를 유지하고, revision을 1 올리며, updated_at을 갱신한다. status는 requested를 유지한다(취소 아님)."

5-2. 수정 시 소스가 지켜야 할 규칙

동일성 유지: request_id 불변, external_id(정산코드) 불변, task_id 불변.

revision 증가: 수정할 때마다 +1 (0 → 1 → 2 …). 아래 §5-4의 의미 변경 참조.

status는 requested: 수정은 취소가 아니다. cancelled로 만들지 않는다.

settlement.status를 null로 리셋: 금액 등이 바뀌었으므로 정산 미러가 처음부터 재검토하도록 처리 상태를 초기화한다. (미러는 이를 신호로 보류/지급예정을 풀고 received부터 다시 처리하며, 담당자에게 "수정 반영" 알림을 보낸다.)

updated_at 갱신: 폴링 커서·정렬 기준이므로 반드시 최신화(§3, 최소 1회 배달·request_id upsert 규약은 그대로 유효 — 같은 id를 덮어쓰면 됨).

5-3. 경계 — 무엇은 여전히 금지/유지되나

paid 이후 수정 불가: 지급 완료 요청은 되돌리지 않는다. 금액 정정이 필요하면 기존 예외인 paid → paid 재전송(사유 필수) 만 사용(계약 §7, 정산 미러 CRITICAL 규칙과 일치).

진짜 폐기(취소)는 그대로 유지: 작업을 실제로 없앨 때는 종전대로 status: "cancelled" + cancelled.reason. "수정"과 "폐기"를 데이터로 구분한다(수정=requested+revision↑, 폐기=cancelled).

처리중(claimed) 중 수정: 정산 미러가 이미 결제 처리를 잡고 있는(claimed) 상태에서 수정이 들어오면, 미러가 클레임을 해제하고 재검토를 유도한다(미러 측 처리, §6·016 취소 수렴과 동일 패턴).

5-4. §5 revision 필드 의미 변경

(현행) revision: 0 요청됨 / 1 취소됨

(신규) revision: 원본 요청의 수정 횟수(0 최초, 1 1차 수정, 2 2차 수정 …). 취소 여부는 status 필드로 표현하며 revision과 무관하다.

revision을 정렬·중복 판정에 쓰지 않는다(§3, updated_at 기준)는 규약은 그대로. 정산 미러는 revision 증가를 "수정 발생" 신호로만 사용.

5-5. 이전 제안(previous_request_id/request_seq)은 철회

취소+재생성 모델에서 옛·새 건을 잇기 위해 제안했던 previous_request_id·request_seq 필드는, 제자리 수정에서는 request_id가 하나뿐이라 불필요합니다. 본 제안이 채택되면 그 두 필드는 추가하지 않아도 됩니다.

6. 정산 미러 측이 함께 바꾸는 것 (참고 — 우리가 구현)

소스 변경에 맞춰 정산 미러도 다음을 구현합니다(소스 승인 후 병행):

revision 허용 범위 확장: 스키마 CHECK IN (0,1) → >= 0, 파싱 스키마 0|1 → 정수(마이그레이션 + source-types.ts).

재유입 전이 추가: 이전에 본 요청이 revision 증가(또는 settlement.status: null 리셋)로 다시 들어오면, 보류/지급예정을 풀고 received → scheduled로 재처리 + 상태 이력 "수정 반영" + 담당자 알림. (현재 이 지점은 sync.ts에서 아무 전이도 안 하는 noEffects.)

처리중(claimed) 중 수정 유입 시 클레임 해제·재검토 유도.

임시 봉합(취소 스레드 접기)은 레거시·진짜 폐기 대응용으로만 유지(신규 데이터는 쪼개지지 않으므로 자연히 미적용).

목 서버(mock-server/)에 제자리 수정 시나리오를 구현해 소스 구현의 참조 규격으로 제공.

  "external_id": "CBX-260907-004",

→ 정산 미러: 같은 코드 CBX-260907-004 한 건이 "지급예정 → (수정 반영) → 지급예정(수수료 5% 적용)"으로 이어짐. 신규 코드 005 발급 없음, 취소 표시 없음.

8. 소스 측에 요청하는 것 (정리)

§3-1을 §5-1의 "제자리 수정"으로 전환 — 미지급 요청 in-place 수정, 같은 request_id·external_id 유지.

수정 시 revision +1, status requested 유지, settlement.status null 리셋, updated_at 갱신(§5-2).

revision 값 범위를 0/1에서 증가하는 정수로 확장(§5-4). 미지급 판단·paid 잠금·진짜 취소 경계 유지(§5-3).

(철회) previous_request_id·request_seq는 불필요(§5-5).
