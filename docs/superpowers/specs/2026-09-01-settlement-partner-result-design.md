# 정산 프로덕트가 보낸 결과를 남기고, 차액을 확인한다 — 설계 (2026-09-01)

브랜치 `cb-koo/payment-api`(main 8bdc728). 선행: `2026-08-28-payment-api-design.md`(연동 계약), `2026-08-28-settlement-page-design.md`(정산 페이지), `2026-09-01-krw-real-cost-design.md`(실질 비용 — 실지급액 집계는 그 문서에서도 "다음 작업"으로 미뤄 둔 부분이고, 이 문서도 집계는 다루지 않는다).

## 0. 한 줄 정의

**그쪽이 보낸 내용을 잃지 않게 남기고, 실지급액이 요청 금액과 다르면 담당자가 확인하고 지나가게 한다.**

## 1. 왜 (2026-08-31~09-01 사고에서 나옴)

8/31에 그쪽이 보낸 지급 완료(실지급 31,650원)가 우리 쪽 수동 정리 과정에서 지워졌다. 복구는 했지만(다른 세션 작업 기록에 값이 남아 있었다), 조사 과정에서 잃고 있는 것 셋이 드러났다.

| 잃는 것 | 지금 상태 |
|---|---|
| 그쪽이 보낸 본문 | 저장하지 않는다. 호출 기록에는 `status` 값과 결과만 남는다 |
| 메모(`note`) 이력 | 칸이 하나라 다음 상태가 오면 덮어쓴다. 실제로 `"보내도 될 것 같아요"`(지급 예정)가 지급 완료가 오면서 사라졌다 |
| 차액에 대한 우리 판단 | 화면에 숫자는 뜨지만 눈에 띄지 않고, 누가 확인했는지 흔적이 없다 |
| **차액 자체가 틀리게 나온다** | **기존 결함.** 비교 기준을 `amount_krw`(수수료 **제외** 순액)로 잡아, 실제로 정확히 일치한 지급이 차액 있는 것처럼 보인다(§6-1) |

거기에 조사 중 **호출 기록 자체가 유실될 수 있는 구조적 결함**이 드러났다(§7).

koo 결정(09-01):
- 차액은 **협의로 조정된 결과**다. 그래서 "왜 달라졌는지"가 남아야 한다.
- **차액 기준은 1원.** 임계값을 두지 않는다 — 비교 기준을 §6-1로 바로잡으면 실제 지급 1건은 송금액과 정확히 일치하므로 반올림 잡음이 생기지 않는다.
- **사유는 정산 쪽만 작성한다.** 우리는 사유를 쓰지 않고, 그쪽이 안 적었으면 공란으로 받아 처리한다.
- 확인 장치는 **화면의 확인 버튼 + 기록**. 슬랙 알림은 추후.
- `external_id`는 **화면에 드러내고, 보내 달라는 요청은 코드 밖**에서 한다(`docs/api/settlement-handoff/06_우리_external_id요청_슬랙_20260901.md`).

## 2. 범위

| 한다 | 하지 않는다 |
|---|---|
| 그쪽이 보낸 본문 원문 보관 | 우리가 내보내는 응답 보관(계좌번호·이메일이 쌓인다) |
| 차액을 눈에 띄게 하고 확인 기록 남기기 | 요청 금액 고치기(요청은 불변 — 금액 변경은 취소 후 재요청) |
| 그쪽이 보낸 값을 우리 값과 분리해 보여주기 | 예산·집계에 실지급액 반영(§9) |
| 호출 기록 유실 막기 | 슬랙 알림(추후) |
| 호출 기록 화면에서 찾을 수 있게 하기 | 호출 기록 보관 기간·페이지네이션(§9) |

**외부 API 계약은 바뀌지 않는다.** 그쪽이 보내는 것도, 우리가 내려주는 Item도 그대로다. 차액 확인은 우리 내부 상태이므로 `settlement` 객체에 넣지 않는다.

## 3. 데이터

마이그레이션 **046**(현재 045까지 있음). 새 표는 만들지 않는다 — 실지급액·지급 시각·메모·그쪽 상태는 이미 041이 `payment_request`에 넣어 뒀다.

```sql
-- 046
alter table external_api_log add column if not exists body text;   -- 그쪽이 보낸 본문 원문(파싱 전). 4KB 상한, 넘으면 잘라 저장
alter table payment_request add column if not exists diff_ack_at timestamptz;    -- 차액 확인 시각
alter table payment_request add column if not exists diff_ack_by_name text;      -- 확인한 사람 이름 스냅샷(cancelled_by_name 선례)
```

**`body`는 `jsonb`가 아니라 `text`다.** JSON이 깨져 400으로 거부된 본문이야말로 가장 보고 싶은 것인데 `jsonb`에는 들어가지 않는다. 화면에서 JSON으로 읽히면 줄을 맞춰 보여주고, 아니면 원문 그대로 보여준다.

확인한 사람은 이름 스냅샷만 남긴다(`member` 참조를 걸지 않는다) — 취소 기록(`cancelled_by_name`)과 같은 태도. 사유 칸은 만들지 않는다(§1 koo 결정).

## 4. 본문 기록 (그쪽 → 우리)

`recordExternalCallSafe`에 `body`를 추가하고, 상태 전송(POST) 라우트가 **파싱 전 원문 문자열**을 넘긴다.

| 경우 | 본문 저장 |
|---|---|
| 200 정상 적용 / `stale` | 저장 |
| **400 형식 오류** | **저장** — 지금은 "어느 필드가 틀렸다"만 남아 무엇을 보냈는지 알 수 없다 |
| 409 충돌 | 저장 |
| 404 없는 요청 | 저장 |
| **401 인증 실패** | **저장하지 않음** — 인증 안 된 호출의 본문은 아무 내용이나 올 수 있는 자리다. 본문을 읽지도 않는다(현재 동작 유지) |
| GET(목록·단건) | 해당 없음(본문 없음) |

- 상한 **4KB**. 넘으면 잘라 저장하고 화면에 잘림을 표시한다. 계약상 본문은 1KB를 넘을 일이 없다.
- 크기 영향은 미미하다 — 본문이 붙는 건 상태 전송뿐이고 건당 몇 개다.

## 5. 요청 내역 탭 — 펼침을 방향으로 두 블록

지금은 그쪽이 보낸 내용이 우리 데이터 목록 안에 `정산` **한 줄**로 섞여 있고, 그 한 줄에 상태·시각·실지급액·차액·메모를 전부 눌러 담는다(`settlementDetail`). 방향도 안 보이고 읽기도 어렵다.

### 5-1. 위 블록 — 우리가 보낸 요청 내용

기존 항목 그대로 두고 `정산` 줄만 뺀다. 한 곳만 덧붙인다:

```
증빙   [썸네일]   ← 정산에는 안 보내요 (우리 보관용)
```

`증빙`만 외부 Item에 없다. 이 한 줄이 없으면 "우리가 보낸 것"이라는 제목이 거짓이 된다.

### 5-2. 아래 블록 — 정산 프로덕트가 보낸 결과

```
─────────────────────────────────────────────────────────
정산 프로덕트가 보낸 결과                          8/31 20:02 받음

  처리 상태    지급 완료
  실지급액     30,000원   우리가 보낸 송금액 31,650원보다 1,650원 적어요
  지급 시각    8/31 19:59
  메모         —  정산 쪽이 안 적었어요
  그쪽 건 번호  —

  ⚠ 차액 확인이 필요해요                             [ 확인함 ]

  이 요청의 호출 기록 보기 →
─────────────────────────────────────────────────────────
```

확인 후 `⚠` 자리:

```
  차액 확인    확인함 · 박구건 · 9/1 14:20                    [ 확인 취소 ]
```

- `확인함` 옆 도움말: `정산 쪽 조정 금액을 확인했다는 표시예요 — 사유는 정산 쪽 메모에만 있어요.` (우리가 사유를 적는 자리라는 오해를 막는다)
- **메모가 공란이면 공란임을 사실대로 쓴다.** 확인은 그래도 된다.
- **`그쪽 건 번호 —`** 가 드러난다. 그쪽이 한 번도 안 보내고 있다는 사실이 보여야 요청할 근거가 된다.
- 차액이 없으면 `⚠` 줄을 **그리지 않는다**(거짓 어포던스 금지).
- 그쪽이 아무것도 안 보낸 요청은 이 블록이 `아직 정산 쪽에서 확인 전이에요` 한 줄로만 나온다(기존 문구 유지).
- **`이 요청의 호출 기록 보기`** 가 §4와 이어진다 — 메모가 덮어써져 사라져도 원문 이력을 볼 수 있다.

## 6. 차액 확인 상태

### 6-1. 차액의 기준은 `gross_krw`다 (기존 결함 수정)

| 칸 | 뜻 | ¥3,000 건 실제 값 |
|---|---|---|
| `amount_krw` | 수수료 **제외** 순액의 원화 | 30,000원 |
| `gross_krw` | **실제 송금액의 원화**(045 생성 컬럼, `amount_gross × 환율`) | 31,650원 |
| `paid_amount_krw` | 그쪽이 실제 지급한 원화 | **31,650원** |

그쪽이 지급한 값은 우리가 보낸 **실제 송금액**과 비교해야 한다. 그래서 **차액 = `paid_amount_krw` − `gross_krw`** 다.

지금 화면은 `paidText(r.amountKrw, r.paidAmountKrw)`로 `amount_krw`와 비교한다(`RequestRow.tsx:31`, `settlementDisplay.settlementDetail`). 그래서 실제로 **정확히 일치한** 8/31 지급 건이 화면에는 이렇게 나온다:

```
지금:  실지급 31,650원 (요청 30,000원, +1,650)   ← 틀림. 수수료 ¥165를 차액으로 오해
맞음:  실지급 31,650원                           ← 차액 0
```

**즉 지금까지 차액 사례는 0건이다.** 이 비교 기준을 고치는 것이 이 작업의 첫 항목이다 — 안 고치면 수수료가 붙은 모든 지급이 영구히 `차액 확인 필요`로 뜬다(운영 계정 대부분에 수수료가 붙는다).

`gross_krw`는 DB 생성 컬럼이라 항상 값이 있고 원본과 갈릴 수 없다. `grossKrw`는 이미 `PaymentRequestRow`에 `Number`로 들어와 있다.

### 6-2. 파생값 하나

`settlementDisplay.displayStatus`에 키를 하나 더한다 — 정산 상태 표시는 한 자리에서 나온다는 기존 원칙(파일 머리 주석)을 지킨다. 목록 배지·상태 필터·캠페인 표 배지가 전부 같은 값을 쓰므로 "한쪽은 지급 완료, 한쪽은 확인 필요" 같은 어긋남이 생기지 않는다.

| 조건 | 배지 | 톤 |
|---|---|---|
| `paid` + 차액(§6-1) ≠ 0 + 미확인 | `지급 완료 · 차액 확인 필요` | 노랑 |
| `paid` + 차액 ≠ 0 + 확인됨 | `지급 완료 8/31` | 초록 |
| `paid` + 차액 0 | `지급 완료 8/31` | 초록 |
| 취소된 요청 | `취소됨 …` | 회색 (차액 확인 안 뜬다) |

취소와 지급 완료가 겹치는 조합은 생기지 않는다 — 지급 완료 후 취소는 구조적으로 막혀 있고, 취소된 건에 지급 완료가 오면 409로 거부된다.

**판정에 필요한 입력이 늘어난다.** `StatusSource`에 `paidAmountKrw`·`grossKrw`·`diffAckAt`이 필요하고, 캠페인 표 배지(`campaignTaskStore.settlementByTaskIds`)의 조회에도 `paid_amount_krw`·`gross_krw`·`diff_ack_at`을 더해야 한다. 안 더하면 캠페인 표만 다른 값을 보게 된다.

### 6-3. 금액이 정정되면 확인이 풀린다

계약상 `paid → paid` 재전송으로 금액을 고칠 수 있다(계약 문서 §6 규칙 6). 30,000원을 확인해 뒀는데 28,000원으로 정정되면 **그 확인은 다른 금액에 대한 확인**이다.

→ `applyExternalStatus` 안에서, 적용 결과 `paid_amount_krw`가 이전 값과 다르면 `diff_ack_at`·`diff_ack_by_name`을 비운다. 화면 규칙이 아니라 **상태를 적용하는 코드에서 강제한다** — 사람이 잊으면 틀린 확인이 남고, 8/31 사고가 정확히 "손으로 만진 것이 어긋난" 경우였다.

정정으로 금액이 송금액(`gross_krw`)과 같아지면 차액이 사라지므로 확인 요구도 함께 사라진다.

### 6-4. 확인·확인 취소

- 로그인한 멤버 누구나 확인할 수 있고, **누구나 취소할 수 있다**(팀이 소수라 확인한 사람으로 묶을 이유가 없다). 취소하면 다시 `차액 확인 필요`가 된다.
- 확인·취소는 우리 내부 상태 변경이므로 `payment_request.updated_at`을 **건드리지 않는다.** 건드리면 그쪽 폴링에 무의미한 변경이 흘러간다.

### 6-5. 놓치지 않게 하는 장치 (알림 없이)

- 요청 내역 탭 상단에 한 줄: `차액 확인이 필요한 지급이 1건 있어요 [보기]` — 0건이면 줄 자체가 없다.
- 상태 필터(`STATUS_GROUP_OPTIONS`)에 `차액 확인 필요` 추가.

## 7. 호출 기록 유실 막기

### 7-1. 원인

현재 `recordExternalCallSafe`는 응답을 보낸 뒤 기록을 백그라운드로 던져놓고 기다리지 않는다(`void (async () => …)()`). 이 서버는 요청마다 뜨고 지므로, **응답을 반환한 순간 함수가 정지될 수 있고** 그러면 기록이 저장되기 전에 사라진다. 플랫폼에게 "이 뒷작업이 끝날 때까지 기다려 달라"고 말한 적이 없다.

8/31에 그쪽 커서(`14:19:10.791678`)를 받아 간 호출이 기록에 없었던 것의 가장 그럴듯한 설명이다.

그 밖의 원인: 기록 전용 풀(최대 2) 소진, DB 일시 오류, 마이그레이션 미적용, 킬스위치 `EXTERNAL_API_LOG=off`, 기능 배포 전(8/31 19:33 이전).

### 7-2. 고치는 방법

`next/server`의 `after()`로 감싼다. Next 16.2.10에 있고 라우트 핸들러에서 쓸 수 있으며, 문서에 "응답을 막지 않아야 하는 로깅·분석 작업"이 바로 이 용도로 적혀 있다. 응답이 실패한 경우에도 실행된다.

```
지금:  응답 보냄 → 기록을 던져놓음 → 함수가 멈추면 유실
바꿈:  응답 보냄 → 플랫폼이 기록이 끝날 때까지 함수를 살려둠 → 유실 없음
```

**응답을 막지 않는 성질은 그대로다.** 그쪽 호출은 지금과 똑같이 즉시 응답받는다.

추가로:
- **재시도 1회** — 저장 실패 시 짧게 한 번 더(풀 소진·일시 오류 완화).
- **실패를 매번 남긴다** — 지금은 최초 1회만 경고를 찍고 그 뒤로는 조용하다. 매번 오류로 남긴다.

### 7-3. 사후 복원은 불가능하다

기록이 빠진 뒤 그 내용을 되살릴 방법은 없다 — 그 순간의 본문·IP·시각은 우리 어디에도 없고 그쪽에 물어봐야 한다. 그래서 대응은 "미생성이 확인되면 보완"이 아니라 **"애초에 미생성이 안 생기게"** 뿐이다.

이걸 넣으면 화면 문구가 좁아진다:

```
전:  드물게 기록이 빠질 수 있어요 — 기록이 없다고 호출이 없었던 건 아니에요
후:  8/31 이전 호출은 기록 기능 배포 전이라 남아 있지 않아요
```

## 8. 호출 기록 탭 — 찾을 수 있게

현재 `listExternalLog(sql, 50)`로 **최근 50건 고정**이다. 8/31 사고를 빠르게 판정한 건 기록이 15건이었기 때문이다. 그쪽 폴링이 5분마다면 하루 288건이라 50건은 **약 4시간치**다. 그러면 본문을 남겨도 상태 전송 몇 건이 목록 폴링 수백 건 사이에 묻혀 화면 밖으로 밀려나고, §4의 가치가 사라진다.

- **필터 추가:** 방식(상태 전송만 / 가져가기만) · 결과(거부된 것만) · 요청별(`?tab=log&request=<id>` — §5-2 링크가 여기로 온다).
- **펼침 항목에 주어를 붙인다:** `보낸 상태값` → `정산 프로덕트가 보낸 상태`, 그리고 신규 `정산 프로덕트가 보낸 내용`(본문 원문). 항목 이름만 떼어 놓고 보면 방향이 헷갈린다.
- **커서를 사람 말로 푼다.** 목록 폴링 기록에는 요청 번호가 없어서(`3건`만 남음) "이 요청이 언제 넘어갔나"가 안 보인다. 추가 데이터 없이 문구로 풀린다:

```
지금:  요청 목록을 가져갔어요                    0건
바꿈:  8/31 23:19 이후 바뀐 것을 가져갔어요 — 새로 바뀐 게 없었어요
```

8/31에 커서를 손으로 디코드해 판정한 일을 화면이 대신한다.

## 9. 이번에 하지 않는 것 (경계)

- **실지급액 기준 집계.** 클라이언트 월 예산 소진은 캠페인 비용(단가) 기준으로 계산하고 `payment_request`를 보지 않는다. 30,000원이 지급되든 31,650원이 지급되든 예산 숫자는 바뀌지 않는다. 실지급 기준으로 맞추려면 어느 시점 금액을 정답으로 볼지·미지급 건은 어떻게 셀지를 새로 정해야 하는 별개 작업이다(`2026-09-01-krw-real-cost-design.md`도 같은 판단).

- **호출 기록 보관 기간·페이지네이션** — 목록 폴링 기록의 증가는 별도 문제. 이번에는 필터로 실사용을 해결한다.
- **그쪽에 메모 필수 요구** — koo 결정으로 넣지 않는다. 공란으로 받아 처리한다.
