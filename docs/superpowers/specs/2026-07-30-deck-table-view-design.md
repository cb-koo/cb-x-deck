# 덱 표 보기 — 지표 기반 훑기 + 내보내기 (설계)

2026-07-30.

**요청 출처.** 사내 슬랙 `#x-리서치-프로덕트` 스레드(2026-07-30 11:55, 심영훈): *"임베딩 방식 외에도 엑셀 표 형태로 정리되어 있어도 좋을 것 같아요. 지표 기반으로 조회수 상위 게시물 추려서 보거나 향후 데이터 분석 목적으로?"* 요청자가 **우선순위가 높지 않다고 명시**했다. 같은 스레드에서 모에카는 "콘텐츠 기획은 계속 노션에서 관리할 거라"고 했다 — 즉 최종 목적지는 이 앱이 아니라 노션·엑셀이다.

원문 문구의 "임베딩 방식"은 브리핑의 인용 카드를 가리킬 수도 있었으나, **덱 대상으로 확정**했다(사용자 결정).

**문제.** 덱은 X를 미러링한 카드 피드다. 카드는 한 건을 깊게 보기에는 좋지만 **여러 건을 지표로 비교**하기에는 나쁘다. 지금 지표 기반 훑기를 하려면 컬럼 정렬을 바꿔 카드를 위에서부터 눈으로 세는 방법뿐이고, 열이 여러 개면 열마다 따로 해야 한다. 그리고 수집한 데이터를 **앱 밖으로 빼낼 방법이 전혀 없다** — 내보내기 기능이 0건이다(v1 백로그의 "보관함 내보내기(마크다운 리포트)"는 대상도 형식도 다르고 미구현).

**해결.** 덱에 **표 보기 모드**를 둔다. 워크스페이스의 모든 열에 수집된 트윗을 한 표의 행으로 놓고, 지표로 정렬하고, 노션·엑셀로 빼낸다.

## 원칙

- **같은 데이터의 다른 표현이다.** 표는 새 데이터가 아니라 덱의 다른 보기다. 새 화면·새 사이드바 항목을 만들지 않는다.
- **보이는 칸 = 내보내는 칸.** 화면과 붙여넣기 결과가 다르면 사용자는 예측할 수 없다. (예외 하나는 §E.)
- **비교 가능해 보이는 숫자는 비교 가능해야 한다.** 표는 카드와 달리 숫자를 나란히 놓아 비교를 유도한다. 그래서 카드에서는 넘어갔던 지표 신선도 문제를 표에서는 다뤄야 한다(§E).
- **훑는 화면과 판단하는 화면을 섞지 않는다.** 표는 훑고 빼내는 곳, 저장·버림·번역 같은 판단 액션은 카드 모드에 남긴다.
- **컨트롤을 늘리지 않는다.** 사용자는 비개발 콘텐츠 기획 담당자다(`AGENTS.md`). 정렬로 해결되는 것을 필터 UI로 만들지 않는다.

## A. 진입과 전환

덱 상단 툴바(`+ 컬럼` 옆)에 `보기: [카드 | 표]` 토글을 둔다.

- 주소에 **`?view=table`** 을 남긴다. 새로고침·북마크·팀에 링크 공유로 표 상태가 유지된다.
- 표 모드에서도 열 자체(순서·설정·폭)는 건드리지 않는다. 카드로 돌아오면 그대로다.
- **표를 컬럼 안에 넣지 않는다.** 컬럼 폭은 280~720px로 제한돼 있어(`src/components/Column.tsx:96`) 표가 들어갈 수 없다. 표 모드는 덱 스트립 대신 전체 폭을 쓴다.

## B. 행 구성

- **행 = 이 워크스페이스의 모든 열에 수집된 트윗.** 열을 따로 고르지 않아도 전체가 기본이다.
- **같은 트윗이 여러 열에 걸리면 한 행으로 합친다.** `column_tweet`은 (열, 트윗) 쌍이므로(`migrations/001_init.sql:29-34`) 키워드 열 두 개가 같은 글을 잡으면 행이 둘로 늘어난다. `tweet_id`로 묶고 `열` 칸에 열 이름을 모두 적는다.
- **열 칩으로 좁힐 수 있다.** 기본 `전체`, 단일 선택(보관함의 멤버 필터와 같은 방식).
- **버림한 트윗은 항상 제외한다.** 버림은 워크스페이스 단위(`migrations/005_dismissed.sql:2-8`)라 표에서도 그대로 빠진다. 버림 목록 열람은 카드 모드의 `보기: 버림`에 남긴다 — 표에 보기 축을 하나 더 만들지 않는다.

## C. 칸 구성

**기본 8칸**: `열` · `계정` · `날짜` · `본문` · `조회` · `좋아요` · `RT` · `링크`

- `본문`은 2줄 말줄임. 전문은 카드 모드에서 본다.
- `링크`는 실제 링크(새 탭). 내보낼 때는 URL 문자열. 주소는 `tweetPermalink`(`src/lib/tweetLink.ts`)로 만든다 — 링크 복사 기능과 같은 정규형을 쓴다.

**`+ 칸 더보기`로 펼치는 6칸**: `답글` · `인용` · `북마크` · `팔로워` · `저장` · `기준`

- `저장` = 이 트윗을 저장한 멤버 이름들, 없으면 빈칸. 덱 카드의 멤버 이니셜 점과 **같은 출처**를 쓴다 — `candidate` + `member`를 워크스페이스로 스코프한 기존 서브쿼리(`src/lib/tweetStore.ts:118-120`)를 그대로 재사용한다. 팀이 이미 챙긴 글인지가 표에서 바로 보인다.
  - **`library_item`이 아니라 `candidate`를 쓴다.** 둘은 의도적으로 분리돼 있다(마이그레이션 012: `library_item`=팀 보관함 소속, `candidate`=개인 저장). 카드의 ★가 개인 저장이므로 표도 같아야 한다 — 표와 카드에서 같은 트윗의 저장 상태가 다르게 보이면 안 된다.
- `기준` = 그 트윗 지표를 마지막으로 가져온 시각(`tweet.last_fetched_at`). 근거는 §E.
- 펼친 상태는 **localStorage에 기억한다**(투어의 `tour-seen:` 방식과 같은 계층). 서버에 저장하지 않는다 — 개인 보기 취향이고 멤버·기기별로 달라도 무해하다.

펼치면 14칸이다. 기본을 8칸으로 접어두는 이유: 지표를 다 펼치면 `본문` 칸이 여지에 밀려 "어떤 글인지" 파악이 안 된다 — 표를 보는 첫 목적이 훼손된다.

## D. 정렬

- 칸 머리글 클릭으로 정렬. 활성 칸을 다시 누르면 방향이 뒤집힌다(덱 정렬 탭과 같은 규칙, `Column.tsx:275-287`).
- **접근성**: 진짜 `<table>`로 만들고 머리글은 `<th scope="col">`. 정렬 가능한 머리글은 안의 `<button>`으로 누르며, `<th>`에 **`aria-sort="ascending" | "descending" | "none"`** 을 준다. 스크린리더 사용자가 "지금 무엇으로 정렬돼 있는지"를 알 수 없으면 정렬 기능 자체가 없는 것과 같다(WCAG). 버튼 라벨은 덱 정렬 탭처럼 방향을 말로 붙인다 — `조회수 많은순 — 다시 누르면 정렬 순서가 바뀝니다`(`Column.tsx:33-35`의 `dirLabel` 방식 재사용).
- **지표 6종 전부 + 날짜**를 정렬할 수 있다. 지금 서버 정렬식에는 4종만 있다(`src/lib/tweetStore.ts:34-39` — views/date/bookmarks/retweets). **좋아요·답글·인용은 저장돼 있고 화면에도 나오는데 정렬이 안 된다.** "지표 기반으로 추리기"가 목적이므로 이 구멍을 메운다(정렬식에 3개 추가).
- 기본 정렬은 **조회수 많은순** — 요청 문구가 "조회수 상위 게시물 추려서"다.

## E. 지표 신선도 — 표라서 생기는 정직성 문제

지표는 실시간이 아니라 **각 트윗을 마지막으로 가져온 시점의 값**이다. 열을 새로고침한 시점이 트윗마다 다르므로 A행은 3일 전 조회수, B행은 오늘 조회수일 수 있다. 카드로 하나씩 볼 때는 드러나지 않지만, **표는 숫자를 나란히 놓아 "비교 가능한 값"이라는 신호를 준다.** 요청 목적이 "데이터 분석"이므로 이걸 방치하면 잘못된 결론으로 이어진다.

- `기준` 칸으로 행별 기준 시각을 볼 수 있게 한다.
- 표 상단에 한 줄: **"지표는 각 글을 마지막으로 가져온 시점 기준이에요 — 카드 보기에서 열을 새로고침하면 갱신됩니다"**
  - **"열을 새로고침하면"으로만 쓰면 죽은 안내가 된다.** 새로고침 버튼은 열 헤더에 있고(`Column.tsx:265`) 그건 카드 모드다. 표 모드 화면에는 누를 것이 없다. 안내는 **어디서 할 수 있는지까지** 말해야 한다.
  - 표 모드에 새로고침 버튼을 두지 않는 이유: 새로고침은 비용 유발 액션이라 열마다 금액 안내가 붙어 있고(`AGENTS.md` 원칙 6), 그 체계를 표에 다시 만들면 표가 판단·실행 화면이 된다(§원칙 "훑는 화면과 판단하는 화면을 섞지 않는다").
- **내보낼 때는 `기준` 칸을 항상 포함한다.** 화면에서 접어놨더라도 넣는다. §원칙의 "보이는 칸 = 내보내는 칸"의 **유일한 예외**이며, 근거는 분석 정직성이다 — 기준 시각 없는 지표 표는 스프레드시트에서 그냥 틀린 비교가 된다.

"저장 트윗 지표 일괄 재추적"은 v1 백로그에 있고 미구현이다. 그게 들어오면 이 문제는 줄어들지만, 없어지지는 않는다(재추적 시점도 일괄이 아닐 수 있음).

### 제거 경위 — `표 복사`(TSV 클립보드)

당초 근거는 "클립보드는 지금 보고 있는 것을 담는 도구, 파일은 전체 데이터를 담는 도구"로 범위를 다르게 두는 것까지
설계돼 있었다(지금 로드된 행 vs 조건에 맞는 전체 행). 구현해서 두 경로를 실제로 써본 뒤, 사용자가 클립보드 복사는
쓰지 않는다고 판단해 버튼·핸들러(`copyTable`)·직렬화 함수(`toTsv`)·전용 테스트를 모두 제거했다. CSV 저장으로
용도가 충분히 커버되고, 두 번째 내보내기 경로를 유지할 실사용 근거가 없었다는 것이 사용자가 밝힌 이유다.

### 범위 — CSV는 "이 데이터" 전체를 받는 도구

| | 범위 | 근거 |
|---|---|---|
| `CSV 저장` | **조건에 맞는 전체 행** (상한 5,000건) | 파일은 "이 데이터"를 받는 도구다. 1,240건 중 200건만 든 파일을 받고 전체라고 믿으면 분석 결론이 틀린다 — 요청의 명시적 목적이 "데이터 분석"이므로 여기서 로드된 행만 담으면 목적 미달이다 |

- **버튼 라벨에 건수를 박는다**: `CSV 저장 (전체 1,240건)`. 눌러서 뭘 받는지 누르기 전에 알아야 한다(§원칙 "행동 전 기대 설정", `AGENTS.md` 원칙 2).
- 완료 토스트에도 건수를 남긴다: `CSV 1,240줄을 저장했어요`.
- **상한 5,000건**을 두고, 넘으면 잘랐다는 사실을 말한다: `상위 5,000줄만 저장했어요 — 열 칩으로 범위를 좁혀보세요`. 조용히 자르면 전체를 받았다고 오해한다.
- CSV는 같은 쿼리를 `limit 5000`으로 다시 불러와, 화면에 로드된 행이 아니라 전체를 담는다.
- 칸은 **보이는 칸 + `기준`**.

### 값 표기 — 화면과 내보내기가 달라야 하는 곳

칸 목록은 화면과 내보내기가 같지만(§원칙), **값의 표기는 다르다.** 스프레드시트에서 계산·정렬되어야 하기 때문이다.

| 값 | 화면 | 내보내기 | 이유 |
|---|---|---|---|
| 지표 숫자 | `128,000` (`formatFull`) | `128000` | **개정 2026-07-31**: 원래 화면은 X식 축약(`128K`)이었는데, 사용자가 "DB에 원본이 있으면 전체 숫자로 보여달라"고 요청했다. 표는 숫자를 나란히 놓고 자리수를 눈으로 맞추는 화면이라 `23.7M`은 비교를 방해한다. **카드뷰는 X와 같아 보이는 것이 제품 가치이므로 `formatCount` 축약을 그대로 유지한다**(같은 요청에서 사용자가 표만 바꾸기로 결정). 내보내기는 콤마조차 없는 원값 — `128K`도 `128,000`도 엑셀에서 문자열이 되어 정렬·합계가 깨진다 |
| 날짜 | `2026-07-11` | `2026-07-11` | 카드의 `7월 2일`·`2시간 전` 상대 표기를 쓰지 않는다. 표는 정렬 축이고 스프레드시트는 날짜로 인식해야 한다 |
| 값 없음 | 빈칸 | 빈칸 | `0`으로 채우지 않는다. 지표는 `number \| null`이고(`src/lib/types.ts:50-56`) "0회"와 "모름"은 다르다 — 0을 넣으면 평균이 왜곡된다 |
| `열`·`저장` (여러 값) | 쉼표+공백 | 쉼표+공백 | 셀 하나에 담는다. 열마다 칸을 쪼개면 열 개수에 따라 표 모양이 바뀐다 |

이것이 "화면 그대로"의 예외처럼 보이지만, 사용자가 기대하는 것은 **같은 데이터**이지 같은 문자열이 아니다. 화면의 `128K`는 읽기 편하려고 줄인 표기이고, 엑셀에 필요한 것은 그 원래 값이다.

## G. 서버

**새 마이그레이션이 필요 없다.** 기존 테이블 조인만으로 된다.

```
column_tweet ct
  join deck_column dc on dc.id = ct.column_id and dc.workspace_id = $1   -- 워크스페이스 스코프
  join tweet t on t.tweet_id = ct.tweet_id
  where not exists (dismissed_tweet d where d.workspace_id = $1 and d.tweet_id = t.tweet_id)
  group by t.tweet_id                     -- 여러 열에 걸린 트윗을 한 행으로
  order by <지표식> <방향>, t.tweet_id     -- tie-break로 안정 정렬
  limit 200 offset $2
```

- `deck_column.workspace_id`는 not null이다(`migrations/002_workspace_member.sql:29-31`).
- 열 이름은 `array_agg(distinct dc.title)`로 모은다.
- **정렬은 서버 SQL이다.** 그래서 "조회수 많은순 200건"은 **전체에서의 진짜 상위 200건**이다 — 클라이언트가 200건만 받아서 그 안에서 정렬하는 게 아니다. 이게 이 기능이 쓸모 있으려면 반드시 지켜져야 하는 성질이다.
- 200건씩 `더보기`. 페이지 크기는 기존 상수를 따른다 — `PAGE_SIZE`(`src/lib/tweetStore.ts:96`)와 클라이언트 `PAGE`(`src/components/Column.tsx:114`)에 같은 값이 중복돼 있으니 표에서 세 번째 사본을 만들지 않는다.
- 새 API 라우트 하나. 기존 `/api/columns/[id]/tweets`는 열 단위라 재사용할 수 없다.

## G-2. 화면 4상태

표는 데이터 로딩 화면이므로 네 상태를 모두 설계한다(체크리스트 §G). **보관함에서 이미 같은 버그를 겪었다** — 로딩 중 '저장 없음'이 번쩍이고 에러가 빈 상태로 위장됐다(2026-07-25 수정). 표에서 되풀이하지 않는다.

| 상태 | 화면 |
|---|---|
| 로딩(첫 조회) | `불러오는 중…`. **빈 상태 문구를 먼저 보여주지 않는다** — 첫 로드 완료 플래그로 구분한다 |
| 에러 | `표를 불러오지 못했어요.` + `재시도` 버튼. 빈 상태로 위장하지 않는다 |
| 진짜 0건 (수집된 글이 없음) | `아직 수집된 글이 없어요 — 카드 보기에서 열을 새로고침하면 여기에 모입니다` (할 수 있는 곳을 말한다) |
| 필터 0건 (열 칩으로 좁혀서 0건) | `이 열에는 글이 없어요` + `전체 보기`로 되돌리는 버튼. 진짜 0건과 **다른 문구**여야 한다 — 같으면 사용자가 데이터가 없다고 오해한다 |

열이 아예 없는 워크스페이스는 진짜 0건과 같은 갈래로 처리하되 문구를 `아직 열이 없어요 — 카드 보기에서 열을 만들어보세요`로 바꾼다.

## H. 범위에서 제외

- **"조회수 N 이상" 같은 값 필터.** 상위부터 정렬하면 목적이 달성된다. 필터 UI는 컨트롤을 늘린다(Hick's Law). 실사용에서 필요가 확인되면 그때 추가한다.
- **표에서 저장·버림·번역.** 훑는 화면과 판단하는 화면을 섞지 않는다(§원칙).
- **칸 켜고 끄기 선택기.** `칸 더보기` 하나로 접었다 펴는 것까지만. 15칸 개별 토글은 리서치하러 온 사람에게 설정 화면을 내미는 일이 된다.
- **브리핑 안의 표.** 요청 문구가 가리킬 수 있었으나 덱으로 확정했다.
- **정렬·열 필터를 주소에 남기기.** `?view=table`만 남긴다. 표 상태 전체를 URL에 넣는 것은 이번 목적(훑고 빼내기)에 필요하지 않다.

## I. 검증

- 순수 함수 유닛 테스트 — 이 저장소에는 컴포넌트·라우트 테스트 하네스가 없으므로(`deckReorder.test.ts`·`toastState.test.ts`와 같은 방식) 테스트 가능한 부분을 순수 함수로 뽑는다:
  - 표 → CSV 직렬화: 머리글, RFC 4180 이스케이프(본문 줄바꿈·따옴표·쉼표), `기준` 칸 강제 포함, BOM, CRLF, 수식 주입 가드(`= + - @`로 시작하는 셀)
  - 여러 열에 걸린 트윗의 행 병합과 열 이름 집계
- SQL은 실 DB 대상 테스트가 이 저장소에 이미 있다(워크스페이스 CRUD 등). 교차 열 쿼리에 대해 **같은 트윗이 두 열에 있을 때 행이 하나로 나오는지**, **버림이 빠지는지**, **정렬이 전체 기준인지**(201번째보다 큰 값이 1페이지에 오는지), **다른 워크스페이스의 열이 섞이지 않는지**를 검사한다.
- 4상태(§G-2)는 코드 검증만 가능한 것이 섞여 있다 — 에러 상태는 실데이터로 트리거할 수 없다(같은 한계가 이전 UI 라운드에도 기록돼 있음). 로딩·진짜 0건·필터 0건은 실물로 확인한다.
- 화면 확인: 로컬 dev + 실제 로그인 세션. CSV가 엑셀에서 안 깨지는지(BOM)와 지표가 숫자로 인식되는지는 실제 엑셀에서만 확인된다 — **사용자 확인 항목**이다. (2026-07-31 확인 완료: 문제 없음)
- `npm test` 전체 통과, `tsc` 클린, 린트는 기준선 22개 + 표 컨테이너의 `set-state-in-effect` 2건 = 24개까지 허용(SSR 환경에서 effect가 정답이라 대안이 없음).
