# 원고 목록 규모 대응 설계 — 전량 로드 · 점진 렌더 · 칸반 재정의

작성일 2026-08-13

## 배경

`/generate`는 서버에서 **최근 50건만** 받아온 뒤(`page.tsx`의 `apiFetch('/api/drafts')`, 파라미터 없음 → `listDrafts`의 기본 `limit 50`), 검색·필터·기간·상태 탭 건수를 **전부 그 50건 안에서** 계산한다. 51번째부터는 이렇게 된다:

- 스크롤을 내려도 더 나올 게 없다 — 아예 볼 수 없다
- 검색해도 안 나온다(로드된 50건 안에서만 찾는다)
- 기간 필터로 과거를 지정해도 안 나온다
- **상태 탭 건수가 실제와 다르다** — "검수 대기 3"이 전체가 아니라 최근 50건 중 3건이다(AGENTS 원칙 4 위반)
- 클라이언트별로 보면 더 빨리 체감된다. 클라이언트가 5곳이면 각각 최근 10건 남짓만 보인다

오류가 나지 않고 조용히 나빠지는 종류의 고장이다. 사용자는 "예전 거가 없네?"만 보고 원인을 알 수 없다.

**측정값 (2026-08-13 프로덕션)**

| | |
|---|---|
| 현재 원고 | 44건 (2026-08-05 첫 원고, 8일간) |
| 생성 속도 | 하루 5.5건 = **월 165건** |
| 한 건의 무게 | JSON 2.2 KB, **gzip 0.46 KB** |
| 44건 전체 | JSON 97 KB, gzip 20 KB |
| 1000건이면 | JSON 2.2 MB, **gzip 450 KB** |

즉 **8일 뒤면 50건 벽에 닿고**, 데이터를 전부 가져오는 것 자체는 1000건(약 6개월치)까지 부담이 아니다.

## 확정 판단

### A. 병목은 통신이 아니라 렌더링이다 — 가져오는 건 전부, 그리는 건 조금씩

gzip 450 KB(1000건)는 이미지 한 장 수준이다. 반면 지금 카드 뷰는 걸러진 원고를 **하나도 빠짐없이 전부** `DraftCard`로 그리고, 표도 전 행을 그린다. 500건이면 카드 500장이 한 번에 DOM에 올라간다. 느려지는 건 통신이 아니라 이쪽이다.

그래서 **데이터 상한만 1000으로 올리고**(`listDrafts`의 기본 50 → 라우트에서 1000), 화면에 그리는 개수를 따로 제한한다.

이 한 줄로 지금 잘못된 것들이 전부 한꺼번에 바로잡힌다: 검색이 전체에서 찾고, 상태 탭 건수가 진짜 전체 건수가 되고, 기간 필터가 과거를 실제로 찾아내고, 클라이언트별 보기가 온전해진다. **검색·필터·정렬·집계 로직은 한 줄도 바꾸지 않는다.**

서버로 옮기지 않는 이유: 서버 필터링으로 가는 순간 SQL 검색 재작성(본문이 jsonb이고 한국어 대역은 앱에서 계산한 해시로 찾으므로 SQL에서 재현 불가), 커서 페이징, 정렬 이관, 칸반 열별 페이징이 줄줄이 따라온다. 같은 결과를 훨씬 적은 위험으로 얻을 수 있는데 지금 그 복잡도를 살 이유가 없다.

**재검토 시점**: 원고 1000건 도달(약 6개월 뒤) 또는 초기 로딩 지연이 체감될 때. 그때가 서버 페이지네이션을 제대로 만들 시점이다.

### B. 상한에 닿으면 정직하게 알린다

응답이 정확히 상한 개수로 오면 더 있을 수 있다는 뜻이다. 그때 목록 위에 한 줄을 띄운다: *"원고가 1000건을 넘어 최근 1000건만 보고 있어요."*

정확히 1000건일 때도 이 문구가 뜨지만 문장 자체는 참이라 해롭지 않다. 정확한 판정(`limit+1` 조회)을 하려면 응답을 배열에서 객체로 바꿔야 하고, 그러면 호출부가 전부 영향을 받는다 — 6개월 뒤 어차피 갈아엎을 곳에 지금 그 비용을 쓰지 않는다.

### C. 카드·표는 "더 보기", 남은 개수를 버튼에 적는다

처음 50개만 그리고 아래에 `더 보기 (남은 312건)`. 지금의 진짜 죄는 잘리는 것이 아니라 **잘렸다는 걸 아무도 모르는 것**이므로, 남은 개수를 버튼에 적는 것이 이 설계의 핵심이다.

필터·검색·기간·클라이언트가 바뀌면 표시 개수를 50으로 되돌린다. 새 조건에서 이전에 늘려둔 개수가 남아 있으면 "왜 이만큼 보이지"가 설명되지 않는다.

### D. 표 정렬은 자르기보다 먼저 일어나야 한다 — 정렬 상태를 페이지로 올린다

지금 정렬은 `DraftTable` 안에서 일어난다(`useState<TableSort>` + `sortDrafts`). 페이지에서 먼저 50개로 자르면 **"최근 50건을 클라이언트명으로 정렬"**이 되는데, 사용자는 그 화면을 **"전체를 클라이언트명으로 정렬한 상위 50"**으로 읽는다. 표시가 값을 배신한다.

정렬 상태(`TableSort`)를 페이지로 끌어올리고, 페이지가 `sortDrafts` → `slice` 순서로 처리해 그 결과만 `DraftTable`에 넘긴다. `DraftTable`은 정렬 머리글의 표시와 클릭 콜백만 담당한다. 선택 상태를 페이지가 소유하기로 한 것(2026-08-13 일괄 처리 설계 §화면)과 같은 방향이다.

### E. 선택의 "보이는 것"은 **그려진 것**이다

현재 표 전체 선택은 `visibleDrafts`(필터 결과 전체) 기준이다. 렌더만 50개로 자르면 헤더 체크박스가 **화면에 없는 262건까지 선택**하고, 그대로 일괄 삭제할 수 있다. 일괄 처리 설계가 세운 유일한 안전 규칙 — *"보이지 않는 것은 건드리지 않는다"* — 이 그대로 무력화된다.

따라서 `visibleIds`(전체 선택·`pruneSelection`의 입력)를 **잘라낸 뒤의 배열**에서 파생시킨다. "더 보기"로 늘리면 선택은 유지되고(덜어내기만 하는 `pruneSelection` 특성), 필터가 바뀌면 표시 개수가 50으로 리셋되며 선택도 함께 정리된다.

### F. 칸반은 "지금 할 일" 보드다

상태 축은 원래 진행도 라벨이다(`draftStatus.ts`): `draft → review → approved`는 아직 할 일이 남은 상태, `delivered`·`unused`는 결정이 끝난 종착 상태다. 종착 상태는 시간이 갈수록 **쌓이기만 한다**. 1년 뒤 '전달됨' 열의 900장을 스크롤할 일은 사실상 없고, 그건 검색·정렬을 가진 표 뷰가 할 일이다.

| 열 | 처리 |
|---|---|
| 초안 · 검수 대기 · 사용 확정 | 작업 공간. 상위 50장 + `더 보기 (+N)` |
| 전달됨 · 미사용 | 최근 10장. 아래에 **`전달된 원고 302건 전체 보기`** 버튼 — 누르면 표 뷰로 전환하며 그 상태 필터가 걸린다 |

"전체는 표에서 보세요"라는 **안내문이 아니라 실제로 데려가는 버튼**이어야 한다. 말만 하고 사용자가 직접 뷰를 바꾸고 필터를 걸게 하면 거짓 어포던스다.

열 머리의 건수는 **항상 전체 기준**이다. 10장만 그려도 "전달됨 302"는 진짜 302다.

### G. 열마다 고정 높이와 자체 스크롤

지금 칸반 열에는 높이 제한이 없어서 **가장 긴 열이 페이지 전체를 끌고 늘어난다.** 한 열만 길어져도 페이지가 끝없이 길어지고 다른 열은 위쪽에만 붙어 있다. 실제 칸반 도구가 모두 열 단위로 스크롤하는 것과 같은 이유다.

### H. 방금 옮긴 카드는 그 열 맨 위에 고정한다

`groupByStatus`는 열 안에서 최신순으로 정렬한다. 열마다 상위 N만 그리면, **3개월 된 원고를 '전달됨'으로 드래그하는 순간 그 카드는 200번째쯤으로 정렬돼 화면에서 사라진다.** 사용자에겐 "옮겼는데 없어졌다"이다.

드롭한 카드의 id를 세션 동안 기억해 해당 열의 맨 앞에 고정하고, 옅은 표식(`방금 옮김`)을 단다. 실제 칸반 도구들이 드롭한 자리에 카드를 남겨두는 것과 같은 처리다. 페이지를 새로 고치면 사라지는 세션 한정 상태다(서버에 저장할 성질이 아니다).

### I. 폴링은 전량을 가져오지 않는다

생성 기다리기를 취소하면 5초마다 최대 2분(24회) `/api/drafts`를 통째로 다시 받는다(`page.tsx`의 `cancelGenerate`). 상한이 1000이 되면 취소 한 번에 수 MB를 주고받는다.

폴링이 찾는 것은 **방금 만들어진 것뿐**이고 새 원고는 항상 최신순 맨 앞에 온다(시안은 최대 5개). `/api/drafts?limit=20`이면 충분하다. 라우트에 `limit` 파라미터를 받되 서버에서 상한을 걸어 임의의 큰 값이 들어오지 않게 한다.

### J. 사람이 붙인 제목이 검색에 걸리지 않는다

`searchDrafts`는 자동 제목(`koTitle`)·한국어 대역·본문·방향성을 뒤지지만 **사람이 붙인 `title`은 빠져 있다**(2026-08-13 제목 기능에서 누락). 이름을 붙여놓고 그 이름으로 못 찾는 상태다. 검색 대상에 추가한다.

## 화면

**목록 위 안내** — 상한에 닿았을 때만: `원고가 1000건을 넘어 최근 1000건만 보고 있어요`

**카드·표 하단** — 남은 것이 있을 때만:
```
        더 보기 (남은 312건)
```

**칸반 열**
```
● 전달됨  302                    ← 건수는 항상 전체 기준
┌──────────────┐
│ [카드]        │  ← 최근 10장, 열 안에서 스크롤
│ [카드]        │
│ …            │
├──────────────┤
│ 전달된 원고 302건 전체 보기 →  │  ← 표 뷰로 전환 + 상태 필터 적용
└──────────────┘
```

진행 상태 열은 같은 모양이되 상위 50장 + `더 보기 (+N)`.

## 구현 순서

1. 라우트 `GET /api/drafts`에 `limit` 파라미터(기본 1000, 상한 1000) — 폴링은 20으로 호출
2. 표시 개수 상태(`shownCount`)와 조건 변경 시 리셋 + `visibleIds`를 잘라낸 배열에서 파생
3. 표 정렬 상태를 페이지로 리프팅 — 정렬 후 자르기
4. 카드·표 `더 보기` 버튼, 상한 도달 안내
5. 칸반 — 열 스크롤, 진행/종착 분리, 종착 열의 표 이동 버튼
6. 칸반 — 방금 옮긴 카드 상단 고정
7. `searchDrafts`에 `title` 추가

## 검증

- **순수 함수 단위 테스트**(`tsx`, 수초): `searchDrafts`의 `title` 검색, 표시 개수 계산(남은 건수·리셋 조건), 칸반 열 분류(진행/종착)와 열별 상한, 고정 카드가 정렬 앞에 오는지
- **실 DB 테스트**: `listDrafts`의 `limit` 경계
- **라우트·컴포넌트 하네스 없음** — 화면 확인은 로컬 dev 서버에서 사용자가 직접
- **린트 기준선 24개**를 넘기지 않는다

## 열린 항목

- 서버 페이지네이션(커서 + 서버 검색·필터·정렬)은 원고 1000건 도달 시 재검토. 그때 칸반 열별 페이징도 함께 다뤄야 한다.
- 공유 링크(`/generate?draft=<id>`)는 이 작업 다음. 링크로 들어온 원고가 로드된 목록에 없을 때의 단건 조회는 이 설계와 무관하게 여전히 필요하다.
