## 2. 왜 이 방식을 골랐나

명세 §6에 이렇게 적어 보냈다:

> `category.code` — 분류 옵션의 안정 키(예 `promo-rt`, `fee`, `info-post`). **사용자가 추가한 옵션은
> uuid 문자열. 옵션은 삭제되지 않고 숨김만 되므로 코드는 항상 유효하다.**

처음에는 기존 코드의 이름만 바꾸거나 코드 자체를 새로 짜는 안을 검토했는데, 둘 다 그쪽 부담이 있었다.
**새로 추가 + 기존 숨김**은 위 문장이 이미 약속한 동작 그대로라 **협의 없이 진행할 수 있다.**
새 코드가 uuid인 것도 명세에 적힌 그대로다.

부수 효과로 옛 코드(`promo-rt` 등)와 뜻이 어긋나는 문제도 사라진다 — 옛 코드는 옛 기록에만 남고,
새 기록은 새 코드로 간다.

## 3. 그쪽에 달라지는 것 / 그대로인 것

**달라지는 것**
- 앞으로 오는 요청의 `category.code`가 **uuid 문자열**이 된다(위 4개).
- `category.label` 문구가 새 이름으로 바뀐다.

**그대로인 것**
- `task_type`(`post`/`quoteRt`/`rt`/`visit`) — 분류와 별개 축. **작업 유형 기준 매핑은 계속 유효하다.**
- 식별자 전부: `request_id` · `task_id` · `clinic.id` · `influencer.id`
- 금액·통화·수수료 구조
- **과거 기록의 옛 코드는 계속 유효하다** — 숨김이지 삭제가 아니다.
- 분류는 요청 생성 시점 스냅샷이라 **이미 보낸 요청의 `category`는 바뀌지 않는다.**

## 5. 보낼 문안 (슬랙)

> 아래만 떼어 붙인다.

저희 정산 **분류 체계를 개편**했습니다(9/11 적용). 그쪽에서 바꾸실 것은 없고, 참고로만 알려드립니다.

*무엇이 바뀌었나*
분류 선택지를 3개 → 4개로 정리했습니다. 가장 큰 변화는 **인용RT가 RT 묶음에서 게시물 묶음으로 이동**한 것입니다.

• `X 콘텐츠 게시 및 인용 RT` — 투고·인용RT
• `X 2차 바이럴 작업 (RT, 댓글)` — RT
• `X 방문형 협찬 원고` — 방문협찬
• `X 방문형 협찬 기타 비용` — (신설)

*그쪽에 달라지는 것*
• 앞으로 오는 요청의 `category.code`가 **uuid 문자열**이 됩니다. 명세 §6에 "사용자가 추가한 옵션은 uuid 문자열"로 적어 둔 그대로입니다.
• `category.label` 문구가 위 이름으로 바뀝니다.

*그대로인 것*
• **기존 코드(`promo-rt`·`fee`·`info-post`)는 삭제하지 않고 숨김 처리**했습니다 — 과거 기록의 코드는 계속 유효합니다.
• `task_type`(`post`/`quoteRt`/`rt`/`visit`)은 그대로입니다. **작업 유형 기준으로 매핑하고 계시다면 아무 영향이 없습니다.**
• 식별자(`request_id`·`task_id`·`clinic.id`·`influencer.id`)와 금액 구조도 그대로입니다.
• 분류는 요청 시점 스냅샷이라 이미 보내드린 요청의 분류는 바뀌지 않습니다.

*하나 여쭤볼 것*
`category.label` 문구를 지금은 `X 콘텐츠 게시 및 인용 RT` 형태로 두었는데, 기존에는 `마케팅비 > X(트위터) …` 접두어가 붙어 있었습니다. 그쪽 계정과목과 맞물리는 문구라면 접두어를 되살리겠습니다 — 어느 쪽이 편하신지 알려주세요.
