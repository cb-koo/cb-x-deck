# X 업로드 현황 — 기획 (2026-10-20, 초안)

> 상태: 화면 시안 확정(koo 10-20, 시안 6) · 방향 확정(koo 10-20) · 1차 구현 완료(담당자 표시는 1차에서 뺌) · 브랜치 `cb-koo/owned-channels`.
> 시안: `~/claude-outputs/owned-channels/x-운영현황-시안6-20261020.html` (1~5는 거쳐 온 안).

## 0. 결정 (koo 10-20)

- **목적: 우리가 클라이언트에게 약속한 업로드 횟수를 지키고 있는지 관리·감독한다.** 개설 파악이 아니라 개설 후 운영이다. 계정은 우리가 운영을 맡은 계정이고, 약속은 '주 N회'다. 성장(팔로워)은 있으면 좋은 부가 정보다.
- **판정 기준은 "그 주에 올렸는가"다.** 올린 뒤 지운 글도 그 주에 올린 것으로 센다. 지우는 데는 실수 정정 같은 이유가 있고, 업로드 약속은 올린 시점에 지켜진 것이다(koo 10-20). 지운 글은 '지워짐' 표시만 붙여 감독자가 알 수 있게 한다(§4-3).
- **지난 주 판정은 바뀌지 않는다.** 글은 쌓이기만 하고(지워도 남는다) 약속 횟수는 주마다 그때 값으로 남긴다(§3). 몇 달 뒤에 봐도 그 주 기록이 같다.
- **X부터 만든다.** 다른 채널(Instagram·LINE 등)은 같은 틀에 하나씩 붙인다. 데이터 이름은 채널을 가리지 않게 짓는다(§3).
- **셀 글 = 새 글과 인용.** 단순 RT와 답글은 횟수에서 뺀다(목록에는 '제외'로 보인다).
- **X 계정은 덱에서 입력한다.** monthly-report 온보딩에 받은 계정이 있으면 채우기를 제안한다.
- **약속 횟수는 클라이언트(채널)마다 '주 N회'.** 비우면 점검하지 않는다. 화면 용어는 '약속'으로 쓴다(우리가 한 약속이라는 뜻이 드러나게).
- **주 = 월~일, 한국 시간.** 일본 시간과 같아 주 경계가 어긋나지 않는다.
- **확인은 매일 아침 7시 자동 + 화면의 ↻(직접 누를 때만).** 주 1회 확인이면 '이번 주' 패널이 늘 비어 있다. 비용은 10곳 기준 한 달 약 900원이다.
- **최상단은 이번 주만, 그 아래 지난 8주 흐름.** 이번 주는 카드가 아니라 아직 못 채운 곳만 한 줄씩 보여 준다. 클라이언트가 늘어도 목록 길이는 "아직 못 채운 곳 수"다.
- **화면 문구에 `·` 구분자를 쓰지 않는다.** 날짜는 `9/26(25일 전)`, 나열은 쉼표로 쓴다.

## 1. 무엇을 하나

운영 책임자와 담당자가 월요일 아침이나 주 중간에 열어서 답을 얻는 화면이다.

- 이번 주 약속을 아직 못 채운 계정은 어디인가? 그중 지난주에도 빠진 곳(먼저 챙길 곳)은?
- 지난 몇 주 동안 약속을 지켰나, 몇 주째 빠지고 있나?
- (부가) 팔로워가 늘고 있나?

글은 덱 밖(X나 예약 도구)에서 올린다. 그래서 X에서 그 계정의 글을 직접 읽어 와서 센다. 사람이 '올렸어요'를 누르는 방식이 아니라 X에 실제로 올라간 것을 기준으로 하므로 감독 기록으로 쓸 수 있다.

## 2. 화면

### 2-1. `/channels` — 사이드바 '캠페인 운영' 묶음, '인플루언서' 다음 'X 업로드 현황'

주소는 채널을 가리지 않는 이름으로 둔다. 다른 채널이 붙으면 메뉴 이름을 '채널 업로드 현황'으로 바꾸고, 표에 채널 칸을 더한다.

연회색 바닥 위 흰 패널 두 장(캠페인 상세 관례, `ui.tsx` PANEL)이다.

```
X 업로드 현황
클라이언트에게 약속한 횟수만큼 X에 글(새 글, 인용)을 올렸는지 봐요. RT와 답글은 세지 않아요.

┌ 이번 주                                              5일 남음 ┐
│ 10/20(월) ~ 26(일)                      오늘 07:00에 확인했어요 ↻ │
│ 2 / 6곳 채웠어요                                                 │
│ ██████░░░░░░░░░░░░░                                            │
│ 아직 못 채운 곳 4곳   이번 주   상황                  마지막 글     │
│ 더스퀘어 @…          0 / 1회   3주째 못 채우는 중 — …  9/26(25일 전)  X에서 보기 ↗ │
│ 백수약국 @…          0 / 1회   지난주 못 채움 — …      10/11(10일 전) X에서 보기 ↗ │
│ 가은치유한의원 @…     0 / 1회   아직                   10/16(5일 전)  X에서 보기 ↗ │
│ 마인드클리닉 @…       1 / 2회   1번 더                 10/20(어제)    X에서 보기 ↗ │
│ ✓ 채운 곳 2곳  연세바른한의원, 브릿지피부과                   펼치기 ▾ │
└──────────────────────────────────────────────────────────────┘
┌ 지난 8주                                                       ┐
│ 칸 숫자는 그 주에 올린 글 수예요. 줄을 누르면 게시물과 팔로워가 보여요.    │
│ 클라이언트  약속  │ 8/25 9/1 … 10/6 지난주 │ 요약                    │
│ 더스퀘어   주 1회 │  1    1  …  0    0   │ 3주 연속 못 채움          │
└──────────────────────────────────────────────────────────────┘
```

**이번 주 패널**
- 머리: 기간, 남은 날(오늘 포함, 일요일이면 "오늘까지"), 마지막 확인 시각, ↻.
  - ↻는 캠페인 상세 성과 카드의 ↻와 같은 모양이다. 누르면 점검 대상 전부를 지금 다시 받는다. 도는 동안 아이콘이 돈다.
  - 마지막 확인 시각 = 전 계정 중 가장 오래된 성공 시각. 실패한 계정이 있으면 그 줄에 따로 표시한다(§5).
- 큰 숫자: `채운 곳 / 점검 대상 수` + 검은 진행 막대(cardStyles BIG·COMP·BAR).
- **아직 못 채운 곳**(이번 주 센 글 < 약속) 한 줄씩. 칸: 클라이언트(+@핸들) · 이번 주(`센 수 / 약속회`) · 상황 · 마지막 글 · X에서 보기 ↗.
  - 상황 문구:
    - 지난주까지 연속 k주 못 채움(k ≥ 2): **주황** "k주째 못 채우는 중 — 이번 주 꼭 챙겨요"
    - 지난주만 못 채움: **주황** "지난주 못 채움 — 2주 연속이 될 수 있어요"
    - 그 밖에, 0회면 "아직", 일부면 "n번 더"
  - 주황 줄의 칩도 주황, 나머지 칩은 회색이다. **이번 주에는 빨강을 쓰지 않는다** — 주가 끝나기 전엔 실패가 아니다.
  - 정렬: 연속 못 채운 주 많은 순 → 남은 횟수 많은 순 → 마지막 글 오래된 순.
  - 마지막 글: 셀 글(새 글·인용) 기준 날짜와 상대 날짜, `9/26(25일 전)` / `10/20(어제)` / `10/21(오늘)`. 글이 없으면 "기록 없음".
  - X에서 보기 ↗: `https://x.com/{handle}` 새 탭.
- **채운 곳**은 한 줄로 접는다: `✓ 채운 곳 n곳  이름, 이름, …` + 펼치기 ▾. 펼치면 같은 칸 모양의 줄(상황 = "✓ 채웠어요", 칩 초록).
- 모두 채웠으면 목록 대신 "이번 주 모두 채웠어요 ✓"만 보인다.

**지난 8주 패널**
- 줄 = 점검 대상 채널, 칸 = 이번 주를 뺀 지난 8주(왼쪽이 과거, 맨 오른쪽 '지난주'는 머리 글자만 진하게).
- 칸 = 그 주에 센 글 수. 그 주 약속 이상이면 초록, 미만이면 빨강, 기록 시작 전이면 `—`(§4-4).
- 요약(맨 오른쪽 한 줄, UX 원칙 3):
  - 지난주까지 연속 못 채움 k ≥ 2: 빨강 "k주 연속 못 채움"
  - 8주 모두 채움: "8주 모두 채움"
  - 기록이 8주보다 짧고 모두 채움: "시작 후 n주 모두 채움"
  - 그 밖: "8주 중 n주 채움"(기록이 짧으면 "n주 중 m주 채움")
- 정렬: 지난주 못 채운 곳 → 연속 못 채운 주 많은 순 → 이름순.
- 범례: 채움 · 못 채움 · `—` 기록 시작 전.

**줄을 누르면 — 오른쪽 패널(시안 1의 패널 모양)**
- 머리: 클라이언트 이름, @핸들 ↗, "약속 주 1회" + 약속 바꾸기(클라이언트 설정으로 이동).
- 팔로워: 지난 8주 주별 막대(그 주 마지막 기록값) + 해석 한 줄 "8주 동안 +412명(5,518 → 5,930), 주 평균 +52명이에요". 감소면 "줄고 있어요". 기록이 2주 미만이면 "팔로워 추이는 2주 뒤부터 보여요".
- 주차별 게시물: 이번 주부터 최근 순. 주 머리에 `센 수 / 그 주 약속회` + 채움/못 채움. 글 한 줄 = 종류 칩(새 글 / 인용 / RT 제외 / 답글 제외) · 본문 두 줄 · 날짜. 누르면 X 원문. 지운 글은 같은 줄에 '지워짐' 표시(§4-3).

**약속이 없는 계정·계정이 없는 클라이언트**는 이 화면에 줄로 나오지 않는다. 지난 8주 패널 아래에 한 줄만: "약속 횟수가 없는 계정 n곳은 여기 안 보여요 — 클라이언트 설정에서 정할 수 있어요 [클라이언트로 →]".

**빈 상태**: 점검 대상이 0곳이면 "아직 X 계정과 업로드 약속을 정한 클라이언트가 없어요 — 클라이언트 설정에서 정하면 다음 날 아침부터 여기에 모여요 [클라이언트로 →]". 불러오기 실패는 빈 상태로 위장하지 않는다("불러오지 못했어요 [다시 시도]", 인플루언서 성과 관례).

### 2-2. 클라이언트 상세 › 기본 정보 — 칸 두 개

```
X 계정 선택
우리가 운영을 맡은 X 계정이에요. 매일 아침 이 계정의 글을 세요.
[ @yonsei_bareun            ]
✓ 연세바른한의원 · 팔로워 5,930          ← 저장 때 확인한 결과
온보딩에서 받은 계정이 있어요: @yonsei_bareun [채우기]   ← 칸이 비었고 온보딩 값이 있을 때만

업로드 약속
클라이언트에게 한 주(월~일)에 새 글이나 인용을 몇 번 올리기로 했는지예요. '약속 없음'이면 점검하지 않아요.
[ 주 1회 ▾ ]   (약속 없음 / 주 1회 / 주 2회 / 주 3회 / 주 5회 / 주 7회)
```

- 핸들 입력은 `@` 있든 없든, `https://x.com/handle` 주소를 붙여 넣어도 받는다. 저장 값은 `@` 없는 소문자 비교 키 + 원래 표기.
- **저장할 때 계정을 확인한다**(X 호출 1번). 없으면 저장하지 않고 "X에서 @… 계정을 찾지 못했어요" — 틀린 핸들로 매일 0을 세는 것을 막는다.
- 저장되면 **지난 8주 글을 바로 받아 온다**(§4-2). 페이지에 들어가면 첫날부터 흐름이 보인다.
- 핸들을 다른 계정으로 바꾸면 이전 계정의 기록은 지운다(다른 계정 글이 섞이지 않게). 저장 전에 "이전 계정 기록이 지워져요" 확인을 한 번 거친다.
- 칸을 비우면 채널 연결을 끊는다(기록도 지움, 같은 확인).
- 약속 횟수를 바꾸면 **이번 주부터** 새 값으로 판정한다. 지난 주들은 그때 약속 그대로다(§3 `owned_channel_week`). 저장 옆에 "이번 주부터 주 2회로 판정해요" 한 줄.
- 기본 정보 패널 바로 아래 'X 업로드' 패널로 둔다(저장할 때 X 확인·기록 삭제 확인이 있어 저장 버튼을 따로 둔다). 미저장 경고 레지스트리에는 등록한다 — '저장하고 이동'은 기록이 지워지는 저장이면 멈추고 확인을 받는다.

## 3. 데이터 (마이그레이션 `081_owned_channel.sql`, 추가만)

```sql
-- 클라이언트가 운영하는 채널 계정. 지금은 X만, 채널이 늘면 같은 표에 줄이 는다.
create table if not exists owned_channel (
  id uuid primary key default gen_random_uuid(),
  client_id uuid not null references client(id) on delete cascade,
  channel text not null check (channel in ('x')),
  handle text not null,                 -- 표기 그대로(@ 없음)
  account_id text,                      -- X 숫자 id(핸들이 바뀌어도 같은 계정을 따라간다)
  account_created_at timestamptz,       -- 계정 개설일(그 전 주는 '—', §4-4)
  weekly_target int check (weekly_target between 1 and 14),  -- 지금 약속. null = 점검 안 함
  last_collected_at timestamptz,        -- 마지막 성공
  last_error text,                      -- 마지막 실패 사유(성공하면 null)
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (client_id, channel)
);

-- 읽어 온 글. 쌓이기만 한다 — X에서 지워져도 줄은 남고 deleted_at만 찍힌다. 횟수에는 그대로 들어간다(§4-3).
create table if not exists owned_post (
  id uuid primary key default gen_random_uuid(),
  channel_id uuid not null references owned_channel(id) on delete cascade,
  post_id text not null,
  kind text not null check (kind in ('original', 'quote', 'retweet', 'reply')),
  text text not null default '',
  posted_at timestamptz not null,
  deleted_at timestamptz,               -- X에서 지워진 것을 확인한 때(표시용). 다시 보이면 null
  created_at timestamptz not null default now(),
  unique (channel_id, post_id)
);
create index if not exists owned_post_channel_time on owned_post (channel_id, posted_at desc);

-- 주마다 그 주의 약속. 주의 첫 수집(또는 약속 저장) 때 한 줄 생기고, 그 주 안에서 약속을 바꾸면 이 줄도 바뀐다.
-- 주가 끝나면 손대지 않는다 — 지난 주 판정이 나중 약속 변경에 흔들리지 않게.
create table if not exists owned_channel_week (
  channel_id uuid not null references owned_channel(id) on delete cascade,
  week_start date not null,             -- 그 주 월요일(한국)
  target int not null,
  primary key (channel_id, week_start)
);

-- 팔로워 기록. 하루 한 줄(한국 날짜), ↻로 다시 받으면 그날 줄을 덮는다.
create table if not exists owned_channel_snapshot (
  channel_id uuid not null references owned_channel(id) on delete cascade,
  captured_on date not null,
  followers int not null,
  captured_at timestamptz not null default now(),
  primary key (channel_id, captured_on)
);
```

- 채널이 늘 때 `channel` 체크를 넓히는 건 옛 값을 거부하지 않으므로 1번 머지로 된다(AGENTS.md 표 '제약 추가'의 예외 아님).
- **주별 횟수는 저장하지 않고 글에서 센다.** 글이 지워져도 남으므로 센 값이 줄지 않는다. 바뀔 수 있는 건 약속뿐이라 약속만 주마다 남긴다.
- 어떤 주에 줄이 없으면 가장 가까운 앞 주의 약속, 앞 주가 없으면 가장 가까운 뒤 주의 약속을 쓴다. 그래서 등록 전 8주는 따로 줄을 만들지 않아도 등록 주의 약속으로 판정된다(그 전 약속은 모르므로).
- `tracked_post`(콘텐츠 성과)는 쓰지 않는다. 그 표는 캠페인 성과 화면들이 읽어서, 클리닉 계정 글이 섞이면 성과 숫자가 틀어진다.
- monthly-report 온보딩 값은 **읽기만** 한다(ADR 0008과 같은 방식, `read only` 트랜잭션, `report` 스키마가 없으면 제안 없음).
  - 경로: `report.clinic.client_id = client.id` → `report.onboarding.clinic_id` → `channel_accounts->'x'`의 `accountId` 또는 `url`.
  - 읽는 칸이 늘었으므로 ADR 0008의 '결과'에 `report.onboarding(clinic_id, channel_accounts)`를 더하고 monthly-report 쪽에 알린다.

## 4. 수집

### 4-1. 언제
- **매일 07:00(한국 시간)** — pg_cron + pg_net이 `POST /api/channels/collect`를 부른다(`scripts/owned-channels-cron.sql`, auto-measure와 같은 구조, 환경별로 한 번 손으로 실행). 비밀키는 성과 자동 측정·클리닉 지도와 같은 `MEASURE_CRON_SECRET`(Vault `measure_cron_secret`)을 쓴다 — 새 환경변수가 없다. 미설정이면 전부 거부.
- **↻** — 로그인한 팀원이 `POST /api/channels/refresh`. 같은 수집을 점검 대상 전부에. 연속으로 눌러도 1분 안에 다시 누르면 무시한다.
- **계정 저장 직후** — 그 채널 하나만, 8주치.

### 4-2. 무엇을
채널 하나당:
1. `getUserInfo(handle)` → 팔로워, 숫자 id. id가 저장값과 다르면(핸들을 다른 사람이 가져감) 실패로 처리하고 기록하지 않는다. 오늘 날짜 스냅샷을 쓴다(upsert).
2. `getUserTweets(id)`를 넘기며 **지난주 월요일 00:00(한국)** 보다 오래된 글이 나올 때까지 읽는다(첫 수집은 8주 전 월요일까지). 고정 글은 시간 순서에서 뺀다(`makeGetxapiTweetSource`의 처리 재사용). 쪽 수 상한 10.
3. 글 종류: `retweeted_tweet` 있음 → retweet / `inReplyToId` 있음 → reply / `quoted_tweet` 있음 → quote / 그 밖 → original. 스레드의 이어지는 글(자기 글에 단 답글)도 reply라 따로 세지 않는다 — 스레드 하나 = 1회.
4. `owned_post`에 넣는다(있으면 그대로).
5. 지운 글 표시(§4-3).
6. 이번 주 `owned_channel_week` 줄이 없으면 지금 약속으로 만든다.
7. 성공이면 `last_collected_at = now(), last_error = null`, 실패면 `last_error`만.

- `/twitter/user/tweets`는 스레드 이어 쓰기(본인 답글, `inReplyToId`·`isReply`)를 함께 돌려준다(실호출 확인 10-20). 본문은 `&amp;` 같은 HTML 표기로 와서 저장 전에 푼다.
- 지난주 월요일부터 다시 읽는 이유: 월요일 아침 실행이 실패해도 화요일 실행이 지난주를 채운다.
- 비용 라벨: `usageFeatures`에 `channels.collect` = 'X 업로드 현황'. 한 계정 하루 보통 2번 호출.
- 한 번에 45초 안에서 끝낸다. 남은 계정은 다음 실행으로(지금 규모 10곳은 한 번에 끝난다).

### 4-3. 지운 글

**원칙: 지운 글도 그 주에 올린 글로 센다.** 이 기능은 우리가 약속한 업로드를 했는지를 본다. 지우는 데는 실수 정정이나 클라이언트 요청 같은 이유가 있고, 올린 시점에 업로드는 이뤄졌다. 횟수와 판정은 지우기와 무관하다.

**그래도 표시는 한다.** 감독자가 "이 주는 1회 채웠는데 그 글이 지금은 없다"를 알아야 이유를 물어볼 수 있다.

- 표시만 하므로 확인은 가볍게 한다. 매일 다시 읽는 범위(이번 주·지난주)에서 기록엔 있는데 목록에 없는 글만 `getTweetDetail`로 한 번 더 보고, '없음'(400/404)이면 `deleted_at`을 찍는다. 다시 보이면 지운다.
- 목록을 지난주 월요일까지 다 읽지 못한 날은 확인을 건너뛴다(잘못된 '지워짐' 표시 방지). 고정 글은 목록에 있는 것으로 친다.
- 지난주보다 오래된 글은 확인하지 않는다. 표시가 판정에 영향이 없어서 굳이 호출을 쓰지 않는다.

**화면:**
- 횟수(칩·칸·요약)는 지운 글을 포함한다.
- 오른쪽 패널 게시물 줄: 종류 칩은 그대로(새 글 등) + 회색 '지워짐' 칩, 본문은 흐리게, 날짜 옆 "10/18에 지워진 것을 확인했어요". X 원문 링크는 두지 않는다(열리지 않으므로).
- 지난 8주 칸: 지운 글이 든 주는 숫자 옆에 작은 점. 마우스를 올리면 "1개는 지금 X에서 지워졌어요(올린 것으로 셌어요)".
- 이번 주 목록에는 따로 문구를 두지 않는다(판정에 영향이 없으므로 '상황' 칸을 어지럽히지 않는다).

### 4-4. 기록 시작 전(`—`)
- 첫 수집이 8주를 거슬러 읽으므로 보통 8주가 다 찬다.
- X 계정 개설일이 그보다 늦으면 개설 주 이전은 `—`. 개설일은 사용자 정보 응답의 `createdAt`(실호출 확인 10-20)을 `owned_channel.account_created_at`에 둔다. 응답에 없으면 `—` 없이 0으로 센다.

## 5. 실패와 경고

- 계정을 못 찾음(이름 변경·정지·비공개): 이번 주 목록에서 그 줄 상황이 "계정을 확인하지 못했어요(이름이 바뀌었을 수 있어요) [클라이언트 설정]" — 주황. 횟수 칩은 `?`. **0으로 세지 않는다.**
- 오늘 수집만 실패(일시 오류): 그 줄 마지막 글 옆에 "어제 기준"처럼 마지막 성공 날짜를 붙인다.
- getxapi 인증·잔액 실패: 화면 머리에 "X 데이터를 받지 못하고 있어요 — 관리자에게 알려 주세요(API 잔액 확인)" 한 줄.

## 6. 정한 한계

- **올리고 하루 안에 지운 글은 모른다.** 다음 아침 확인 전에 사라지면 기록에 없어서, 실제로 올렸어도 '못 채움'이 될 수 있다. 그런 일이 실제로 생기면 '직접 인정(글 주소나 사유 메모)'을 더한다(§7).
- **등록 전 8주의 약속은 등록 때 값으로 채운다.** 그 전에 약속이 달랐다면 첫 8주 판정이 실제와 다를 수 있다.
- **하루 한 번 확인**이라 ↻를 누르지 않으면 오늘 올린 글은 내일 아침에 보인다. 화면 머리의 "오늘 07:00에 확인했어요"가 그것을 말한다.
- 덱에서 만든 원고와 실제 글을 잇지 않는다(글은 덱 밖에서 올린다).

## 8. 테스트

- 판정 로직(순수 함수, `src/lib/ownedChannels.ts`): 주 경계(일요일 23:59·월요일 00:00 한국), 종류 분류, 채움/못 채움(그 주 약속 기준), 연속 못 채움 수, 상황 문구, 요약 문구, 정렬, 남은 날, `—` 처리, 상대 날짜 표기(`9/26(25일 전)`·어제·오늘).
- 저장소: 같은 글 두 번 넣기, 스냅샷 같은 날 덮기, 핸들 변경 시 기록 삭제, 클라이언트 삭제 시 cascade.
- 수집: getxapi 가짜 응답으로 쪽 넘김 중단 시점, 고정 글, 숫자 id 불일치 실패, 실패 시 기록 안 함.

- 주별 약속: 이번 주에 약속 변경 → 이번 주만 바뀜, 지난 주 그대로 / 첫 수집 8주 채우기 / 빈 주는 가까운 주 값.
- 크론 라우트: 시크릿 없음/틀림 401.
- 연습용 DB에서만(testGuard).
