# 표 보기 필터 시스템 (설계)

2026-07-31.

**배경.** 표 보기(`2026-07-30-deck-table-view-design.md`)는 열 칩 하나로만 좁힐 수 있다. 사용자가 노션의 필터 UI를 예시로 들며 열 선택 방식을 바꿔달라고 했고, 확인 결과 **이번 요청은 열 선택기 교체가 아니라 필터 시스템의 시작**이다(사용자 확정).

이 결정은 표 보기 설계 §H의 *"조회수 N 이상 같은 값 필터 — 상위부터 정렬하면 목적이 달성된다. 필터 UI는 컨트롤을 늘린다"* 를 **의도적으로 되돌린다.** 그때는 슬랙 요청(지표 상위 훑기)만 보고 판단했으나, 사용자의 실제 의도가 더 넓었다.

**용도.** 사용자는 "지금은 모르거나 여러 것 다"라고 답했다 — 잠시 좁혀보기·조건 저장·팀 공유 중 어느 하나로 확정되지 않았다. 그래서 **가장 가벼운 것만 만들고, 나중에 저장된 뷰나 주소 공유를 얹을 수 있는 구조**로 짓는다.

## 원칙

- **두 가지 거르기를 사용자가 헷갈리지 않게 한다.** 이것이 이 설계의 핵심 난제다(§C).
- **논리 연산자를 노출하지 않는다.** 조건은 모두 AND. OR·괄호를 주면 화면이 쿼리 빌더가 된다 — 사용자는 비개발 콘텐츠 기획 담당자다(`AGENTS.md`).
- **가장 자주 하는 조작은 1클릭을 지킨다.** 열 바꾸기는 전용 컨트롤로 상시 노출하고, 드물게 쓰는 축만 접어둔다.
- **성능은 측정으로 판단한다.** 추측으로 인덱스를 넣지 않는다(§E).

## A. 화면 구조

```
[열: 전체 ▾]  [+ 필터]                       (오른쪽) − 칸 접기 | ⤓ CSV 저장

  계정     포함    @beautyfulence                    ✕
  조회수   이상    100,000                           ✕
  ─────────────────────────────────────────────────────
  이미 모은 843건 중에서만 걸러요 (새로 가져오지 않아서 무료)
```

- **`열`은 전용 드롭다운으로 상시 노출**한다. 조건 행 안에 넣지 않는다 — 가장 자주 바꾸는 축이라 2클릭으로 밀면 매번 비용이 든다. 접힌 드롭다운이 어포던스를 숨긴다는 문제도 이 상시 노출로 해소된다(`ColumnGrip`의 "상시 노출" 규칙과 같은 판단).
- 트리거 라벨이 **현재 값을 말한다**: `열: 전체` / `열: PDRN 크림` / `열: 3개`. 라벨과 값을 항상 일치시킨다(`AGENTS.md` 원칙 4).
- **열은 여러 개 선택할 수 있다.** 칩(단일 선택)으로는 안 되던 것이고, 드롭다운으로 바꾸면서 자연히 얻는다.
- 목록에는 **열마다 건수**를 함께 적는다(`PDRN 크림 56`). 고르기 전에 판단이 선다.
  - **이건 공짜가 아니다.** 서버는 지금 *조건에 맞는 총계* 하나만 센다(`getWorkspaceTableCount`). 열별 건수는 `group by ct.column_id`로 **세는 쿼리를 새로 하나** 만들어야 한다. 워크스페이스당 한 번이고 §E의 규모에서 무해하지만, 없던 일이 생기는 것이므로 계획에 태스크로 잡는다.
  - 이 건수는 **다른 조건을 반영하지 않는다** — 그 열의 전체 건수다. 조건을 걸 때마다 12개 열의 건수를 다시 세면 매 조작에 쿼리가 하나 더 붙고, "지금 조건에서 이 열은 3건"이라는 정보는 어차피 골라보면 바로 나온다.
- **`열`은 조건 행으로 추가할 수 없다.** 전용 드롭다운이 유일한 경로다 — 같은 축에 두 개의 UI를 두면 어느 쪽이 이기는지 사용자가 알 수 없다.
- 나머지 축은 `+ 필터`로 **조건 행을 쌓는다**. 건 조건만 보이므로 평소엔 자리를 차지하지 않고, 축이 늘어나도 형태가 그대로다.
- 구현은 기존 `<details>/<summary>` 드롭다운 패턴(`Column.tsx:288`의 `보기: 전체 ▾`)을 따른다. 새 라이브러리·헤드리스 프리미티브를 도입하지 않고 키보드 조작과 Esc 닫기를 네이티브로 얻는다.
- 조건이 하나도 없을 때 `+ 필터`만 있고 설명 줄은 감춘다 — 빈 화면에 안내를 먼저 깔지 않는다.
- **다중 선택 트리거 라벨은 이름을 보여준다** — `열: 3개`로만 쓰면 무엇이 걸렸는지 열어봐야 안다. `열: PDRN 크림 +2`처럼 첫 이름과 나머지 개수를 적는다(라벨과 값 일치, `AGENTS.md` 원칙 4).
- **접근성**: 조건 행의 축·연산자 선택은 `<select>`(라벨을 `aria-label`로), 값 입력은 `<input>`에 `aria-label`, 삭제는 `aria-label="이 조건 지우기"`. 드롭다운은 `<details>/<summary>`라 키보드·Esc가 네이티브로 따라오고, 열 항목은 다중 선택이므로 `<input type="checkbox">`로 상태를 스크린리더에 그대로 노출한다 — 체크 상태를 아이콘으로만 표현하지 않는다.

## B. 필터 축과 연산자

| 축 | 연산자 | 값 |
|---|---|---|
| 열 (`columns`) | 여러 개 중 하나 | 열 id 목록 (전용 드롭다운) |
| 계정 (`handle`) | 같음 / 포함 | 텍스트 |
| 본문 (`text`) | 포함 / 제외 | 텍스트 |
| 조회수·좋아요·RT·답글·인용·북마크·팔로워 | 이상 / 이하 | 정수 |
| 날짜 (`date`) · 기준 (`fetchedAt`) | 이후 / 이전 | `YYYY-MM-DD` |

- **조건은 모두 AND로 묶는다.** 열 다중 선택만 내부적으로 OR(그중 하나)이다.
- 같은 축을 두 번 쌓을 수 있다 — `조회수 이상 10000` + `조회수 이하 500000`으로 범위가 된다. 별도의 "사이" 연산자를 만들지 않는다(연산자 수를 늘리지 않고 같은 결과).
- **값이 비어 있는 조건 행은 쿼리에 보내지 않는다.** 축만 고르고 값을 아직 안 넣은 중간 상태에서 결과가 0건으로 튀면 안 된다.
- 본문 검색은 대소문자 무시 부분일치다. 일본어에는 대소문자 개념이 없어 실질 차이가 없지만 영문 혼용 본문이 있어 무시로 둔다.

## C. 수집 설정과의 혼동 방지 (핵심)

이 앱에는 거르는 지점이 **두 군데**이고 시점이 다르다.

| | 언제 | 무엇을 | 비용 | 되돌리기 |
|---|---|---|---|---|
| 컬럼 설정 (`SearchConfig`) | **가져올 때** — X 검색 쿼리에 들어간다 | 애초에 무엇을 수집할지 | API 과금 | 불가 (없는 건 없다) |
| 표 필터 (이 설계) | **볼 때** | 이미 모은 것 중 무엇을 보일지 | 없음 | 즉시 |

**따라서 표 필터로는 더 좁힐 수만 있고 더 넓힐 수는 없다.** 사용자가 `좋아요 ≥ 100`을 걸며 "기준을 낮췄으니 더 나오겠지" 기대하면 한 건도 늘지 않는다 — 그 열이 `minFaves 300`으로 수집 중이면 300 미만은 존재한 적이 없다. 화면이 무반응이라 필터가 고장 났다고 오해한다.

**이건 이론이 아니라 현재 상태다.** 실측(2026-07-31): 열 38개 중 **29개**가 수집 필터를 쓰고 있다. 기본 워크스페이스의 `PDRN 크림`은 `minFaves 300` + `minViews 100000` + `sinceDate 2026-06-01`이다.

### 장치 두 개

**1. 상시 한 줄** — 조건이 하나 이상 있을 때 필터 패널 아래에 고정:
> `이미 모은 843건 중에서만 걸러요 (새로 가져오지 않아서 무료)`

**2. 모순 경고** — 조건이 선택된 열의 수집 기준보다 느슨해서 아무 효과가 없을 때, 그 자리에서 말한다:
> `이 열은 좋아요 300 이상만 모으고 있어서 100으로 낮춰도 더 나오지 않아요`

열이 여러 개(또는 전체)면 요약한다:
> `선택한 열 중 9개는 좋아요 300 이상만 모아요`

경고는 **두 종류**다. 방향에 따라 결과가 다르고, 뒤쪽이 더 위험하다.

**(a) 느슨해서 무효 — "더 나오지 않아요"**
조건이 수집 기준보다 느슨하면 아무 효과가 없다. 사용자는 필터가 고장 났다고 오해한다.

| 필터 조건 | 비교할 설정 | 조건 |
|---|---|---|
| `좋아요 이상 X` | `minFaves` | `X < minFaves` |
| `RT 이상 X` | `minRetweets` | `X < minRetweets` |
| `답글 이상 X` | `minReplies` | `X < minReplies` |
| `조회수 이상 X` | `minViews` | `X < minViews` |
| `날짜 이후 X` | `sinceDate` | `X < sinceDate` |
| `날짜 이전 X` | `untilDate` | `X > untilDate` |

**(b) 엄격해서 항상 0건 — "한 건도 나오지 않아요"**
반대 방향은 결과가 **반드시 비어 있다.** 화면이 빈 상태가 되는데 사용자는 자기 조건이 틀린 줄 알고 값을 이리저리 바꿔본다 — 무엇을 해도 0건이다. (a)보다 훨씬 헷갈리므로 문구도 더 강하게 말한다.

| 필터 조건 | 비교할 설정 | 조건 | 결과 |
|---|---|---|---|
| `좋아요 이하 X` | `minFaves` | `X < minFaves` | 항상 0건 |
| `RT 이하 X` | `minRetweets` | `X < minRetweets` | 항상 0건 |
| `답글 이하 X` | `minReplies` | `X < minReplies` | 항상 0건 |
| `조회수 이하 X` | `minViews` | `X < minViews` | 항상 0건 |
| `날짜 이전 X` | `sinceDate` | `X < sinceDate` | 항상 0건 |
| `날짜 이후 X` | `untilDate` | `X > untilDate` | 항상 0건 |

(b)의 문구: **`이 열은 좋아요 300 이상만 모으고 있어서 200 이하로는 한 건도 나오지 않아요`**

같은 축에 `이상`과 `이하`를 함께 걸어 범위를 만들 수 있으므로(§B), 한 조건이 (a)이고 다른 조건이 (b)일 수 있다. 각 조건 행마다 따로 판정한다.

- 인플루언서(`watchlist`) 열은 이런 설정이 없으므로 경고 대상이 아니다.
- `기준`(지표를 가져온 시각)은 수집 설정에 대응 항목이 없어 경고가 없다.
- 열 설정은 이미 이 화면에 프롭으로 들어와 있다(`TweetTableView({ wsId, columns })`) — 서버 왕복이 필요 없다.
- 이 비교는 **순수 함수**로 뽑아 테스트한다. 경고는 조건을 막지 않는다 — 사용자가 알고도 걸 수 있다(차단이 아니라 정보 제공).

## D. 서버

새 마이그레이션이 없다. 조건을 SQL 조각으로 바꿔 기존 쿼리에 `and`로 붙인다.

**안전 규칙 — 이 기능에서 문자열이 SQL에 직접 들어가는 유일한 지점이다:**

- 축 → SQL 식은 **허용 목록 맵**에서만 나온다. 기존 `ORDER_EXPR`(`tweetStore.ts:34`)와 같은 방식이다.
- 연산자 → SQL 연산자도 **허용 목록**. 사용자 입력이 연산자 위치에 오지 못한다.
- **값은 전부 바인딩 파라미터.** 어떤 경우에도 값을 문자열로 이어붙이지 않는다.
- 조각 생성은 순수 함수(`buildFilterSql`)로 분리해 유닛 테스트한다.

**같이 고치는 것 — `열` 칸이 필터된 열만 보여주는 문제.** 지금은 `array_agg(distinct dc.title)`가 필터된 조인 위에서 돌아, 열 필터를 걸면 그 트윗이 실제로 속한 다른 열이 사라진다(2026-07-30 최종 리뷰가 Minor로 남긴 항목). 내보낸 파일은 필터보다 오래 남으므로 소속을 축소해 적는 것은 부정직하다. **열 이름 집계를 필터와 분리**해 항상 그 트윗이 속한 워크스페이스 내 모든 열을 적는다.

성능 우려로 이 분리를 미루지 않아도 된다 — §E의 측정에서 두 형태가 사실상 동일했다.

**건수 계산.** 지금은 `더보기` 페이지마다 `count(distinct)`를 다시 돈다. 필터가 붙으면 매 페이지에 조건부 집계가 한 번 더 도는 셈이다. **건수는 필터·열 선택이 바뀔 때만 계산하고 `더보기`에서는 재사용**한다(같은 조건에서 총계는 변하지 않는다).

## E. 성능 — 측정과 임계점

추측 대신 실제로 재고 결정했다. 측정일 2026-07-31, 프로덕션 DB(싱가포르).

**현재 규모**

| | |
|---|---|
| 전체 트윗 | 2,808행 / 4.7MB |
| `column_tweet` 링크 | 2,977행 |
| 가장 큰 워크스페이스 | 843 트윗 (기본) |
| 기존 인덱스 | `tweet_pkey`, `column_tweet_pkey`, `idx_column_tweet_col`, `idx_tweet_seen` |

**최악 조건 쿼리** (지표 필터 + 일본어 본문 `ILIKE` + 팔로워 + 날짜 + 조회수 정렬, 가장 큰 워크스페이스):

| | 시간 |
|---|---|
| 웜 캐시 중앙값 (5회) | **12.9ms** |
| 콜드 캐시 1회 | 129ms |

**필터는 거의 공짜다.** `EXPLAIN`상 비용은 그 워크스페이스의 행을 훑는 것 자체에서 나오고, 조건을 네 개 붙여도 크게 늘지 않는다.

### 검증하고 버린 최적화

조인+`group by` 대신 `tweet`에서 출발해 필터를 먼저 적용하고 소속을 `EXISTS`로 확인하는 형태를 시도했다. 첫 측정에서 129ms → 15ms(8배)로 보였으나 **캐시 워밍 착시**였다. 같은 조건에서 번갈아 5회씩 재측정한 결과:

| 형태 | 중앙값 |
|---|---|
| 기존 (join + group by) | 12.9ms → 재측정 12.7ms |
| 대안 (filter-first + EXISTS) | 13.3ms |

**기존 구조가 미세하게 더 빠르다. 쿼리 형태를 바꾸지 않는다.** (열 이름 집계 분리는 성능이 아니라 §D의 정직성 이유로 한다.)

### 인덱스를 지금 넣지 않는 이유

**본문 부분검색에 `pg_trgm` GIN 인덱스를 넣지 않는다.** 이것이 교과서 처방이지만 **일본어에는 무효**다. 짧은 CJK 패턴(`'%定す%'`)은 쓸 수 있는 trigram이 0개로 추출돼 플래너가 올바르게 순차 스캔을 고른다. 인덱스는 쓰이지도 않으면서 쓰기 성능만 깎는다. 근거: PostgreSQL 공식 문서(`pg_trgm` — "a pattern with no extractable trigrams will degenerate to a full-index scan")와 dba.stackexchange의 상세 분석("trigram 방식은 표어문자 언어에 적합하지 않다").

**지표(jsonb) 필터·정렬의 정답은 표현식 B-tree 인덱스**다 — `((metrics->>'views')::bigint)`. **GIN은 `->>` 추출에 전혀 도움이 안 된다**(containment `@>`만 가속) — 흔한 오해라 여기 적어둔다. 다만 843행에서는 플래너가 인덱스를 고르지 않아 지금 넣으면 순수 낭비다.

### 임계점 — 언제 손대는가

감시 지표는 **워크스페이스당 트윗 수**(현재 최대 843).

| 임계 | 조치 |
|---|---|
| ~5,000건 | 정렬 기본값이 조회수라 여기가 먼저 아프다. `create index on tweet (((metrics->>'views')::bigint))` 검토. 인덱스가 쓰이려면 쿼리의 식과 **정확히 같아야** 한다 |
| ~50,000건 | 지표를 jsonb에서 실제 컬럼(또는 생성 컬럼)으로 승격 검토. 참고 자료들이 100만행 기준 타입 컬럼이 jsonb 표현식 인덱스보다 20% 이상 빠르다고 보고 |
| 본문 검색이 느려짐 | 인덱스로 못 고친다. CJK 대응 전문검색(pgroonga 또는 bigram 설정) 도입 여부를 별도 판단 — 확장 도입이므로 이 설계의 범위가 아니다 |

## F. 나머지와의 연동

- **CSV·건수 라벨**: 필터 전체가 반영된다(지금은 열만). `CSV 저장 (전체 N건)`이 필터 결과와 일치해야 한다 — 라벨과 값 불일치는 금지다.
- **정렬·더보기**: 필터가 바뀌면 offset 0에서 다시 불러온다(이미 그 구조).
- **빈 상태**: `이 열에는 글이 없어요`를 **`조건에 맞는 글이 없어요`** + `필터 지우기`로 일반화한다. 진짜 0건(수집된 글이 아예 없음) 문구는 그대로 구분해 유지한다 — 두 상태를 합치면 사용자가 데이터가 없다고 오해한다.
- **표 모드를 벗어나면 필터는 사라진다**(휘발). 필터 상태를 `TweetTableView`가 들고 있으므로 카드로 전환하면 초기화된다. 필터 모델은 직렬화 가능한 순수 데이터이므로 나중에 주소·저장된 뷰를 얹을 때 UI를 다시 짓지 않아도 된다.
  - **알려진 비대칭**: `?view=table`은 주소에 남는데 필터는 안 남는다. 새로고침하면 표는 그대로인데 조건만 사라져 놀랄 수 있다. 이번 범위에서는 감수하되, 조건이 하나 이상 걸려 있을 때 **`필터 지우기` 버튼을 상시 노출**해 "지금 걸려 있다"는 사실만은 화면에서 읽히게 한다. 주소에 담는 것은 후속(§G).
- **CSV 파일명에 조건을 요약해 넣는다** — `x-deck-table-2026-07-31.csv`는 같은 날 다른 조건으로 두 번 받으면 구분이 안 된다. 필터가 여러 개가 되면서 실제 문제가 되므로, 걸린 열 이름이나 조건 개수를 파일명에 넣는다(예: `x-deck-table-PDRN크림-2026-07-31.csv`, 조건이 여러 축이면 `-필터3개`). 파일명에 쓸 수 없는 문자는 제거한다.

## G. 범위에서 제외

- **OR 조합과 조건 그룹(괄호)** — 논리 연산자를 노출하지 않는다는 원칙.
- **저장된 뷰, 주소 공유** — 용도가 확정되지 않았다. 모델을 직렬화 가능하게 두는 것까지만 준비한다.
- **보관함·브리핑에 같은 필터 적용** — 지금 요청은 표 보기다. 필터 모델을 `src/lib`의 순수 모듈에 두어 재사용 가능하게만 남긴다.
- **인덱스·스키마 변경** — §E의 임계점에 도달하기 전에는 하지 않는다.
- **`pg_trgm` 도입** — 일본어에 무효(§E).

## H. 분량에 관한 메모

이 설계는 표 보기 본체와 비슷한 규모다 — 필터 모델·SQL 조각 생성·모순 감지·열 드롭다운·조건 행 UI·열별 건수 쿼리·CSV/건수/빈 상태 연동·테스트. 한 계획으로 묶을 수는 있으나 작지 않다.

한 번에 다 하지 않으려면 자연스러운 절단선은 **축 단위**다:

1. 필터 골격 + `열`(다중 선택 드롭다운, 칩 제거) + 빈 상태·CSV 연동 — 이번 요청의 출발점
2. `계정`·`본문` 조건 행 — 수집 설정과 겹치지 않아 경고 로직이 필요 없다
3. 지표·날짜 조건 행 + §C의 모순 경고 — 여기가 가장 무겁다

1단계만으로도 사용자가 처음 말한 "열 선택 방식"은 해결된다. 계획 단계에서 사용자와 정한다.

- **순수 함수 유닛 테스트** (이 저장소에 컴포넌트·라우트 하네스가 없으므로 테스트 가능한 부분을 순수 함수로 뽑는다):

  - 모순 감지: §C 표의 6가지 규칙 각각, 여러 열일 때의 요약, watchlist 열이 대상에서 빠지는지

  - **열 이름 집계가 필터와 무관하게 그 트윗의 모든 열을 담는지**(§D의 정직성 수정)
