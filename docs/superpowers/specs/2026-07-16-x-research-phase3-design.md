# X 리서치 Phase 3 — 트렌드 모니터링 + 기간 종합 브리핑

날짜: 2026-07-16 · 상태: 승인 대기(박구건) · 상위: `2026-07-14-x-research-roadmap.md` · 선행: Phase 2(`2026-07-15-x-research-phase2-design.md`, 머지 완료 7bb77d0) · 사전 실측: `~/claude-outputs/cb-x-deck-phase3-스파이크-트렌드성립성-20260716.md`

## 목표

**축 ④-1 트렌드 모니터링 (덱)**: 모든 컬럼에 **[추이 보기]** 버튼을 추가한다. 누르면 그 컬럼에 쌓인 트윗을 주 단위로 집계해 "이 컬럼/이 주제가 뜨고 있나, 식고 있나"를 표와 한 줄 판정으로 보여준다. 이미 수집된 트윗의 작성 날짜로 세는 것이라 추가 비용 $0.

**축 ④-2 기간 종합 브리핑 (리서치 페이지)**: 리서치 페이지에 새 섹션을 추가한다. 컬럼과 기간(최근 2/4/8주)을 골라 버튼을 누르면 "그 기간에 무슨 일이 있었나"를 LLM이 보고서로 작성한다. 생성물은 저장되어 목록에서 재열람·비교할 수 있다. 기존 웹 리서치(exa) 섹션은 변경하지 않는다.

**성공 기준**: 주간 루틴에서 (a) 추이 패널이 "지금 이 화두를 다뤄야 하나"라는 타이밍 판단을 스크롤 없이 제공하는가, (b) 브리핑이 처음 읽는 팀원도 배경 설명 없이 이해할 수 있는 공유용 문서로 기능하는가.

## 사전 결정 사항 (명료화·스파이크·파일럿로 확정)

| 항목 | 결정 |
|---|---|
| 주차 정의 | 트윗 작성 시점(`tweet_created_at`) 기준, **월요일 시작, 일본 시간(JST)**. 과거 소급 계산 성립이 실측 확인됨(대기 불필요) |
| 해상도 이원화 | 컬럼 수준 = 주간 / 주제 수준 = 격주(2주 묶음). 주제×주간은 표본 붕괴로 불성립(실측) |
| 최신 주 처리 | 항상 "집계 중"으로 분리 표시, 판정·비교에서 제외 (좋아요 미포화+수집 랙으로 항상 낮게 나옴 — 실측) |
| 집계 대푯값 | 좋아요 **중앙값** (단발 대박 왜곡 방지 + 지표 조작 방어) |
| 트렌드 단위 | 주제(LLM 분류, Phase 2 `tweet_topic` 재사용). 해시태그 배제(사용자 결정). **계정 컬럼 전용** — 검색 컬럼 주제 분류 확장은 v1 제외(아래 파일럿 기록) |
| 트렌드 UI | 컬럼 내 패널(Phase 2 주제 분석 패널 패턴), 모든 컬럼 종류 |
| 데이터 계산 | **조회 시 계산(저장 없음)** — 로드맵 원안("시계열 저장 필요")은 스파이크로 전제가 뒤집힘. 트윗 원본이 누적 저장되므로 언제든 재계산 가능. 승격 조건: 컬럼당 집계가 체감 지연(수백 ms↑)을 만들면 캐시 테이블 검토 |
| 브리핑 단위 | 컬럼별 선택 + 기간 선택(완성 주 기준 소급 2/4/8주) |
| 브리핑 보관 | DB 저장 + 지난 브리핑 목록(재열람·삭제·작성자 배지) |
| 백필 | 포함 — 완성 주 3개 미만 컬럼에 "과거 트윗 더 가져오기(약 $0.01)" 버튼. **메커니즘은 컬럼 종류별로 다름**(아래 §4) |
| 브리핑 문체 | 전문용어·압축어 금지(불가피하면 풀어쓰기), AI 상투 문체 금지, 짧은 완결 문장, 처음 읽는 팀원 기준. 금지 표현은 회귀 테스트로 일부 고정 |

## 파일럿 기록 — 검색 컬럼 주제 분류 (v1 제외 근거, v2 판단 자료)

2026-07-16, 니키비跡 검색 컬럼 238건에 `deriveTopics` 1회 실행(~$0.03, DB 저장 없음):

- 주제 7개 도출, 220건 배정. 분류 자체는 유의미(성분 지식/시술/내복약·호르몬 등), 잡음 트윗을 "일상·개인경험"으로 격리하는 동작도 올바름.
- 그러나 상위 2개 버킷(제품 추천 91건 + 일상 63건)이 배정의 65%를 차지하는 거대·조잡 분류였고, 정작 세부 화두들은 8주 누적 2~17건 = **주당 1~2건으로 표본이 다시 붕괴**. "검색 컬럼 확장이 주제×주간의 전제"라는 스파이크 가설은 상위 2~3개 주제에서만 성립.
- **v2 승격 시 숙제**: 거대 버킷 세분화 프롬프트(부위·고민별), 잡음 주제 트렌드 제외 처리. 달러 비용은 근거 확보됨(초기 ~$0.5 + 유지 ~$0.5/월, 무시 가능) — 실질 트레이드오프는 주간 분류 클릭 마찰과 분류 품질.

## 아키텍처 위치 (경계)

트렌드 = **덱** 컬럼 패널(검색·계정 모든 컬럼). 브리핑 = **리서치 페이지** 새 섹션(기존 exa 웹 트랙 UI 불변 — 요약은 새 섹션으로만 추가). 신규 저장은 `briefing` 테이블 1개(마이그레이션 008)뿐이고, 트렌드는 아무것도 저장하지 않는다. 인용 역탐색(quotes) 영구 제외, 스레드 1페이지 한계 등 기존 제약 유지.

## 컴포넌트 설계

### 1. 추이 집계 엔진 — `src/lib/trend.ts` (순수 함수)

- `computeWeeklyTrend(tweets, now)` → 주차 버킷 `{weekStart, count, medianLikes}[]` + `partialWeek`(최신 미완성 주, 분리 반환). 주 경계는 JST 월요일 00:00. 조회 창 = 최근 12주, 표시 = 완성 주 최근 8개.
- **컬럼 수준 판정(파생값 — 라벨↔값 모순 금지, 원칙 4)**: 최근 완성 1주를 직전 완성 주 최대 3개(있는 만큼, 최소 2개) 평균과 비교. 게시량·♥중앙값 각각 `▲`(+50% 이상) / `▼`(−33% 이하) / `─`(사이). `judgment`는 두 축을 고정 형식으로 병렬 서술(원칙 3): "게시량은 {늘어나는 중|유지|줄어드는 중}, 반응은 {…}" — 예) "게시량은 유지되고 있는데, 반응은 줄어드는 중이에요".
- `computeTopicTrend(tweets, topics)` (계정 컬럼 + 주제 분석 존재 시): 완성 주만 최신부터 소급해 2주씩 묶고(남는 1주는 버림), 주제별 최근 격주 vs 직전 격주의 `{count, medianLikes}` 비교 → 주제별 `▲ 뜨는 중 / ▼ 식는 중 / ─ 유지` 판정. 배정은 Phase 2 `tweet_topic` 재사용 — 조회 시 계산이므로 **주제를 재도출해도 과거 추이가 새 주제 기준으로 자동 소급 재계산**된다(시계열 연속성 문제 원천 차단).
- **표본 부족 판정 2단계**: 완성 주 3개 미만 → `insufficient`(추이 대신 안내+백필 버튼) / 주당 건수 중앙값 5건 미만 → `sparse`(숫자는 표시하되 판정문 대신 "표본이 적어 추이가 흔들릴 수 있어요" 라벨).
- 데이터 로드는 `pillarStore.listAnalysisTweets` 재사용(작성일·좋아요·주제 배정·버림 제외를 이미 반환). 트렌드용 상한 옵션(2000건)만 추가.

### 2. 추이 API — `GET /api/columns/[id]/trend`

thin proxy: 컬럼 확인 → 트윗 로드 → `trend.ts` 계산 → `{weekly, partialWeek, judgment, topicTrends|null, sufficiency, samplePeriod}`. LLM·외부 API 호출 없음(항상 $0).

### 3. 추이 패널 — `src/components/TrendPanel.tsx`

- 컬럼 헤더에 **[추이 보기]** 버튼(모든 컬럼). 도움말(원칙 2): "이 컬럼에 쌓인 트윗으로 주간 추이를 보여줘요 · 추가 비용 없음".
- 패널: 주차별 행(주 시작일 · 게시량 CSS 막대 · ♥중앙값) → 집계 중 주는 `▒ 집계 중` → 판정문 한 줄 → (계정 컬럼) 주제별 격주 목록. 주제 분석이 없으면 "주제 분석을 먼저 실행하면 주제별 추이도 보여요" 안내.
- `♥중앙값` 라벨에 툴팁 "그 주 트윗의 보통 반응 수준(좋아요 중앙값)" (기술값을 맥락으로 감싸기, 원칙 5).
- `insufficient`면: "아직 데이터가 N주치뿐이에요" + **[과거 트윗 더 가져오기 · 약 $0.01]**.

### 4. 백필 — 컬럼 종류별 메커니즘

- **계정 컬럼**: 기존 `refresh` `maxPages=10` 재사용(시간순 페이지네이션이라 과거 주가 채워짐 — Phase 2에서 확인).
- **검색 컬럼**: Top 정렬 페이지네이션은 "더 인기 있는 트윗"을 줄 뿐 과거 주를 채운다는 보장이 없음 → **X 검색의 기간 지정(`since:`/`until:`)으로 부족한 주 구간을 직접 검색**. `queryBuilder.ts`에 since/until 지원 추가(+회귀 테스트), refresh 라우트에 백필 파라미터 추가. 실계약(연산자 동작·Top 모드와의 조합)은 구현 시 스모크 스크립트로 확인 — Phase 2 Task 7의 실계약 편차 선례를 따름.

### 5. DB — `migrations/008_briefing.sql` (멱등)

```sql
create table if not exists briefing (
  id uuid primary key default gen_random_uuid(),
  workspace_id uuid not null,
  column_id uuid not null references deck_column(id) on delete cascade,
  period_from date not null,
  period_to date not null,
  sample_size int not null,
  content jsonb not null,   -- {tldr: string[], body: string, citations: [...], stats: {...}}
  model text,
  created_by text,
  created_at timestamptz not null default now()
);
create index if not exists briefing_ws_created on briefing (workspace_id, created_at desc);
```

- `content.body`는 LLM 서술(트윗 인용은 `[T3]` 토큰), `citations`는 토큰→실트윗 복원 정보(`{n, tweetId, text, likes, url, flags}`), `stats`는 코드가 계산한 수치 블록, `tldr`은 3줄 요약. 저장 시점에 렌더링에 필요한 전부를 담아 원본 트윗이 나중에 변해도 문서가 재현된다.

### 6. 브리핑 생성 엔진 — `src/lib/briefing.ts`

`suggest.ts` 패턴(주입 가능 `AnthropicLike`, `MODEL`, `extractJson`), `max_tokens` 3000.

- **기간 정의**: 마지막 완성 주 기준 소급 N주(2/4/8) — 집계 중 주가 섞여 후반부가 식어 보이는 왜곡 방지. 문서 머리에 "6/15~7/13 · 표본 187건 기준" 명시(기대 설정, 원칙 2).
- **입력 구성**: 기간 내 트윗 최대 300건(초과 시 좋아요 상위 우선 + 주별 안배로 시간 편중 방지), `pillar.ts`의 번호 매핑 패턴으로 `[T1..Tn]` 부여. 여기에 `trend.ts`가 계산한 주별 수치를 함께 주입.
- **숫자/서술 분리(핵심 요건)**: LLM은 집계 계산 금지 — 주입된 수치만 인용하도록 프롬프트에 명시. 수치 요약 블록은 LLM을 거치지 않고 코드가 `stats`로 직접 생성. 숫자 환각이 구조적으로 불가능.
- **프롬프트 산출 구조(고정 — 회차 간 비교 가능)**: ①3줄 요약 ②핵심 화두 ③반응 좋았던 것(트윗은 `[T번호]`로만 인용) ④변화(주입 수치 근거) ⑤기획 시사점. 컬럼 주제와 무관한 잡음 트윗은 무시 지시(파일럿에서 확인된 한계의 완화 — 완전 차단은 불가, 한계로 수용).
- **문체 요건(프롬프트 명시)**: 전문용어·업계 압축어 금지(불가피하면 바로 풀어쓰기 — 예: "인게이지먼트"✕ → "반응(좋아요·리트윗)"○), "~라고 할 수 있습니다"·"주목할 만한 점은" 등 AI 상투 표현 금지, 과장 수식어 금지, 짧은 완결 문장, 한 문단에 하나의 요지, 처음 읽는 팀원 기준.
- **검증(방어)**: `extractJson` 파싱 → 존재하지 않는 `[T번호]` 인용 제거(Phase 2 방어 패턴) → 금지 표현 목록 검사(회귀 테스트로 고정). 검증 실패 시 저장하지 않는다.
- **규제 배지**: `citations`의 각 트윗에 기존 `complianceFlags`를 적용해 `flags` 저장 — 렌더링 시 경고 배지 표시(코드 처리, LLM 무관). 필터링은 하지 않음(로드맵 결정 F — 가벼운 경고만).

### 7. 브리핑 저장소·API

- `src/lib/briefingStore.ts`: `saveBriefing`, `listBriefings`(workspace 단위, 최신순), `getBriefing`, `removeBriefing`.
- `POST /api/briefings` — body `{columnId, weeks}`: 트윗 로드 → trend 수치 계산 → 생성 → 검증 → 저장 → 반환. LLM 실패·파싱 실패 시 502 "생성 실패 — 다시 시도해주세요", **저장 안 함**(반쪽 문서가 목록에 남지 않음).
- `GET /api/briefings?workspaceId=` 목록 / `GET·DELETE /api/briefings/[id]`.
- 생성 전 표본 확인은 별도 엔드포인트 없이 **기존 trend GET 재사용**(클라이언트가 주별 건수 합산).

### 8. 브리핑 UI — `src/components/BriefingSection.tsx` (리서치 페이지)

- 컬럼 선택(덱의 모든 컬럼) · 기간 선택(2/4/8주) · **[브리핑 생성 · 약 $0.1 이하]**(opt-in, 원칙 6).
- 선택 시 "이 기간 표본 N건" 미리 표시. **10건 미만이면** "이 기간엔 트윗이 N건뿐이라 브리핑이 빈약해요" 경고 후 진행 여부 선택(부실 문서에 비용 지출 방지).
- 결과 화면: 머리(컬럼·기간·표본·생성일·작성자) → 수치 블록(코드 렌더) → 3줄 요약 → 본문(인용 토큰은 실트윗 카드로 복원: 원문·♥·X 링크·규제 배지).
- **지난 브리핑 목록**: 컬럼·기간·생성일·작성자 배지, 클릭 열람, 삭제. 스카우트 보관함(`ScoutList`)의 목록 패턴 참조.
- 기존 웹 리서치 섹션은 마크업·동작 모두 불변.

## 데이터 흐름

**트렌드**: 컬럼 새로고침(기존, 트윗 누적) → [추이 보기] → GET trend → 즉석 집계 표시. 다음 주 새로고침하면 새 주가 자동으로 나타남(저장·갱신 작업 없음).

**브리핑**: 리서치 페이지 → 컬럼·기간 선택(표본 수 미리 확인) → [브리핑 생성] → POST → LLM 생성+검증 → 저장 → 표시. 이후 목록에서 재열람 — 재생성 비용 없음.

**백필**: 추이 패널의 부족 안내 → 버튼 클릭 → (계정) refresh maxPages / (검색) since·until 구간 검색 → 수집 후 추이 재조회.
