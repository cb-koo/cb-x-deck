## 0. 결정 (koo 10-22)

- **목적: 팀원이 덱을 쓰다 불편한 점을 그 자리에서 바로 보내고, 해결되면 답을 받는다.** 사용자는 비개발 기획 담당 2~5명이다.
- **보내는 곳은 모든 화면 오른쪽 아래의 둥근 버튼이다.** 40px, 아이콘만 두고 글자는 붙이지 않는다(koo). 마우스를 올리면 말풍선 도움말 `불편 알리기`만 뜬다.
- **버튼은 숨지 않고 비켜선다.** 패널에 대한 이슈일수록 패널을 띄운 채 보내야 한다(koo 질문 "패널 관련 이슈면?"). 비켜서는 규칙은 §2-1.
- **입력은 내용(필수)과 스크린샷 붙여넣기(선택, 1장)다.** 급한 정도는 묻지 않는다.
- **위치는 자동으로 붙인다.** 화면 이름, 열린 패널이나 창 제목, 주소. 보내는 창 맨 위에 한 줄로 보여 준다.
- **받는 곳은 앱 안 이슈 목록과 슬랙 채널 알림 한 줄이다.**
- **상태는 접수 / 확인 중 / 해결 세 단계다.** 해결할 때 한 줄 답을 남기면 보낸 사람이 '내가 보낸 것'에서 본다.
- **상태 바꾸기와 해결 답은 koo(gugeon.park@)와 태정님(taejeong.jeon@)만 한다.** 다른 팀원은 상태와 답을 읽기만 한다. 앱에 역할 모델이 없으므로 이메일 목록으로 둔다(§5).
- **목록 탭은 할 일(접수 + 확인 중) / 해결됨 / 내가 보낸 것이다.** '할 일' 이름은 일단 확정, 필요하면 나중에 바꾼다(koo).
- **목록 자리는 사이드바 맨 아래 '업데이트 소식' 밑의 `이슈`다.** 보낸 것과 고친 것이 한곳에 모인다.
- **보류: 직전 10분 동안 한 일 자동 기록**(화면 이동, 버튼, 서버 요청 결과, 화면 오류). 방법은 정리됐으나(§8) 이번 범위에서 뺀다(koo 10-22).
- **스크린샷 자동 캡처는 하지 않는다.** 외부 이미지가 캡처에서 깨지기 쉽고 라이브러리가 무겁다. 맥 캡처(⌘⇧⌃4)를 붙여 넣는다.
- **화면 문구에 `·` 구분자를 쓰지 않는다.** 날짜는 `10/22(오늘)`, `10/20(2일 전)` 형식이다.

## 2. 화면

### 2-1. 둥근 버튼 (모든 로그인 화면)

- 루트 레이아웃에 한 번 붙인다(`IssueReportButton`). 로그인 화면, 거부 화면, 공유 링크처럼 사이드바가 없는 화면에는 두지 않는다.
- 기본 자리: 오른쪽 아래(right 24, bottom 24). z-index는 패널(z-40)과 다이얼로그(z-50) 위.
- **비켜서기**(시안 ②③): 버튼이 화면을 스스로 살펴 자리를 정한다. 새 패널이 생겨도 화면마다 손볼 필요가 없게 한다.
  - 오른쪽에 붙은 패널이 열려 있으면 패널 왼쪽 바깥 아래로 옮긴다. 대상은 화면 오른쪽 끝에 붙은 `role="dialog"`나 `<aside>`다. 지금은 작업 패널(`TaskPanel`, 560px)과 X 업로드 현황 상세(`ChannelDetailPanel`)가 해당한다.
  - 화면 아래에 고정 줄이 보이면 그 줄 위로 올린다. 일괄 처리 바(`BulkActionBar`)와 트래킹 하단 줄은 `data-bottom-bar` 표시를 달아 찾는다.
  - 가운데 다이얼로그는 구석과 겹치지 않으므로 그대로 둔다.
  - 감지는 DOM 변화 관찰(MutationObserver)과 창 크기 변화로 다시 계산한다. 이동은 짧은 transition으로 보여 준다.
- **예외: 브라우저 기본 창(`<dialog>`.showModal)** — `EditorParts`의 편집 패널은 열려 있는 동안 창 바깥을 누를 수 없다. 그래서 이 공용 부품의 머리글 ✕ 옆에 같은 아이콘 버튼을 둔다. 공용 부품이라 한 곳만 고치면 된다.
- 버튼을 눌러도 아래에 열린 패널과 창은 닫히지 않는다. 패널들의 '바깥 클릭이면 닫기' 처리가 이 버튼과 보내는 창을 바깥으로 치지 않게 `data-issue-report` 영역을 제외한다.

### 2-2. 보내는 창 (시안 ④)

버튼 바로 위에 붙는 400px 작은 창이다. 화면 가운데를 덮지 않아서 보던 패널을 보면서 쓸 수 있다.

```
불편 알리기                                       ✕
┌──────────────────────────────────────────────┐
│ 📍 캠페인 › 10월 4주차 가은치유한의원 › 작업 @miyuxxx48 에서 보내요 │
└──────────────────────────────────────────────┘
[ 무엇이 불편했나요?                               ]
[ 예: 게시일을 바꿨는데 표에는 예전 날짜가 그대로예요 ]
[ 스크린샷 붙여넣기 (⌘V)                          ]
[ ⌘⇧⌃4로 찍으면 바로 붙여 넣을 수 있어요            ]
                                   [취소] [보내기]
```

- 내용이 비어 있으면 [보내기]가 꺼져 있다.
- 스크린샷은 창 어디서든 ⌘V로 붙여 넣는다(글 칸에 포커스가 있어도). 끌어다 놓기와 파일 고르기도 받는다. 붙이면 섬네일 + `스크린샷 1장` + `✕ 빼기`로 바뀐다. 1장까지만 받고, 다시 붙이면 바꾼다.
- 형식과 용량은 RT 증빙(`taskProof.ts`)과 같다. jpg, png, webp, 10MB까지. 오류 문구도 같은 말을 쓴다.
- 보내면 창이 닫히고 토스트 `보냈어요` + [보기](이슈 상세)를 띄운다. 실패하면 창을 닫지 않고 쓴 내용을 그대로 둔 채 오류 한 줄을 보여 준다.
- 쓰다가 ✕나 [취소]를 누르면, 내용이 있을 때만 "쓴 내용이 사라져요"를 확인한다.

### 2-3. 위치 자동 기록

보내는 순간 아래를 모은다. 한 줄 표시는 `화면 › 제목 › 패널`로 이어 붙인다.

| 칸 | 출처 | 예 |
|---|---|---|
| 화면 이름 | 주소 앞부분 → 사이드바 메뉴 이름(`issueReport.ts`의 `screenNameFor` 표, 사이드바에 메뉴를 더하면 여기도 한 줄) | 캠페인 |
| 화면 제목 | 본문의 첫 `h1` 글자 | 10월 4주차 가은치유한의원 |
| 열린 패널이나 창 | 맨 위에 열린 `role="dialog"`, `dialog[open]`, `aside[role=dialog]`의 `aria-label` 또는 머리글(`h2`/`h3`) 글자 | 작업 @miyuxxx48 |
| 주소 | `location.pathname + search` | /campaigns/flow?c=… |
| 화면 크기 | `innerWidth × innerHeight` | 1440×900 (상세에만 작게) |

- 캠페인 작업 패널의 머리글은 `인용RT · @miyuxxx48`처럼 내부 구분자를 쓴다. 기록에는 머리글 그대로 남기고 표시도 그대로 한다(이 칸은 화면 문구가 아니라 인용이다).
- **[이 화면 열기]는 주소로 간다.** 주소에 패널 상태가 들어가는 화면(콘텐츠 생성 `?draft=`, 클라이언트 `?client=`, 정산 `?task=`)은 패널까지 열린다. 캠페인 작업 패널은 열려도 주소가 바뀌지 않지만, 캠페인 화면이 이미 `?id=<캠페인>&task=<작업>`을 읽어 그 패널을 연다(FlowDetail의 linkedTaskId). 그래서 보낼 때 패널의 `data-issue-task-id`로 작업 id를 읽어 두고, [이 화면 열기]가 `?task=`를 붙인다(`locationHref`). 캠페인 쪽 코드 변경은 없다.

### 2-4. 이슈 목록 `/issues` (시안 ⑤)

- 사이드바 하단 묶음에 `업데이트 소식` → `이슈` → `API 사용량` 순서로 둔다. 답이 달렸는데 안 본 내 이슈가 있으면 파란 숫자 칩을 붙인다.
- 탭: `할 일 N` / `해결됨 N` / `내가 보낸 것 N`. 처음 열면 `할 일`이다. 단, 안 본 답이 있는 사람은 `내가 보낸 것`으로 연다.
- 표(행 하나 = 한 줄, 행 높이 48px): 상태 칩 | 내용(한 줄 말줄임) | 화면 | 보낸 사람 | 보낸 날. 최신순.
  - 상태 칩 색: 접수 = 주황(warn), 확인 중 = 파랑(info), 해결 = 초록(ok).
- 행을 누르면 오른쪽 480px 상세 패널이 열린다.
  - 보낸 사람, 보낸 시각
  - 보낸 곳 한 줄 + [이 화면 열기 ↗]
  - 내용 전문
  - 스크린샷(누르면 크게, 기존 확대 보기 재사용)
  - 상태: koo와 태정님에게는 `접수 | 확인 중 | 해결` 세 칸 버튼. 다른 팀원에게는 칩만 보인다.
  - 해결 답: koo와 태정님에게는 입력 칸(한 줄, 링크 붙여넣기 가능). 다른 팀원에게는 답이 있을 때만 글로 보인다.
  - 버튼: `해결`을 고르면 [취소][해결로 바꾸기], 그 밖에는 바로 저장된다(접수 ↔ 확인 중은 되돌리기 쉬운 표시라 확인을 받지 않는다).
- 보낸 사람이 상세를 열면 그 답을 '봤음'으로 표시한다(숫자 칩이 줄어든다).
- 지우기는 두지 않는다. 잘못 보낸 건은 해결로 닫고 답에 "중복" 등으로 적는다.

## 3. 데이터 — 마이그레이션 083 (추가만, 멱등)

```sql
create table if not exists issue_report (
  id uuid primary key default gen_random_uuid(),
  reporter_id uuid not null references member(id),
  body text not null check (length(btrim(body)) > 0),
  screenshot_path text,                 -- issue-screenshot 버킷 안 경로, 없으면 null
  location jsonb not null,              -- {screen, title, panel, path, taskId, viewport}
  status text not null default 'open'
    check (status in ('open','checking','resolved')),
  reply text,                           -- 해결 답(한 줄)
  replied_by uuid references member(id),
  replied_at timestamptz,
  reply_seen_at timestamptz,            -- 보낸 사람이 답을 본 때 — 안 본 답 수 = reply_at > seen
  status_changed_at timestamptz,
  created_at timestamptz not null default now()
);
create index if not exists issue_report_created_idx on issue_report (created_at desc);
create index if not exists issue_report_reporter_idx on issue_report (reporter_id);
```

- 스크린샷 버킷 `issue-screenshot`: 비공개, 10MB, jpeg/png/webp. 044(task-proof)와 같은 꼴로 만들고(insert … on conflict do nothing + update로 값 맞추기), 정책은 read/insert만 준다. task-proof를 재사용하지 않는 이유: 경로 규칙과 목적이 다르고, 이슈 스크린샷이 정산 증빙 버킷에 섞이면 안 된다.
- 경로: `issue/<yyyy-mm>/<uuid>.<ext>`.
- 스크린샷은 브라우저에서 바로 스토리지에 올리고(증빙과 같은 방식), 서버에는 경로만 보낸다. 서버는 경로가 `issue/` 규칙에 맞는지 확인한다.

## 4. API

| 요청 | 하는 일 | 권한 |
|---|---|---|
| `POST /api/issues` | 새 이슈. body, screenshotPath?, location → 저장 후 슬랙 알림 | 로그인 사용자 |
| `GET /api/issues?tab=todo\|resolved\|mine` | 목록 + 탭별 건수 + 내 안 본 답 수 | 로그인 사용자 |
| `GET /api/issues/unseen` | 사이드바 숫자 칩용 안 본 답 수(가벼운 쿼리) | 로그인 사용자 |
| `PATCH /api/issues/:id` | status, reply 바꾸기 | koo, 태정님만(아니면 403) |
| `POST /api/issues/:id/seen` | 보낸 사람이 답 봤음 | 그 이슈를 보낸 사람만 |

- 신원은 `requireAllowedUser()` → `resolveMember()`로 member를 얻는다.
- 위치(location)는 브라우저가 보낸 값을 그대로 믿되 길이를 자른다(칸마다 200자, path 500자).

## 6. 슬랙 알림

- 새 이슈가 저장된 뒤 슬랙 Incoming Webhook으로 보낸다. 칸으로 나눠 한눈에 읽히게 한다(koo 10-28).
  ```
  🙋 *새 이슈* 박구건
  > 게시일을 10/21로 바꾸고 저장했는데 왼쪽 표에는 10/20으로 그대로 나와요.
  > 새로고침하면 맞게 나와요.

  *화면* 캠페인 › 미모드림의원 10월 방문협찬
  *패널* 작업 @miyuxxx48              ← 열려 있었을 때만
  *창* 기존 방문 작업에 예약 추가     ← 떠 있었을 때만
  *스크린샷* 1장                       ← 있을 때만
  이슈 열기 ↗
  ```
  내용은 인용 상자에 줄바꿈을 살려 300자까지(넘으면 `…`). 링크는 `<요청 origin>/issues?id=<id>`.
- 환경변수 `SLACK_ISSUE_WEBHOOK_URL`(런타임에서만 읽으므로 sensitive 등록 가능). **등록 완료(10-22):** 슬랙 앱 `CB Deck Issues`(A0CC33T5G0Y)의 Incoming Webhook → `#l-tech`(C0A564UESR1). Vercel cb-x-deck에 Production만 등록(Encrypted). 스테이징·로컬에는 없어서 알림이 안 간다. 메시지 보낸 이 이름은 `CB Deck Issues`로 보인다.
- 슬랙 전송이 실패해도 이슈 저장은 성공으로 돌려준다(보낸 사람에게 실패를 보이지 않는다). 실패는 서버 로그에만 남긴다. 값이 없으면(로컬, 스테이징) 보내지 않는다.
- 상태 변경과 해결 답은 슬랙에 보내지 않는다(1차). 보낸 사람은 앱의 숫자 칩으로 안다.

## 7. 테스트

- 단위(tsx): 위치 한 줄 만들기, 비켜서기 자리 계산(패널 폭, 하단 줄 높이를 입력으로 받는 순수 함수), 담당자 판정, 스크린샷 검증, 탭 분류, 안 본 답 계산.
- 스토어(연습용 DB): 저장, 탭별 목록과 건수, PATCH 권한(담당자 아니면 403), seen 처리.
- 화면 확인은 koo가 스테이징에서: 작업 패널을 연 채 보내기, 일괄 처리 바가 뜬 화면, 편집 패널(`EditorParts`) 안 아이콘, 스크린샷 붙여넣기, 슬랙 수신.

## 8. 보류 — 직전 10분 동안 한 일 (koo 10-22 보류)

나중에 되살릴 때를 위해 정리만 남긴다.

- 출처는 전부 그 팀원의 브라우저 안이다: 화면 이동(주소 변화), 버튼 누름(버튼 글자 또는 aria-label), 서버 요청과 성공/실패(브라우저 요청 통로 `fetch` 한 곳에 기록을 건다. 화면이 서버를 부르는 177곳 중 164곳은 `apiFetch`, 13곳은 직접 `fetch`), 화면 오류(error, unhandledrejection).
- 입력한 내용은 남기지 않는다. 서버 요청은 자주 쓰는 30~40개에 사람 말 이름을 붙이고 나머지는 주소로 남긴다.
- 탭이 살아 있는 동안 sessionStorage에 최근 10분을 보관한다(새로고침 전 기록 보존). 불편 알리기를 보낼 때만 서버로 간다. 보내는 창에 "직전 10분 동안 한 일 N건이 함께 가요 [보기]"로 투명하게 보여 준다.
- 서버 로그(Vercel) 자동 첨부는 별도 큰 작업이다.
- 보류한 '사용 행동 트래킹'(08-12)과 다르다: 상시 수집, 분석이 아니라 보낼 때만 붙는다.
