# 정산 API 협의 회신 (협찬 비용 관리 → cb-x-deck, 2026-08-28)

보내주신 「협의 체크리스트 회신」과 최종 명세(`settlement-external-api_최종.md`) 잘 받았습니다. 요청드렸던 사항(집계 키 non-null, `task_id` 연결, 스테이징 가짜 데이터)이 반영되어 감사합니다. 문의하신 4가지에 답하고, 남은 확인 사항을 정리해 보냅니다.

## 1. 문의하신 것에 대한 답

### 1-1. `paid` 이후 되돌림 — **동의합니다**

환불 상태 없이 "paid 이후 변경은 409 + 정정은 사람 협의"로 가는 방식에 동의합니다. 우리 쪽도 환불은 1차 스코프에서 제외했고, 지급 확정 데이터 보호는 우리가 원했던 바입니다. 금액 정정은 `paid → paid` 재전송으로 처리하겠습니다.

### 1-2. 개인정보 보호 방침

결제수단 민감정보(계좌·PayPal 식별값 등)는 다음과 같이 다룹니다:

- **별도 신규 Supabase DB** 사용, 기존 운영 DB와 분리 + 접근 권한 분리.
- 결제수단 민감 필드는 **저장 시 암호화**.
- **RLS(Row Level Security)** 로 DB 접근 제한.
- 화면에서는 **마스킹 표시**(계좌 뒷자리만 표시 등) — 마스킹 수준은 설정에서 관리하며 기본은 마스킹 켜짐.

### 1-3. 기획서 공유 — **공유합니다**

`0828Plan.md`를 함께 보냅니다. 체크리스트 밖 요구(기간 집계 기준일 토글, 금액 기준선 배지 등)와 API 커버리지 대조 부탁드립니다.

### 1-4. 시간대 — **문제 없습니다**

시각 필드 UTC ISO 8601, `deadline` 한국 날짜 방식 그대로 진행해 주세요. 우리 쪽에서 표시 시 KST 변환하고, 데드라인 판정은 한국 날짜 기준으로 합니다.

## 2. "부탁드리는 것" 수용 확인

0. 가져간 직후 `received` 전송 — **수용.** 폴링으로 새 요청(재요청 포함)을 수신하면 즉시 자동 전송하겠습니다.
1. `updated_at`은 우리 서버의 실제 변경 시각 — 수용 (요청별 단조 증가 보장).
2. 실패 시 같은 본문 재전송, 409는 단건 재조회 — 수용.
3. 폴링에서 `cancelled` 확인 시 지급 중단 — 수용. 추가로 우리 쪽에서 **송금 실행 직전 단건 GET으로 취소 여부를 재확인**하는 절차를 넣습니다.
4. 수정 요청은 `on_hold` + `note` — 수용.
5. 요청자 슬랙 멘션은 우리가 발송 — **수용** (`slack_id`, 없으면 `email`로 `users.lookupByEmail`).
6. `payer`/`cc`는 우리 설정으로 — 수용.

## 3. 남은 확인 요청 (4건)

1. **폴링 에코 여부**: 우리가 상태 POST를 보내면 그 건의 최상위 `updated_at`이 갱신되어 다음 폴링에 다시 내려오나요? (우리 쪽 변경 감지·알림 중복 방지 설계에 필요)
2. **우리 발 취소의 사유 전달**: 우리가 `status: cancelled` + `note`를 보내면 `cancelled.reason`에 note가 들어가나요? (§3-1은 그쪽 담당자 취소 케이스만 명시)
3. **`payment_method` 명세 정리**: 회신에는 `type`이 `paypal`/`paypay`/`bank`로 안내됐는데, 최종 명세 필드표에는 "빈 객체 가능"이 남아 있습니다. 결제수단 없는 요청은 업무상 없을 것으로 보이니 **`type` 필수**로 확정 부탁드립니다.
4. **커서 무효화**: 서버 재배포·스키마 변경 등으로 저장해 둔 커서가 무효해지는 경우가 생기면 **반드시 400**을 주시나요? (그러면 우리가 커서를 버리고 전량 재동기화합니다)

## 4. 운영 합의 제안

- **긴급 취소 병행 통지**: 취소 전파가 폴링(5분)이라, 지급 임박 건을 급히 취소하실 때는 슬랙/구두로도 알려주시면 안전합니다.
- 담당자·채널: 사내 직접 소통(오프라인)으로 진행하시죠. 스테이징 URL·키·상세 문서 전달 일정 알려주시면 맞춰 시작하겠습니다.
