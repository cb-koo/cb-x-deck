# 결제 요청 API 연동 협의 체크리스트 (2026-08-28)

> 협찬 비용 관리 프로덕트(신규)가 결제 요청 프로덕트(소스)와 연동하기 위해 확인·협의가 필요한 사항.
> 관련 기획: [0828Plan.md](./0828Plan.md)

## 0. 전제 (우리 쪽 확정 원칙)

- **소스 오브 트루스는 소스 프로덕트.** 우리는 결제 요청 원본을 **수정하지 않는다** (read-only 미러 보관).
- 우리가 소스로 보내는 것: ① 수정 요청 알림 ② 결제 상태 변경 ③ 실제 결제 금액.
- 우리 상태 모델: `접수 → 지급예정 → 완료` + `보류` / `취소`.

## 1. 연동 방식

| # | 확인 사항 | 우리 쪽 제안 |
|---|---|---|
| 1-1 | 결제 요청 데이터를 제공하는 API가 **신설 가능한가?** (현재 없음) | REST + JSON |
| 1-2 | 전달 방식: **웹훅 push vs 우리가 폴링?** | 웹훅(생성/수정/취소 이벤트) + 폴링 백업(누락 대비, 멱등) |
| 1-3 | 인증 방식 | API Key + 웹훅 서명(HMAC) |
| 1-4 | **테스트/스테이징 환경** 제공 여부 | 필수 — 실데이터로 연동 개발 불가 |
| 1-5 | API 변경 시 공지·버저닝 정책 | 스키마에 `version` 포함 |

## 2. 결제 요청 스키마 (필드별 확인)

기존 폼 필드를 기준으로 하되, 아래 항목은 **구조화가 필요**하다:

| 필드 | 확인 사항 | 중요도 |
|---|---|---|
| `request_id` | 결제 요청 건의 **불변 고유 ID** 발급 가능한가? | 필수 |
| `influencer_uuid` | **인플루언서 고유 ID**(UUID) 발급·전달 가능한가? handle 변경에도 UUID 유지 보장 | 필수 |
| `influencer_handle` | 요청 시점의 @handle (표시용) | 필수 |
| `clinic_id` + `clinic_name` | **클리닉이 자유 텍스트면 클리닉별 집계가 깨진다** ("마인드피부과의원" vs "마인드피부과"). 정규화된 클리닉 ID 필요 | 필수 |
| `amount` + `currency` | 금액과 통화 분리. **통화는 ¥ 고정인가, 다통화인가?** | 필수 |
| `amount_krw_estimated` | **잠정 원화 환산액 — 소스에서 계산해 주는가?** 환율 기준(시점·출처) 명시 필요 | 필수 (책임 소재 협의) |
| `payment_method` | 결제수단 **구조화**: `{ type, recipient_name, account }` — 문자열 한 덩어리면 수단별 통계 불가 | 필수 |
| `deadline` | 날짜 포맷(ISO 8601) | 필수 |
| `requester` / `payer` / `cc` | Slack user ID로 주는가? (알림 발송에 사용) | 권장 |
| `category` / `item` / `purpose` | 분류·항목·목적 — 분류는 코드화 가능한가? | 권장 |
| `reference_url` | 참고자료 (X 게시물 URL 등) | 권장 |
| `updated_at` / `revision` | 수정 감지·순서 보장용 | 필수 |

## 3. 인플루언서 엔티티

- 3-1. 소스 프로덕트가 **인플루언서 엔티티를 자체 관리**할 수 있는가? (UUID 발급 주체)
- 3-2. handle 변경 시 **UUID가 유지**되고, 이후 요청에 최신 handle이 실려 오는가?
- 3-3. 기존 생태계의 Supabase 인플루언서 마스터와의 관계는? (독립 운영인지, 연동 계획이 있는지 — 장기 과제로만 확인)

## 4. 수정·취소 전파 (소스 → 우리)

- 4-1. 소스에서 요청이 **수정되면** 어떻게 전파되는가? (웹훅 update 이벤트 + `revision` 증가 제안)
- 4-2. 소스에서 요청이 **삭제·철회될 수 있는가?** 그 경우 이벤트 전파 방식은?
- 4-3. 이미 우리 쪽에서 `지급예정`/`완료`인 건이 소스에서 수정되면? → **완료 건 수정은 차단 또는 별도 합의 필요** (지출 확정 데이터 보호)

## 5. 역방향 수신 (우리 → 소스)

- 5-1. **상태 변경 수신 엔드포인트** 제공 가능한가? (`지급예정`/`보류`/`취소`/`완료`)
- 5-2. **실제 결제 금액(원화 확정치)** 을 소스에 저장·표시할 것인가, 수신만 할 것인가?
- 5-3. 우리가 보내는 **수정 요청 알림**을 어떤 형태로 받고 싶은가? (API? 슬랙 멘션? 둘 다?)
- 5-4. 소스 UI에서도 결제 상태를 표시할 계획이 있는가? (이중 표기 시 기준 화면 합의)

## 6. 운영·정합성

- 6-1. **멱등성**: 모든 이벤트에 `event_id` 포함 → 중복 수신 시 무시 가능하게.
- 6-2. 웹훅 실패 시 **재전송 정책** (횟수·간격)과 우리 쪽 폴링 주기 합의.
- 6-3. **과거 데이터 백필**: 기존 구글폼/슬랙 요청 데이터를 이관할 것인가? 범위(기간)와 형식은?
- 6-4. 양쪽 **기술 담당자** 지정 및 장애 시 연락 채널(슬랙 채널) 합의.

### 우선 순위 요약

1. **API 신설 여부와 일정** (1-1) — 전체 프로젝트의 선결 조건
2. **`influencer_uuid` + `clinic_id` 발급** (2) — 이게 없으면 핵심 문제(인플루언서별·클리닉별 집계)가 해결되지 않음
3. **잠정 원화 환산 책임** (2) — 소스 계산으로 합의 필요
4. 나머지 항목은 킥오프 미팅에서 순차 협의
