# 인플루언서 성과 페이지 — 설계

- 날짜: 2026-09-30 · 브랜치 `cb-koo/influencer-performance`(origin/main `33e0980`에서)
- 대상: 새 화면 `/influencers/performance` + 사이드바 메뉴 1개
- DB 변경 없음(마이그레이션 0) — 기존 `campaign_task`·`tracked_post`·`post_metric_snapshot`·`influencer`를 읽기만 한다.

## 1. 왜

기존 `/influencers`는 **한 명씩** 여는 명부·프로필 화면이라, 여러 인플을 나란히 놓고 비교할 수 없다.
이 페이지의 목적은 **캠페인에 참여시킬 인플을 빠르게 선별하는 것** — 전체 인플의 성과를 한 표에서 한눈에 보고 지표별로 줄 세운다(koo 09-30).

- **표의 주인공은 성과 지표다.** 인플 식별·이력은 왼쪽에 짧게, 나머지 폭은 성과에. 성과를 펼친 영역으로 숨기지 않는다(koo 지적 — 한눈에 판단하려면 표에 보여야 한다).
- 펼친 영역은 **근거 확인용**("이 숫자가 어느 게시물에서 나왔지?").

## 2. 성과의 기준 (koo 결정)

- **A = 우리 캠페인에서 낸 성과**만 쓴다: 작업(`campaign_task`)에 붙은 게시물의 최신 지표.
- **B = 계정 평소 실력**(`influencer.analysis`, 8주 조회 중앙값 등)은 이번 범위 밖 — 나중에 필요하면 열을 추가한다.

## 3. 대상 행

- **작업을 1건 이상 한 인플**만(09-30 기준 56명). 명부 전원(약 160명)은 넣지 않는다.
- **취소된 작업(`cancelled_at is not null`)은 모든 계산에서 제외**(건수·캠페인 수·최근 게시일·성과 전부).
- 미배정 작업(`influencer_handle is null`)은 제외. 핸들 비교는 `lower()`(리포 관례).
- 명부에 없는 핸들이 작업에 있으면 행은 만들되 사진·이름 없이 `@핸들`만 표시한다.

## 4. 표

한 행 = 한 줄. 인플 열은 가로 스크롤 시 고정. **모든 수치 열에서 정렬**(머리 첫 클릭 → **좋은 쪽부터**: 대부분 내림차순, **조회당 비용만 오름차순**(싼 쪽이 좋음) / 한 번 더 → 반대). 값 없음(`—`)은 정렬 방향과 무관하게 항상 맨 아래.

열 머리는 두 줄 — 위에 묶음 이름, 묶음 사이 구분선.

| 묶음 | 열 | 정의 |
|---|---|---|
| — | **인플** | 사진 · 이름 · @핸들 (고정 열) |
| 이력 | **캠페인** | 참여 캠페인 수(서로 다른 `campaign_id`) |
| 이력 | **최근 게시일** | 가장 최근 `campaign_task.posted_at`(게시 확인일, 서울 날짜) `M/D`. 게시 전 작업만 있으면 `—`. 예정·취소 작업은 쓰지 않는다 |
| 작업 | **투고 · 인용RT · RT · 방문협찬** | 유형별 작업 건수(4열, 유형 순서는 `DISPLAY_TYPE_ORDER`). **게시 전 작업도 센다**(캠페인 화면 건수와 일치). 투고는 현재 0건이어도 열 유지 |
| 노출 | **조회** | 게시물 작업별 조회의 중앙값/평균 |
| 노출 | **조회당 비용** | 게시물 작업별 (비용 원화 ÷ 조회)의 중앙값/평균, `○.○원` |
| — | **참여율** | 게시물 작업별 (좋아요+답글+북마크+RT+인용) ÷ 조회의 중앙값/평균, `○.○%` |
| 반응 | **좋아요 · 답글 · 북마크** | 게시물 작업별 값의 중앙값/평균 |
| 확산 | **RT수 · 인용수** | 게시물 작업별 값의 중앙값/평균 |

작업 묶음의 `RT`(건수)와 확산 묶음의 `RT수`(지표)는 이름으로 구분한다.

### 4-1. 성과 계산 규칙

- **성과 표본 = 게시물이 있는 작업**: 유형이 `post`·`quoteRt`·`visit`이고 조회(`views`)가 수집된 작업. **RT(`rt`)는 건수만 세고 성과 표본에서 제외** — RT는 조회가 원글에 쌓여 인플 몫이 없고, 넣으면 중앙값이 0 쪽으로 끌려간다.
- **작업 1건의 지표** = 그 작업(`tracked_post.task_id`)에 붙은 게시물들의 **최신 스냅샷 합** — 캠페인 화면(`campaignStore` 성과)과 같은 방식이라 두 화면 숫자가 어긋나지 않는다.
- 스냅샷에 조회가 없는(null) 작업은 표본에서 뺀다. 개별 반응 지표가 null이면 그 지표의 표본에서만 뺀다.
- 참여율: 반응 5가지 중 null이 있으면 **그 작업을 참여율 표본에서 뺀다**(0으로 채우면 참여율이 낮게 왜곡된다).
- 조회당 비용: 비용이 없는(null) 작업은 그 표본에서 뺀다(09-30 현재 전 작업에 비용 있음).
- **비율은 작업마다 먼저 계산한 뒤 모은다**(참여율·조회당 비용). 한 게시물의 큰 조회가 비율을 혼자 좌우하지 않게.
- 조회가 0인 작업은 비율 표본에서 뺀다(0으로 나누기 방지).
- **비용 환산**: 엔화는 기존 규칙(1엔=10원, `clientBudget.toKrw`)으로 원화로 바꾼다. 조회당 비용에는 **게시물 작업의 비용만** 쓴다(RT 비용을 넣으면 조회 없는 돈이 섞여 부풀려진다).
- 평균·중앙값 계산은 `analysisStats.median`을 재사용한다.
- RT만 한 인플은 성과 칸 전부 `—`.

### 4-2. 중앙값 / 평균 전환

- 표 위 `[중앙값 | 평균]` 토글. 기본 **중앙값**(한 번 터진 글에 덜 흔들림 → "맡기면 보통 이 정도").
- 성과 열 전체와 정렬이 선택한 기준으로 바뀐다. 표 칸에 둘을 나란히 두지 않는다(열이 두 배가 됨).

### 4-3. 표본 부족 표시

- 조회 칸 옆 건수 괄호는 두지 않는다 — 유형별 작업 열이 곧 표본 수다.
- **예외**: **게시된** 게시물 작업 수(유형 `post`·`quoteRt`·`visit` 중 `post_url` 또는 `posted_at`이 있는 것) ≠ 성과 표본 수(조회 미수집이 있음)일 때만 조회 칸에 흐린 `2/3`(표본/게시된 게시물 작업)을 붙인다. 평소엔 숫자만.
- 게시 전 작업은 분모에 넣지 않는다 — 넣으면 예정 작업이 있는 인플마다 '미수집'처럼 보인다(09-30 기준 게시 전 10건 vs 실제 미수집 3건).

### 4-4. 참여율 도움말

열 머리 도움말: `공개 반응(좋아요·답글·북마크·RT·인용) ÷ 조회 · X 분석 화면보다 낮게 나와요 (클릭 수 미포함)`.
근거: X 공식 참여율은 비공개 클릭까지 포함한 참여 ÷ 노출이고, 인플 마케팅 업계엔 단일 표준이 없으며 조회(도달) 기준이 흔히 쓰인다(09-30 조사).

### 4-5. 기본 상태와 주소

- 첫 진입: **조회 내림차순**, 중앙값.
- 정렬 기준·방향과 중앙값/평균 선택은 주소(쿼리)에 둔다 — 새로고침·링크 공유 시 유지. 쿼리가 틀린 값이면 기본값으로.
- 주소 갱신은 `history.replaceState`로 한다(`router.replace` 금지 — 서버 왕복으로 클릭이 멈추던 캠페인 목록 사례, 09-27 수정).

## 5. 행 펼치기

행 클릭 → 그 아래에 그 인플의 **작업 목록**(최근 게시일 내림차순, 게시 전 작업은 맨 아래).

| 날짜 | 캠페인 | 유형 | 비용 | 조회 | 참여율 | 좋아요 | 답글 | 북마크 | RT수 | 인용수 | 게시물 |
|---|---|---|---|---|---|---|---|---|---|---|---|

- 성과 열 순서는 위 표와 같다(눈으로 따라 내려가며 비교). 조회당 비용은 작업 목록에서는 비용·조회 칸으로 대신한다.
- 날짜 = `campaign_task.posted_at`(표의 최근 게시일과 같은 칸), 게시 전이면 `게시 전`.
- 비용은 원래 통화로 표시(`formatAmount`).
- RT 작업: 성과 칸 자리에 `RT는 조회가 원글에 쌓여요`.
- 게시물은 있으나 조회 미수집: `수집 전` — 계산에서 빠진 이유가 보이게.
- 게시물 칸 `↗` = X 원 게시물 새 창(`post_url`, 없으면 칸 비움).
- 맨 아래 **[인플루언서 프로필 열기]** → `/influencers?i={id}`(명부에 없는 핸들이면 숨김). 단가·정산 수단·메모는 여기서 반복하지 않는다.
- 여러 행을 동시에 펼칠 수 있다. 펼침 상태는 주소에 두지 않는다.

## 6. 위치

- 사이드바 `인플루언서` **바로 아래** 새 메뉴 **`인플루언서 성과`**(`/influencers/performance`). `성과`만 쓰면 기존 `콘텐츠 성과`와 헷갈린다.
- 사이드바 활성 표시는 주소 완전 일치(`pathname === href`)라 `인플루언서`와 동시에 켜지지 않는다.
- 명부(한 명씩 관리)와 성과 비교(여럿을 줄 세우기)는 다른 일이라 화면을 나눈다.
- 페이지 상단 한 줄 도움말(UX 원칙 2): `캠페인에 참여한 인플의 게시물 성과를 비교해요. 열 이름을 누르면 그 기준으로 줄을 세워요.`

## 7. 구조

- **API** `GET /api/influencers/performance` → 인플별 행 + 작업 목록(작업마다 유형·캠페인·게시일·비용·post_url·최신 지표 합). 워크스페이스 무관(인플루언서 명부와 같은 최상위). 인증은 기존 API와 같은 가드.
- **스토어**(`src/lib/influencerPerformanceStore.ts`): SQL 한 번으로 작업 + 최신 스냅샷 합(`campaignStore`의 lateral 방식) + 명부 조인.
- **계산 모듈**(`src/lib/influencerPerformance.ts`, 순수 함수·DB 없음): 행 집계(건수·캠페인 수·최근 게시일·지표별 중앙값/평균·표본 수) + 정렬(null 맨 아래). 전환·정렬은 클라이언트에서 이 모듈로 바로 계산 — 데이터가 작아(작업 약 113건) 서버를 다시 부르지 않는다.
- **화면**(`src/app/influencers/performance/page.tsx` + 표 컴포넌트): 기존 표 스타일·가독성 기준(14~15px, 행 44px 이상, 한 행 한 줄).

## 8. 오류·빈 상태

- 로드 실패는 빈 상태로 위장하지 않고 오류 문구 + 다시 시도(`/influencers` 관례).
- 작업이 하나도 없으면: `아직 캠페인 작업이 없어요 — 캠페인에서 작업을 만들고 게시되면 여기에 성과가 모여요` + 캠페인 바로가기.

- 취소 작업은 어디에도 안 들어간다

## 12. QA 1차 반영 (koo 09-30)

화면 확인 뒤 결정. **아래가 위 절과 충돌하면 이 절이 우선한다.**

### 12-1. 표 모양 = 정산 표 공용 모양
다른 화면 표(정산·캠페인)와 달라 보인다는 지적. 정산 표 공용 모양(`src/app/settlement/tableStyle.ts`, koo 09-28 확인)을 기준으로 맞춘다.
- 열 머리: 연회색 배경·보통 굵기(semibold)·회색 글자 — `HEAD` 상수 재사용. 굵은(bold) 머리·흰 배경 금지.
- 본문 칸: `CELL` 상수(행 48px·흐린 아래선) 재사용, 본문 15px.
- 인플 칸: **사진 + `@핸들`(굵게) 하나만.** 이름은 마우스를 올리면(title) 보인다 — 이름과 핸들이 둘 다 잘리던 문제.
- 묶음 머리 줄(이력·게시한 작업·노출·반응·확산)은 남기되 작고 흐리게. 세로 구분선은 묶음 경계에만 흐린 선으로.
- 표 전체 폭은 1440px 노트북에서 가로 스크롤이 없게 유지(현재 1168px 이하).

### 12-2. `n/m 수집` 표시 제거 (§4-3 대체)
표 조회 칸에 표본 부족 표시를 두지 않는다. 이유는 펼친 화면의 게시물 줄(`수집 전`/`삭제됨`)에서 보인다. 원인이던 3건은 데이터 오류(잘못 붙은 링크·끊긴 연결·등록 누락)였고 09-30에 바로잡음.

### 12-3. 작업 건수 = 게시된 작업 (§4 작업 열 대체)
- 유형별 건수는 **게시된 작업만** 센다: `posted_at` 또는 `post_url`이 있는 것(RT도 같은 규칙). 예정 작업은 세지 않는다 — 섭외 판단엔 "실제로 해 본 횟수"가 필요하다.
- 묶음 이름 `작업` → **`게시한 작업`**. 캠페인 화면(예정 포함)과 숫자가 다를 수 있음을 이름으로 드러낸다.
- 캠페인 수도 게시된 작업이 있는 캠페인만 센다.
- **대상 행(§3 대체)**: 게시된 작업이 1건 이상인 인플. 예정만 있는 인플은 표에 없다.
- 펼친 작업 목록은 예정 작업도 그대로 보여준다(`게시 전` 표시) — 곧 할 일도 판단 참고.

### 12-4. 삭제된 게시물
- 작업의 `removed_at`(게시 내림일)이 있으면 그 작업은 성과 표본에서 뺀다(조회가 남아 있어도). 게시한 작업 건수에는 센다(일은 했다).
- 펼친 화면 성과 자리: `삭제됨` + 사유(`removed_reason`, 있으면) — `수집 전`보다 우선.

## 13. QA 2차 반영 (koo 09-30) — §5·§12보다 우선

1. 인플 칸 `@핸들` 굵기: semibold → **medium**.
2. **펼친 행 = 부모와 같은 열 격자.** 별도 안쪽 표를 없애고, 작업마다 같은 `<table>`의 행으로 넣는다(같은 colgroup) — 숫자가 부모와 같은 세로줄에 선다.
   - 인플 열: 캠페인 이름(들여쓰기, 한 줄 말줄임) + `↗`(post_url 있을 때 새 창). 별도 게시물 열은 없앤다.
   - 캠페인 열: 비움. 최근 게시일 열: 그 작업의 게시일(`M/D`, 게시 전이면 `게시 전`, 게시됐는데 날짜 없음 `—`).
   - 게시한 작업 4열: 하나로 합쳐 `유형 · 비용`(비용 원래 통화, 없으면 유형만).
   - 노출~확산 열: 그 작업의 값을 부모와 같은 열에(조회·**조회당 비용(taskCpv)**·참여율·좋아요·답글·북마크·RT수·인용수).
   - 성과가 없는 작업은 노출~확산 열을 합친 한 칸에 사유: `삭제됨 · {사유}` > RT 안내(`RT는 조회가 원글에 쌓여요`) > `게시 전`(—로 둬도 됨: 게시일 칸이 이미 말함) > `수집 전`.
   - 자식 행 배경은 부모보다 한 톤 흐리게, 행 높이는 부모보다 약간 낮아도 된다(≥ 40px). 맨 아래 행에 `인플루언서 프로필 열기 →`(명부에 있을 때만).
3. **큰 수는 전부 표시**: 조회·좋아요·답글·북마크·RT수·인용수는 `5,611`처럼 쉼표 전체 숫자(`formatKoCount` 축약 금지). 조회당 비용(`○.○원`)·참여율(`○.○%`)은 그대로. 표 폭은 1168px 이하 유지 — 가장 큰 조회 `528,625`가 조회 열에 잘리지 않아야 한다.

## 14. QA 3차 반영 (koo 09-30, 시안 B 채택) — §13 색·프로필 링크보다 우선

- **작업(자식) 행 = 흰 바탕**, 글자 한 단계 흐리게(`text-x-secondary`)·14px, 행 높이 40px. 회색(`x-surface`) 바탕 금지 — 열 머리와 같은 색이라 표 안에 머리가 또 있는 것처럼 무거웠다. sticky 인플 칸도 흰 바탕.
- **펼친 인플(부모) 행만 옅은 파랑**(`#f2f8fd` 수준, 예: `bg-x-blue/5`) — 여러 명을 펼쳐도 누가 열렸는지 보이게. sticky 칸도 같은 색. hover도 이 색과 충돌하지 않게.
- 묶음 끝(마지막 작업 행 아래)은 진한 선(`border-x-border-strong`)으로 다음 인플과 구분.
- **`인플루언서 프로필 열기` 줄 삭제.** 대신 `@핸들`이 프로필 링크(`/influencers?i={id}`) — hover 시 밑줄, 클릭은 이동만(행 펼침 토글 안 함). 명부에 없는 핸들은 링크 없이 글자만. 행의 나머지 영역 클릭·▸ 버튼은 펼침 토글 그대로.

## 15. 필터·검색 (koo 09-30 승인) — §10의 '기간 필터·유형 칩'을 여기서 구현

### 15-1. 두 종류
- **① 사람 좁히기** — 행만 거른다, 숫자 불변: **검색**(핸들·표시 이름, 대소문자 무시, 공백 무시 부분 일치), **최소 게시 수**(`1건 이상`(기본) / `2건 이상` / `3건 이상` — 필터 적용 후 게시한 작업 수 기준).
- **② 성과 범위 바꾸기** — 계산에 쓸 작업을 먼저 거른 뒤 §4-1·§12·§13 규칙으로 다시 집계: **기간**(`전체 기간`(기본) / `최근 30일` / `최근 90일` — 게시일(서울) 기준, 오늘 포함 N일, `kstDaysAgo` 사용. 게시 전 작업은 기간 필터가 켜지면 빠진다), **클라이언트**(`전체 클라이언트` + 데이터에 있는 클라이언트 이름 목록, 캠페인의 `client_id`/`client_name` 스냅샷 기준), **유형**(`전체 유형` / 투고 / 인용RT / RT / 방문협찬).
- ②가 걸리면 게시한 작업 열·캠페인 수·최근 게시일·성과·펼친 작업 목록이 **모두 걸러진 작업 기준**(라벨-값 일치). 걸러진 작업이 게시 0건인 인플은 표에서 빠진다.

### 15-2. 화면
- 표 바로 위 한 줄: 왼쪽 검색칸(돋보기, placeholder `핸들·이름 검색`) → 드롭다운 4개(기간·클라이언트·유형·최소 게시 수) → 오른쪽 끝 기존 `[중앙값|평균]` 토글과 도움말. 좁으면 줄바꿈(가로 스크롤 금지).
- 모양은 정산 화면 필터(`src/app/settlement/CandidateTable.tsx`의 `SEL`)·캠페인 검색칸(`src/app/campaigns/flow/FlowFilterBar.tsx`)과 같은 계열. 기본값이 아닌 드롭다운은 **켜진 상태가 보이게**(테두리·글자색을 파랑 계열로 한 단계 강조).
- 필터가 하나라도 켜지면 표 위에 요약 한 줄(작은 회색): `{클라이언트} · {기간} · {유형} 게시물만으로 계산했어요 · {n}명` (②가 없고 ①만이면 `{n}명` + 검색어/최소 게시 수 요약) + 오른쪽 `필터 지우기`(텍스트 버튼). 필터 없으면 줄 자체가 없다(레이아웃 점프 최소화: 높이 고정 자리 없이 조용히 나타남 OK).
- 결과 0명: 표 대신 `조건에 맞는 인플이 없어요` + `필터 지우기`.
- 상태는 주소 쿼리에(`q`, `period=30|90`, `client={id}`, `type=post|quoteRt|rt|visit`, `min=2|3`), 기본값은 생략, `history.replaceState`(§4-5와 같은 방식). 검색 입력은 타이핑마다 주소를 갱신해도 되나 입력이 끊기지 않게(상태는 로컬 즉시, 주소는 디바운스 가능).

### 15-3. 데이터
- 스토어가 작업마다 `clientId`·`clientName`(캠페인의 client_id, client_name 스냅샷)을 추가로 내려준다. DB 변경 없음.
- 필터·집계는 클라이언트에서 계산 모듈 순수 함수로(`filterTasks`/행 필터) — 서버 재호출 없음. 규칙은 단위 테스트로 고정.

## 16. 필터 2차 (koo 09-30) — §15의 기간·클라이언트·유형·최소 게시 수 UI를 대체

- **기간**: 빠른 선택 세그먼트 `[전체 | 7일 | 30일 | 60일 | 90일]` + `직접 지정 [시작일] ~ [종료일]`(`<input type="date">`, 모양은 `src/app/performance/page.tsx`의 기간 그룹·직접 지정과 같게). 빠른 선택 N일 = 오늘 포함 N일(서울). 직접 지정은 **둘 다 있을 때만 적용**(시작·종료 포함, 서울 게시일 기준). 한쪽만이면 적용 안 하고 흐린 안내(`종료일도 골라 주세요` / `시작일도 골라 주세요`). 날짜를 고르면 빠른 선택은 꺼진 상태로 보인다. 시작>종료는 입력 min/max로 막는다. 주소: `period=7|30|60|90` 또는 `from=YYYY-MM-DD&to=YYYY-MM-DD`(기본 전체는 생략).
- **클라이언트·유형: 복수 선택.** 버튼(`클라이언트: 전체 ▾` / `백수약국` / `백수약국 외 1`, 유형은 `인용RT, 방문협찬`처럼 2개까지 나열·3개 이상 `인용RT 외 2`) → 체크박스 목록 팝오버(캠페인 화면 `FlowFilterBar`의 FilterGroup 모양·동작: 바깥 클릭/ESC 닫기). 항목 오른쪽 숫자 = 현재 다른 필터 기준 그 항목의 **게시된 작업 수**(없어도 목록엔 남김). 맨 아래 `모두 해제`. 아무것도 안 고르면 전체. 선택 안 OR, 필터 간 AND. 주소: `client=id1,id2`, `type=quoteRt,visit`(모르는 값은 무시).
- **최소 게시 수: 직접 입력.** 문장형 `게시 [ n ]건 이상`(숫자 입력, 정수 ≥1, 폭 좁게, 키보드 ↑↓·스핀 버튼). 비움·0·음수·소수는 1로 정규화(= 필터 없음). 주소 `min=n`(1은 생략). 타이핑 중엔 입력값을 그대로 두고 적용값만 정규화(입력이 튀지 않게).
- **배치 2줄**: 1줄 = 검색 · 클라이언트 · 유형 · `게시 [n]건 이상` ··· 오른쪽 끝 `[중앙값|평균]`+도움말. 2줄 = 기간 세그먼트 · 직접 지정. 그 아래 요약 줄(§15-2 형식, 기간은 `최근 30일` 또는 `9/1~9/30`) + `필터 지우기`. 모든 컨트롤 높이 통일, 켜진 필터는 파랑 강조(§15-2).

## 17. 기간 필터 제거 (koo 09-30) — §15·§16의 기간 부분 삭제

- 기간 필터(빠른 선택·직접 지정)를 **화면·계산·주소에서 모두 뺀다.** 이유: 작업 데이터가 9월 한 달뿐이라 30/60/90일은 전체와 같고, 7일은 인당 게시물 1건 남짓이라 비교 기준이 안 된다. 최근성은 `최근 게시일` 열(정렬 가능)로 본다.
- 필터 줄은 **한 줄**: 검색 · 클라이언트 · 유형 · `게시 [n]건 이상` ··· `[중앙값|평균]`. 요약 줄에서 기간 표기 제거.
- 옛 주소의 `period`/`from`/`to`는 조용히 무시한다.
- **재검토 조건:** 작업 데이터가 3개월 이상 쌓이면 다시 넣는다(구현은 커밋 8fc0471 이력 참고).
