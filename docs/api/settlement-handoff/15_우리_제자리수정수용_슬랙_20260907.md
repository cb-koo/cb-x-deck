「제자리 수정」 제안 확인했습니다. **수용합니다.** 요청을 취소하고 새로 만드는 대신, 같은 `request_id`·정산코드를 유지한 채 요청을 고쳐 개정 번호를 올려 다시 내려보내겠습니다. §9의 기본안 5개도 그대로 받습니다. 저희가 진행하는 방식과, 그쪽에 부탁드릴 3가지를 정리합니다.

*1. 저희가 이렇게 바꿉니다*
• 지급 전(`paid` 이전) 요청은 저희 담당자가 제자리에서 고칩니다. `request_id`·`external_id`·`task_id`는 그대로, `revision`은 +1, `status`는 `requested` 유지, `updated_at` 갱신.
• 고칠 때 `settlement.*`(status·note·paid 필드)를 비워 보냅니다. `external_id`는 유지합니다. 그쪽이 `received`부터 다시 처리해 주시면 됩니다.
• `revision`의 뜻이 바뀝니다: 앞으로는 **수정 횟수**(0, 1, 2…)입니다. 취소 여부는 `status`로만 보세요. 취소된 요청도 `revision`은 그때까지의 수정 횟수를 그대로 가집니다.
• 고칠 수 있는 값: 요청을 만들 때 정하는 값 전부(금액·수수료·결제 수단·분류·마감·참고 링크). 고친 값은 새 요청을 만들 때와 같은 검사(증빙·링크·결제 수단)를 다시 통과해야만 반영됩니다.
• 지급 완료된 요청은 고칠 수 없습니다. 금액 정정은 지금처럼 `paid → paid` 재전송만 씁니다. 진짜 폐기는 지금처럼 `cancelled`입니다.
• 저희 쪽에는 고치기 전 내용을 개정 이력으로 남깁니다(돈 기록 보존). 그쪽 API에는 나가지 않습니다.

*2. 그쪽에 부탁드리는 것 (3가지)*

① **상태 POST에 `revision`을 함께 보내 주세요.**
   저희가 2판으로 고친 직후, 그쪽이 1판에 대해 보낸 "지급 예정"이 늦게 도착하면 2판에 잘못 붙습니다. 이를 막기 위해 상태 본문에 `"revision": <그쪽이 마지막으로 받은 값>`을 넣어 주세요. 저희는 현재 판과 다르면 **409** `{ code: "revision-mismatch", request: Item }`로 거절하고 최신 아이템을 돌려드립니다 → 그쪽은 그 아이템으로 재검토 후 다시 보내면 됩니다. (전환 후에는 이 필드가 필수입니다.)

② **송금을 실행하는 순간 `paid`를 먼저 보내 주세요.**
   저희 쪽 수정은 `paid`가 도착한 뒤에는 막힙니다. 송금을 이미 눌렀는데 `paid`가 아직 안 온 사이에 저희가 고치면, 돈은 옛 금액으로 나가고 서류만 새 금액이 됩니다. 송금 실행과 `paid` 전송을 같은 시점에 해 주시면 이 틈이 없어집니다. (그쪽 CRITICAL 규칙과 같은 방향입니다.)

③ **`revision`을 0/1이 아닌 정수로 받도록 바꿔 주세요.** (§6에 이미 적어 주신 내용의 확인입니다.)

*3. 배포 순서 — 그쪽이 준비되기 전에는 지금과 똑같이 나갑니다*
• 저희는 새 동작을 **스위치로 잠가서** 먼저 배포합니다. 스위치가 꺼진 동안은 `revision`도 지금처럼 0/1, 수정 기능도 화면에 없습니다.
• 그쪽 배포가 끝났다고 알려 주시면 저희가 스위치를 켭니다. 그 시점부터 `revision`이 수정 횟수로 바뀌고 제자리 수정이 나갑니다.
• 그래서 "누가 먼저 배포하나"를 맞출 필요가 없습니다. 스위치를 켜는 시각만 슬랙으로 맞추면 됩니다.

*4. 일정*
1. 저희가 명세 개정 초안(§3-1·§5 `revision`·§6 `revision` 필드·409 규칙)을 써서 보냅니다 — 이번 주 중.
2. 초안에 이견 없으시면 저희 구현·배포(스위치 꺼짐) — 초안 합의 후 2~3일.
3. 그쪽 배포 완료 알림 → 저희 스위치 켜기.
• 전환 전까지는 현행(취소 + 재요청)으로 운영합니다. 그쪽 임시 스레드 봉합은 그때까지 유지해 주세요.
