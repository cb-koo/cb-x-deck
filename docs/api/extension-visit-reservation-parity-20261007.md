# 익스텐션 수정 항목 — 웹 방문 예약 구현 기준 (2026-10-07)

웹(cb-x-deck, `feat/visit-reservation` 작업 트리)에 구현된 방문 예약 기능을 기준으로, 크롬 익스텐션(`cb_x_extension`)이 고쳐야 할 것을 항목별로 정리했다. 서버 코드·웹 화면 코드·익스텐션 코드를 모두 읽고 대조한 결과이며, **실행·연동 테스트는 하지 않았다**(양쪽 저장소 모두 2026-10-06 문서에 "서버 연동 미실행"으로 적혀 있고, 익스텐션 저장소는 커밋이 없다).

## 0. 읽는 법

- **[필수]** 지금 코드대로면 서버와 어긋나 오동작하거나, 웹과 눈에 띄게 다른 것. 연동 전에 고친다.
- **[권장]** 웹과 같은 사용 경험을 위해 맞추는 것(문구·순서·버튼). 기능은 돌아간다.
- **[선택]** 있으면 좋지만 없어도 웹과 어긋나지 않는 것.
- **[결정]** 익스텐션 혼자 정할 수 없는 것. 서버·정책 결정이 먼저다. 5장에 모았다.
- 익스텐션 경로는 `cb_x_extension/src/` 기준, 웹·서버 경로는 `cb-x-deck/src/` 기준이다.
- 문구는 코드에 있는 그대로 인용했다. 익스텐션은 서버 `error.message`를 사용자에게 그대로 보여 주므로, 서버 문구는 여기 적힌 것이 곧 화면 문구다.
- 서버 계약의 정본은 `src/lib/extensionProductApi.ts`, `reservationCommands.ts`, `reservationPolicy.ts`, `reservationSheet.ts`다. 이 문서와 코드가 다르면 코드가 맞다.

## 0-2. 서버 적용 기록 (cb-x-deck, 2026-10-07)

0-1의 결정 중 서버 몫을 이 저장소에 적용했다. 실행·연동 테스트는 여전히 하지 않았다(순수 판정 테스트·타입 검사·린트만 통과).

| 결정 | 바뀐 것 | 파일 |
|---|---|---|
| D-1 | 동의서 첨부·교체·제거는 취소·노쇼로 끝나기 전 **어느 단계든**(대기·완료 포함) 허용. `allowedActions`의 `manage_consent`가 그 범위를 그대로 알려 준다. 거부 문구: '취소되거나 노쇼로 끝난 예약에는 동의서를 변경할 수 없어요.' | `reservationPolicy.ts`, `reservationAgreement.ts` |

| D-3 확인 대기 | '방문 노쇼' 명시 기록을 위해 `kind`를 **선택 항목**으로 남겼다(`{ kind: 'visit_no_show', reason?, note? }` → 그 종류를 단계 규칙으로 검증). 익스텐션에 종류 선택을 남길지, 서버 규칙에 분기를 넣을지는 아직 결정 전 — 결정되면 이 항목을 지우거나 고정한다. | `reservationCommands.ts` |
| 문서 | handoff 문서의 `features` → `featureFlags`, `/end` 본문, 동의서 게이트, 오류 코드 표를 코드에 맞췄다. | `docs/api/extension-product-local-handoff.md` |

## 2. 계약·공통 (A)

### A-1. [필수] 기능 플래그와 쓰기 게이트

- 서버 `GET /session`은 `featureFlags: { writes, reservations, consents }`를 준다(`src/app/api/extension/v1/session/route.ts`). handoff 문서의 `features`라는 이름은 틀렸다. 지금은 세 값이 항상 같지만(테이블 존재 && `EXTENSION_PRODUCT_ENABLED`가 false가 아님) 웹은 `reservations`로 예약 UI를, `consents`로 동의서를 가린다. 익스텐션도 `writes`만 보지 말고 셋을 각각 쓴다(`extension/live.ts:25`).
- 서버는 `writes`가 false면 **모든 비GET**에 `SERVER_NOT_READY` 503 '예약 기능의 서버 준비가 아직 끝나지 않았어요. 관리자에게 설정 적용을 요청해 주세요.'를 준다. 카드의 `방문완료`가 `writesReady` 검사 없이 호출된다(`ExtensionApp.tsx:219-230`). 게이트에 넣는다.
- `supportedClientVersions`는 서버가 읽지 않는 안내값이다(`X-Client-Version` 미검사). 비교 로직은 필요 없다.

### A-3. [필수] 버전(If-Match) 출처

- 서버 트리거(064)는 **예약 쓰기마다 `campaign_task`도 갱신해 `task.version`을 올린다**(예약 생성·수정·확정·종료·동의서 확정·제거 모두). 웹의 메모·금액·게시 확인·동의서 붙이기도 올린다.
- 익스텐션의 `방문완료`는 목록 카드의 `task.version`(`ExtensionApp.tsx:222`), 종료·삭제는 상세를 열 때 받은 `task.version`(`TaskDialog.tsx:135, :154`)을 보낸다. 그 사이에 예약을 한 번이라도 고쳤으면 `VERSION_CONFLICT`가 난다. 호출 직전에 `GET /tasks/{id}`(또는 예약 상세의 `task.version`)를 다시 읽어 보낸다. 웹은 `detail.task.version`을 쓴다.
- 예약 쓰기(수정·확정·중단·동의서)는 `reservation.version`이 맞다. `consents/uploads`는 버전을 올리지 않으므로 prepare와 finalize에 같은 값을 보내는 지금 방식은 맞다.
- 서버는 따옴표를 벗겨 `^[1-9]\d{0,8}$`로 읽는다. 익스텐션의 `"\"<version>\""`는 그대로 둬도 된다.

### A-4. [권장] 이름은 한글·로마자 두 칸

- 웹 수정 창은 '이름(한글/로마자)'을 **한글·로마자 두 칸**으로 받고 시트에는 `한글(로마자)`로 저장한다(`reservationSheet.formatReservationName`). 서버 `fields`는 `name`(한글만)·`romanizedName`(로마자만)으로 쪼개 준다.
- 익스텐션의 단일 `name` 칸(placeholder "곤도 사에(kondo sae)")은 줄 전체 문자열을 그대로 보내므로 **지금도 저장은 깨지지 않는다.** 바꾸는 이유는 웹과 같은 입력 경험이다.
- 두 칸으로 나누면 반드시 `fieldEdits`에 `name`과 `romanizedName`을 **둘 다** 넣는다. 서버는 `name`만 오면 이름 줄 전체를 그 값으로 바꾸고(로마자가 사라짐), `romanizedName`이 함께 오면 `formatReservationName({korean: name ?? 기존, roman})`으로 합친다(`reservationCommands.ts:43-49`). worker `EDIT_KEYS`(`messages.ts:60`)에 `romanizedName`을 추가한다. 표시는 `fields.name`·`fields.romanizedName`을 쓴다(`sheetFields.name`은 원문 줄).

### A-5. [필수] 업로드 기한과 `deadlineMode`

- 서버 PATCH/confirm body는 `{ sheetText | fieldEdits, deadlineMode?, reason? }`. `fieldEdits.uploadDeadline`(YYYY-MM-DD)을 받고, `deadlineMode`를 생략하면 저장된 방식을 유지한다.
- 규칙: `default`면 저장할 때마다 서버가 기한을 **방문일 + 14일**로 덮어쓴다(방문 다음 날이 1일차, 주말·공휴일 포함). `manual`이면 시트의 날짜를 유지하되 유효한 날짜여야 하고(`DATE_INVALID`), 방문일보다 이르면 `DEADLINE_BEFORE_VISIT`(방문 당일은 허용).
- 익스텐션은 생성 때 `deadlineMode: "default"`를 고정 주입하고(`api/client.ts:112`) 수정·확정에는 기한 관련 값을 전혀 보내지 않는다. 웹은 수정 창과 날짜 줄에서 기한을 직접 고친다(B-4). 익스텐션도 `uploadDeadline` 키와 `deadlineMode`를 보낼 수 있게 타입(`ReservationEdit`)·worker 검증(`EDIT_KEYS`)·클라이언트를 열어 둔다. 웹 규칙: 기한을 정확히 방문일+14로 고르면 `default`, 다른 날이면 `manual`.
- `uploadDeadline`만 보내고 `deadlineMode`를 빼면(저장된 방식이 `default`일 때) 서버가 **같은 저장에서 방문일+14로 되돌린다.** 직접 지정한 날짜를 남기려면 같은 body에 `deadlineMode: 'manual'`을 함께 보낸다.
- 익스텐션 상세의 "웹에서 직접 지정한 기한" / "직접 지정한 기한은 서버 규칙대로 유지돼요" 문구는 B-4를 적용하면 지운다.
- **결정됨(2026-10-07): 웹 프로덕트에 맞춘다.** 익스텐션 계획서(`2026-10-04-cb-x-extension-implementation.md` §3)의 "익스텐션에 직접 편집 기능을 추가하지 않는다"는 폐기한다. 수정 창(B-4)에 업로드 기한 칸과 `[기본 기한으로]`를 넣고 `uploadDeadline` + `deadlineMode`를 보낸다.

### A-6. [필수] 동의서 파일 형식

- 서버(`reservationAgreement.ts`)는 `application/pdf`·`image/jpeg`·`image/png`, 1바이트~10MiB를 받고, finalize에서 바이트 길이와 매직 바이트(`%PDF-`, PNG 시그니처, `FF D8 FF`)를 검사한다. 웹 동의서 칸은 PDF·JPG·PNG에 **이미지 붙여넣기(⌘V)·끌어다 놓기**까지 받는다(2026-10-06 결정: 063 작업 단위 동의서 재사용).
- 익스텐션은 PDF만 받고 mime을 `"application/pdf"`로 **고정**한다(prepare body와 PUT `Content-Type` 둘 다, `background.ts:51, :60`). `accept`, 확장자 검사, 매직 바이트 검사, PUT 헤더 모두 세 형식으로 넓히고, prepare 응답의 `mime`을 PUT에 쓴다.
- 서버 prepare 응답은 `{ uploadId, path, signedUrl, token, mime, size }`다. 익스텐션 타입에 `path`·`token`이 없다. signedUrl PUT으로 올리는 지금 방식은 동작하지만 타입은 맞춰 둔다.
- **결정(2026-10-07): D-10에 따른다.** 익스텐션에서 첨부를 지원하기로 하면 웹과 같은 형식(PDF·JPG·PNG, 10MB)을 따른다. 익스텐션 계획서 §11의 "PDF만 선택 허용"은 그 경우 폐기. D-10 제안은 5-1.
- 서버 오류 문구: `UNSUPPORTED_FILE` 'PDF·JPG·PNG 파일을 선택해 주세요.' / `FILE_TOO_LARGE` '빈 파일은 사용할 수 없고, 최대 10MB까지 첨부할 수 있어요.' / finalize의 `UNSUPPORTED_FILE` '파일 크기나 실제 형식이 선택한 파일과 달라요. 다시 첨부해 주세요.'

### A-10. [권장] 저장 요청 키 보존과 결과 복구

- 서버 멱등 규칙: `(member, operation, key)`가 같고 body 해시가 같으면 저장된 응답을 재생, 다르면 `IDEMPOTENCY_KEY_REUSED` 409. 실패한 요청은 행이 롤백돼 같은 키로 재실행된다(AI 파싱도 다시 과금). `expires_at` 7일은 기록만 하고 검사하지 않는다.
- 익스텐션 키는 content 스크립트 메모리 `Map`에 있어 새로고침·방 전환으로 사라진다(`extension/request.ts:26-37`). "결과 모름"(네트워크·worker 오류) 뒤에 다시 시도해도 새 키가 되면 예약 생성이 두 번 될 수 있다(생성만은 `create_operation_id` unique로 서버가 막지만, 수정·종료·동의서는 아니다). 진행 중인 쓰기의 키를 `chrome.storage.session`에 두고, 결과를 못 받았으면 `POST /operations/lookup { operation: 'PATCH:/reservations/<id>', key }`로 먼저 조회한다(`{status:'succeeded', result}` 또는 `{status:'not_found'}`).
- `operation` 문자열은 `${METHOD}:${/api/extension/v1 이후 경로}`다.

### A-11. 그대로 둬도 되는 것(확인 완료)

- 변경 내역 `nextCursor`는 숫자 오프셋 문자열이다. worker의 `/^\d{1,6}$/` 검사는 통과한다. 사람 목록 cursor(base64url)와 형식이 다르니 섞어 쓰지 않는다.
- `GET /campaigns`를 쿼리 없이 부르고 `kind === 'visit' || kind === null`로 거르는 방식은 웹과 같은 결과를 준다(서버 `?kind=visit`는 kind가 빈 캠페인을 제외하므로 오히려 쓰면 안 된다). 종료 캠페인은 기본 제외.
- `webUrl`은 `…/campaigns/flow?id=<캠페인>&task=<작업>`으로 작업 패널을 바로 연다.
- 파싱 `POST /reservation-extractions`는 202이지만 **동기**이고 `{id, status:'succeeded', result}`로 끝난다. 폴링은 필요 없다. 결과는 1시간 보관.
- 확정을 `{fieldEdits:{}}`로 보내는 것은 서버가 저장본 그대로 확정하므로 맞다(웹은 `sheetText`를 다시 보냄).
- `fieldEdits.preferred`를 `YYYY-MM-DD HH:mm`로 보내는 것은 맞다(`visitAt` 키만 ISO 검증).

### B-1. [필수] 단계 표시

웹 패널 첫 상자(`src/app/campaigns/flow/panel/StageTypeBox.tsx`)는 방문협찬을 **7단계 한 줄**로 그린다.

```
대기 › 확정 › 방문 › 전달 › 게시 › 정산 › 완료
```

현재 칩(검은 배경) 판정 `visitStep(task, phase)`(`src/lib/campaignFlowView.ts`) — 익스텐션은 `TaskDto.visitPhase`와 `TaskDto.flowStage`로 같은 계산을 한다.

| 조건(위에서 첫 일치) | 현재 칩 |
|---|---|
| `flowStage === 'canc'` 또는 phase가 `cancelled`·`visit_no_show`·`upload_no_show` | 줄 대신 **칩 하나**: `visit_no_show` → '방문 노쇼', `upload_no_show` → '업로드 노쇼', 그 외 '취소' |
| `flowStage === 'done'` 또는 phase `completed` | 완료 |
| `flowStage === 'settle'` 또는 phase `settling` | 정산 |
| `flowStage === 'posted'` 또는 phase `uploaded` | 게시 |
| phase `visited` | `flowStage === 'handed'`(원고 전달됨)면 **전달**, 아니면 방문 |
| phase `confirmed` | 확정 |
| 그 외(`unregistered`·`waiting`) | 대기 |

- '전달'은 원고(`draftStatus`)가 '전달됨'·'미사용'일 때의 공통 단계다. 방문 전에 원고를 전달해도 패널 줄은 '확정'이다(웹 결정, D-2 참고).
- 익스텐션 현재(`TaskDialog.tsx:189-192`): `[unregistered] + 대기·확정·방문·업로드·정산·완료 + [종료 phase]`. 바꿀 것: '예약 전' 칩 제거, '업로드' → '게시', '전달' 추가, 종료는 줄을 없애고 칩 하나, 현재 판정은 위 표. `format.ts:9 visitStages` 교체.
- 카드 알약의 단계 글자(`VISIT_PHASE_LABEL`과 같은 `format.ts:4-7`)는 그대로 둬도 된다. 다만 웹 표 칩은 공통 단계(`flowStageLabel`: 준비 자리에만 대기/확정)라 익스텐션 카드와 글자가 다를 수 있다. 통일하려면 카드도 B-1 규칙의 현재 칩 글자를 쓴다.
- `partnerLookup.ts:8-11`의 두 번째 라벨 맵('예약 대기'·'예약 확정'·'방문 완료'·'게시 확인'·'정산 중')은 어디에도 그려지지 않는다. 지운다.

### B-11. [권장] 종료(취소·노쇼)

- 웹에는 **종료 종류를 고르는 화면이 없다.** `[진행 안 됨]` → '작업 취소' 창(거절/무응답/기타 칩 + 한 줄 메모, 둘 다 선택)이고, 서버 `endReservedTaskByCancel`이 종류를 정한다(`cancel` 허용이면 '취소', 아니면 `upload_no_show`, 아니면 `visit_no_show`). 그래서 웹은 '방문 노쇼'를 기록할 수 없다.

### B-15. [선택] 단계별 상자 기본 펼침

웹(`src/lib/taskSectionView.ts`)은 상자를 단계에 따라 기본으로 펼친다: 협찬 동의서 = `confirmed`, 원고·게시 = `visited`, 예산 · 정산 = `uploaded`·`settling`, 변경 내역·메모 = 항상 접힘. 사용자가 직접 펼친 것은 단계가 바뀌어도 유지, 직접 접은 것은 그 단계에서만 유효. 익스텐션은 동의서만 `confirmed`에서 펼친다. 상세에 원고·게시·정산 상자가 없다면 해당 없음.

| 유지보수 | 동의서 UI가 웹·익스텐션 두 벌. 형식·크기 규칙이 바뀌면 둘 다 고친다(서버가 최후 방어라 어긋나도 저장은 안 깨진다) | 한 벌. 규칙 변경은 웹만 |
| 웹에서 올린 JPG/PNG | 그대로 보기·교체 가능 | 보기만. 교체는 웹 |
| 붙여넣기·끌어다 놓기 | 선택. 넣지 않아도 파일 고르기로 충분 | 웹 기능 그대로 |

**권장은 A.** 이유는 세 가지다. 동의서는 인플루언서가 DM으로 이미지로 보내는 경우가 많아 X 화면을 떠나지 않고 올리는 것이 흐름에 맞다. 업로드 경로(prepare → signedUrl PUT → finalize)가 이미 구현돼 있어 추가 작업이 형식 검사 몇 줄이다. 서버가 크기·형식·매직 바이트를 최종 검사하므로 두 벌 UI의 규칙이 어긋나도 잘못 저장되지 않는다. B는 익스텐션 범위를 줄여야 할 때의 대안이다. 그 경우 카드에 파일 카드(형식 딱지·파일명·올린 사람)와 `[보기 ↗]`·`[웹에서 첨부 ↗]`만 둔다.

A로 확정되면 A-6과 B-10을 그대로 적용한다. B로 가면 A-6은 빼고 B-10은 파일 카드와 링크만 남긴다.

## 6. 연동 확인 체크리스트 (수동)

서버는 064·070 적용 상태면 기본으로 켜진다(`EXTENSION_PRODUCT_ENABLED=false`일 때만 꺼짐, 2026-10-12 결정). `GET /session`의 `featureFlags.writes`가 true인지 먼저 본다.

1. 확정된 예약에서 `[예약 수정]` → 사유 창 → '인플루언서 요청' → 수정 창에 딱지 '인플루언서 요청 · 현재 n/3회' → 희망 시술만 바꿔 저장 → 변경 내역에 '고객 요청 변경 · {이름}' + '시술: A → B', 요약 n+1/3.
2. 같은 예약에서 '내 입력 정정'으로 저장 → 횟수 그대로, 제목 '내 입력 정정'.
3. 이름 칸에 한글·로마자 입력 → 서버 `fields.name`/`romanizedName`이 각각 들어오고 시트 줄이 `한글(로마자)`.
4. 업로드 기한을 방문일+14가 아닌 날로 저장 → `deadlineMode: manual`, 힌트 '직접 설정한 기한'. `[기본 기한으로]` → `default`.
5. 인플루언서 요청 3회 뒤 4번째 → '변경 요청 3회를 모두 사용했어요' → `[요청 기록·협찬 중단]` → 단계 칩 '취소' 하나, 변경 내역 '요청 기록·협찬 중단'.
6. 예약을 고친 직후 카드 `[방문 완료]`(방문 당일) → `VERSION_CONFLICT`가 나지 않아야 한다(A-3).
7. JPG 동의서 첨부 → finalize 성공, 상세에 'JPG' 딱지. 5바이트짜리 파일 → `FILE_TOO_LARGE`가 아니라 finalize `UNSUPPORTED_FILE`.
8. 양식에 `{{naver}}`가 있는 클리닉 → 입력창에 `{{naver}}` 글자가 남지 않는다.
9. 예약 없는 방문 작업을 종료 → 응답이 예약 상세가 아니어도 화면이 깨지지 않는다(A-7). 웹 작업 패널에서 `[되돌리기]`가 된다.
11. 예약이 있는 작업을 `/end`로 종료(칩 '거절' + 메모) → 작업 표에 '취소'·사유 칩, 붙어 있던 원고가 떼어지고, 인플루언서 타임라인에 거절 기록, 되돌리기는 막힌다.
10. 단계 줄: 대기·확정·방문(각 단계 작업) → 원고 '전달됨' + 방문 뒤 → '전달', 게시 URL 등록 → '게시', 정산 요청 → '정산', 지급 → '완료', 노쇼 종료 → '방문 노쇼' 칩 하나.
