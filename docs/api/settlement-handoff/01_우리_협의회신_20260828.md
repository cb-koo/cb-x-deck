# 결제 요청 API 연동 — 협의 체크리스트 회신 (cb-x-deck → 협찬 비용 관리)

보내주신 「결제 요청 API 연동 협의 체크리스트(2026-08-28)」에 항목별로 답합니다. 용어는 그쪽 문서를 따르되, "소스" = cb-x-deck(우리), "우리" = 협찬 비용 관리 프로덕트(그쪽)로 읽어 주세요.

**한 줄 요약:** API는 만들어져 있습니다. 결제 요청은 **그쪽이 주기적으로 가져가는 방식(폴링 GET)**, 처리 상태·실지급액은 **그쪽이 우리에게 보내는 방식(POST)** 입니다. 연습용 서버(스테이징)와 가짜 데이터를 준비해 URL·키·상세 문서를 별도로 전달드릴 예정입니다. 상세 스펙(필드표·규칙표·curl 예시)은 함께 보내는 `settlement-external-api.md`를 보시면 됩니다.

---

## 0. 전제 — 일치합니다

- 우리가 원본(소스 오브 트루스), 그쪽은 읽기 전용 미러. 우리 요청은 만든 뒤 **수정이 없고 취소만** 있습니다(스냅샷).
- 그쪽 상태 모델 `접수 → 지급예정 → 완료 + 보류/취소`를 그대로 받아 우리 화면에 표시합니다.
- 그쪽이 보내는 것 ①수정 요청 ②상태 변경 ③실제 결제 금액 — 셋 다 **상태 변경 API 하나**로 받습니다(아래 5-3).

## 1. 연동 방식

| # | 질문 | 답 |
|---|---|---|
| 1-1 | API 신설 가능? | **완료.** REST + JSON. |
| 1-2 | 웹훅 push vs 폴링? | **폴링(그쪽이 가져가기)으로 확정.** 웹훅은 이번엔 두지 않습니다. 이유: 요청은 취소 외 변경이 없고 마감이 주 단위라 분 단위 지연이 업무에 영향이 없으며, 폴링은 누락·중복이 구조적으로 없습니다(그쪽이 마지막 위치를 들고 옵니다). 필요가 확인되면 알림용 웹훅을 2차로 검토하겠습니다. |
| 1-3 | 인증 | `Authorization: Bearer <API Key>`. 웹훅이 없으므로 HMAC 서명은 불필요합니다. 키는 스테이징·운영 각각 다른 값, 1:1 채널로 전달(문서에는 싣지 않음). |
| 1-4 | 테스트/스테이징 | **제공합니다.** `https://cb-x-deck-staging.vercel.app` — 별도 DB, 가짜 클리닉·인플루언서·요청(취소 포함)을 채워 둡니다. 실데이터 없음. 상태 POST를 마음껏 보내도 됩니다. |
| 1-5 | 버저닝 | 목록 응답에 `version: 1`. 하위 호환이 깨지는 변경은 `/v2` 경로로 새로 열고 사전 공지합니다. |

## 2. 결제 요청 스키마 — 필드 대응

| 그쪽 요청 필드 | 우리 응답 필드 | 비고 |
|---|---|---|
| `request_id` | `request_id` (uuid, 불변) | ✅ |
| `influencer_uuid` | `influencer.id` (uuid) | ✅ 항상 값. 요청 시점 스냅샷 — 핸들 변경·삭제 뒤에도 유지. 우리가 발급 주체. |
| `influencer_handle` | `influencer.handle` | 요청 시점 표기(스냅샷) |
| `clinic_id` + `clinic_name` | `clinic.id` + `clinic.name` | ✅ 항상 값(스냅샷). 이름 불일치는 ID로 매핑해 주세요. |
| `amount` + `currency` | `payout.gross` + `payout.currency` | `gross`가 **실제 송금액**(양식의 "금액"). `payout.net`(순액)·`payout.fee`·`payout.fee_amount`(수수료)도 분리해서 같이 갑니다. 통화는 KRW/JPY 다통화. |
| `amount_krw_estimated` | `amount_krw` + `payout.rate_krw_per_jpy` | "잠정"이 아니라 **우리 기준 확정 원화**입니다. 환율은 우리 설정값(현재 10원=1엔)을 요청 시점에 스냅샷으로 저장해 같이 보냅니다. 출처·시점 명시 요구 충족. |
| `payment_method` 구조화 | `payment_method: { type, holder, currency, email?, paypal_id?, identifier?, bank?, branch?, account? }` | ✅ `type`은 `paypal` / `paypay` / `bank` |
| `deadline` | `deadline` (`YYYY-MM-DD`) | ✅ |
| `requester` / `payer` / `cc` Slack ID | `requester: { name, email, slack_id }` | **requester만 제공.** `slack_id`는 채워진 경우에만 값, 아니면 `null` — 이메일로 Slack `users.lookupByEmail` 조회를 권장합니다. **`payer`/`cc`는 우리 데이터가 아니라 그쪽 설정값이므로 제공하지 않습니다.** |
| `category` 코드화 | `category: { code, label }` | ✅ 항상 값. `code` = 분류 옵션 안정 키(예 `promo-rt`, `fee`, `info-post`), `label` = 정산 쪽 이름 텍스트 |
| `item` / `purpose` | `item` / `purpose` | ✅ |
| `reference_url` | `reference_url` | ✅ (없으면 null) |
| `updated_at` / `revision` | `updated_at` / `revision` | `updated_at`이 **정렬·중복 판정 기준**. `revision`은 우리 원본의 변경 횟수(0=요청됨, 1=취소됨)라 그쪽 상태 반영으로는 오르지 않습니다 — 정렬에 쓰지 마세요. |
| (추가) | `settlement: { status, paid_amount_krw, paid_at, note, updated_at, external_id }` | 그쪽이 보낸 값을 되비쳐 드립니다(대조용). |
| (추가) | `status`(`requested`/`cancelled`) · `cancelled: { at, by_name, reason }` · `task_id` · `campaign: { id, name }` · `task_type` · `note` | |

## 3. 인플루언서 엔티티

- 3-1 우리가 자체 관리하며 UUID 발급 주체입니다.
- 3-2 핸들 변경 시 UUID 유지. 요청에는 **요청 시점 핸들**이 실리고(스냅샷), 최신 핸들이 필요하면 UUID로 우리 쪽 명부를 기준으로 삼으시면 됩니다.
- 3-3 "기존 Supabase 인플루언서 마스터"가 곧 우리 `influencer` 테이블입니다(같은 DB). 별도 연동 불필요.

## 4. 수정·취소 전파 (우리 → 그쪽)

- 4-1 요청은 **수정되지 않습니다.** 내용을 고쳐야 하면 담당자가 **취소하고 같은 작업으로 새 요청**을 만듭니다 → 그쪽에는 옛 건 `cancelled` + 새 `request_id`가 보이고, 둘은 **`task_id`가 같아서** 이어 볼 수 있습니다(상세 문서 §3-1). 보류에 대한 우리 쪽 응답도 이 흐름입니다. 바뀐 행은 폴링 목록에 `updated_at`이 갱신되어 다시 나옵니다. **그쪽이 `지급예정`으로 둔 건에 `cancelled`가 보이면 지급을 중단하고 그쪽 상태를 취소로 바꿔 주세요.**
- 4-2 삭제·철회 없음. 취소만 있고 행은 남습니다.
- 4-3 **완료 건 보호:** 그쪽이 `paid`(완료)를 보낸 뒤에는 우리 쪽에서도 취소가 막힙니다(화면·서버·DB 3중). 되돌려야 하는 경우는 API가 아니라 사람이 협의합니다.

## 5. 역방향 수신 (그쪽 → 우리)

- 5-1 **상태 변경 엔드포인트 제공:** `POST /api/external/settlement/requests/{request_id}/status`
  본문: `status`(`received` 접수 / `scheduled` 지급예정 / `paid` 완료 / `on_hold` 보류 / `cancelled` 취소, 필수) · `updated_at`(그쪽 서버의 실제 변경 시각 ISO 8601, 필수) · `note`(≤500자, 선택) · `paid_amount_krw` + `paid_at`(`paid`면 둘 다 필수) · `external_id`(그쪽 건 ID, 선택)
  응답: 200 `{ applied: true, request }` / 200 `{ applied: false, reason: "stale" }`(더 오래된 변경 → 무시, 멱등) / 400 `{ error, field }` / 404 / 409 `{ code: "request-cancelled" }`(우리가 취소한 건) / 409 `{ code: "paid-locked" }`(완료 후 다른 상태)
- 5-2 **실제 결제 금액: 저장하고 화면에 표시합니다.** 요청 내역에 `지급 완료 · 실지급 29,700원 (요청 30,000원, −300)`처럼 차이까지 보여줍니다.
- 5-3 **수정 요청 알림: 별도 API 없이 `status: on_hold` + `note`에 사유**로 보내 주세요. 우리 화면에 "보류 · 사유"가 노란 배지로 떠서 요청자가 보고 취소→재요청합니다. 요청자 슬랙 멘션은 그쪽에서 (2번의 이메일/slack_id 활용) 보내시면 됩니다. `note`는 어떤 상태에도 붙일 수 있습니다(완료 시 차액 설명 등).
- 5-4 우리 화면에도 상태를 표시합니다. **기준:** 요청 원본은 우리, 처리 상태는 그쪽 — 우리 화면은 그쪽이 보낸 상태를 그대로 비추기만 합니다.

## 6. 운영·정합성

- 6-1 `event_id`: 웹훅이 없어 필요 없습니다. 목록은 `request_id` 기준 upsert(`updated_at` 최신 것 채택), 역방향 POST는 `updated_at` 비교로 중복·역순을 흡수합니다 — **실패하면 같은 본문 그대로 재전송**하시면 됩니다.
- 6-2 재전송·주기: 웹훅 재전송 없음. **폴링 권장 5분**, 응답의 `next_cursor`를 항상 저장해 다음 호출에 사용, `has_more: true`면 즉시 다음 페이지. 전달은 at-least-once(같은 행이 두 번 보일 수 있음). 새/변경 요청은 **약 30초 뒤부터** 목록에 나타납니다(동시 저장을 건너뛰지 않기 위한 안전 지연). 409를 받으면 해당 건을 단건 GET으로 다시 가져가 미러를 맞춰 주세요.
- 6-3 과거 데이터 백필: **범위 밖.** 구글폼·슬랙 시절 요청은 우리 DB에 없습니다(분석용 CSV만). 8월 말 이후 정산 페이지에서 만든 요청부터 흘러갑니다.
- 6-4 담당자·채널: 우리 쪽 기술 담당은 [담당자 이름], 장애·문의 채널은 [슬랙 채널명] 제안드립니다. 그쪽 담당자와 채널을 알려 주세요.

## 그쪽에 부탁드리는 것 (정리)

0. **요청을 가져간 직후 `received`(접수)를 보내 주세요** — 우리 담당자 화면의 "정산 접수" 표시가 이것으로만 바뀝니다.
1. `updated_at`은 그쪽 서버의 실제 변경 시각으로, 매 POST에 필수.
2. 실패 시 같은 본문 재전송(멱등), 409는 단건 재조회.
3. 폴링에서 `status: cancelled`를 보면 지급 중단.
4. 수정 요청은 `on_hold` + `note`.
5. 요청자 슬랙 멘션은 그쪽에서(이메일 조회 또는 `slack_id`).
6. `payer` / `cc`는 그쪽 설정으로.

## 협의가 필요한 것 (답을 주시면 좋겠습니다)

1. **완료(paid) 이후 되돌림:** 그쪽 상태 모델에 '환불'이 없어, 우리는 `paid` 이후 어떤 상태 변경도 거부(409)하고 정정은 사람이 협의하는 것으로 두었습니다. 이 방식에 동의하시는지, 아니면 환불 상태가 필요한지.
2. **개인정보:** 결제 수단에 인플루언서 실제 계좌·PayPal 식별값이 포함됩니다(요청하신 구조화 필드). 그쪽 저장소에서의 암호화·접근 제한 방침을 알려 주세요.
3. **기획서(`0828Plan.md`) 공유:** 체크리스트가 참조한 기획서를 받지 못했습니다. 체크리스트 밖 요구(월별 집계 기준일, 예산 대비 계산 등)가 있으면 대조하겠습니다.
4. **시간대:** 시각은 UTC ISO, `deadline`은 한국 날짜입니다(상세 문서 §3). 문제 없는지 확인 부탁드립니다.
