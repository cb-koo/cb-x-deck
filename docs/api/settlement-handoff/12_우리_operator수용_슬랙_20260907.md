# 우리 회신 (우리 → 정산 프로덕트, 슬랙용) — 2026-09-07 operator 수용

> 아래 그대로 붙여넣기. 첨부: `settlement-external-api.md` 현재 판(2026-09-07 갱신본 — §6 요청 본문에 `operator` 행과 "모르는 키는 무시" 문장 추가. 9/3 판을 대체).

---

`operator` 수용 요청 확인했습니다. **지금 바로 보내셔도 됩니다 — 상태 전송을 재개해 주세요.**

*1. 결론*
• 저희 상태 수신은 원래부터 **모르는 키를 무시**합니다(400을 내지 않습니다). `operator`가 붙어 와도 그대로 반영됐을 겁니다. 명세에 그 문장이 없어서 확신하기 어려우셨을 텐데, 이번 판 §6에 명시했습니다.
• 거기서 한 걸음 더 가서 오늘(9/7) **`operator`를 저장하고 화면에 보이도록** 배포했습니다. 저희 요청 내역의 "정산 프로덕트가 보낸 결과"에 "처리한 사람: ○○○ · 정산 프로덕트 담당자"로 나옵니다.

*2. 받는 규칙 (그쪽 목 서버와 같습니다)*
• `operator`는 선택. 있으면 `{ id: string, name: string }`만 받습니다(각 100자 이하, 빈 문자열 불가). 모양이 틀리면 400 `{ field: "operator" }`.
• `null`은 "없음"으로 처리합니다. 자동 전이에 키를 안 넣으시는 것도 그대로 됩니다.
• 마지막으로 적용된 전이의 담당자만 남깁니다. 자동 전이(`received→scheduled`)가 뒤에 오면 담당자 칸은 비워집니다 — "자동으로 넘어갔다"는 뜻으로 보입니다.
• 아이템(GET)에는 `operator`를 되비치지 않습니다. 필요하시면 말씀해 주세요.

*3. 함께 확인된 것*
• `external_id` 에코(6-4) — 9/4 실요청 3건(`CBX-260904-001`~`003`)에 보내주신 값이 그대로 저장돼 단건 GET의 `settlement.external_id`로 나옵니다. 확인 끝났습니다.
• 보내주신 문서 §4 예시의 `external_id`가 `S-20260904-001` 형식인데, 실제로 오는 값은 예고대로 `CBX-YYMMDD-NNN`이었습니다. 실제 동작은 맞고 문서 예시만 옛 표기인 것으로 보입니다.

*4. 부탁*
