# 우리 회신 (우리 → 정산 프로덕트, 슬랙용) — 2026-09-07 구현 보고 확인·②는 절차로 합의·전환 준비 완료

> 아래 그대로 붙여넣기. 첨부: `settlement-external-api.md` 현재 판(§3-1 "5. 송금 중 수정 방지"를 합의한 절차로 고침).

---

구현 보고(「제자리 수정 수용 반영 및 전환 절차」) 확인했습니다. 저희도 구현을 마쳐 **스위치 꺼진 상태로 운영·스테이징에 배포**해 두었습니다. 지금 나가는 데이터는 이전과 똑같습니다(`revision` 0/1, `revised_at` null).

*1. ②(송금 시점 `paid`)는 절차로 대체 — 별도 채널에서 합의한 내용 확인*
• 그쪽이 이미 처리한 요청(`settlement.status`가 `null`이 아닌 건)을 저희가 고칠 때는 **슬랙으로 결제 담당자에게 먼저 확인하고 반영**합니다.
• 저희 화면은 그런 건에 "정산 담당자에게 확인했어요" 체크 없이는 반영 버튼이 열리지 않고, 서버도 체크 없는 요청을 거절합니다. 확인 여부는 개정 이력에 남습니다.
• 그쪽의 안전장치(송금이 끝난 건에 수정본이 오면 금액을 덮지 않고 정합 오류로 막기, 잠금 해제 시 미송금 확인)는 그대로 유지해 주세요. 저희 절차가 빠져도 그쪽에서 한 번 더 걸리는 구조가 맞습니다.
• 이 내용을 명세 §3-1의 5번으로 바꿔 첨부했습니다. 잠금 API는 지금 규모(주 몇 건·담당자 1명·토요일 일괄)에서는 만들지 않고, 건수·담당자가 늘면 "송금 진행 중" 상태 추가로 격상하겠습니다.

*2. 스위치 순서 — 그쪽이 먼저, 저희가 뒤에*
• 그쪽 보고대로 그쪽 스위치가 꺼진 상태에서 저희 수정본이 가면 그쪽 폴링이 멈춥니다. 그래서 **그쪽 ON → 확인 회신 → 저희 ON** 순서로 합니다.
• 저희 스위치는 환경 변수 + 재배포라 켜는 데 5분쯤 걸립니다. 켜기 전 30분은 저희도 취소·수정을 하지 않겠습니다. 그쪽도 그 시간에 결제 조작을 멈추고 진행 중 전송을 마무리해 주세요(그쪽 보고 §전환 순서).

*3. 스테이징 공동 점검(운영 전에)*
• 스테이징에서 양쪽 스위치를 먼저 켜고 아래를 함께 봅니다. 저희 스테이징 주소·키는 8/29에 드린 그대로입니다.
  ① 한 건을 두 번 고쳐 같은 `request_id`·같은 정산코드로 `revision` 0→1→2, `revised_at` 갱신, `settlement.*` 리셋 뒤 그쪽 `received→scheduled` 재처리·수정 알림.
  ② 옛 판(`revision` 0)으로 상태 POST → 409 `revision-mismatch` + 최신 Item, 그쪽 outbox에서 옛 판만 폐기.
  ③ 상태 POST에 `revision` 없음 → 400 `field: "revision"`.
  ④ 진짜 폐기(`cancelled`)와 `paid → paid` 정정은 종전과 같음.
  ⑤ 처리 전(`settlement.status: null`) 요청은 저희가 담당자 확인 없이 고칠 수 있음 — 확인 대상은 그쪽이 처리한 건만.
• 시나리오는 지난 @Qni6F 건과 같습니다(보류 → 수수료 변경 → 다시 반영). 편한 시간 알려 주시면 맞추겠습니다.

*4. 확인 부탁*
• 위 1·2 동의, 3의 일정.
• 그쪽 보고에 "소스팀 초안의 2~3일 일정은 확정하지 않는다"고 하셨는데, 저희 구현은 끝났으니 일정은 스테이징 점검 결과에 맞추면 됩니다.
