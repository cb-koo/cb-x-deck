# 우리 회신 (우리 → 정산 프로덕트, 슬랙용) — 2026-09-07 재요청 이력 연결·"취소로 보임" 확인

---

재요청 이력 건 확인했습니다. 결론 두 가지와 확인 요청 하나입니다.

*1. 옛 건과 새 건을 잇는 열쇠는 이미 나가고 있습니다 — `task_id`*
• 이번 테스트의 두 건(옛 `f6189ec9…`·새 `1f264104…`)은 `task_id`가 둘 다 `7cf4dfaa…`로 같습니다. 보내주신 JSON에도 그렇게 찍혀 있습니다.
• 규칙은 명세 §3-1·§5에 있습니다: "같은 작업을 다시 요청하면 새 `request_id`가 생기고 `task_id`는 같다 — 옛 건과 새 건을 잇는 열쇠". 8/28 회신에서 확인해 주신 항목입니다.
• 그래서 지금 데이터로도 **`task_id`가 같은 건을 한 묶음으로 보시면** 이력이 이어집니다. 한 작업에는 살아 있는 요청이 동시에 하나뿐이라, 묶음 안에서 `created_at` 순서가 곧 이력 순서입니다.

*2. 더 직접적인 표시가 필요하시면 두 값을 추가해 드립니다*
• `previous_request_id` — 이 요청이 대체하는 직전(취소된) 요청의 `request_id`. 첫 요청이면 `null`.
• `request_seq` — 같은 작업의 몇 번째 요청인지(1, 2, 3…).
• 둘 다 아이템(GET)에 실립니다. 기존 필드는 바뀌지 않고, 이미 나간 건에도 조회 시점에 채워집니다.
• 원하시면 알려 주세요. **명세 갱신본을 먼저 보내고 다음 날 배포**합니다(지난 회신에서 약속한 절차). 미러가 모르는 키를 무시하도록 바꾸셨다고 하셨으니 배포가 먼저 나가도 깨지진 않습니다.

*3. "재요청이 취소(cancelled)로 온다" — 저희 데이터는 다릅니다, 확인 부탁드립니다*
• 저희가 내려보내는 새 건 `1f264104…`는 `status: "requested"`, `revision: 0`, `cancelled: null`, `settlement.status: "scheduled"`입니다. 보내주신 JSON에도 `"status": "requested"`로 찍혀 있습니다.
• 그쪽 화면에 취소로 보였다면 저장 단계에서 섞인 것으로 보입니다. 가장 의심되는 구조는 **`task_id` 단위로 한 줄에 덮어쓰는 미러**입니다. 옛 건은 취소된 뒤에도 그쪽이 상태를 보낼 때마다 `updated_at`이 갱신돼 폴링에 다시 내려옵니다(명세 §3 "에코", 정상 동작). 이때 옛 건의 "취소"가 같은 `task_id`의 새 건 위에 덮어써지면 새 요청이 취소된 것처럼 보입니다. 이번에도 옛 건(12:51)과 새 건(12:57)이 같은 폴링 페이지에 함께 내려갔습니다.
• 확인 부탁드리는 것 둘:
  ① 취소로 보인 건의 `request_id`와, 그때 저희에게서 받은 응답 원문(아이템 JSON). 새 번호 `1f264104…`가 취소로 보였다면 원문으로 바로 판별됩니다.
  ② 미러의 저장 키가 `request_id`인지 `task_id`인지. **저장은 `request_id`별로 하고, 이력 묶기만 `task_id`(또는 위 `previous_request_id`)로** 하셔야 옛 건의 에코가 새 건을 덮지 않습니다.
