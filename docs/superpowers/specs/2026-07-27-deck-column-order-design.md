# 덱 컬럼 순서 — 새 컬럼 안내 + 드래그 재정렬 (설계)

2026-07-27.

**배경.** 덱은 가로 스크롤 컬럼 스트립이다(`src/app/w/[wsId]/page.tsx:79`). 컬럼 기본 폭은 400px, 사용자 조절 범위 280~720px(`src/components/Column.tsx:59`). 1440px 화면이면 3~4개만 보인다.

두 가지 문제가 있다.

1. **생성 피드백이 없다.** `+ 컬럼`으로 만든 컬럼은 스트립 오른쪽 끝에 붙는데, 생성 후 `load()`만 하고 스크롤하지 않는다(`page.tsx:60`). 컬럼이 4개 이상이면 화면에 아무 변화가 없다. 새 컬럼에 걸리는 자동 새로고침(`page.tsx:59` → `Column.tsx:141`)도 화면 밖에서 돈다. 사용자는 "저장이 안 됐나?" 하고 다시 누른다. **니엘슨 1원칙(시스템 상태 가시성) 위반.**
2. **순서를 바꿀 수 없다.** `deck_column.position`은 생성 시 항상 `0`이 들어가고(`src/lib/columnStore.ts:28`, API 호출부가 `body.position`을 안 보냄), 정렬은 `order by position, created_at`(`columnStore.ts:13`)이라 **실질 생성순 고정**이다. 순서를 바꾸려면 삭제 후 재생성뿐이고, 그러면 그 컬럼에 쌓인 트윗·버림 처리가 사라진다.

**해결.** 새 컬럼은 지금처럼 오른쪽 끝에 추가하되 **화면이 따라가게** 하고, **그립 드래그로 순서를 바꿀 수 있게** 한다. 죽어 있는 `position`을 살린다.

## 원칙

- **공간 기억을 깨지 않는다.** 새 컬럼을 왼쪽에 끼워넣으면 기존 컬럼이 매번 밀려 사용자의 위치 기억이 무너진다. 오른쪽 끝 추가를 유지한다(TweetDeck·Trello·브라우저 탭의 공통 관습).
- **행동에는 보이는 결과가 따른다.** 생성했으면 그 결과로 화면이 이동한다.
- **어포던스는 상시 보인다.** "끌 수 있다"를 hover에 숨기지 않는다. 반대로 **끌 수 없을 때는 어포던스를 없앤다**(컬럼 1개면 그립 숨김) — 거짓 어포던스 금지.
- **끄는 동안 최종 결과를 그대로 보여준다.** 삽입선 같은 추상 기호가 아니라 실제 자리 밀림으로.
- **60fps는 요구사항이지 목표가 아니다.** 컬럼 하나에 트윗 최대 200개(`Column.tsx`의 `PAGE = 200`), 컬럼 5개면 트윗 카드 1,000개가 떠 있다. 프레임 예산 16ms, 핸들러 8ms 이내.
- **사용자에게 내부어 노출 금지.** UI 언어는 "순서 변경". `position`·`transform` 같은 말은 쓰지 않는다.

## A. 새 컬럼 — 오른쪽 끝 추가 + 데려가기

`+ 컬럼` 버튼은 **상단 툴바 왼쪽 그대로 둔다.** 툴바는 가로 스크롤과 분리된 고정 바라, 툴바 안에서 오른쪽으로 옮겨도 "버튼 위치 = 새 컬럼 자리"가 성립하지 않는다(컬럼 5개면 툴바 오른쪽 끝 아래에 있는 건 3번째 컬럼이다). 스트립 끝 인라인 슬롯(Trello 방식)은 진짜 공간 매핑이 되지만 컬럼이 많으면 버튼 자체가 화면 밖으로 나간다. **자동 스크롤이 "결과가 어디 생기는지" 문제를 해결하므로 항상 같은 자리에 있는 고정 버튼이 낫다.**

생성 흐름:

```
생성 성공 → 목록 갱신 → 새 컬럼 DOM 부착
        → 그 컬럼으로 가로 스크롤 (inline: 'end')
        → 1.5초간 파란 테두리 강조
        → (기존대로) 자동 새로고침 1회
```

- 기존 `autoRefreshId` state를 `newColumnId`로 넓혀 **자동 새로고침·스크롤·강조** 세 트리거로 공유한다. 새 state를 만들지 않는다.
- 스크롤 시점은 새 컬럼이 실제로 렌더된 뒤여야 한다 → `columns`에 해당 id가 들어온 것을 확인하는 effect에서 실행.
- `prefers-reduced-motion: reduce`면 `behavior: 'smooth'` 대신 `'auto'`.
- 강조는 1.5초 후 해제(타이머). 자동 새로고침은 지금처럼 1회만.

## B. 순서 변경 — 그립 드래그

### 어포던스

컬럼 제목 왼쪽에 **그립 아이콘 상시 표시**. hover 시 배경 강조 + `grab` 커서 + 툴팁 "끌어서 순서 변경".

헤더 전체를 손잡이로 삼는 안은 버렸다 — 평소에 끌 수 있다는 표시가 없고, 제목 텍스트 드래그 선택이 막히고, 헤더의 기존 버튼 3개(새로고침·설정·삭제)와 오작동이 겹친다. 전용 그립은 영역이 명확해서 이 셋을 모두 피한다.

**컬럼이 1개면 그립을 렌더하지 않는다.**

**크기.** 헤더의 기존 아이콘 버튼과 동일 규격(`Button variant="icon"` = `p-1.5` + 16px 아이콘 ≈ 28px)을 따른다. 체크리스트 I·C의 터치 타깃 44×44px에는 미달하나, **이는 헤더 아이콘 전체의 기존 패턴**이고 그립만 키우면 정렬이 깨진다(체크리스트 J — 일관성). 덱은 가로 스크롤 스트립 기반의 데스크톱 우선 화면이며 드래그도 포인터 조작이다. 헤더 아이콘 규격 전체를 손보는 것은 이 작업의 범위 밖 — **별도 과제로 남긴다.**

**포커스.** 키보드 포커스 시 2px 아웃라인을 명시적으로 노출한다(체크리스트 I).

### 드래그 시작 조건 (오작동 방지)

`pointerdown` 즉시 드래그로 치지 않는다. **포인터가 5px 이상 이동해야** 드래그가 시작된다(dnd-kit의 activation constraint와 같은 개념).

없으면 그립을 그냥 클릭했을 때 1~2px의 미세 이동만으로 순서 변경으로 인식되어 불필요한 저장 요청이 나가고, 사용자는 자기가 뭘 했는지도 모른다. 체크리스트 B-5(오류 예방) · K(확신·안심).

### 드래그 중 피드백

- 잡은 컬럼: 포인터를 따라 이동, `opacity: .85` + 그림자 + `rotate(1.5deg)`, 다른 컬럼 위로 올라옴(z-index).
- 나머지 컬럼: 새 위치에 맞춰 좌/우로 비켜섬, `transform 150ms ease`.
- **배열은 건드리지 않는다.** 시각적 이동만 하고, **놓는 순간에만** 실제 순서를 확정한다. 드래그 중에 배열을 재정렬하면 매 프레임 화면이 튄다.
- 컬럼 폭이 제각각이므로 **비켜서는 거리 = 잡은 컬럼의 실제 폭.**
- 포인터가 덱 좌/우 가장자리 영역에 들어가면 자동 가로 스크롤(아래 성능 설계 참조).
- `prefers-reduced-motion: reduce`면 비켜서는 transition을 끈다(즉시 이동). 잡은 컬럼이 포인터를 따라오는 것은 직접 조작이므로 유지한다.

### 취소

**드래그 중 `Escape`를 누르면 원래 자리로 되돌리고 아무것도 저장하지 않는다.** 드래그를 시작했다가 마음이 바뀌는 것은 흔한 일이고, 되돌릴 길이 없으면 사용자는 애초에 드래그를 시도하지 않는다. 체크리스트 B-3(사용자 통제·자유) · K(실수로 망칠까 두려움).

포인터가 창 밖으로 나가 드래그가 강제 종료된 경우(`pointercancel`)도 동일하게 취소 처리한다.

**순서 변경 자체에 대한 실행취소(Undo)는 두지 않는다.** 파괴적이지 않고 되돌리는 비용이 드래그 1회로 낮다. (팀 보관함에서 빼기 같은 파괴적 액션과 달리 잃는 데이터가 없다.)

### 놓았을 때

1. 화면은 즉시 새 순서로 확정(낙관적).
2. 서버 저장을 뒤에서 실행.
3. **실패하면 이전 순서로 되돌리지 않고 `load()`로 서버의 현재 순서를 다시 받는다.** + Toast로 알림.
   - 이유: 저장이 거부되는 경우는 대개 다른 멤버가 그 사이 순서를 바꾼 경우다. 드래그 직전 순서로 되돌리면 그것도 이미 낡은 순서다.
   - **문구(체크리스트 B-9·G·H — 원인 + 다음 행동, 에러코드·사용자 탓 금지):**
     - 집합 불일치(409): `"다른 팀원이 컬럼을 바꿔서 순서를 저장하지 못했어요. 최신 상태로 새로 불러왔습니다."`
     - 그 외 실패: `"순서를 저장하지 못했어요. 잠시 후 다시 옮겨주세요."`

### 키보드

> **개정(2026-07-27, 구현 중 리뷰 반영).** 아래 원안의 `role="button"` + `aria-live` 조합은 **채택하지 않았다.** 다음 문단의 최종 명세를 따를 것.
>
> - `role="button"`은 Enter·스페이스로 눌린다는 기대를 만드는데 이 손잡이는 화살표로만 움직여 어긋난다. 그렇다고 `role`을 비우면 역할 없는 포커스 요소가 되어 스크린리더의 컨트롤 탐색에서 아예 잡히지 않는다(WCAG 4.1.2).
> - **최종:** `role="slider"` + `aria-roledescription="순서 변경 손잡이"` + `aria-valuemin/max/now` + `aria-valuetext="{N}개 중 {M}번째"`. "N개 중 M번째를 화살표로 바꾸는 컨트롤"이 slider의 정의에 맞고(ARIA APG), roledescription이 "슬라이더" 대신 사용자 말로 읽히게 한다.
> - **`aria-live`는 두지 않는다.** `aria-valuetext`가 바뀌면 스크린리더가 자동으로 읽으므로 별도 안내 채널을 두면 **같은 내용이 두 번 읽힌다.** 따라서 `useDeckDrag`에도 안내 콜백을 두지 않는다. (실패 Toast는 `Toast.tsx`가 자체적으로 `role="status" aria-live="polite"`를 갖는다 — 이건 별개이며 유지.)

원안(미채택): 그립은 `tabIndex=0`, `role="button"`, `aria-label="{컬럼명} 순서 변경 — 끌어서 이동하거나 화살표 키를 누르세요"`. 이동 후 `aria-live="polite"`로 "{컬럼명}, N개 중 M번째" 안내.

포커스 상태에서 `←` `→`로 한 칸씩 이동. 이동 후 해당 컬럼을 화면에 보이도록 스크롤한다.

**경계에서는 아무 일도 일어나지 않는다** — 첫 컬럼에서 `←`, 마지막 컬럼에서 `→`는 무시(저장 요청도 없음). 체크리스트 F(제약).

**좌/우 이동 버튼을 UI에 추가하지 않는다.** 같은 일을 하는 조작이 둘로 보이면 노이즈다. 키보드 경로만 조용히 확보한다.

## 데이터 모델

| | 지금 | 바뀐 뒤 |
|---|---|---|
| `deck_column.position` | 항상 `0` | 워크스페이스 내 `0,1,2…` |
| 실질 정렬 | 생성순 | 사용자 지정 순서 |

- **마이그레이션 `migrations/013_column_position.sql`** — 기존 행에 현재 보이는 순서 그대로 번호 부여. 사용자 눈에 변화 없음.

  **배포 순서 주의:** backfill 가드가 `having max(position) = 0`("아직 번호가 안 매겨진 워크스페이스")이므로, **마이그레이션보다 코드가 먼저 배포되면** 그 사이 생성된 컬럼이 `max`를 1 이상으로 올려 해당 워크스페이스가 backfill 대상에서 영구히 제외된다. 사용자 피해는 없다(`order by position, created_at`의 tie-break로 보이는 순서가 유지되고, 첫 재정렬에서 0..n-1로 자동 복구). 그래도 **`npm run migrate`를 배포 이전 또는 배포와 함께** 실행한다.

  **불변식의 실제 범위:** 보장되는 것은 워크스페이스별 **중복 없는 증가 값**이지 연속된 0..n-1이 아니다. `deleteColumn`은 번호를 다시 매기지 않아 구멍이 남는다. 연속성을 읽는 코드가 없고 재정렬이 자동 복구하므로 무해하다. DB 유니크 제약은 없고 애플리케이션 레벨 보장이다.

  ```sql
  update deck_column c set position = s.rn
  from (
    select id, row_number() over (
      partition by workspace_id order by position, created_at
    ) - 1 as rn
    from deck_column
  ) s
  where c.id = s.id;
  ```

- **생성 시 position은 서버가 계산한다** (`coalesce(max(position) + 1, 0)`, 워크스페이스 범위). 클라이언트가 보내면 동시 생성 시 번호가 겹친다. API의 `body.position` 통로는 제거한다.

- **재정렬 저장 = 전체 순서 배열 전송.** `PATCH /api/columns/reorder`, body `{ workspaceId, ids: string[] }`. 트랜잭션으로 `position = 배열 인덱스` 일괄 갱신.
  - 움직인 항목 하나만 보내는 안은 버렸다 — 한 개 위치가 바뀌면 나머지도 밀려야 하니 결국 서버가 재계산해야 하고, 어긋날 여지만 는다. 분수 인덱싱은 컬럼 수(보통 3~8) 대비 과하다.
  - **알려진 한계:** 두 멤버가 동시에 순서를 바꾸면 나중에 저장한 쪽이 이긴다. 컬럼·트윗이 사라지지는 않으므로 감수한다. (검증: 요청의 `ids`가 서버의 현재 컬럼 집합과 정확히 일치하지 않으면 409 반환 → 클라이언트는 `load()`로 재동기화.)
  - 권한 확인은 기존 컬럼 API의 워크스페이스 멤버십 패턴을 따른다.

## 성능 설계

리서치 근거: dnd-kit([PointerSensor rAF 배칭 커밋](https://github.com/clauderic/dnd-kit/commit/ac13c9298cc8b4eb680039cf17fb10582ab8d023), 2025-05), Atlassian Pragmatic DnD, [react-beautiful-dnd 자동 스크롤 설계](https://github.com/pbakaus/dnd/blob/master/docs/guides/auto-scrolling.md), [Google Chrome 팀 복잡 레이아웃 인터랙션 가이드](https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/performance/interactions-in-complex-layouts.md).

**프레임 예산 16ms, 포인터 핸들러 8ms 이내.**

### 필수 규칙 6가지

| 규칙 | 어기면 | 적용 |
|---|---|---|
| pointermove를 rAF로 모아 프레임당 1회 처리 | 초당 60회 React 리렌더 → 확정적 jank | 핸들러는 최신 좌표만 저장하고 rAF 예약 |
| `transform`만 사용 (`left`·`top` 금지) | 매 프레임 전체 레이아웃 재계산 | 컴포지터 전용 속성만 |
| 크기·좌표는 **드래그 시작 시 1회** 측정해 캐시 | 핸들러 안 `getBoundingClientRect` = 강제 동기 리플로 | `offsetLeft`/`offsetWidth` 스냅샷 |
| 그립에 `setPointerCapture` | 커서가 컬럼 밖으로 나가면 드래그 끊김 | `pointerdown`에서 설정 |
| 그립에 `touch-action: none` | 터치 시 덱 가로 스크롤과 제스처 충돌 | CSS |
| `will-change: transform`은 **드래그 중에만** | 상시 적용 시 GPU 메모리 낭비 | 시작 시 부여, 종료 시 제거 |

### 리렌더 0회 원칙

드래그 중에는 **React state를 갱신하지 않는다.** 위치는 ref로 잡은 DOM 노드에 `el.style.transform`을 직접 쓴다. React가 관리하는 `style` prop에는 `transform`을 **넣지 않는다** — 넣으면 React가 diff 대상으로 삼아 충돌한다. 현재 `style={{ width }}`만 관리하므로 안전하다.

순서 확정(드롭)과 키보드 이동에서만 `setState` 1회.

### 자동 스크롤

- rAF 루프에서 처리. 속도는 **시간 기반**(px/초 × 경과시간)이라 프레임 레이트가 흔들려도 체감이 같다.
- 가장자리 영역은 **컨테이너 폭의 비율**로 정의(픽셀 고정 아님). 화면 크기가 달라도 같은 느낌.
- 가장자리에 가까울수록 **제곱으로 가속.** 일정 속도는 답답하거나 과하다.
- 시작값(react-beautiful-dnd 기본값 기준, 실사용 확인 후 조정): 스크롤 시작 = 컨테이너 폭의 **25%** 지점, 최고 속도 도달 = **5%** 지점, 최고 속도 **1,700px/초**(≈28px/프레임), 가속 곡선 = 진입 비율의 제곱.
- **그 방향으로 실제 이동이 있은 뒤에만 시작한다.** 오른쪽 끝 컬럼을 집자마자 스트립이 날아가는 것을 막는다. 새 컬럼이 항상 오른쪽 끝에 생기는 우리 구조에선 특히 자주 걸리는 상황이다. (근거: [react-beautiful-dnd #349](https://github.com/atlassian/react-beautiful-dnd/issues/349))
- 프로그램 스크롤 중에는 `scroll-behavior`를 일시적으로 `auto`로 강제(부드러운 스크롤 설정과 싸우지 않게).
- 스크롤되면 포인터의 콘텐츠 좌표가 달라지므로 매 프레임 `scrollLeft`를 반영해 드롭 위치를 다시 계산한다.

### content-visibility — 덱 전체 최적화

컬럼 `<section>`에 `content-visibility: auto` + **폭축에만** `contain-intrinsic-width` 적용.

높이축은 지정하지 않는다. `content-visibility: auto`가 화면 밖에서 강제하는 size containment는 **내용에서 파생되는(intrinsic) 크기만** 무효화하는데, 이 `<section>`의 높이는 상위 `main`의 `flex-1` 배분에서 내려오는 definite 값이라 무효화 대상이 아니다. 단 이 근거는 이 파일 밖의 조상 체인에 의존한다 — 중간 래퍼가 `height: auto`로 바뀌면 화면 밖에서 0px로 접히므로 그때는 `contain-intrinsic-height`를 추가해야 한다. (구현 시 `Column.tsx` 주석으로 이 의존성을 남긴다.)

- 화면 밖 컬럼의 트윗은 레이아웃·페인트를 건너뛴다. 컬럼 6개 중 3개만 보이면 트윗 약 600개분 렌더 작업이 빠진다.
- 화면 안 컬럼도 이득이 있다: 강제되는 layout/style/paint containment가 경계가 되어, **한 컬럼 내부의 변화가 다른 컬럼의 레이아웃 재계산을 유발하지 않는다.** Google Chrome 팀 가이드가 "칸반 보드의 컬럼"을 대표 사례로 든다.
- 드래그와 무관하게 평소 스크롤·새로고침도 가벼워진다.

**알려진 위험과 그것이 우리에게 적용되지 않는 이유:**

`content-visibility: auto` 하위로의 `scrollIntoView`가 어긋나는 [미해결 이슈](https://github.com/w3c/csswg-drafts/issues/9833)가 있다. 하필 A의 "새 컬럼으로 자동 스크롤"이 그 시나리오다. 그러나 이 버그는 **브라우저가 요소 크기를 추측해야 할 때** 생긴다. 우리 컬럼은 폭이 픽셀로 명시(`style={{ width }}`, `Column.tsx:209`)되고 높이는 `h-full`로 고정이라 추측 여지가 없다. `contain-intrinsic-size`는 실제 값과 동일하게 지정한다.

**검증 결과(2026-07-27, localhost·컬럼 8개·폭 400~553px):** 위험은 예측대로 발생하지 않았다.

- `scrollIntoView({inline:'end'})`가 마지막 컬럼에서 `scrollLeft = maxScroll`과 **정확히 일치**, 잘림 0px. 중간 컬럼·재호출도 동일.
- 폭 미붕괴(합계 3747px = 개별 폭 합과 일치), 높이 8개 모두 773px 유지.
- 화면 밖 컬럼 `innerText` 42,545자 DOM 잔존 → 페이지 내 검색 가능.
- 컬럼 내부 세로 스크롤 위치 유지(800 → 화면 밖 → 800).
- **미측정:** 프레임 부드러움·Rendering 시간. 검증 당시 브라우저 탭이 `visibilityState: hidden`(창 가려짐)이어서 rAF·타이머가 억제돼 프로파일링이 불가능했다 → 사람이 창을 띄우고 확인할 항목.

**검증 의무(원문):** 구현 후 실제로 (1) 새 컬럼 자동 스크롤이 정확히 멈추는지, (2) 컬럼 6개 이상에서 가로 스크롤이 매끄러운지 확인한다. [Firefox에서 가로 스크롤 컬럼에 적용 시 터치 스와이프가 뻑뻑해진 사례](https://bugzilla.mozilla.org/show_bug.cgi?id=1922904)가 있다(scroll-snap 관련이며 우리는 미사용). 문제가 재현되면 이 최적화만 되돌린다 — A·B와 독립적이라 분리 제거가 가능하다.

### 채택하지 않은 것

- **`useOptimistic`(React 19).** 이 화면은 Server Action이 아니라 `apiFetch` 직접 호출이라 자동 롤백의 이점이 얇고, 정본 state를 따로 유지해야 하는 함정이 있다. 무엇보다 **우리가 원하는 실패 처리는 롤백이 아니라 재조회**다(위 "놓았을 때" 3번).
- **DnD 라이브러리 도입.** dnd-kit ~25kB. 필요한 것은 단일 축·소수 항목·단일 컨테이너 재정렬 하나뿐이고, 라이브러리의 충돌 감지·다중 컨테이너·센서 추상화가 전부 불필요하다. 대신 위 6가지 규칙을 직접 지킨다.
- **가상 스크롤(virtualization).** 트윗 목록에 도입하면 이득이 크지만 범위가 다르다. `content-visibility`가 훨씬 적은 비용으로 상당 부분을 커버한다.
- **맥락 삽입.** 컬럼 안의 태그를 눌러 만드는 파생 컬럼(`onPickTag` → `presetKeyword`)을 원본 컬럼 바로 오른쪽에 끼워넣는 안. 파생 관계가 위치로 드러나는 이점이 있으나, 일부 컬럼만 특수 규칙을 타면 "새 컬럼은 오른쪽 끝"이라는 예측 가능성이 깨진다. **모든 생성 경로가 동일하게 오른쪽 끝 + 자동 스크롤을 탄다.** 재정렬이 생기므로 사용자가 직접 옮기면 된다.
- **투어 단계 추가.** 덱 투어는 이미 9단계다(`src/lib/tour/tourSteps.ts`). 그립은 상시 노출 + 툴팁이라 그 자체가 발견 수단이므로 단계를 늘리지 않는다. (의식적 결정 — 누락 아님)
