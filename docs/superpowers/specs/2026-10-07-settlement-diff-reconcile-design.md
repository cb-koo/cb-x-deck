# 정산팀 지급 금액 ≠ 작업 금액 처리 — 설계

- 날짜: 2026-10-07 · 브랜치 `cb-koo/settlement-diff`(origin/main `3b48521`에서)
- 마이그레이션 `065`(추가만) — 064는 방문 예약용으로 예약됨
- 시안: https://claude.ai/artifact/5UDZ5e3PMgHcjLzXqj4qhK (koo 10-07 확정: 1번 장면 단순화·버튼 순서 `[그대로 두기][지급 금액에 맞추기]`)

## 1. 왜 (koo 10-07)

캠페인 작업 금액을 잘못 넣은 채 정산 요청이 나가면, 정산팀은 실제 금액으로 지급하고 메모로 알려 준다. 우리 쪽은 그걸 받아도 **작업 금액을 고치는 절차와 연결돼 있지 않아** 담당자가 캠페인 화면에 찾아가 손으로 고친다. 그 수정은 **누가·언제·얼마에서 얼마로·왜**가 남지 않는다. 예산·집행은 작업 금액으로 계산하므로, 고치기 전까지 예산 화면이 틀린다.

실례(운영, 지급완료 97건 중):
- @17dsy_ 더스퀘어치과_10월1주차 인용RT — 요청 4,000엔, 정산팀 지급 6,000엔(메모 "인용 6000엔"). 10-07 12:57 작업 수정 → 13:05 차액 확인. 수정 기록 없음.
- @saachan0013 더스퀘어치과_9월2주차 인용RT — 요청 50,000원, 정산팀 지급 $104.08(=139,758원). 09-21 차액 확인 → 09-30 작업 수정(9일간 예산이 5만원으로 집계).

## 2. 원인

1. **같은 건의 금액이 세 군데 따로 있다** — 작업 금액(예산·집행 기준) / 정산 요청 금액(보낸 순간 고정) / 정산팀 지급 금액(예산·집행 어디에도 안 쓰임).
2. **지급 후엔 공식 정정 경로가 없다** — 요청 수정은 지급 전만. 지급 후엔 '확인함'만 있고 작업과 연결이 없다.
3. **작업 금액은 언제든 기록 없이 바뀐다** — 결제 수단·삭제엔 잠금이 있는데 금액만 없다.
4. **차액 판정이 '요청 vs 지급'만 본다** — 작업 금액이 맞춰졌는지 모른다. 또 달러 지급·엔화 값 누락 건은 판정이 아예 안 된다(saachan 건이 지금 규칙으론 경고 없이 지나간다).

## 3. 결정

1. **판정 기준을 '작업 금액 vs 정산팀 지급'으로 바꾼다**(§4). 작업 금액을 고치면 표시가 저절로 풀린다.
2. **정산 화면에서 그 자리에서 처리**: `[그대로 두기]`(사유) / `[지급 금액에 맞추기]`(금액·사유 확인 창). 맞추기는 작업 금액 변경 + 처리 기록 + 변경 이력을 한 트랜잭션으로.
3. **작업 금액이 바뀔 때마다 이력을 남긴다**(어디서 바꿨든). 지급 완료된 작업은 캠페인 화면에서 고칠 때도 **사유 필수**.
4. 예산·집행 기준은 **계속 작업 금액**. 지급액 기준으로 바꾸지 않는다(지급 전 건·'다른 곳에서 정산함' 건과 기준이 갈린다). 이 기능이 "작업 금액 = 실제 지급"을 보장한다.
5. **정산 요청 행·정산팀 연동은 건드리지 않는다** — 지급 완료 요청은 고칠 수 없고(기존 잠금), 처리 기록은 `updated_at`을 바꾸지 않아 정산팀 폴링에 흐르지 않는다.
6. 이번에 같이: 정산 화면 문구·표 정리(§8). 별도 작업: 앱 전체 버튼 순서(§11).

## 4. 판정 — "정산팀 지급 금액이 작업 금액과 다르다"

순수 함수 하나(`settlementDisplay.ts` `taskPaidMismatch`)가 화면 배지·상단 안내·서버 가드를 모두 결정한다(기존 `hasPaidDiff` 자리를 대신한다).

입력: 요청 스냅샷(지급 통화·수수료·환율), 정산팀 결과(지급 원화·엔화·달러), **지금 작업 금액**.

1. 대상: 취소 안 된 요청 + 정산팀 상태 `paid` + 작업이 있음. 아니면 판정 안 함.
2. 기대 송금액 = `computeMoney(지금 작업 금액, 요청의 지급 통화, 요청의 수수료, 요청의 환율).amountGross` — 요청을 만들 때와 같은 계산을 지금 작업 금액으로 다시 한다.
3. 비교:
   - 원화 지급: `지급 원화 ≠ 기대 송금액` 이면 다름.
   - 엔화 지급 + 정산팀이 엔화 금액을 보냄: `지급 엔화 ≠ 기대 송금액` 이면 다름.
   - 그 밖(달러 지급, 엔화 금액 없음): 정확히 비교할 수 없으므로 **같은 날 다른 지급 건과 비교**한다(koo 10-07 개정).
     - 비율 = `지급 원화 ÷ (기대 송금액 × 요청 환율)`. 비교 대상(peers) = 지급일(`paidAt`의 **서울 날짜**)이 같고 지급 방식(달러 값 있음 `usd` / 없음 `jpy-no-amount`)이 같은 다른 건 중 이 분기로 오는 행. 각 peer의 비율은 그 peer의 **지금 작업 금액**으로 계산한다. 자기 자신은 뺀다.
     - peers가 **3건 이상**이면 그 비율들의 중앙값(짝수 개면 가운데 두 값 평균)과 비교해 **±3% 넘게 벗어나면 다름**(`|비율 ÷ 중앙값 − 1| > 0.03`). 3건 미만이면 고정 범위 **0.80 ~ 1.00** 밖일 때 다름.
     - 근거(운영 달러 지급 66건): 같은 지급일 안에서는 비율이 거의 같고 날짜를 넘으면 4% 넘게 움직인다 → 고정 범위는 넓어서 +13%·−9% 이내 오지급을 놓친다.

       | 지급일 | 비율 |
       |---|---|
       | 09-14 | 0.885 (saachan만 2.655) |
       | 09-21 | 0.899 ~ 0.900 |
       | 09-28 | 0.872 |
       | 10-06 | 0.862 ~ 0.863 |

       (정상 엔화 지급 84건 0.847 ~ 0.900, 오류 2건 1.27·2.65 — 고정 범위의 근거.)
     - 상수(`FX_RATIO_BAND`·`PEER_RATIO_TOLERANCE`·`PEER_MIN_COUNT`)와 판정은 `settlementDisplay.ts` 한 곳. 비율 식도 한 곳(`bandRatio`). peer 비율이 필요한 자리(요청 목록·캠페인 배지·서버 가드)는 저장소의 `attachPeerRatios` 하나로 같은 날 행을 읽어 채운다 — 빠뜨리면 고정 범위로 떨어진다. 기대 원화가 0이라 비율이 무한대인 행은 peers에서 뺀다(그 행 자체는 다름).
4. **처리 기록이 있으면 숨긴다** — 단, 처리할 때의 작업 금액·지급 금액이 지금과 같을 때만. 그 뒤 누가 작업 금액을 다시 바꾸거나 정산팀이 금액을 정정하면 다시 뜬다.

결과 (운영 기준 예상): 지금 미처리 0건(두 실례는 이미 손으로 맞춰져 있어 판정상 같음). 배포 전 운영 데이터로 판정을 돌려 목록 확인.

## 5. 처리 동작

### 5-1. 지급 금액에 맞추기 (확인 창)
- 창 위: `작업 금액 {현재} → 정산팀 지급 {지급}`(달러·엔화 지급이면 괄호에 그 통화 금액).
- **새 작업 금액** 칸 — 미리 채운 값:
  - 정확히 비교 가능한 경우(§4-3 앞 두 줄): 지급 금액에서 요청의 송금 수수료를 빼고(정액은 빼기, 비율은 `지급 × (1 − 비율)` 반올림) 작업 통화로 바꾼 값(작업이 원화·지급이 엔화면 요청 환율을 곱한다).
  - 달러·엔화 금액 없음: **비워 둔다**. 아래 안내로 직접 적게 한다(환산값을 넣으면 틀린 금액이 그럴듯해 보인다).
- **사유** 칸 — 정산팀 메모로 미리 채움. 비어 있으면 저장 불가.
- 하단: `{캠페인} 집행액이 {±차이}원 돼요` (원화 환산은 예산 화면과 같은 고정 환율).
- 저장 = 한 트랜잭션: 작업 금액 변경(지금 값이 창을 연 때와 같을 때만 — 아니면 "그 사이 작업 금액이 바뀌었어요" 409) + 이력 1행(출처 `settlement`, 요청 id) + 요청에 처리 기록(`matched`, 처리 때의 작업 금액·지급 금액).

### 5-2. 그대로 두기
- 작은 창: 사유 선택 — `환율·송금 수수료 차이` / `추가 지급(별도 합의)` / `기타` + 메모(기타면 필수). 정산팀 메모가 있으면 메모 칸에 미리 채움.
- 저장 = 요청에 처리 기록(`kept`, 사유, 처리 때의 작업 금액·지급 금액). 작업은 안 바뀜.

### 5-3. 처리 취소
- 펼친 행의 처리 기록 옆 `처리 취소` — `kept`만. `matched`는 이미 작업 금액이 바뀌었으므로 되돌리려면 캠페인 화면에서 금액을 고친다(그것도 이력에 남는다).

## 6. 작업 금액 변경 이력

- 모든 작업 금액 변경이 1행: 캠페인 화면(작업 패널·표)·인플 교체·정산 화면 맞추기.
- 작업을 만들 때의 금액은 기록하지 않는다(기존 작업과 모양을 맞춤) — 이력의 첫 행 '이전 값'이 곧 처음 금액. 시안 3번의 `— → 4,000엔 작업을 만들 때` 줄은 빠진다.
- **지급 완료된 정산 요청이 있는 작업**의 금액을 캠페인 화면에서 바꾸면 사유 칸이 함께 열리고, 사유 없으면 저장 안 됨(서버도 400).
- 지급 전 정산 요청이 있는 작업의 금액을 바꾸면 저장 후 안내: `정산 요청은 아직 {이전 금액}이에요 — 정산 화면에서 '고친 값으로 다시 반영'을 눌러 주세요 [정산 요청 보기]`.
- 이력은 지우거나 고칠 수 없다(API 없음).
- 표시: 작업 패널 금액 옆 `변경 이력 N`(0이면 숨김) → 펼침(시안 3). 정산 요청 펼침의 처리 기록에도 해당 행.

## 8. 화면 정리 (같이 하는 것, koo 10-07 A·B-2)

1. **"정산팀"으로 통일** — 사용자에게 보이는 문구의 `정산 쪽`·`정산 프로덕트`·`정산 담당자`·`그쪽` 전부. 대상: 정산 화면 전 탭(상태 설명·연동 기록·요청 수정 창·개정 이력·오류 문구 `externalLogCopy`·`settlementRevisionCopy`), 캠페인 작업 패널의 정산 배지 설명, 인플루언서 타임라인 정정 줄. 지난 업데이트 소식 글·코드 주석은 그대로.
2. 상태 라벨 `정산에서 취소` → `정산팀이 취소`. 그 밖 라벨(정산 접수·지급 예정·지급 완료·보류)은 유지. 새 라벨 `지급 금액 다름`(표에서는 버튼이 대신하므로 캠페인 배지에만).
3. **표 열** — 요청 내역: `인플루언서 | 유형 | 작업 금액 | 송금액 | 정산팀 지급 | 차이 | 결제 수단 | 상태 · 처리 | ▸`('마감' 열 삭제). '작업 금액'은 **지금 작업 금액**(요청과 다르면 아래 작은 글씨 `요청 {금액}`). 검토 대기: `요청액` → `작업 금액`(마감 열 유지).
4. **차이 칸** — 작업 금액 기준 판정이 '다름'이면 주황 숫자(보낸 통화), 아니면 `—`. 회색 환율 차이 숫자는 표에서 뺀다(펼침에서만 `환율 1엔 = 8.49원`).
5. **상단 안내 한 줄** — `정산팀 지급 금액이 작업 금액과 다른 건이 N건 있어요 — 표에서 어느 쪽이 맞는지 정해 주세요. [그 N건만 보기]`. 0건이면 없음.
6. **펼침** — 좌우 두 블록 `우리가 보낸 요청` / `정산팀이 보낸 결과`, 그 아래 `처리 기록`, 그 아래 기존 `개정 이력`을 같은 모양(시각·사람 / 전→후 / 사유)으로. 요청자·클리닉·항목·목적 줄은 표·묶음 머리와 겹쳐 뺀다(항목·목적은 '우리가 보낸 요청' 블록 맨 아래 흐린 글씨로 남김 — 정산팀에 나간 문구라 확인할 일이 있음).
7. **빈 값은 `—` 하나** — `— 정산 쪽이 안 적었어요`·`— 아직 보내오지 않아요` 제거.
8. **필터를 제목 줄 오른쪽으로** — 요청 내역·검토 대기 두 탭 같이(B-2). 다른 화면은 그대로.

## 9. 화면 문구표 (구현·리뷰 기준 — 여기 없는 문구를 새로 만들지 않는다)

| 자리 | 문구 |
|---|---|

## 10. 테스트

- 순수(`taskPaidMismatch`·제안 금액): 원화/엔화/달러/엔화 없음 × 수수료 없음/정액/비율 × 작업 통화 원화/엔화. 실례 2건 + 정상 환율 건(0.85·0.90) + 경계(0.80·1.00). 같은 날 비교: 정상 3건+이상치(2.655·0.92 다름 / 0.90 같음)·peers 2건이면 고정 범위·서울 날짜 경계(UTC 같은 날, 서울 다른 날)·지급 방식 다른 행 제외·자기 제외·짝수 중앙값. 처리 기록이 있고 작업 금액이 같으면 숨김, 바뀌면 다시 표시.
- DB(연습용): 같은 날 정상 3건+0.92 → 목록·배지·서버 가드가 같은 peer로 판정, 맞추기 트랜잭션(작업 금액·이력·처리 기록 3개가 같이), 경합 409, 그대로 두기·처리 취소, 지급 완료 작업의 캠페인 화면 금액 수정 사유 없으면 400·있으면 이력, 인플 교체 시 이력, 처리 기록이 `payment_request.updated_at`을 안 바꾸는지(정산팀 폴링 불변).
- 문구: §9 표의 문구가 화면 코드와 일치하는지(리뷰 항목). `정산 쪽`·`정산 프로덕트`·`그쪽`이 사용자 문구에 남지 않았는지 grep.
- 배포 전: 운영 데이터로 판정 실행 → '다름' 목록 확인(예상 0건).

## 11. 범위 밖

- **앱 전체 버튼 순서 통일**(확정 오른쪽·취소 왼쪽·삭제는 빨강) — 클라이언트·워크스페이스·예산 패널·클라이언트 상세·브리핑·인플 타임라인 등 6~7곳. **별도 작업으로 곧 진행**(koo 10-07 B-1).
- 금액 외 칸(게시물 링크·인플 교체·결제 수단)의 변경 이력 — 테이블은 준비, 필요 사례가 생기면 추가(B-3).
- 정산팀에 우리 쪽 처리 결과를 알려 주는 연동 — 없음(지급 완료 건은 정산팀이 이미 실제 금액을 안다).

## 12. 업데이트 소식

`개선`: `정산팀이 다른 금액으로 지급한 건을 정산 화면에서 바로 처리할 수 있어요` — 작업 금액을 지급 금액에 맞추거나 그대로 두고, 누가 언제 왜 바꿨는지 작업의 '변경 이력'에 남아요. 달러로 지급된 건도 이제 금액이 크게 다르면 알려 줘요. 정산 화면 문구를 '정산팀'으로 통일하고, 요청 내역 표의 '요청액'을 '작업 금액'으로 바꿨어요(마감 열은 뺐어요).
