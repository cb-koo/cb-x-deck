# RT 작업 증빙 스크린샷 (2026-08-31)

## 1. 목적과 배경

캠페인의 RT 작업은 인플루언서가 대상 게시물을 리포스트하는 일이다. RT는 **새 게시물을 만들지 않는다** — 그래서 이 시스템에는 RT 이행의 증거가 하나도 없다.

- `campaign_task.post_url`은 비어 있다(RT엔 자기 게시물이 없다). `TaskTable.tsx:180`이 RT 행에서 [게시물 연결]을 아예 빼고, `PostedCell.tsx:103`이 게시 확인 팝오버에서 '게시물 링크' 칸을 숨기는 이유다.
- 정산으로 나가는 참고자료는 `referenceUrlFor`(settlementCalc.ts)가 RT일 때 **대상 트윗 URL**로 대체한다 — "이 인플이 RT했다"가 아니라 "무엇을 RT하라고 했는지"만 넘어간다.
- 자동 확인(`checkPostedRun`)은 리포스터 목록을 조회해 판정하지만 그 판정은 흔적이 남지 않고, 비공개 계정이면 `pending`으로 빠진다.

실무에서는 담당자가 인플루언서 피드에서 RT 내역을 스크린샷으로 찍어 증명 자료로 제출한다. 그 스크린샷이 시스템 안에 없어서 슬랙·로컬 폴더에 흩어진다.

**이 작업의 목적:** RT 작업을 게시됨으로 표시할 때 스크린샷 1장을 반드시 첨부하게 하고, 그 이미지를 작업에 붙여 보관·확대·내려받기 하며, 정산 후보 화면에도 함께 보이게 한다.

## 2. 확정된 결정 (koo, 2026-08-31)

| # | 결정 | 근거 |
|---|---|---|
| 1 | 스크린샷은 **필수** | 증거 없는 게시 확인을 남기지 않는다 |
| 2 | 리포스트 목록 자동 검증은 **보류** | 자동 경로는 스크린샷을 만들지 못한다 — 필수와 충돌 |
| 3 | 적용 범위는 **RT 작업만** | 투고·인용RT는 `post_url`이 증거, 방문은 이번 범위 아님 |
| 4 | **1장**이면 충분 | 피드 캡처 한 장에 RT 내역이 담긴다 |
| 5 | 언제든 바꿔 끼울 수 있고, **누가 언제 올렸는지 표시** | 스스로 바로잡되 책임이 남는다. 게시됨인 RT에서 완전히 비우는 것은 막는다(결정 1과의 정합 — §5-1) |
| 6 | 행선지는 **우리 팀 기록 + 내려받기**(이번 범위) + **정산 요청에 담을 준비**(전송은 계약 열릴 때) | 정산 프로덕트 API는 URL 문자열 칸만 있다 |
| 7 | 기존 게시된 RT(증빙 없음)는 **'증빙 없음' 표시만**, 뒤늦게 채울 수 있게 | 지난 건은 소급 강제하지 않는다 |
| 8 | 정산 화면에서 증빙 없는 RT는 **노랑 경고 — 보낼 수는 있다** | 진짜 예외(삭제된 피드 등)가 정산을 막지 않게 |

## 3. 이 결정의 대가 (수용됨)

- **손이 늘어난다.** 자동 확인이 빠지고 필수가 붙으면 RT 30건짜리 캠페인은 캡처·붙여넣기 30번이다. 완화는 팝오버에서 `Ctrl+V` 한 번으로 끝나게 만드는 것뿐. **여러 건 일괄 처리는 이번 범위 밖** — 실사용 마찰이 확인되면 후속 작업으로 승격한다(AGENTS UX 원칙 6의 태도).
- **스크린샷은 위조·오인이 가능한 증거다.** 자동 판독(OCR)은 하지 않는다 — 사람 눈으로 본다. 실제 방어선은 ① 누가 언제 올렸는지 기록 ② 캡처에 무엇이 보여야 하는지 안내하는 한 줄이다.

## 4. 저장 설계

### 4-1. 선택한 방식과 탈락안

| 안 | 판단 |
|---|---|
| **A. `campaign_task.proof jsonb` 한 칸** | **채택.** 1장 결정과 맞고, 작업 행을 이미 읽는 모든 화면이 조인 없이 함께 읽는다 |
| B. 별도 테이블 `campaign_task_proof` | 탈락(YAGNI). 여러 장·교체 이력이 필요해지면 그때 |
| C. 원고 이미지 첨부(`draft.content.media`) 재사용 | **불가.** RT 작업엔 원고가 없다(`TaskAddModal.tsx:103` — RT엔 원고 칸을 주지 않는다) |

### 4-2. 컬럼

```
alter table campaign_task add column if not exists proof jsonb;
```

값의 모양 (없으면 `null`):

```ts
interface TaskProof {
  url: string;        // 스토리지 경로. task/<작업id>/<파일id>.<확장자>
  by: string | null;  // 올린 member.id
  byName: string;     // 올린 사람 이름 스냅샷 (payment_request의 requester_name 관례)
  at: string;         // ISO 시각
}
```

이름을 스냅샷으로 두는 이유: 표시할 때마다 member를 조인하지 않기 위해서다(payment_request가 같은 방식을 쓴다).

### 4-3. 버킷

`draft-media`를 재사용하지 않고 **`task-proof`를 새로 만든다.**

- `draftMediaGuard`의 경로 정규식이 `draft/<uuid>/…`에 묶여 있다 — 증빙 경로를 통과시키려면 그 방어선을 느슨하게 만들어야 한다
- 스크린샷은 용량 상한이 달라야 한다 (전체 화면 캡처 PNG는 5MB를 넘는다)

| 항목 | 값 |
|---|---|
| 공개 여부 | 비공개 — 표시·내려받기 모두 서명 URL |
| 상한 | **10MB** (코드 상수와 버킷 `file_size_limit`이 반드시 같은 값) |
| 허용 형식 | `image/jpeg`, `image/png`, `image/webp` — **gif 제외**(스크린샷은 정지 화면, 클립보드 붙여넣기는 png로 온다) |
| 경로 | `task/<작업id>/<파일id>.<확장자>` |
| 정책 | `select`·`insert`만 `authenticated`에 준다 (`draft-media`와 같은 태도) |

**삭제 정책을 주지 않는 이유:** '지우기'·'바꾸기'는 `campaign_task.proof` 포인터만 바꾼다. 스토리지 객체는 남는다(비공개라 새지 않고, 교체 흔적이 남는 쪽이 증빙에 유리하다). 쓰지 않을 권한을 만들지 않는다.

## 5. 필수를 어디서 지키나

UI만 막으면 뚫린다. `posted_at`을 쓰는 경로를 전수 확인했다.

| 경로 | 조치 |
|---|---|
| `PATCH /api/campaigns/[id]/tasks/[taskId]` (사람이 게시 확인) | **막는다.** `type='rt'`인 작업에 `postedAt`을 채우려면 같은 요청에 `proof`가 오거나 이미 행에 있어야 한다 — 없으면 400 |
| `POST/PATCH /api/tracking` → `linkTrackedPost` (게시물 연결) | **막는다.** `coalesce`로 RT 작업의 `posted_at`까지 채운다. UI는 이미 RT를 제외하지만(`TaskTable.tsx:180`) API는 열려 있다. RT 작업에 게시물을 붙이는 것은 원래도 개념상 틀린 연결이므로 라우트에서 400으로 거절한다 |
| `POST /api/campaigns/[id]/check-posted` → `markPosted` (자동 확인) | **수용된 틈.** 결정 2에 따라 버튼을 제거하면 도달 경로가 없다. 라우트·`checkPostedRun`·테스트는 되살릴 자산으로 보존한다. 되살릴 때 스크린샷 필수와의 관계를 다시 결정해야 한다 |
| `cutoverDraftsToTasks` | 해당 없음(1회성 전환 스크립트, 이미 실행됨) |

**DB CHECK 제약은 쓰지 않는다.** `check (not (type='rt' and posted_at is not null and proof is null))`은 기존 게시된 RT 행을 위반한다. `NOT VALID`로 넣어도 그 행을 나중에 수정(메모 한 줄 고치기)하면 500이 난다. 앱 계층이 유일한 방어선이다.

### 5-1. 입력 검증 (`campaignTaskInput.parseTaskPatch`)

`proof` 키가 오면:
- `null` → 떼기. **단 `posted_at`이 이미 있는 RT 작업에서는 거절한다**(400) — 게시됨인 RT는 증빙이 반드시 있어야 하므로(결정 1), 비우는 것이 아니라 바꾸는 것만 허용한다. 아직 게시 확인 전이면 자유롭게 뗄 수 있다
- 객체 → `url`이 `^task/<uuid>/<uuid>\.(jpg|jpeg|png|webp)$` 정규식을 통과해야 한다. `by`·`byName`·`at`은 **클라이언트 값을 믿지 않고 서버가 채운다**(로그인한 member로)
- 그 외 → 400

정규식으로 좁히는 이유는 `draftMediaGuard`에 적힌 것과 같다: 임의 URL이 jsonb에 저장되면 워크스페이스 전원의 브라우저가 그 주소로 요청을 보낸다(추적 픽셀·IP 유출). 원고 첨부 때 리뷰에서 잡힌 함정이다.

`type !== 'rt'`인 작업에 `proof`가 오면 400 — 범위를 코드가 지킨다(결정 3).

## 6. 화면

### 6-1. 게시 확인 팝오버 (`PostedCell.tsx`)

RT일 때 지금 비어 있는 '게시물 링크' 자리에 증빙 칸이 들어간다. 팝오버의 세 상태에 각각:

**① 아직 게시 안 된 RT**
```
게시 확인
게시된 날을 적고 증빙 스크린샷을 넣으면 게시됨으로 바뀌고 정산 후보가 돼요

게시된 날  [2026-08-31]

증빙 스크린샷  (필수)
┌────────────────────────────────┐
│  여기를 누르거나 Ctrl+V로 붙여넣기 │
└────────────────────────────────┘
인플루언서 피드에서 RT가 보이는 화면을 찍어주세요 — 계정 이름과 RT 표시가 함께 보이면 좋아요

                    [취소]  [게시됨으로 표시]   ← 스크린샷 없으면 비활성
```
- 붙여넣기(`Ctrl+V`)와 파일 고르기 둘 다. 스크린샷은 거의 항상 클립보드에 있으니 **붙여넣기가 주 경로**다 — 현재 코드베이스에 `onPaste` 핸들러가 하나도 없어 신규 구현이다
- 넣으면 즉시 미리보기(작은 썸네일) + [바꾸기]
- 버튼 비활성 이유는 문구로 말한다: `증빙 스크린샷을 넣어야 게시됨으로 표시할 수 있어요`
- 업로드는 즉시(파일을 고른 순간) 스토리지로 올라가고, `proof`는 [게시됨으로 표시]를 누를 때 `postedAt`과 **한 요청으로** 저장된다. 팝오버를 그냥 닫으면 올라간 객체는 참조 없이 남는다 — 비공개 버킷이고 용량이 작아 수용한다(정리 작업은 두지 않는다)

**② 게시된 RT + 증빙 있음** — 기존 '게시 내림 표시' 화면 위에 증빙 블록 추가
```
증빙 스크린샷
[썸네일]  구건 박이 8/31 올림
          [크게 보기]  [바꾸기]  [받기]
```
[지우기]가 없다: 게시됨인 RT는 증빙이 반드시 있어야 하므로(결정 1) 비우는 것이 아니라 **바꾸는 것만** 된다. 잘못 올렸으면 [바꾸기]로 덮는다. 결정 5의 '언제든 바꿔 끼울 수 있다'는 이렇게 지켜진다 — 아직 게시 확인 전이면 [지우기]도 있다.

**③ 게시된 RT + 증빙 없음(기존 건)**
```
증빙 스크린샷
증빙 없음 — 지금 채울 수 있어요
┌────────────────────────────────┐
│  여기를 누르거나 Ctrl+V로 붙여넣기 │
└────────────────────────────────┘
```

### 6-2. 작업 표 (`TaskTable.tsx`)

단계 칩 옆에:
- 증빙 있으면 작은 썸네일 — 클릭하면 확대(`ImageLightbox` 재사용)
- 게시된 RT인데 증빙 없으면 `증빙 없음` 회색 태그

### 6-3. 자동 확인 버튼 제거

`CampaignDetail.tsx:320`의 [게시 확인하기] 버튼과 옆 설명줄(`게시 확인하기 — RT 대상 게시글의 리포스트 계정을 찾아…`), 그리고 `rtPendingCount`·`checkPosted()`·`CheckPostedModal` 렌더를 화면에서 제거한다. `checkPostedApi`·라우트·`checkPostedRun`·`checkPosted.ts`·해당 테스트 파일은 **삭제하지 않는다**(결정 2 — 보류이지 폐기가 아니다).

- **후보 행(`CandidateRow.tsx`)**: 참고 링크 칸 옆에 증빙 썸네일(클릭 확대). 없으면 아무것도 안 그린다

- **요청 내역 행(`RequestRow.tsx`)**: '참고자료' 항목 아래에 증빙 썸네일

## 8. 라이브러리 구성

기존 원고 이미지 첨부 코드를 **재사용하지 않고 나란히 둔다** — 상한·형식·경로·수명이 모두 다르고, `draftMedia.ts`는 원고 파일명 조립 같은 원고 전용 규칙을 안고 있다.

| 파일 | 내용 |
|---|---|
| `src/lib/taskProof.ts` (신규) | 순수 규칙 + 업로드. 검증(형식·용량)·경로 조립·경로 정규식·서명 URL 발급·업로드·내려받기 |
| `src/lib/taskProofGuard.ts` (신규) | 서버측 `proof` 정규화·검증(`draftMediaGuard`와 같은 역할). `parseTaskPatch`가 호출 |
| `src/components/TaskProofField.tsx` (신규) | 팝오버·정산 양쪽이 쓰는 첨부 칸(붙여넣기·파일 고르기·미리보기·바꾸기·지우기·받기) |

정규식은 **한 곳(`taskProofGuard`)에만 두고** `taskProof`가 그것을 가져와 쓴다 — 클라이언트가 통과시킨 값이 서버에서 거절되는 일이 없게(원고 첨부에서 상한을 두 곳에 두며 배운 것).
