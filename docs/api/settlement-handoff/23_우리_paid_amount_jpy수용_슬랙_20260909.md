# 우리 회신 (우리 → 정산 프로덕트, 슬랙용) — 2026-09-09 paid_amount_jpy 확장 요청 수용 + paid_currency 제안

> 아래 그대로 붙여넣기. 첨부: `settlement-external-api.md` 현재 판(§5 `settlement.paid_amount_jpy`, §6 `paid_amount_jpy`·`paid_currency` 행 + "외화 실지급액의 저장 의미" 표, §8 개정 기록).

---

「엔화 실지급액 상태 POST API 확장 요청」 확인했습니다. **수용했고 오늘 배포합니다.** §7에서 물으신 항목별 답입니다.

*1. 필드·검증 — 제안 그대로*
• `paid_amount_jpy`: 0 이상 안전 정수(0 ~ 9,007,199,254,740,991). `null`·소수·문자열·상한 초과는 400 `field: "paid_amount_jpy"`. 0은 유효(필드 존재로 판정).
• `paid`에서만 허용. 다른 상태에 오면 400. `paid_amount_usd`도 같은 규칙으로 맞췄습니다(어제 안내 때는 이 제한이 없었는데, 이번에 함께 적용했습니다).
• `paid_amount_usd`와 동시 전송은 400, 오류 필드는 `paid_amount_jpy`.
• `paid_amount_krw`·`paid_at`는 지금처럼 필수. 외화만 오면 400 `field: "paid_amount_krw"`.
• 차액 판정은 종전대로 `paid_amount_krw` 기준입니다.

*2. 신·구 전송 구별 — 버전 게이트 대신 `paid_currency` 명시 필드를 제안합니다*
• 문제의 핵심은 "외화 필드가 없을 때 그게 원화 지급이라는 뜻인지, 옛 전송이라 빠진 건지"였습니다. 시각·버전으로 가르는 대신, **의미가 있을 때만 명시**하는 쪽이 단순합니다.
• `paid_currency: "KRW" | "JPY" | "USD"`(선택, `paid`에서만). 보내면 그 통화로 확정합니다. `"KRW"`면 저장된 외화(USD·JPY)를 둘 다 지웁니다 — 계좌 엔화 지급을 원화 지급으로 정정하는 경우가 이것입니다. 외화 필드와 어긋나면 400 `field: "paid_currency"`.
• **안 보내면 "부재는 의미 없음"** — 저장된 외화를 건드리지 않습니다. 그래서 구버전 outbox·재시도가 외화를 지우는 일이 없고, 전환 시점 합의도 필요 없습니다.
• 저장 의미는 이렇습니다: JPY가 오면 JPY 저장·USD 지움 / USD가 오면 USD 저장·JPY 지움 / 외화 없음 + `paid_currency: "KRW"` → 둘 다 지움 / 외화 없음 + `paid_currency` 없음 → 기존 유지 / stale → 아무것도 안 바꿈. 과거 금액을 환율로 역산하지 않습니다.
• 저희 쪽 기존 결함도 이걸로 고쳤습니다: 어제까지는 외화 없는 `paid` 정정이 저장된 달러를 지웠습니다. 이제 "보낸 것만 갱신"입니다.

*3. 되비침*
• POST 응답과 GET의 `settlement.paid_amount_jpy`(number | null). 외화 없는 지급·구버전 데이터는 `null`. 필드 생략은 없고 항상 키가 있습니다.

*4. 배포·순서*
• 저희 수신은 오늘 배포합니다(배포 완료 시 슬랙으로 알리겠습니다). 그쪽 순서: 020 마이그레이션 적용 확인 → 송신 배포 → 게이트 전환. 기존 건 소급 전송 없음, outbox 재시도는 동일 본문·동일 `updated_at` — 제안하신 대로입니다.
