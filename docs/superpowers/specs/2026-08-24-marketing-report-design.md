# 마케팅 리포트 페이지 설계 (외부 클리닉 리포트 API 연동)

2026-08-24 · 브레인스토밍(시안 3회) + exa 리서치 + 시스템 대조 검토 반영

## 목적

클리닉 X 마케팅 캠페인의 성과(LINE 친구 → 인입 → 상담 → 예약 → 매출 → 비용)를
**내부 콘텐츠 기획자가 직관적으로 파악**하고, 월간보고서 작성 시 숫자를 확인·복사하는 화면.
데이터 출처는 외부 "클리닉 마케팅 리포트 API"(linemessagedashboard.vercel.app) 하나다.

- 용도: **내부 확인용** (보고서 대체·클라이언트 공유는 비범위)
- 기간·단위 자유형: **일간/주간/월간** 어느 단위로도 캠페인 흐름을 볼 수 있어야 한다
- 이후 X 콘텐츠 데이터(자체 트래킹)와 "같이 보기"로 확장할 수 있는 구조

## 결정 사항 (사용자 확인 완료)

| 결정 | 내용 |
| --- | --- |
| 화면 방향 | A안 "KPI 대시보드형" + 추이 통합, 탭 없는 **한 스크롤 3층 구조** |
| X 조회수 | 외부 API의 X 조회수는 신뢰 불가 → **기본 숨김**, 경고 딸린 토글로만 표시 |
| 클리닉 관리 | `client.clinic_code` 컬럼으로 기존 클라이언트에 매핑 |
| 기간 | 프리셋 고정 아님 — **직접 지정**(자주 쓰는 기간은 칩), 단위는 일/주/월 자동 추천+수동 변경 |
| 저장 | **처음부터 DB 스냅샷 수집**(사용자 제안) — 일간 백필은 2026-04부터 |

## 화면 설계 — `/reports`

사이드바 전역 그룹(트래킹·클라이언트와 같은 층위)에 "리포트" 추가.

### 컨트롤 (상단 1열)

- 클리닉 선택: `clinic_code` 매핑된 클라이언트만 목록에. 하나도 없으면 클라이언트
  페이지로 안내 링크.
- 기간: 시작일~끝일 날짜 단위 직접 지정(기존 PeriodPicker의 "직접 지정" 패턴 재사용).
  자주 쓰는 기간 칩: 지난달(보고서용)·이번 달·최근 7일·최근 30일·최근 6개월.
- 단위: 일간/주간/월간 세그먼트. 자동 추천 — 기간 ≤31일 일간, ≤120일 주간, 초과 월간.
  수동 변경 가능하되 **버킷 120개 초과 조합은 막고 이유를 안내**(차트 가독성 —
  흐름 층은 DB에서 읽으므로 호출 수 제약은 아니다).
- [리포트 불러오기] 버튼 — 외부 호출은 opt-in(AGENTS.md 원칙 6).

### 3층 구조 (단위와 무관하게 동일)

1. **기간 요약** — 선택 기간 전체 합계 KPI 타일(친구 증감·인입·상담·예약·매출)
   + 직전 같은 길이 기간 대비 증감. "지난달" 프리셋일 때만 "전월 대비"로 표기.
2. **기간 구성** — 기간 전체 집계의 분해: 지점별 예약·매출(가로 막대), 고객 흐름
   깔때기(인입→상담→예약자→방문, 단계별 전환율), 초진/재진 구성, 예약 상태
   (확정·취소·노쇼), 비용(매체별 광고비·ROAS·CPA).
3. **흐름** — 선택 단위로 쪼갠 추이 차트: 전환율 라인(인입→상담, 상담→예약),
   예약 건수 막대, 매출 스택(초진/재진), 취소·노쇼율 라인(+업계 통상 범위 5~8% 띠),
   광고비 막대 + ROAS 라인(별도 차트, 3개월 이동평균 병기).

### 표기 규칙 (외부 데이터의 함정 대응 — 문서 6·7절 근거)

- **null은 "—"** + "데이터 없음 — 0이 아닙니다" 툴팁. 0은 그대로 0.
- 파생값(차단율·기존 인입·재진율·객단가)은 화면에서 계산, `(계산)` 표기.
- 광고비 0원이면 "시트 미입력일 수 있음" 경고 + ROAS·CPA 표시 안 함(분모 없음).
- **일간 단위에서 ROAS·CPA 숨김**(하루 단위는 노이즈 — 리서치 근거). 주말은 옅은 색.
- 진행 중 버킷(오늘·이번 주·이번 달)은 옅은 색/점선 + "진행 중" 주석.
- LINE 친구 수는 기록 없는 날 **선을 끊어서** 표시(스냅샷 누락 = 모름).
- 주간 버킷은 **월요일 시작, KST**.
- `upcoming_confirmed`("지금 이후 확정 예약")는 조회 기간과 무관함을 ⓘ로 설명.
- 지점 `기타`(표기 불명 합산)는 `source_values` 원본을 툴팁으로, 마스터 미등록
  지점은 [미등록] 뱃지로 — 숨기지 않는다.
- `unavailable` 묶음은 그 섹션만 "가져오지 못함(사유)", 나머지는 정상 표시.
- CPA·ROAS는 항상 접수일(created_at) 기준으로 계산·표기. 접수일/방문일 전환 토글은
  요약·구성 층에 제공(`date_basis=both`로 받아 재호출 없이 전환).
- X 조회수: 기본 숨김. 설정 토글(localStorage)로 켜면 "외부 집계·부정확할 수 있음"
  경고와 함께 표시. 수집(저장)은 항상 한다 — 표시만 통제.
- 각 층에 데이터 시각 표기: 흐름 층은 "○일 ○시 동기화", 요약·구성 층은 "방금 조회".

## 데이터 계층

### 외부 API 요점

- `GET /api/reports/v1/metrics?clinic&start&end[&include&date_basis&compare&group_by]`
- 헤더 `x-api-key` 인증. 분당 60회. 응답은 저쪽에서 5분 캐시. 기간 최대 366일.
- **기간을 통째로 합산해서 반환** — 버킷별 수치는 버킷마다 1회 호출해야 얻는다.
- 인입·상담·예약자 등 사람 수 지표는 **중복 제거 값이라 일간 합산으로 상위 단위를
  만들 수 없다** → 주간·월간 버킷도 각각 저장한다.

### 스냅샷 테이블 (마이그레이션 028)

```sql
create table report_snapshot (
  clinic_code  text not null,
  granularity  text not null check (granularity in ('day','week','month')),
  period_start date not null,          -- KST 기준 버킷 시작일
  period_end   date not null,
  payload      jsonb not null,          -- 외부 응답 current 원본(전 묶음, 지점 분해 포함)
  fetched_at   timestamptz not null default now(),
  primary key (clinic_code, granularity, period_start)
);
alter table client add column clinic_code text unique;
```

- 수집 호출 파라미터: `include=` 전 묶음, `date_basis=both`, `compare=none`,
  `group_by=branch`. 원본 JSON을 그대로 저장 — 파싱·파생은 읽기 쪽 lib 책임.

### 동기화 (Vercel 크론, 매일 04:00 KST)

- `POST /api/reports/sync` — `Authorization: Bearer CRON_SECRET` 게이트.
- **재개 가능한 예산 방식**: 실행당 시간 250초·호출 수 상한 안에서, 우선순위대로
  가장 오래된 것부터 처리. 못 끝낸 몫은 다음 실행이 이어서 한다(플랜의 크론
  빈도·함수 실행 시간 제한에 안전).
  1. 어제 일간 버킷(전 클리닉) → 2. 막 닫힌 주간/월간 버킷 →
  3. 최근 90일 창 안에서 `fetched_at`이 가장 오래된 버킷 재동기화.
- 재동기화가 필요한 이유: 예약 상태는 소급해서 바뀌고(취소·노쇼), 광고비 시트는
  늦게 입력된다(블리비 6월 실사례).

### 백필 (1회성, 로컬 스크립트)

- `scripts/backfill-reports.ts` (tsx, `.env` 사용 — 기존 scripts/ 관례).
- 2026-04-01부터 어제까지 일간 + 닫힌 주간·월간 버킷. 분당 55회로 스로틀.
  전 묶음이 비어 있는 달이 이어지면 그 이전은 데이터 시작 전으로 보고 중단.
- 6클리닉 × 약 5개월 ≈ 900여 호출, 15~20분 예상.

### 읽기 경로 (모두 `requireMember` 게이트)

- `GET /api/reports/summary?clientId&start&end` — 요약·구성 층. 외부 API를 그 기간으로
  1회 직접 호출해 그대로 반환. 비교 기준: 기간이 정확히 캘린더 월이면
  `compare=calendar`(전월 대비 — 보고서 관례), 아니면 `compare=period`(직전 같은 길이).
- `GET /api/reports/series?clientId&start&end&unit` — 흐름 층. DB 스냅샷에서 버킷을
  읽고, **진행 중인 마지막 버킷만** 외부 1회 호출로 보충. 저장 안 된 버킷은 채우러
  가지 않고 "미수집" 공백으로 정직하게 표시(백필 전·크론 밀림 상태가 화면에 드러남).
  응답에 버킷별 `fetched_at`·`inProgress` 포함.
- 화면당 외부 호출: 요약 1회 + 진행 중 버킷 0~1회. 나머지는 DB.

### lib 구성 (각각 단위 테스트 대상)

- `src/lib/reportApi.ts` — 외부 클라이언트: URL 조립, `x-api-key`, 오류 매핑
  (401/400/404/429), 응답 타입. 여기만 외부 API를 안다.
- `src/lib/reportStore.ts` — 스냅샷 upsert/조회, 동기화 대기열(우선순위·예산) 계산.
- `src/lib/reportSeries.ts` — KST 버킷 경계(주=월요일 시작), 버킷 나열, 진행 중 버킷
  판정, 파생값 계산(차단율·객단가·재진율·취소노쇼율·3개월 이동평균), null 전파 규칙.

## 보안

- `REPORT_API_KEY`·`CRON_SECRET`은 Vercel 환경변수. 외부 호출은 전부 서버에서 —
  키는 절대 클라이언트로 가지 않는다.
- 전달 문서에 실키가 적혀 있었음 → **작성자에게 키 재발급 요청 권고** (연동과 별개 진행).

## 테스트

- lib 3파일 단위 테스트: 실 응답 fixture(JSON) 기반 파싱, null vs 0 전파, 버킷 경계
  (월요일·월말·KST), 예산 대기열 우선순위, 파생값 계산.
- 라우트·컴포넌트 하네스는 기존 관례대로 없음 — 화면 검증은 build+start 로컬 확인
  (127.0.0.1:3001) 후 사용자 QA.

## 비범위 (v1 제외)

- 클라이언트 공유·내보내기(인쇄/PDF), 전 클리닉 매트릭스 비교 뷰
- X 콘텐츠 데이터(자체 트래킹)와의 결합 뷰 — 구조만 열어둠(스냅샷 테이블·3층 화면)
- 서버 계산 객단가·전환율 API 요청(외부 10번 항목) 등 외부 API 측 변경 요청

## 열린 질문 (구현 중 확인)

- Vercel 플랜의 크론 빈도 제한 — 하루 1회로 충분하게 설계했으나, 더 자주 돌 수
  있으면 재동기화 창을 넓힌다.
- 실응답의 정확한 필드 구조는 openapi.yaml로 확정(구현 첫 작업에서 fixture 채집).
