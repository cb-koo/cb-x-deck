# 인증 확인을 로컬 JWT 검증으로 (설계)

2026-08-08.

**배경.** 모든 API 라우트가 `requireAllowedUser()`를 지나고, 그 안의 `supabase.auth.getUser()`는 **호출마다 Supabase 인증 서버로 네트워크 요청**을 보낸다. 2026-08-01 카드 팝업 작업 중 성능을 재다가 발견했고(30~45ms), 전 라우트에 걸린 문제라 그 기능에 얹지 않고 백로그로 남겼다.

## 착수 전 확인한 것

착수 조건이 프로젝트 설정에 달려 있어 먼저 확인했다. **둘 다 충족한다.**

**① 서명키가 비대칭이다.** JWKS 엔드포인트가 `alg: ES256` / `kty: EC` 키를 내려준다. 대칭 시크릿(HS*)이었다면 `getClaims()`가 내부에서 `getUser()`로 떨어져(`GoTrueClient.js:5246-5259`) 이득이 0이었다.

**② 필요한 값이 전부 JWT 클레임에 있다.** 인증 경로가 `user` 객체에서 실제로 쓰는 것은 셋뿐이다.

| 쓰는 곳 | 필드 | 클레임 |
|---|---|---|
| `isAllowedUser` (`auth.ts:17`) | `email` | ✅ |
| `isAllowedUser` | `app_metadata.provider` / `providers` | ✅ |
| `resolveMember` (`workspaceStore.ts:36`) | `email`, `user_metadata.full_name`/`name` | ✅ |

## ★ 핵심 함정 — 그냥 바꾸면 이득이 거의 없다

`getClaims()`의 JWKS 캐시는 **인스턴스 변수**다(`this.jwks` / `this.jwks_cached_at`, `GoTrueClient.js:5129-5145`). 그런데 이 저장소의 `createClient()`(`supabase/server.ts`)는 요청 쿠키에 묶이므로 **요청마다 새 클라이언트를 만든다.** 즉 캐시가 매번 비어 있어 요청마다 `/.well-known/jwks.json`을 새로 받는다.

실측:

| 경로 | 첫 요청 | 연결 재사용 |
|---|---|---|
| JWKS | 320ms | **13ms** |
| auth `/user` (현재) | — | **37~40ms** |

그냥 바꾸면 37ms → 13ms다. 나쁘지 않지만 목표는 아니다.

**해법은 코드에 이미 있다.** `getClaims(jwt, { jwks })`로 키를 직접 넘기면 `fetchJwk`가 첫 줄에서 그대로 반환하고 네트워크를 타지 않는다(`GoTrueClient.js:5122-5126`). 그래서 **JWKS를 우리 모듈 레벨에 캐시**한다 — 모듈 스코프는 워밍된 람다 인스턴스 안에서 요청 간에 살아남는다.

## 설계

### A. `src/lib/authJwks.ts` (신규)

모듈 레벨 JWKS 캐시 하나. 책임은 "지금 쓸 수 있는 JWKS를 준다" 하나뿐이다.

- 최초 호출에서 `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`을 받아 모듈 변수에 담는다.
- TTL을 둔다(10분). 만료되면 다음 호출에서 다시 받는다.
- **동시 요청이 몰려도 fetch는 한 번만** — 진행 중인 Promise를 들고 있다가 공유한다. 콜드 스타트 직후 요청이 여러 개면 그렇지 않을 때 같은 fetch가 N번 나간다.
- 실패하면 **던지지 않고 `null`을 돌려준다.** 그러면 호출부가 `jwks` 없이 `getClaims`를 부르고, 그때는 라이브러리가 알아서 네트워크로 받아온다 — 즉 캐시는 최적화일 뿐이고, 실패해도 인증이 죽지 않는다.

### B. `requireAllowedUser` 교체 (`src/lib/authGuard.ts`)

`getUser()` → `getClaims(undefined, { jwks })`.

- 반환 타입을 바꾸지 않는다. 지금 `{ user: User }`를 돌려주고 `requireMember`가 그걸 `resolveMember`에 넘긴다. 클레임에서 **필요한 필드만 담은 객체**를 만들어 같은 모양으로 돌려준다.
- **키 회전 대비:** 우리 캐시에 그 `kid`가 없으면 `fetchJwk`가 네트워크로 받아온다(라이브러리 기본 동작). 이때 우리 캐시도 무효화해 다음 요청부터 새 키를 쓰게 한다.
- 실패·만료·서명 불일치는 전부 지금과 같은 401 + 같은 문구로 떨어진다. **문구를 바꾸지 않는다** — 사용자에게 보이는 것이 달라질 이유가 없다.

### C. 무엇이 검증되는가 — 지금과 같은가

`getClaims`는 만료(`validateExp`)와 **서명(`crypto.subtle.verify`)** 을 검증한다(`GoTrueClient.js:5229-5270`). 서명이 안 맞으면 `AuthInvalidJwtError`를 던진다.

**지금보다 약해지는 지점이 하나 있다.** `getUser()`는 인증 서버에 물어보므로 **토큰 발급 후 서버에서 무효화된 세션**(로그아웃·강제 만료·계정 삭제)을 즉시 반영한다. 로컬 검증은 토큰이 만료될 때까지 그걸 모른다.

이 제품에서는 감수한다: 액세스 토큰 수명이 짧고(기본 1시간), 사용자는 사내 구글 계정 도메인으로 게이팅된 소수이며, 회원 탈퇴·강제 로그아웃 기능 자체가 없다. **다만 이 판단은 기록해 둔다** — 나중에 외부 사용자를 받거나 강제 로그아웃이 생기면 이 트레이드오프를 다시 봐야 한다.

## D. 검증

- **테스트 가능한 부분:** JWKS 캐시 모듈(TTL·동시 요청 병합·실패 시 null)은 fetch를 주입받는 순수 모듈로 만들어 실 네트워크 없이 테스트한다. 이 저장소가 `actualCost.ts`에서 이미 쓰는 패턴이다.
- **테스트 불가능한 부분:** 라우트 게이트 자체는 하네스가 없다. 배포 후 프로덕션에서 확인한다.
- **배포 후 확인:** ①비로그인 API가 여전히 401인가(가장 중요 — 느슨해지지 않았는지) ②로그인 상태로 화면이 정상 동작하는가 ③응답 시간이 실제로 줄었는가.

## E. 하지 않는 것

- **`getSession()`만 쓰고 검증을 생략하는 것** — 쿠키의 토큰을 검증 없이 믿는 것이라 명백히 위험하다. `getClaims`는 서명을 실제로 검증하므로 다르다.
- **`createClient()`를 싱글턴으로** — 요청 쿠키에 묶여 있어 불가능하고, 그렇게 하면 세션이 요청 간에 섞인다.
- **`requireMember`의 DB 조회 제거** — 멤버 해석은 DB가 진실이다. 이번 범위 아님.
- **미들웨어(`proxy.ts`)의 세션 갱신 경로 변경** — 별개 관심사.
