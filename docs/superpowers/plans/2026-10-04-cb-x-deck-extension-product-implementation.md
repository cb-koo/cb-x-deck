# cb-x-deck 목업 기반 구현 계획서

작성일: 2026-10-04

`/mockup/x-extension`에서 승인된 화면과 업무 흐름을 기존 cb-x-deck의 실제 데이터·저장·파일 기능으로 연결한다. 인플루언서의 협업 콘텐츠에서 예약 업무로 이동하고, 캠페인 작업에서 일정·원고·게시·정산을 계속 처리할 수 있게 한다. 익스텐션은 이 제품에 저장한 같은 업무 데이터를 사용한다.

이 문서는 실제 기능 개발을 위한 계획이다. 현재 목업의 샘플 버튼 동작과 운영 기능을 구분한다. 함께 읽을 문서: [익스텐션 구현 계획](2026-10-04-cb-x-extension-implementation.md), [공통 API 구현 계획](2026-10-04-extension-product-api-implementation.md).

## 1 기준과 기존 구현

최신 기준은 [웹 목업 설명](../../mockups/x-extension-web-20261004.md)과 `src/app/mockup/x-extension/`이다. 그다음 [익스텐션 README](../../../../cb_x_extension/README.md), [인계 문서](<../../../../cb_x_extension/docs/인계/cb-x-deck 기능 추가 목업 인계.md>), 변경되지 않은 초기 상세 기획을 따른다. 화면 간 차이는 API 계획서에 명시한다.

2026-10-04 로컬 HEAD `fe6c2a1`과 작업 중인 웹 목업을 확인했다. 확인 범위는 현재 체크아웃이며 운영 배포나 다른 브랜치의 기능까지 확인한 것은 아니다.

## 2 화면별 구현 범위

### 인플루언서

기본 흐름은 인플루언서 → 협업 콘텐츠 → 참여 캠페인 → 그 사람의 작업·예약 상세다. 참여 캠페인에는 캠페인명·기간·유형별 작업 수·기간 상태·통화별 소계만 표시한다. 캠페인 기간 상태와 개별 작업의 완료 여부를 구분하고, 기간이 끝나도 미완료 작업을 처리할 수 있게 한다.

종료 기록은 참여 캠페인을 지우지 않는다. 취소·노쇼는 작업 수·금액 소계에서 제외하며 KRW/JPY를 합산하지 않는다. 기존 참여 캠페인의 작업 수는 완료 작업을 포함할 수 있으므로 익스텐션의 진행중 건수와 같은 숫자로 취급하지 않는다. 화면의 라벨과 집계 조건을 각각 명확히 한다.

참여 캠페인 아래 넘긴 원고를 유지한다. 원고의 초안·전달됨 상태를 예약·정산 상태로 바꾸지 않는다. 작업 화면으로 이동·복귀할 때 사람·캠페인 필터를 유지하고 `전체 작업 보기`로 범위를 해제한다. 계정 정보의 고정 메모, 거래 정보의 기본 단가·변경 이력을 기존 위치에 연결한다.

### 캠페인 목록과 작업 표

기존 공통 단계·유형 필터와 검색을 유지한다. 표의 단계 / 유형 / 인플루언서 / 원고 / 게시 예정일 / 작업 비용에 방문 예약 열을 추가한다. 예약 대기·확정만으로 공통 준비·전달 단계를 변경하지 않는다.

새 방문 작업은 작업 추가 → 작업 상세 → 이 작업에 예약 추가로 진행한다. 예약을 붙일 때 작업 ID·금액·기존 방문 기록을 보존한다. 기존 예약이 있으면 중복 등록 대신 상세·수정으로 이동한다. 방문협찬 이외 유형의 일정과 RT 증빙·대상 선택 동작을 유지한다.

### 방문 작업 상세

상세 순서는 헤더 → 단계 → 일정·예약 정보 → 예약 변경 내역 → 협찬 동의서 → 예산·정산 → 원고 → 메모 → 게시다. 일정은 방문일·시간과 업로드 기한을 나란히 보여주며 클리닉·예약자·시술·지금 할 일을 모은다. 예약자와 시술은 별도 줄, 이름 입력은 한글·로마자로 나눈다.

부가 카드는 접어도 요약·누락·오류를 보여준다. 기본 펼침은 대기 모두 접힘, 확정 동의서, 방문 원고·게시, 업로드·정산 예산·정산, 완료·종료 모두 접힘이다. 직접 펼친 선택은 작업 이동 후에도 유지하고, 같은 단계에서 직접 닫은 영역은 자동으로 다시 열지 않는다. 접기는 입력을 버리지 않는다.

현재 단계의 주 행동 한 개만 강조한다. 예약 확정, 방문일 당일 방문 완료, 게시 확인, 정산 요청, 지급 완료 중 서버가 허용한 행동을 표시한다. 원고·게시·정산은 기존 운영 API와 연결하며 목업의 가짜 성공을 실제 기능으로 가져오지 않는다.

일정의 `자세히 보기`는 예약 정보 / 기재 시트 / 고객 원문 탭을 연다. 이력은 일정 다음·동의서 바로 위에서 최근 3건·전체를 보여준다. 고정 이전/다음은 현재 사람·캠페인·검색·유형·단계 필터 안에서 이동한다.

### 예약 등록과 수정

고객 양식 → 응답 파싱의 두 단계를 유지한다. 웹에서는 양식을 복사하고 필요하면 X로 이동한다. 자동 DM 전송은 없다. 원문과 편집 가능한 시트를 나란히 비교하고 모바일에서는 위아래로 배치한다.

복사와 대기 저장은 같은 사용자 행동으로 이어지지만 두 동작의 성공 여부는 따로 안내한다. 복사 실패이면 저장하지 않으며 직접 복사 후 대기 저장으로 이어간다. 서버 저장이 실패하면 현재 시트와 요청 식별자를 유지한다.

대기 예약은 사유 없이 바로 수정하며 `예약 수정 · 확정 전` 이력으로 남긴다. 첫 확정에 포함한 수정도 요청 횟수에서 제외한다. 확정 후 일정·시간·업로드 기한·전체 항목 수정은 같은 사유 선택과 같은 서버 command를 통과한다. 뒤로가기·닫기는 예약 초안을 보존한다.

방문일 변경에 따라 기본 기한은 14일 후로 이동한다. 직접 지정한 기한은 유지하고 `기본 기한으로`를 제공한다. 기한이 새 방문일보다 이르면 조용히 옮기지 않고 다시 확인하도록 한다. 최종 시트·표의 게시 예정일·상세·익스텐션은 같은 저장 날짜를 사용한다.

### 동의서와 종료

확정 이후 PDF 10 MiB 이하를 첨부하고 교체·열기·제거할 수 있게 한다. 잘못된 파일이나 업로드 실패는 기존 첨부를 보존한다. 서버가 검증한 비공개 파일만 연결하고 열 때 짧은 서명 URL을 발급한다.

방문 전 취소, 방문 당일 취소/방문 노쇼, 방문 이후 업로드 노쇼를 구분한다. 게시 확인·활성 정산 이후에는 해당 메뉴를 제공하지 않는다. 자정이나 동시 수정으로 조건이 바뀌면 저장 시 서버가 거부한다. 종료는 삭제가 아니며 예약·시트·이력·동의서·원고·메모를 열람할 수 있게 보존한다.

기존 작업 취소는 원고를 떼는 동작과 복원을 포함한다. 예약이 연결된 visit 작업의 종료는 이 동작을 그대로 적용하지 않고, 원고 연결과 증빙을 보존하는 별도 분기로 설계한다. 종료 복원은 결정 전까지 막으며 다른 유형의 기존 복원은 유지한다.

### 예산과 정산

인플루언서 기본 단가와 작업 확정 금액을 구분한다. `금액 미등록`, `0원/0엔`, `비용 없음`은 각각 표시한다. 비용 없음은 명시적으로 설정해야 하며 게시 확인되면 완료, 정산 후보에서 제외한다. 유상 작업은 기존 정산 결과의 지급 완료로 끝난다.

활성 정산 요청이 붙은 작업은 금액·통화·비용 없음을 변경하지 못한다. 게시됐지만 금액도 없고 비용 없음도 정하지 않았다면 `금액 확인 필요`와 다음 행동을 표시한다. 결제 수단·정산 요청·지급 결과는 기존 정책을 사용하며 임의로 지급 완료 상태를 만들어 저장하지 않는다.

### 클리닉 설정

기존 클라이언트 상세에 기본 정보 / 운영시간 / 방문 안내·양식 탭을 연결한다. 본점 한 곳만 제공하며 지점 추가·분리·예약 접수 ON/OFF는 제외한다. 기본 정보·금지 표현이 실제 원고 생성 입력으로 사용하는 기존 client 데이터와 중복 저장되지 않게 한다.

운영시간 화면은 왼쪽 주간·공휴일 설정, 오른쪽 월 캘린더다. 주간 설정은 요일 묶음·시작/종료·점심·휴무를, 공휴일은 운영/휴무를 제공하고 미설정은 확인 필요로 둔다. 특정 날짜 사이드 모달은 별도 운영·휴무·메모·기본 운영으로 되돌리기를 제공한다. 모달 적용은 편집 초안에 반영하고 최종 설정 저장을 따로 둔다.

운영 판정은 날짜 예외 → 공휴일 → 요일 순이다. 종료 ≤ 시작, 운영 범위 밖 점심은 저장하지 않는다. 공휴일 자료가 없거나 갱신 실패이면 평일로 단정하지 않는다. 월 샘플 데이터를 운영 데이터로 배포하지 않으며 현재 연도·다음 연도 확보를 초기 목표로 제안한다.

방문 안내·양식은 지도·방문 안내 / 고객 예약 양식·기재 시트로 나눈다. 고객 양식과 시트는 각각 수정·저장하고 다른 항목의 미저장 입력을 보존한다. 시트의 핸들 삽입은 `[인플핸들]` 하나로 유지한다. 저장된 과거 시트·이력·동의서는 새 설정으로 덮어쓰지 않는다.

양식 저장 시 목업의 파싱 형식 변경 안내를 유지한다. 서버에는 양식 revision과 parser 호환 상태를 기록한다. 호환성이 확인되지 않은 새 양식은 수동 입력으로 이어갈 수 있게 안내하고 자동 파싱 결과를 확정된 정보로 취급하지 않는다. 저장 안내가 개발자 메시지 발송이나 파서 자동 수정 기능을 뜻하지 않는다.

### 빠른 메시지와 확장 연결

팀 공용 빠른 메시지는 제안 기능이다. 초기 포함을 결정하면 제목·언어·본문·순서·사용 여부·검색·미리보기를 실제 저장한다. 지도·예약 양식을 여기에 중복 등록하도록 요구하지 않는다. 개인 저장소는 제외한다.

운영 연결 화면은 회사 연결 상태와 사용법·버전만 제공한다. 목업의 일치·조회 실패·0건·ID 불일치·권한 체험 버튼은 개발 전용으로 남긴다. 특정 작업 URL은 실제 라우트에서 캠페인·작업 관계를 검증한 뒤 연다.

## 3 데이터와 서비스 설계

서버 도메인 함수가 웹·익스텐션 저장을 함께 처리한다. 웹 UI와 확장 API가 같은 DB에 각각 다른 저장 규칙을 적용하지 않게 한다. 제안 모델의 상세 필드·제약·API는 공통 API 계획서를 따른다.

| 데이터 | 제안 변경 |
| --- | --- |
| `campaign_task` | `no_cost`, 방문 수동 완료 사실, 작업 version. 예약 연결 작업의 일정 쓰기 경로 통합 |
| `visit_reservation` | task unique, 본점 참조, 원문, 최종 시트, 시트에서 검증한 항목, 확정 여부, 기한 방식, version |
| `reservation_change` | 저장 건별 사유·담당자·시각·필드 전후·시트 전후·누적 회차 |
| `reservation_end` | 취소/방문 노쇼/업로드 노쇼/횟수 초과, 사유와 당시 기록 |
| `reservation_consent` | 파일 metadata, object key, 업로드 담당자·시각, 교체/제거 기록 |
| `clinic_location`과 설정 | client당 본점 1개, 주간·공휴일·날짜 예외·지도·안내·양식 revision |
| `holiday_calendar` | 공식 자료·적용 연도·성공 시각·조회 상태 |
| influencer 버전 | 단가와 메모의 독립 version, 기존 변경 로그 재사용 |
| `quick_message` | 팀 공용 기능 채택 시 추가 |
| `api_idempotency` | 사용자·작업 종류·요청 ID·body hash·처리 결과 |

이름·생년월일·시술·원문·PDF는 일반 요청 로그나 채팅 목록 배지 응답에 넣지 않는다. 제품의 업무 데이터는 현재 전사 공유 엔티티 구조를 따른다. 이번 계획만을 위해 캠페인·클라이언트에 가상의 workspace 소속이나 관리자 역할을 만들지 않는다.

## 4 기존 편집 경로의 통합

예약이 있는 visit 작업의 `visitOn`, `scheduledOn`, 종료·배정·교체·삭제는 반드시 예약 관계를 확인한다. 기존 task PATCH가 날짜만 바꾸어 횟수·시트를 우회하지 않도록 서버에서 막거나 동일 command로 전달한다. 이미 열린 구버전 UI에는 `예약 상세에서 일정을 수정해 주세요` 같은 행동 안내와 기계 판독 코드를 반환한다.

예약 없는 과거 작업은 날짜만 있는 상태를 유지한다. `00:00`, 이름, 확정 여부, 고객 원문을 추측해서 만들지 않는다. 실제 예약 연결 때 담당자가 값을 입력하고 기존 기록과 새 예약을 함께 비교한다.

종료가 읽기 전용이 되므로 기존 취소 작업에서 허용하던 메모 편집은 예약이 연결된 종료 visit에서는 차단한다. 예약·이력이 연결된 작업과 캠페인·클라이언트의 hard delete도 차단하거나 보관 방식으로 전환한다. 현재 cascade 삭제와 명부 삭제가 새 이력을 유실시키지 않게 검증한다.

## 6 이관과 출시

1. migration 번호를 구현 브랜치 시작 때 현재 목록에서 확보한다. 이 문서는 번호를 예약하지 않는다. 이미 적용한 파일은 수정하지 않고 새 파일로 추가하며 저장소의 재실행 규칙을 지킨다.
2. schema를 먼저 추가하고 새 기능 기본 OFF 상태에서 기존 화면·API가 정상인지 확인한다. staging에도 같은 schema를 적용한다.
3. 과거 visit 작업은 예약 없는 레거시 기록으로 둔다. 새 예약이 붙은 작업만 일정·시트 동기화 경로로 전환한다. 기존 게시 예정일이 기본 기한과 다르면 직접 지정으로 보존할지 확인하며 일괄 덮어쓰지 않는다.
4. 기존 비용 0·빈 금액을 `비용 없음`으로 자동 이관하지 않는다. 유상/무상 의미를 담당자가 확인해 설정한다.
5. 클라이언트당 본점 식별자를 멱등 생성한다. 샘플 주소·운영시간·공휴일은 넣지 않고 미설정 상태를 보여준다.
6. 파일럿 사용자에게 예약·클리닉 기능과 확장 쓰기를 열고 양쪽 비교 QA를 진행한다. 되돌릴 때는 쓰기 플래그를 내려 데이터·이력을 보존하며 파괴적 down migration을 사용하지 않는다.
7. QA 완료 후 머지 직전에 `src/content/updates.ts`에 작업 단위별 업데이트를 작성하고 같은 브랜치에 포함한다. 새 흐름과 변경된 예약 수정 방식, 내부 저장 안정성 변화도 설명한다.

## 7 검증 기준

새 화면 구현 전 저장소 UX 원칙을 확인한다. 버튼은 사용자 이득과 동작을 말하고, 바로 옆에 실행 결과를 설명한다. 목업의 `예약 정보 파싱`·`파싱 결과 복사하기`는 각각 `응답에서 예약 정보 가져오기`·`기재 시트 복사·대기 저장`으로 다듬는 것을 제안한다. 원문 비교·시트 편집·복사 후 대기 저장이라는 승인된 흐름은 유지한다. 운영시간 결과는 숫자뿐 아니라 `점심시간이라 운영 여부를 확인해 주세요`처럼 판단과 다음 행동을 함께 표시한다. 유료 추출·프로필 조회·번역은 사용자 클릭으로만 실행한다.

| 검증 영역 | 통과 조건 |
| --- | --- |
| 예약 생성 | 새 작업·예약 한 쌍, 기존 작업 연결 ID 유지, 동일 요청 재전송에도 1건 |
| 예약 수정 | 대기 횟수 제외, 확정 후 사유 필수, 여러 항목 한 저장은 1회, 무변경은 증가 없음 |
| 횟수 제한 | 3회 이후 편집 제한, 명시적 4번째 중단, 동시 요청에도 초과 저장 없음 |
| 일정과 텍스트 | 원문·추가 문구·줄바꿈 보존, 기본/직접 기한 구분, 월말·연말·서울 자정 일치 |
| 종료 | 방문일 기준 행동 제한, 자정 경합 거부, 게시 이후 차단, 기록·원고·첨부 보존 |
| 파일 | 형식·10 MiB·대상 검증, 교체 실패 시 기존 파일 유지, 만료 URL 재발급 |
| 금액과 정산 | noCost/0/null 구분, 후보 SQL·UI 동일 조건, 활성 요청 중 변경 거부 |
| 운영시간 | 예외·공휴일·요일 우선순위, 점심 경계, 정보 미등록과 갱신 실패 구분 |
| 동시 수정 | 예약·단가·메모·설정 충돌에서 내 입력 보존, 최신 값 확인 후 재저장 |
| 기존 기능 | RT·인용RT·투고·원고 생성·게시 트래킹·유상 정산 정상 유지 |
| UI | 1600px·390px, 키보드·초점·닫기·미저장 보호·단일 주 행동·오류 요약 |
| 양쪽 연동 | 웹 변경→확장 재조회, 확장 저장→웹 재진입에서 동일 ID·상태·시트·금액 |

순수 판정 테스트와 staging DB 통합 테스트를 나눈다. `npm test`의 staging guard를 유지하며 운영 DB 테스트를 이 작업의 기본 검증으로 사용하지 않는다. DB 통합 이후 관련 route 계약, `npm run lint`, `npx tsc --noEmit`, `npm run build`를 수행한다. 업데이트 글은 `node --import tsx --test src/lib/updates.test.ts`로 확인한다.

Next.js 구현 전에 설치된 `node_modules/next/dist/docs/`의 Route Handlers·Proxy·인증 가이드를 다시 확인한다. 현재 설치본은 `next` 16.2.10이며 `proxy.ts`와 비동기 route params 관례를 사용한다. 기능 문서만 작성한 이번 작업에서는 앱 빌드·DB migration·운영 배포를 수행하지 않는다.

## 8 결정이 남은 항목

공통 API 계획서의 결정 목록을 사용한다. 특히 종료 복원, 직접 방문 완료 후 방문일 수정, 공휴일 데이터 제공처, 운영시간 밖 저장, 팀 공용 빠른 메시지, 기존 날짜 이관을 구현 전에 결정한다. 명확하지 않은 정책을 목업 샘플 데이터의 우연한 동작으로 확정하지 않는다.
