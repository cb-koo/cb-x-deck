「결제 정보(수취정보) 정정 회신 API 요청」 확인했습니다. **§2 계약 그대로 수용해 구현했고, 스테이징에 먼저 올립니다.** §0의 QA 4건은 저희 조치 없음으로 확인했습니다. §3 7개 항목 답입니다.

*1. 엔드포인트 — §2 그대로, 두 군데만 확정*
• 경로·요청 필드·응답 형태(200 `{ applied, correction_id, request }`, 409 `code` 3종 + `request`, 404 `{ error }`, 400 `{ error, field }`) 전부 그대로입니다. **200에는 다른 200과 달리 `version`을 넣지 않았습니다** — 그쪽 스키마가 세 키만 엄격히 받는다고 이해했습니다(필요하면 말씀해 주세요, 넣는 건 한 줄입니다).
• `base_source_updated_at`은 **형식만 검사하고 판정에는 쓰지 않습니다**(정보·로그용). 그쪽 자신의 상태 POST도 저희 `updated_at`을 갱신하므로, 정확히 일치하기를 요구하면 정상 흐름(received 보낸 뒤 정정)에서도 거절이 납니다. 동시성은 `base_source_revision`으로 봅니다 — 취소는 `status`, 지급 완료는 `settlement.status`가 따로 막으니 빠지는 경우가 없습니다. 그쪽 목 서버는 `updated_at`까지 비교하던데, 저희 쪽은 그렇게 하지 않는다는 점만 맞춰 주세요.
• 판정 순서: **취소(request-cancelled) → 지급 완료(paid-locked) → 판 불일치(revision-mismatch)**. 그쪽 목 서버와 같은 순서입니다(상태 POST는 revision을 먼저 보지만, 정정에서는 취소·지급 완료가 판과 무관한 종점이라 먼저 답하는 게 맞다고 봤습니다).
• `payment_method` 안의 모르는 키는 400입니다(최상위 모르는 키는 종전처럼 무시). "정정했다고 믿은 값이 조용히 버려지는 것"이 가장 나쁜 실패라서요. `field`는 `"payment_method.account"`처럼 점으로 잇습니다.

*2. 정정 허용 범위 — 7키 전부 허용, `type`·`currency`는 불가*
• `holder`·`paypal_id`·`email`·`identifier`·`bank`·`branch`·`account` 모두 in-place 정정 가능합니다(예금주 포함 — 수취인 표기 오타도 같은 성격이라 봤습니다).
• 단 **현재 수단 종류에 있는 키만** 받습니다. PayPal 수단에 `bank`를 보내면 400 `field: "payment_method.bank"`. 수단 종류(PayPal↔계좌)·통화를 바꾸는 건 다른 의무라 종전처럼 `on_hold` + `note`로 알려 주시면 저희가 고칩니다.
• 비우기(`null`·`""`)는 선택 항목만: `branch`, 그리고 PayPal의 `email`·`paypal_id`(둘 중 하나는 남아야 합니다). 계좌번호·은행·수취인·PayPay 식별값은 비울 수 없습니다(400).
• 합친 결과는 **저희가 새 요청을 만들 때와 같은 검사**를 통과해야 합니다(이메일 형식, PayPal.me 아이디 영문·숫자·`._-` 3~50자, 수취인 80자 이하 등). PayPal.me 아이디는 `@`·`paypal.me/` 접두어를 떼고 저장합니다.

*3. 정산 상태 보존 — 보장합니다*
• 바뀌는 것은 `payment_method`·`payment_method_correction`(표식)·`updated_at` 셋뿐입니다. **`revision`·`revised_at`·`status`·금액·`settlement.*`(처리 상태·정산코드·실지급액·담당자)는 건드리지 않습니다.** 자동 테스트로 못박았습니다.
• **`revision`을 올리지 않는 이유**: 올리면 그쪽 outbox에 이미 쌓인 상태 POST(옛 revision)가 전부 409가 되고, 그쪽은 계약 §3-1대로 "revision이 커졌다 = 소스가 고쳐서 정산이 리셋됐다"로 읽게 됩니다. 정정은 리셋을 동반하지 않으니 판을 올리지 않고 별도 표식(5번)으로 구분합니다. 정정 뒤에도 그쪽 상태 POST는 같은 `revision`으로 그대로 통합니다.
• 정정은 **이 요청에만** 반영됩니다. 저희 인플루언서 명부의 결제 수단은 그대로라, 같은 인플루언서의 **다음 요청에는 옛 값이 다시 나갈 수 있습니다.** 저희 화면(요청 내역·명부 활동 기록)에 "정산 쪽이 수취 정보를 고쳤어요 · 누가 · 사유 — 명부도 확인"이 뜨게 해서 담당자가 명부를 고치도록 유도합니다. 명부까지 API로 고치는 건 이번에 넣지 않았습니다(명부는 저희 원본 데이터라 사람이 확인하는 게 맞다고 봤습니다).
• 저희가 그 뒤 제자리 수정(§3-1)으로 결제 수단을 명부에서 다시 스냅샷하면 정정은 사라지고 표식이 `null`로 돌아갑니다(그때 `revision`은 커집니다). 저희 화면은 그 전에 "명부를 먼저 확인하라"고 경고합니다.

*4. 멱등 — 보장합니다*
• 같은 `correction_id`, 또는 같은 요청 안의 같은 `idempotency_key`가 이미 반영됐으면 **다시 적용하지 않고 최초 결과를 돌려줍니다**(200, `correction_id`는 최초 반영된 값, `request`는 지금 상태). 쓰기가 없어 `updated_at`도 안 바뀝니다. 본문이 달라도 다시 보지 않습니다 — 재전송은 같은 본문이어야 한다는 §6 규칙과 같습니다.
• `correction_id`만으로 멱등이 되므로 `idempotency_key`는 `null`이어도 됩니다.
• `correction_id`를 **다른 요청**에 재사용하면 400 `field: "correction_id"`입니다(그쪽 버그 신호로 봅니다).

*5. ⭐ 폴링 상관관계 — Item에 `payment_method_correction` 표식*
• `payment_method_correction: { correction_id, at, by_name } | null`을 Item 최상위에 실었습니다. `correction_id`는 그쪽이 보낸 값 그대로, `at`은 저희 반영 시각, `by_name`은 `operator.name`.
• 정정이 반영되면 그 건의 `updated_at`이 갱신돼 다음 폴링에 다시 내려옵니다. **`payment_method_correction.correction_id`가 자기 기록에 있으면 그쪽 자신의 정정의 회신**입니다 — 담당 해제·재검토 경로를 타지 않으면 됩니다. `revision`은 그대로이니 "revision이 커졌다"로도 오인되지 않습니다.
• `null`은 "정정된 적 없음" 또는 "그 뒤 저희가 제자리 수정으로 명부 값을 다시 덮음"(그때는 `revision`도 함께 커짐)입니다. 후자에는 정정이 사라진 것이니 필요하면 새 `correction_id`로 다시 보내 주세요.
• 그쪽 Item 스키마(`source-types.ts`)가 passthrough인 것을 확인했습니다 — 새 키 두 개(`payment_method_correction`, `influencer.display_name`)는 기존 파싱을 깨지 않을 것으로 봅니다.

*6. `operator` — 필수로 받습니다*
• §계약 정본 규약 그대로 `{ id, name }`(각 ≤100자). 상태 POST에서는 선택이지만 정정은 사람이 하는 일이라 **필수**입니다 — 없으면 400 `field: "operator"`. `id` 형식은 강제하지 않습니다(047과 같은 이유).
• 저희 요청 내역과 명부 활동 기록에 "정산 쪽이 수취 정보를 고쳤어요 · {name} · {시각} — {reason}"으로 보입니다. `reason`(≤500자)은 필수입니다.

*7. `influencer.display_name` — 같이 넣었습니다*
• Item `influencer.display_name`(string | null). 명부의 **지금** 표시명(X 프로필 이름)이라 핸들과 달리 스냅샷이 아니라 최신값입니다(표시용은 최신이 맞다는 `proof`와 같은 판단). 프로필 미조회·인플루언서 삭제면 `null`. 매핑 키는 종전처럼 `influencer.id`로 부탁드립니다.

*배포·점검 순서(§4 제안 그대로)*
1. 저희: 마이그레이션 + 엔드포인트를 **스테이징에 먼저 배포**하고 알립니다. 운영은 스테이징 점검 뒤.
2. 스테이징 공동 점검: 그쪽 전송 ON → 정정 POST → 200 `request`의 `payment_method`·`payment_method_correction` 확인 → 다음 폴링 재유입에서 `correction_id` 대조 → 같은 본문 재전송이 200(쓰기 없음)인지 → 판 틀리게 보내 409 `revision-mismatch` 확인.
3. 이상 없으면 운영 배포 → 저희가 "운영 수신 준비 완료"를 알린 뒤 **그쪽 전송 ON**.

명세 갱신본(§6-1)을 첨부합니다. 수정 의견 주시면 바로 맞추겠습니다.
