# X 대화 목록 협찬 상태 요약 구현 계획서

작성일: 2026-10-13

X 대화 목록에서 협찬마다 반복되던 상태를 **가장 먼저 챙길 상태 하나와 나머지 건수**로 바꾼다. 두 건 모두 대기이면 `대기 [+1]`, 방문 일정이 가장 빠르면 `10/16 방문 예정 [+2]`처럼 한 줄로 표시한다. 추가 건수를 누르면 협찬 이름과 상태를 확인하고, 선택한 협찬을 패널에서 찾을 수 있게 한다.

이 문서는 승인된 표시 방식의 구현 범위와 작업 순서를 정한다. 구현 대상은 `cb_x_extension`의 실제 X 화면과 `cb-x-deck`의 확장 API다.

이 문서의 `output/` 링크는 로컬 검수 자료다. 실제 대화가 포함된 화면은 공개 저장소에 올리지 않고 로컬에만 보관한다. 아래 배포 상태는 각 검수 절 작성 시점의 기록이다.

기준 목업: [대표 일정과 나머지 건수](../../../output/mockups/sponsorship-priority.html). 이 파일이 화면 기준이며 임시 로컬 서버 주소에는 의존하지 않는다.

## 1 승인된 동작

| 상황 | 대화 목록 표시 | 추가 목록 |
| --- | --- | --- |
| 두 건 모두 날짜 없는 대기 | `대기 [+1]` | 진행 중 협찬 2건 |
| 세 건 중 방문이 가장 빠름 | `10/16 방문 예정 [+2]` | 해당 방문 건을 맨 위에 표시 |
| 두 건 중 업로드가 가장 빠름 | `10/15 업로드 예정 [+1]` | 해당 업로드 건을 맨 위에 표시 |
| 업로드 기한이 지난 미완료 건이 있음 | `10/11 업로드 지연 [+2]` | 지난 일정부터 표시 |
| 진행 중 한 건 | `대기` 또는 해당 일정 | 추가 건수 버튼 없음 |
| 완료 또는 취소된 건만 있음 | 상태 요약 없음 | 추가 건수 버튼 없음 |

`[+N]`은 **대표 한 건을 제외한 나머지 진행 중 방문협찬 수**다. 대표 건과 상태가 같은 협찬만 세는 것이 아니다. 두 건이면 `+1`, 여섯 건이면 `+5`이며 `+0`은 표시하지 않는다. 평소에는 총건수를 중복 표시하지 않고, 펼친 목록의 제목에 `진행 중 방문협찬 6건`으로 표시한다.

현재 실제 배지가 방문협찬만 표시하므로 이번 변경도 그 범위를 유지한다. 투고·RT·인용RT는 방문협찬의 대표 상태와 추가 건수에 포함하지 않는다. 오른쪽 패널은 기존처럼 다른 종류의 협찬도 보여줄 수 있으므로, 팝업 제목에 대상이 방문협찬임을 명시한다.

## 2 구현 범위

### 포함하는 변경

1. 협찬 여러 줄을 대표 상태 한 줄로 요약한다.
2. 날짜가 지난 미완료 건, 가까운 예정 일정, 날짜 없는 건 순으로 대표를 정한다.
3. `[+N]`으로 전체 진행 중 방문협찬의 이름과 상태를 펼쳐 본다.
4. 대표 상태 또는 펼친 목록의 협찬을 누르면 해당 대화의 패널에서 그 작업을 표시하고 강조한다.
5. 서버 조회 전체 건수와 배지·팝업의 건수를 일치시킨다.
6. 날짜·상태·정렬 판정을 서버와 패널에서 같은 기준으로 사용한다.

### 범위에 포함하지 않는 변경

예약 등록·수정·방문 완료·게시 확인·정산·취소의 업무 규칙은 바꾸지 않는다. 오른쪽 카드의 버튼 배치, A·B·C 배치 선택, 자동 번역, 새 알림도 변경하지 않는다. 첫 목업에서 제시한 접기형 카드·할 일별 묶음형은 이번 구현에 포함하지 않는다.

DB 컬럼이나 저장 구조를 추가할 필요는 없다. 기존 기록을 읽어 표시용 정보를 계산하고, API 응답에 필요한 값을 추가한다.

## 4 상태와 일정의 결정 규칙

### 서버 판정을 기준으로 한다

대기·확정·방문·업로드·정산·완료·종료 여부는 기존 서버의 `visitPhase`와 `classifyTask`를 따른다. 브라우저가 날짜만 보고 업무 상태를 임의로 바꾸지 않는다.

특히 현재 서버는 **확정된 방문일 다음 날 00:00부터 서울 날짜 기준으로 방문 단계로 본다.** 따라서 이 경우에는 지난 방문일을 계속 강조하지 않고 업로드 일정으로 넘어간다. 목업의 단순한 방문 완료 여부보다 실제 서버 판정을 우선한다.

### 단계별 표시

| 서버 상태와 조건 | 대표 일정 | 대화 목록 문구 |
| --- | --- | --- |
| 예약 전 또는 날짜 없는 대기 | 없음 | `대기` |
| 대기이며 희망 방문일이 있음 | 희망 방문일 | `10/16 방문 조율` |
| 대기인 희망 방문일이 지남 | 희망 방문일 | `10/11 일정 확인 필요` |
| 확정이며 방문 전 | 방문일 | `10/16 방문 예정` |
| 방문 단계이며 업로드 기한이 있음 | 업로드 기한 | `10/15 업로드 예정` |
| 방문 단계이며 업로드 기한이 지남 | 업로드 기한 | `10/11 업로드 지연` |
| 방문 단계이며 업로드 기한이 없음 | 없음 | `업로드 대기` |
| 업로드 완료 후 정산을 기다림 | 없음 | `정산 대기` |
| 정산 진행 중 | 없음 | `정산 중` |
| 서버가 완료 또는 종료로 분류 | 대상에서 제외 | 표시하지 않음 |

희망 날짜만 입력된 대기를 `방문 예정`으로 표시하면 예약이 확정된 것으로 오해할 수 있으므로 `방문 조율`로 구분한다. 날짜가 지났다는 이유만으로 노쇼나 취소로 바꾸지 않는다.

이미 게시한 협찬은 지난 업로드 기한을 대표 일정으로 사용하지 않는다. 다만 정산이 남아 서버에서 진행 중으로 분류된 협찬은 추가 건수에 포함한다. 날짜가 있는 미완료 건이 없을 때 `정산 대기` 또는 `정산 중`이 대표가 될 수 있다.

예약 정보가 없는 기존 방문 작업은 기존 서버의 `unregistered` 판정을 유지한다. 방문 여부를 프런트에서 새로 추측하거나 기록을 자동 수정하지 않으며, 이 경우에는 `대기`로 표시하고 예약 정보를 확인할 수 있게 한다.

### 정렬과 날짜 경계

정렬 순서는 아래와 같다. 대표 상태는 이 목록의 첫 번째 항목에서 가져오고, 추가 목록도 같은 순서를 쓴다.

1. 날짜가 지난 미완료 일정: 가장 오래 지난 날짜부터.
2. 오늘 또는 이후의 미완료 일정: 가장 빠른 날짜부터.
3. 날짜가 없는 진행 중 협찬.
4. 같은 날짜 또는 둘 다 날짜가 없으면 작업 ID 오름차순으로 고정한다.

날짜 비교 단위는 서울 기준의 **일자**다. 오늘 방문 시간이 지났더라도 당일에는 이 표시만으로 지연 처리하지 않는다. 같은 날의 시간까지 순위를 나누는 것은 이번 범위에 포함하지 않는다.

일반 날짜는 `M/D`로 표시하고 다른 연도의 일정은 `YYYY/M/D`로 표시한다. 잘못된 날짜 문자열로 화면에 `Invalid Date`를 노출하지 않는다. 실제 날짜를 알 수 없으면 단계에 맞는 날짜 없는 문구로 표시한다.

## 5 추가 목록과 패널 연결

### 펼치기

- 대표 상태와 `[+N]`은 한 줄에 둔다. 추가 건수가 커져도 협찬별 줄을 늘리지 않는다.
- `[+N]`을 누르면 그 상대의 방문협찬 목록을 연다. **펼치는 것만으로 X의 대화방을 바꾸지 않는다.**
- 제목은 `진행 중 방문협찬 N건`, 도움말은 `협찬을 선택하면 패널에서 볼 수 있어요.`로 한다.
- 각 항목에는 서버가 제공한 협찬 제목과 상태·날짜를 표시한다. 캠페인 이름에서 `_` 등을 임의로 잘라 클리닉명이나 월을 추측하지 않는다.
- 한 번에 한 상대의 목록만 연다. 같은 버튼 재클릭, 닫기, 목록 바깥 클릭, Escape로 닫는다.
- 목록이 길면 팝업 안에서 스크롤한다. 목록이 화면 아래에 잘리면 위쪽으로 열고, 화면 너비 안에 들어오도록 위치를 조정한다.
- 상태 색뿐 아니라 글자로 방문 조율·방문 예정·업로드 예정·지연을 구분한다.

### 협찬 선택

대표 상태를 누르면 대표 작업을, 펼친 목록에서 항목을 누르면 그 작업을 선택한다.

1. 선택한 작업의 상대가 현재 대화 상대와 같으면 협찬 패널과 진행 중 탭을 연다.
2. 다른 상대라면 실제 X 대화 행에서 확인한 링크로 해당 대화를 연다. 이동 전에는 상대 ID·본인 X 계정·작업 ID를 임시로 기억한다.
3. X 화면 감지와 서버 조회로 같은 상대가 확인된 뒤에만 선택을 적용한다. 이전 대화 데이터에 작업을 끼워 넣지 않는다.
4. 패널의 현재 묶음에 작업이 없으면 이미 읽은 목록에서 찾고, 필요하면 다음 서버 페이지를 순서대로 가져온다. 조회 도중에는 `선택한 협찬을 찾는 중이에요`를 표시한다.
5. 작업이 있는 화면 묶음으로 이동하고 카드의 테두리를 강조한다. A·B·C 어느 배치에서도 같은 작업을 찾되 사용자가 선택한 배치는 유지한다.

선택 대상이 조회 사이에 완료·취소·삭제되면 임의의 다른 카드를 선택하지 않는다. `협찬 상태가 바뀌었어요. 목록을 새로 불러왔어요.`로 안내하고 현재 목록을 갱신한다. 페이지 조회가 실패하면 찾은 것처럼 강조하지 않고 재시도 안내를 보여준다.

배지 선택은 조회와 화면 이동만 수행한다. 예약 저장·방문 완료·게시 확인·종료 버튼을 대신 실행하지 않는다.

### X 화면 안에서의 클릭 처리

현재 배지는 X 대화 행 링크 내부의 Shadow Root에 삽입되며 `pointer-events:none`이다. 클릭을 받는 버튼에만 포인터 동작을 열고, `[+N]`과 목록 조작이 바깥 X 링크의 클릭으로 전달되지 않게 한다. 팝업은 X 행의 잘림이나 목록 노드 재사용에 영향을 덜 받도록 확장이 관리하는 별도 Shadow Root에 한 개만 둔다.

키보드로 버튼을 선택하고 Enter·Space로 열 수 있어야 한다. 버튼의 접근성 이름은 `추가 방문협찬 2건, 총 3건 보기`처럼 의미를 포함한다. 닫기 또는 Escape 뒤에는 버튼이 아직 있을 때 해당 버튼으로 초점을 돌린다. 대화 전환이나 X의 행 재사용으로 기준 행이 사라지면 팝업도 닫는다.

## 6 서버 응답과 공통 계산

### 다음 미완료 일정

`src/lib/extensionTasks.ts`에 방문 작업의 다음 미완료 일정을 구하는 공통 함수를 둔다. 입력은 기존 작업 사실과 서버가 판정한 단계, 서울 기준 오늘 날짜다. 대기·확정은 유효한 희망/방문 날짜, 방문 단계는 업로드 기한, 게시·정산·완료·종료 단계는 날짜 없음으로 반환한다.

이 결과를 다음 세 군데에서 재사용한다.

- `classifyTask`의 방문협찬 `nextDate`와 `dDay`.
- `toTaskDto`의 새 표시용 일정 정보.
- 배지 응답의 표시용 일정 정보와 일정 정렬.

`bucket`과 허용 행동 계산은 기존 업무 규칙을 유지한다. 비방문 작업의 다음 일정 계산도 기존 규칙을 유지한다. 이미 끝난 일정을 방문 작업 정렬에서 제거하는 효과는 패널의 진행 중 목록에도 반영된다.

### 추가할 응답 필드

필드명은 아래 안으로 서버와 확장의 타입을 함께 맞춘다. 기존 필드의 의미를 바꾸거나 삭제하지 않는 추가 방식이다.

| 응답 위치 | 추가 필드 | 의미 |
| --- | --- | --- |
| 배지의 상대별 결과 | `personId` | 확인된 인물 ID. 미등록·불일치이면 `null` |
| 배지의 상대별 결과 | `activeVisitCount` | 해당 상대의 진행 중 방문협찬 전체 건수 |
| 배지의 상대별 결과 | `asOfDate` | 이 결과를 계산한 서울 날짜 `YYYY-MM-DD` |
| 배지의 각 작업 및 `TaskDto` | `nextSchedule` | `{ kind: 'visit' 또는 'upload', on: 'YYYY-MM-DD', dDay: number }` 또는 `null` |

기존 `activeCount`는 모든 종류의 진행 중 작업 건수라는 의미를 유지한다. 배지의 `tasks`도 기존처럼 전체 진행 중 작업을 반환하며, 새 UI는 방문협찬만 대상으로 삼는다. `activeVisitCount`, 필터한 작업 ID의 수, 팝업 건수, `+N`이 모두 일치해야 한다.

표시 문구는 확장의 공통 함수 한 곳에서 `visitPhase`, `flowStage`, `nextSchedule`로 만든다. 문구·날짜·색·정렬에 서로 다른 판단 코드를 두지 않는다. 서버가 제공한 `nextSchedule.on`을 그대로 날짜로 사용하며, 브라우저 날짜에 D-day를 더해 원래 날짜를 복원하지 않는다.

서버 응답 전체의 `meta.serverNow`는 현재 API 클라이언트가 풀어낸 결과에 남지 않는다. 이 작업을 위해 모든 요청의 반환 구조를 바꾸는 대신, 배지에 필요한 `asOfDate`를 상대별 결과에 추가한다.

## 7 건수와 갱신의 일관성

### 전체 목록을 기준으로 계산한다

배지 API는 해당 상대의 전체 진행 중 작업을 반환한다. 한 번 가져온 이 결과로 대표 상태와 팝업을 계산하고, 팝업을 열 때 작업마다 별도 API를 호출하지 않는다. 패널 작업 상세는 선택한 경우에만 기존 조회를 재사용한다.

현재 `getCurrent()`가 반환하는 `TaskPage.items`는 첫 20건일 수 있다. 이 목록으로 전체 배지 캐시를 매초 덮어쓰는 경로를 제거한다. 열린 대화에서 신뢰할 수 있게 확인한 핸들은 유지하고, 숫자 ID만으로 조회가 안 되는 상대는 `{ handle, observedXUserId }`를 함께 보내 전체 배지 결과를 조회한다. 표시 이름으로 상대를 찾거나 유료 프로필 조회를 자동 실행하지 않는다.

새 계약의 건수와 목록이 맞지 않으면 부분 목록으로 정확한 `+N`인 것처럼 표시하지 않는다. 해당 상대만 다시 조회하고, 해결되지 않으면 팝업에 조회 실패를 표시한다.

### 갱신 시점

- 기존 보이는 상대 최대 50명 일괄 조회와 짧은 캐시를 유지한다.
- 예약 등록·일정 수정·방문 완료·게시 확인·종료 성공 시 해당 상대의 패널과 배지를 함께 갱신한다.
- 웹 작업 후 X로 돌아오면 현재 상대 결과를 다시 가져온다.
- 서버 기준 날짜가 지난 캐시는 다시 조회한다. 브라우저는 날짜 경계에서 재조회만 요청하고 방문 완료를 독자 판정하지 않는다.
- X 계정 또는 회사 로그인 계정이 바뀌면 캐시·팝업·선택 대기 정보를 모두 지운다.
- X가 같은 행을 다른 상대에 재사용하면 이전 배지와 팝업을 제거한다. 늦게 도착한 응답은 요청 당시 계정·상대·세대가 현재와 같을 때만 적용한다.

조회 실패를 `대기`나 `0건`으로 바꾸지 않는다. 성공 결과가 없는 행은 업무 상태를 표시하지 않고, 사용자가 이미 연 팝업에는 `협찬을 불러오지 못했어요`와 다시 불러오기를 제공한다.

## 8 파일별 작업과 구현 순서

확장 배지 연결 함수에는 `getCurrent`와 함께 `onSelectTask` 같은 제한된 콜백을 전달한다. 선택 정보는 본인 X 계정, 상대 X ID, 확인된 인물 ID, 작업 ID를 포함한다. 페이지에서 누구나 보낼 수 있는 전역 이벤트로 내부 선택 명령을 받지 않는다.

새 파일은 화면에 의존하지 않는 표시 규칙 분리에만 사용한다. 별도 상태 관리 라이브러리나 공통 팝업 프레임워크를 추가하지 않는다.

작업 시작 전에 각 저장소의 최신 지침을 적용한다. 서버 코드를 작성할 때는 `node_modules/next/dist/docs/`의 해당 Route Handler 안내를 먼저 읽는다. 이 계획서에 적힌 파일은 현재 구조 기준이며, 구현 시 다른 작업자의 변경을 보존한다.

## 9 인수 기준

아래는 구현 결과를 판단할 사례이며 검증 실행 결과가 아니다. 사용자 작업 원칙에 따라 작업 후 테스트·빌드·타입 검사·브라우저 확인을 자동 실행하지 않는다. 사용자가 검증을 요청하면 요청한 범위에서 이 사례를 사용한다.

| 사례 | 기대 결과 |
| --- | --- |
| 대기 2건 | `대기 [+1]`, 팝업에는 서로 다른 제목 2건 |
| 대기 1건 | `대기`, 추가 버튼 없음 |
| 방문 10/16, 업로드 10/20, 날짜 없는 대기 | `10/16 방문 예정 [+2]` |
| 방문 10/18, 업로드 10/15 | `10/15 업로드 예정 [+1]` |
| 지난 업로드 10/11과 미래 방문 10/16 | 지난 업로드를 먼저 표시 |
| 오늘이 업로드 기한 | 당일에는 `업로드 예정`, 다음 서울 날짜부터 `업로드 지연` |
| 희망 방문일만 입력한 대기 | `방문 조율`로 표시하고 확정으로 오인시키지 않음 |
| 확정 방문일 다음 날 | 서버의 방문 단계에 따라 업로드 일정으로 전환 |
| 게시를 마쳤고 정산이 남음 | 지난 업로드 기한으로 지연 표시하지 않음. 진행 중 건수에는 포함 |
| 완료·취소·노쇼와 진행 중이 섞임 | 서버가 완료·종료로 분류한 건은 대표와 추가 건수에서 제외 |
| 방문 2건과 RT 3건이 섞임 | 대화 목록은 방문협찬 기준 `+1`; 팝업 제목도 방문협찬 2건 |
| 날짜가 같은 두 작업 | 재조회·팝업 열기에도 작업 ID 기준으로 순서 유지 |
| 21건 이상이며 현재 패널은 첫 20건만 조회 | 전체 방문협찬 건수 유지. 뒤쪽 작업도 팝업에서 선택 가능 |
| 선택 작업이 패널의 다음 서버 페이지에 있음 | 필요한 페이지를 조회해 정확한 카드 표시 |
| 추가 버튼 클릭 | X 대화방이 의도치 않게 전환되지 않음 |
| 다른 상대의 협찬 선택 후 빠르게 다른 방으로 이동 | 이전 상대의 선택·응답이 새 방에 적용되지 않음 |
| X 행 재사용·스크롤·창 크기 변경 | 잘못된 상대 배지 또는 화면 밖 팝업이 남지 않음 |
| 키보드 조작·Escape·팝업 밖 클릭 | 열고 선택하고 닫을 수 있고 초점이 적절히 복원됨 |
| API 실패·미등록·상대 불일치 | 실패를 대기 또는 협찬 없음으로 오인시키지 않음 |

규칙 검증이 요청되면 서버의 `extensionApi.test.ts`와 확장의 기존 `conversationBadges.test.ts`를 우선 활용한다. 추가 사례는 정렬·전체 건수·계정 및 행 재사용·선택 작업 연결처럼 실제 오류를 막는 범위에 집중한다.

## 10 배포와 완료 조건

서버 응답을 추가 방식으로 먼저 배포한 뒤 확장 프로그램을 배포한다. 기존 확장은 추가 필드를 무시할 수 있어야 한다. 새 확장이 구 서버에 연결된 경우 날짜를 추정해 새 표시를 만들지 않고 기존 배지 방식으로 동작하게 한다. 필요한 새 필드가 준비되었을 때 새 표시와 팝업을 함께 사용한다.

DB 마이그레이션은 없다. 기존 예약이나 협찬 데이터를 수정하는 배치 작업도 없다. 서버와 확장의 준비 여부를 각각 확인하고, 합의된 범위의 배포 QA가 끝난 뒤 main 머지 절차를 진행한다.

main 머지 직전에 `cb-x-deck/src/content/updates.ts`에 이 작업 한 건을 추가한다. 날짜는 실제 머지 예정일로 한다.

- 유형: `개선`
- 제목: `대화 목록에서 먼저 챙길 협찬을 볼 수 있어요`
- 내용: `여러 줄로 보이던 협찬 상태를 가장 빠른 일정 하나와 추가 건수로 모았어요.`
- 내용: `추가 건수를 누르면 협찬 이름과 일정을 펼쳐 보고, 원하는 협찬을 패널에서 바로 찾을 수 있어요.`
- 내용: `기한이 지난 미완료 일정은 먼저 보여주고, 이미 마친 방문이나 업로드 일정은 제외해요.`

구현 완료 조건은 대표 상태와 추가 건수, 펼친 목록, 실제 패널의 선택 작업이 동일한 서버 사실에 근거해 연결되는 것이다. 구현·검증·머지·배포 상태는 각각 구분해 기록한다.

## 11 구현·검수 기록 (2026-10-13)

사용자가 구현과 마지막 검수를 함께 요청하여 §9의 검증 실행 예외를 적용했다.

### 구현 상태

- 서버: `nextVisitSchedule`로 다음 미완료 일정을 통일하고 배지에 `personId`, `activeVisitCount`, `asOfDate`, `nextSchedule`을 추가했다. 업무 단계·허용 행동·DB 구조는 그대로다.
- 확장: 대표 상태와 `+N`, 전체 방문협찬 목록, 실제 대화 행을 통한 이동, 상대 확인 후 선택 적용, 다음 서버 페이지 조회, 카드 강조·초점 이동을 구현했다.
- 캐시: 전체 배지 응답을 유지하고 확인된 핸들을 조회에 사용한다. 계정 변경·행 재사용·이전 응답 차단·서울 날짜 경계·저장 및 복귀 시 갱신을 처리한다. 동일한 결과 갱신 중에도 열린 목록의 스크롤과 초점을 유지한다.
- 호환성: 새 필드 누락은 기존 배지, 명시적인 `null`은 다음 일정 없음으로 처리한다. API 계약 문서와 업데이트 글도 반영했다.
- 작업 전 존재한 빠른 메시지 삭제 관련 변경과 다른 미커밋 파일은 보존했다.

## 14 배지 색상 후속 조정 (2026-10-13)

사용자의 화면 피드백에 따라 대화 목록 배지를 더 선명하게 바꿨다. 밝은 화면에서는 방문은 진한 파랑, 업로드는 진한 초록, 지연은 진한 빨강, 대기는 짙은 회색 배경에 흰 글씨를 사용한다. 어두운 화면에는 밝은 상태 배경과 어두운 글씨를 적용한다. 추가 건수도 파란 배경·테두리와 굵은 글씨로 강조한다. 펼친 목록의 기존 글자 색과 상태 판정은 유지한다.

이번 후속 요청은 색상 변경이며 검증을 새로 요청하지 않았으므로 사용자 검증 생략 원칙을 적용했다. 색상 수정 후 테스트·빌드·브라우저 확인은 실행하지 않았다. §13의 검수 결과와 스크린샷은 색상 수정 전 버전 기준이다. 설치된 확장에 새 색상을 반영하려면 재빌드와 확장 새로고침이 필요하다.
